# Process Explorer

PX-004 keeps the shell's process list current: a source is polled at a configurable, one-second-by-default interval, and each snapshot difference is published as model operations on the existing transaction path. The semantic node tree — heading, status, native PID/Name table — is still built once. Process actions are not implemented.

Build and run from the repository root:

```sh
cargo build --locked --manifest-path apps/srtop/Cargo.toml
apps/srtop/target/debug/srtop --socket /tmp/srtop-dev/srtop.sock --fake-source
apps/srtop/target/debug/srtop --socket /tmp/srtop-dev/srtop.sock --live-source   # Linux
apps/srtop/target/debug/srtop --socket /tmp/srtop-dev/srtop.sock --fake-sequence --refresh-interval-ms 500
```

The fake snapshot contains three rows in order: `4101 / worker`, `4102 / worker`, and `Unavailable / helper`. Duplicate names have distinct opaque item IDs, and missing data is explicit. Omit every source flag to retain the empty-shell fixture, which does not poll; the source flags are mutually exclusive. Source records, source identity and sample time are typed separately from UI projection; fake mode performs no live process enumeration.

`--live-source` reads `/proc` once through `std` alone (no new dependency) and publishes PID and process name. Each process gets a `ProcessKey` of source, host, boot and PID-namespace identity, the PID, and a creation token taken from `/proc/<pid>/stat` field 22 in kernel clock ticks since boot — not a rounded start-time second. The key resolves to an opaque session item ID, so a reused PID with a different creation token is a different row identity. The host, boot and PID-namespace components are facts about the source rather than about a record, so they are remembered for the session: a scan that cannot read one of those identity files is keyed with the last value that was read, and a transient failure therefore re-keys nothing (see Refresh). Identity that the kernel answers from the *reader's* namespaces is published only when the scanned mount is provably this process's own procfs: the hostname is a sysctl answered from the reader's UTS namespace, so a mount that cannot be proven reports its host identity as unavailable rather than stamping records with a hostname belonging to none of them, and a published hostname names the namespace it was read in (`host@uts:[inode]`) so two readers that disagree disagree visibly instead of both claiming to have named the same machine. A reader that cannot name its own UTS namespace publishes no hostname at all, since an unqualified name would let two readers in different namespaces claim the same identity. The boot identity is not gated that way, being one value per running kernel. The source identity is lossless in the root's bytes, so two roots differing only in invalid UTF-8 can never alias. The PID namespace comes from the scanned mount's own namespace init, `<root>/1/ns/pid`, whenever the scan may read it. An unprivileged scan usually may not, and then falls back to `self/ns/pid` — the reader's own namespace — only under both proofs that it describes these records: `<root>/self` names this process's own PID, and `<root>/self` and `/proc/self` are the same device and inode, since one procfs superblock belongs to exactly one PID namespace. A host `/proc` bind-mounted into a container fails the second proof, a nested namespace that inherited an outer `/proc` fails the first, and either way the namespace is reported unavailable rather than stamped with the reader's. A snapshot is either complete, where an empty list authoritatively means "no processes visible", or incomplete, where individually denied or unparsable records are skipped with a reason and an empty list never means "nothing is running". A process that exits between listing `/proc` and reading it was not unreadable — it no longer exists at sample time — so it is counted separately and does not degrade the scan; ordinary churn on a busy host therefore never leaves the shell labelled incomplete. The status line states what actually fell short: how many records were unreadable when some were, that the process list itself was unavailable and why when the root could not be listed at all, and that host identity is incomplete when only the identity files were missing, and how many entries were beyond the collector's own record limit when the scan stopped at that bound rather than at a read failure — it never publishes a count of zero unreadable, and never describes a record it declined to read as unreadable. Process names are sanitized once on the server: invalid UTF-8 plus every control (Cc), every `Default_Ignorable_Code_Point` including its reserved ranges, the format characters (Cf) outside that set, the line and paragraph separators, and the known blank-glyph characters — only the last group is enumerated by hand, since "renders as nothing" is a property of the glyph and not of any Unicode category — becomes U+FFFD, and every non-ASCII space separator is narrowed to a plain space so a name cannot fake width and the result is length-bounded, while spaces and parentheses stay literal text that is never interpolated into a command. A `stat` past the 64 KiB read bound is skipped with a reason rather than parsed from the bytes that fit, since a cut line still parses and would mint a wrong creation token. The status a source publishes states what it read and from where: only `--live-source` describes its data as live, and a scoped root claims neither liveness nor synthesis, because a path cannot tell a fixture tree from a bind mount of the host's real `/proc`. On a non-Linux host `--live-source` reports an incomplete scan rather than an empty one.

The socket directory must be private to the current non-root user. An existing socket is never replaced. Configure the existing `srui-ssh-bridge` subsystem to point to that socket and connect with the unchanged generic macOS client.

App-specific deterministic checks:

```sh
cargo test --locked --manifest-path apps/srtop/Cargo.toml
bash apps/srtop/test.sh
```

The native entry point builds the app and SSH bridge, then runs `ProcessExplorerShellTests` through the existing Swift client test target over an ephemeral authenticated localhost SSH subsystem, checking both empty and fake-source cases, actual native cell values and retained handles. A second native test drives `--fake-sequence` over the same real SSH path and records every published state: the native table shows the insertion, the deletion, the rename, the retained rows of the failed scan and the recovery, the unchanged row keeps its item ID, the table and status controls are the same objects throughout, and one five-tick cycle of the script costs exactly four transactions. Missing prerequisites fail; they are never silently skipped.

## Refresh

Every collecting mode polls its source on a fixed schedule: `--refresh-interval-ms MS` configures it between 50 ms and 300 s, and the default is one second. The first snapshot creates the shell; every later tick publishes only the difference — inserts, deletes, the values of rows whose displayed cells changed, and the status text when it changed — so a row that did not change keeps its item identity and its native control. Deletions are emitted before insertions, so an insertion index is the row's final index, and a refresh larger than a §26 bound commits as consecutive atomic transactions rather than failing whole.

Three §26 bounds split a refresh, and they are independent. A transaction carries at most the store's operation bound, each model operation at most its items bound, and each transaction at most one 16 MiB frame of encoded payload — the frame ceiling is `DEFAULT_MAX_FRAME_SIZE` less a fixed allowance for the envelope the operations travel in, never a number of this app's choosing. The size bound is the one operation counting alone misses: a host that grows to tens of thousands of long names needs only four `MODEL_INSERT` operations, far inside the operation bound, and still carries more than one frame. Committing that as a single transaction would advance the server's revision and only then have the codec refuse the frame, detaching the client from a server that had already moved on — and the next identical tick would diff clean and republish nothing. Sizes are charged as upper bounds the encoder cannot exceed: every string counts its encoded UTF-8 bytes, not its characters, so a name of 128 four-byte characters is charged 512 bytes.

The collection itself is never larger than a client can be *sent*. Splitting the live mutations is not enough on its own: a client that attaches, or resyncs after a journal gap, is brought up by one catch-up snapshot transaction that carries every cached range of the model at once and is bounded only by its operation count, so a model that encodes past one frame is a collection nobody can attach to, however carefully each refresh was split. The rows that do not fit are therefore not published. The ceiling is the same derived number and the same upper-bound accounting the refresh planner uses, less a fixed allowance for the shell and the exact bytes of the status text, and it applies on the start path exactly as on every later tick — the start path is precisely the attach path this bound exists for. The rows kept are the leading ones of the order the source already publishes (`ProcFsSource` sorts by ascending PID), so the published window is a deterministic function of the snapshot alone: an unchanged host keeps exactly the rows it kept last tick, no row churns in and out, and an identical tick still publishes nothing. The status says what happened in counts and fixed wording, in its own clause (`· 6683 rows beyond the publishable size limit`) — those rows were read perfectly well, so they are never called unreadable, and they are not the entries the collector's own record bound never read (`beyond the record limit`) either. The runtime-side limitation this works around — `sessiond` exports a catch-up snapshot as one unchunked transaction and checks only its operation count — is **not** fixed here: it is core protocol and runtime work, it affects every SRUI application, and it is tracked by ticket PX-004-G01.

A tick whose snapshot holds nothing a client can see opens no transaction at all. Nothing that moves on its own is published: the sample time, the issue counts and the source's internal state stay off the wire, so an unchanging host produces no traffic. Sampling runs off the async runtime, since reading a host's process filesystem blocks.

A scan that fell short is not a collection that emptied, but it is still entitled to report the exits it did observe. A row is deleted only when the scan accounted for its absence: a scan that named the records it could not read has proven that every *other* absent process ended, so those rows go while the named record's row stays exactly where it is and keeps its item ID. Those identities are the scan's own knowledge — every record's PID is recorded as the scan leaves it out, in ledgers bounded by the scan rather than by the host — and never a reading of the bounded `EnumerationIssue` list, which only explains a degraded scan to a person and stops at 32 entries. A host with hundreds of unreadable records therefore still names every one of them and still deletes the rows of processes that really ended. The same holds for a host with more processes than one scan publishes: reaching the record bound stops the scan from reading each further record's detail, not from listing it, and a listing entry *is* a PID, so those entries are named too. Without that, every scan of a large host would be entitled to delete nothing and the collection would grow from the record bound until the model's cached-item limit refused the next refresh. That scoping is not a detail: one permanently denied `/proc/<pid>/stat` makes every scan on a shared host incomplete, and retaining every absence would then accumulate a stale row per exit until the model's cached-item limit refuses the next refresh.

Retention stays whole only where the uncertainty is whole because the identities themselves were never observed: the process list could not be listed or one of its entries could not be examined, the scan left out more records than the ledger naming them may hold, or the snapshot's identities were rejected. Then the last-known rows stay exactly where they are, keep their item IDs, and the status says what happened and how many rows are unconfirmed (`· process list unavailable: permission denied · 3 rows retained from an earlier scan`). A record an otherwise good scan could not read is also not a deletion; it keeps the place it already held, next to the same rows. A record that merely vanished between listing and reading is not uncertain at all and is deleted like any other exit. When the scan recovers, the status returns to the source's own label and no row moves. A host that stays broken republishes nothing, because the explanation has not changed either. The status is built from counts and fixed wording only: no process's own text ever reaches it.

Row identities are session-local and are never reused, and the allocator forgets an identity once its row leaves the collection, so a long-running poll does not accumulate one entry per process that ever ran.

The source's global identity — host, boot and PID namespace — is remembered across scans, because one unreadable identity file would otherwise re-key every record at once while skipping no PID, so retention would have nothing to keep and the whole table would be deleted and reinserted — twice, once on the failure and once on the recovery. A scan that could not read `sys/kernel/hostname`, `sys/kernel/random/boot_id` or the namespace link is keyed with the last value that was observed, so neither the degraded tick nor the recovering one deletes, inserts or moves a row, and every row keeps its item ID and its native control. Nothing remembered reaches the wire: the degradation is still published, from the scan's own issues and in the same count-based wording, on exactly the tick that saw it (`· incomplete scan · 3 processes listed · host identity incomplete`). A component that comes back as a *different* value is not a degradation but a different source: its records are different process instances and visibly take new row identities, and that newly observed value is what the next degraded scan is anchored to. A component never observed at all is never invented.

`--fake-sequence` runs a deterministic cyclic script — three processes, the same three a second later, then one ended, one renamed and one new, then a failed scan, then recovery — for tests that need every refresh case without a host. It is a fixture: it reads no process, no clock and no file, and says so in the status.

`--smoke-fixture` enables a local SIGUSR1 trigger for one deterministic title value. It updates the existing Surface label and heading through a normal atomic transaction. This is a test fixture, not a remote process action. The native test verifies retained window and table handles before and after that update.
