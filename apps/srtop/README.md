# Process Explorer

PX-004 keeps the shell's process list current: a source is polled at a configurable, one-second-by-default interval, and each snapshot difference is published as model operations on the existing transaction path. The semantic node tree — heading, status, native PID/Name table — is still built once. Process actions are not implemented.

Build and run from the repository root:

```sh
cargo build --locked --manifest-path apps/srtop/Cargo.toml
apps/srtop/target/debug/srtop --socket /tmp/srtop-dev/srtop.sock --fake-source
apps/srtop/target/debug/srtop --socket /tmp/srtop-dev/srtop.sock --live-source   # Linux
apps/srtop/target/debug/srtop --socket /tmp/srtop-dev/srtop.sock --fake-sequence --refresh-interval-ms 500
```

The fake snapshot contains three rows in order: `4101 / worker`, `4102 / worker`, and `Unavailable / helper`. Duplicate names have distinct opaque item IDs, and missing data is explicit. Omit every source flag to retain the empty-shell fixture, which does not poll; the source flags are mutually exclusive. Source records, source identity and sample time are typed separately from UI projection; fake mode performs no live process enumeration.

`--live-source` reads `/proc` once through `std` alone (no new dependency) and publishes PID and process name. Each process gets a `ProcessKey` of source, host, boot and PID-namespace identity, the PID, and a creation token taken from `/proc/<pid>/stat` field 22 in kernel clock ticks since boot — not a rounded start-time second. The key resolves to an opaque session item ID, so a reused PID with a different creation token is a different row identity. Identity that the kernel answers from the *reader's* namespaces is published only when the scanned mount is provably this process's own procfs: the hostname is a sysctl answered from the reader's UTS namespace, so a mount that cannot be proven reports its host identity as unavailable rather than stamping records with a hostname belonging to none of them, and a published hostname names the namespace it was read in (`host@uts:[inode]`) so two readers that disagree disagree visibly instead of both claiming to have named the same machine. A reader that cannot name its own UTS namespace publishes no hostname at all, since an unqualified name would let two readers in different namespaces claim the same identity. The boot identity is not gated that way, being one value per running kernel. The source identity is lossless in the root's bytes, so two roots differing only in invalid UTF-8 can never alias. The PID namespace comes from the scanned mount's own namespace init, `<root>/1/ns/pid`, whenever the scan may read it. An unprivileged scan usually may not, and then falls back to `self/ns/pid` — the reader's own namespace — only under both proofs that it describes these records: `<root>/self` names this process's own PID, and `<root>/self` and `/proc/self` are the same device and inode, since one procfs superblock belongs to exactly one PID namespace. A host `/proc` bind-mounted into a container fails the second proof, a nested namespace that inherited an outer `/proc` fails the first, and either way the namespace is reported unavailable rather than stamped with the reader's. A snapshot is either complete, where an empty list authoritatively means "no processes visible", or incomplete, where individually denied or unparsable records are skipped with a reason and an empty list never means "nothing is running". A process that exits between listing `/proc` and reading it was not unreadable — it no longer exists at sample time — so it is counted separately and does not degrade the scan; ordinary churn on a busy host therefore never leaves the shell labelled incomplete. The status line states what actually fell short: how many records were unreadable when some were, that the process list itself was unavailable and why when the root could not be listed at all, and that host identity is incomplete when only the identity files were missing, and how many entries were beyond the collector's own record limit when the scan stopped at that bound rather than at a read failure — it never publishes a count of zero unreadable, and never describes a record it declined to read as unreadable. Process names are sanitized once on the server: invalid UTF-8 plus every control (Cc), every `Default_Ignorable_Code_Point` including its reserved ranges, the format characters (Cf) outside that set, the line and paragraph separators, and the known blank-glyph characters — only the last group is enumerated by hand, since "renders as nothing" is a property of the glyph and not of any Unicode category — becomes U+FFFD, and every non-ASCII space separator is narrowed to a plain space so a name cannot fake width and the result is length-bounded, while spaces and parentheses stay literal text that is never interpolated into a command. A `stat` past the 64 KiB read bound is skipped with a reason rather than parsed from the bytes that fit, since a cut line still parses and would mint a wrong creation token. The status a source publishes states what it read and from where: only `--live-source` describes its data as live, and a scoped root claims neither liveness nor synthesis, because a path cannot tell a fixture tree from a bind mount of the host's real `/proc`. On a non-Linux host `--live-source` reports an incomplete scan rather than an empty one.

The socket directory must be private to the current non-root user. An existing socket is never replaced. Configure the existing `srui-ssh-bridge` subsystem to point to that socket and connect with the unchanged generic macOS client.

App-specific deterministic checks:

```sh
cargo test --locked --manifest-path apps/srtop/Cargo.toml
bash apps/srtop/test.sh
```

The native entry point builds the app and SSH bridge, then runs `ProcessExplorerShellTests` through the existing Swift client test target over an ephemeral authenticated localhost SSH subsystem, checking both empty and fake-source cases, actual native cell values and retained handles. A second native test drives `--fake-sequence` over the same real SSH path and records every published state: the native table shows the insertion, the deletion, the rename, the retained rows of the failed scan and the recovery, the unchanged row keeps its item ID, the table and status controls are the same objects throughout, and one five-tick cycle of the script costs exactly four transactions. Missing prerequisites fail; they are never silently skipped.

## Refresh

Every collecting mode polls its source on a fixed schedule: `--refresh-interval-ms MS` configures it between 50 ms and 300 s, and the default is one second. The first snapshot creates the shell; every later tick publishes only the difference — inserts, deletes, the values of rows whose displayed cells changed, and the status text when it changed — so a row that did not change keeps its item identity and its native control. Deletions are emitted before insertions, so an insertion index is the row's final index, and a refresh larger than the §26 operation bound commits as consecutive atomic transactions rather than failing whole.

A tick whose snapshot holds nothing a client can see opens no transaction at all. Nothing that moves on its own is published: the sample time, the issue counts and the source's internal state stay off the wire, so an unchanging host produces no traffic. Sampling runs off the async runtime, since reading a host's process filesystem blocks.

A scan that fell short is not a collection that emptied, but it is still entitled to report the exits it did observe. A row is deleted only when the scan accounted for its absence: a scan that named the records it could not read has proven that every *other* absent process ended, so those rows go while the named record's row stays exactly where it is and keeps its item ID. Those identities are the scan's own knowledge — every skipped record's PID is recorded as it is skipped, in a set bounded by the same record bound that limits how many records the scan reads — and never a reading of the bounded `EnumerationIssue` list, which only explains a degraded scan to a person and stops at 32 entries. A host with hundreds of unreadable records therefore still names every one of them and still deletes the rows of processes that really ended. That scoping is not a detail: one permanently denied `/proc/<pid>/stat` makes every scan on a shared host incomplete, and retaining every absence would then accumulate a stale row per exit until the model's cached-item limit refuses the next refresh.

Retention stays whole only where the uncertainty is whole because the records were never read, so their identities are unknown: the process list could not be listed or one of its entries could not be examined, the scan stopped at its own record bound without reading the remaining PIDs, it skipped more records than that same bound lets it name, or the snapshot's identities were rejected. Then the last-known rows stay exactly where they are, keep their item IDs, and the status says what happened and how many rows are unconfirmed (`· process list unavailable: permission denied · 3 rows retained from an earlier scan`). A record an otherwise good scan could not read is also not a deletion; it keeps the place it already held, next to the same rows. A record that merely vanished between listing and reading is not uncertain at all and is deleted like any other exit. When the scan recovers, the status returns to the source's own label and no row moves. A host that stays broken republishes nothing, because the explanation has not changed either. The status is built from counts and fixed wording only: no process's own text ever reaches it.

Row identities are session-local and are never reused, and the allocator forgets an identity once its row leaves the collection, so a long-running poll does not accumulate one entry per process that ever ran.

`--fake-sequence` runs a deterministic cyclic script — three processes, the same three a second later, then one ended, one renamed and one new, then a failed scan, then recovery — for tests that need every refresh case without a host. It is a fixture: it reads no process, no clock and no file, and says so in the status.

`--smoke-fixture` enables a local SIGUSR1 trigger for one deterministic title value. It updates the existing Surface label and heading through a normal atomic transaction. This is a test fixture, not a remote process action. The native test verifies retained window and table handles before and after that update.
