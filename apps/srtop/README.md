# Process Explorer

PX-007 adds a system summary and a data-freshness indicator above the list: the host's overall CPU, memory, swap, load averages, uptime and process count, and when and from which source they were sampled. PX-006 added sampled per-process CPU usage beside the resident memory PX-005 added to the list PX-004 keeps current: a source is polled at a configurable, one-second-by-default interval, and each snapshot difference is published as model operations on the existing transaction path. The semantic node tree — heading, status, system summary, sort buttons, native PID/Name/Resident/CPU table — is still built once. PX-009 lets the list be sorted by any of its four columns, on the server ([Sorting](#sorting)). PX-010 adds a responsive, server-authoritative command and process-name filter with pending and committed status indicators ([Filtering](#filtering)). Process actions are not implemented.

## Run it (R0, read-only)

PX-008 closes the first release gate, R0: a real read-only CPU and resident-memory process list. `apps/srtop/run.sh` builds what it needs and opens the explorer in the unchanged generic macOS client, `RendererDemoApp` — the same client that runs `examples/counter`; nothing in it is specific to this app. The gate's commands and results are in the [R0 release record](srui-process-explorer-plan/docs/process-explorer/releases/R0.md).

- **Prerequisites.** macOS 14 or later with Xcode (Swift 6) and the Rust toolchain. Docker Desktop for the dev box. For your own Linux host: SSH key authentication, and its host key already in your `known_hosts` (the client never prompts).
- **Fake mode, no host.** `apps/srtop/run.sh fake` shows the fixed three-row snapshot; `apps/srtop/run.sh sequence 500` cycles the scripted refresh sequence every 500 ms. srtop runs on this Mac on a private socket in a fresh `0700` directory under `/tmp`, and the client connects to it directly, without SSH.
- **A real Linux host.** `apps/srtop/run.sh devbox` reads a real `/proc` in a throwaway Linux container and connects through the real `srui-ssh-bridge` SSH subsystem ([devbox/README.md](devbox/README.md)); `apps/srtop/devbox/r0-scenario.sh` replays the gate's scenario against it. On your own host, as your own non-root user: build srtop and the bridge there (the two `cargo build` commands below, with `server-rust/Cargo.toml -p srui-ssh-bridge` for the bridge), start `srtop --socket <path> --live-source` with `<path>` in a directory only you can enter, have an administrator add `Subsystem srui /path/to/srui-ssh-bridge --socket <path>` to `sshd_config` ([devbox/sshd_config](devbox/sshd_config) is a complete example), then run `apps/srtop/run.sh ssh you@host [port] [identity] [known_hosts]`. With no `--socket`, the bridge connects to the per-user default `$XDG_RUNTIME_DIR/srui-sessiond.sock`, or `${TMPDIR:-/tmp}/srui-<uid>/srui-sessiond.sock` where `XDG_RUNTIME_DIR` is unset, so one `Subsystem` line can serve several users who start srtop at that path.
- **Stopping it.** Quit the client (⌘Q, or close its window). `run.sh fake` and `run.sh sequence` then stop the srtop they started with SIGTERM, which removes its socket, and remove its directory; Ctrl-C in their terminal does the same. Stop the dev box with `apps/srtop/devbox/devbox.sh down`, and an srtop you started on a host with Ctrl-C or SIGTERM.
- **Known limitations.** Read-only: it offers no action on a process — its only input handlers are the four sort buttons, the command filter input, the user filter and PID set, the search controls, the column chooser buttons and the table's selection, which reorder, filter, search and re-lay out the list and describe the selected process — and every test run checks its sources, manifest and binary for the ways of controlling a process that `tests/no_process_control_test.rs` lists — a tripwire against introducing one by accident, not a proof; what it does not see is in the [R0 release record](srui-process-explorer-plan/docs/process-explorer/releases/R0.md#its-remaining-blind-spots). Linux only for live data; on macOS `--live-source` reports a collector error. One list, in the source's PID order until sorted or filtered, or the same processes as a parent/child tree ([Process tree](#process-tree)); a selected row is only described by the inspector, never acted on, and its command line is shown, never run or opened. No owner column yet: the owner is a filter, not a displayed field. The list is what this reader can see — its PID namespace, `hidepid` — and a host past the snapshot-frame ceiling (about 25,000 of the widest rows) shows a truncated list and says so. Resident memory is approximate on Linux 6.2–6.15; per-process CPU is quantized by the tick rate and warms up on its first sample; times are the server's clock in UTC, with no local age. The dev box is a container on Docker Desktop's Linux VM, which lists the container's processes only.

Build and run from the repository root:

apps/srtop/target/debug/srtop --socket /tmp/srtop-dev/srtop.sock --fake-source
apps/srtop/target/debug/srtop --socket /tmp/srtop-dev/srtop.sock --live-source   # Linux
apps/srtop/target/debug/srtop --socket /tmp/srtop-dev/srtop.sock --fake-sequence --refresh-interval-ms 500

The fake snapshot contains three rows in order: `4101 / worker / 1.1 MiB / 250.0%`, `4102 / worker / 0 B / 0.0%`, and `Unavailable / helper / Denied / Warming up` — one value whose fraction is truncated rather than rounded, one process that genuinely holds no resident pages and used no CPU, one whose metric the scan was refused, a multithreaded process using two and a half logical CPUs, and a process seen for the first time. Duplicate names have distinct opaque item IDs, and missing data is explicit. Its summary reads `Overall CPU (100% = all 8 logical CPUs): 31.2%`, `Memory: 4.0 GiB used of 16.0 GiB (25.0% of total)`, `Swap: none configured` — a host with no swap — and `Last successful sample: 2027-01-15 08:00:00 UTC (server clock) · source: fake-processes-v1`, constants like every row. Omit every source flag to retain the empty-shell fixture, which does not poll and whose summary says nothing was sampled; the source flags are mutually exclusive. Source records, source identity and sample time are typed separately from UI projection; fake mode performs no live process enumeration.

`--live-source` reads `/proc` through `std` alone (no new dependency) and publishes PID, process name, resident memory and CPU usage.

CPU usage is published under the heading `CPU (100% = 1 CPU)`, because the number alone cannot say what it is a share of: 100% is one fully used logical CPU, so a multithreaded process may exceed 100% (the convention `sysinfo`'s `Process::cpu_usage` documents). A share of the whole host is a later display option, not this column. The value is `/proc/<pid>/stat` fields 14 (`utime`) and 15 (`stime`) — user plus kernel time in clock ticks, without waited-for children's `cutime`/`cstime` — differenced between two scans of the same process instance and divided by the tick rate the scanned mount reports through `AT_CLKTCK` in its own `self/auxv` (what glibc's `sysconf(_SC_CLK_TCK)` answers from) and by the time between the two reads of that process's `stat` on a **monotonic** clock (`Instant`, `CLOCK_MONOTONIC` on Linux), never the wall clock that stamps the sample, so setting the system time cannot stretch or shrink an interval. It is stored as the exact tick delta, tick rate and interval and turned into text once, on the server, in integer arithmetic with the tenths digit truncated. A percentage needs two samples, so `--live-source` keeps one persistent collector for its whole life, holding one counter baseline per record it last published — bounded by the record bound, and forgotten once a process ends. The baseline is keyed by PID *and* creation token: a process seen for the first time, including a new process under a reused PID, is published as `Warming up` rather than inheriting another process's counters, so the first publication of a live host is visibly warming up. A counter that went backwards, a monotonic interval that did not advance (the older baseline is then kept, so the next scan measures across both) or ran backwards, and a delta implying more than 65,536 logical CPUs are published as `Unavailable` — never as `0.0%` and never as a spike — and a measured zero stays `0.0%`. A mount that cannot state a believable tick rate (absent, zero, or above 1,000,000 per second) publishes `Unavailable`, or `Denied` when its `auxv` is unreadable, on every scan rather than a warm-up that never ends; a boot or PID namespace that comes back *different* discards every baseline, while one a scan merely could not read discards nothing. As with resident memory, an unread CPU value is a per-field state and never makes the record list incomplete. Each record is measured over its own read-to-read interval: the monotonic instant is taken the moment that record's `stat` read returns, so a slow read or a long scan of a very large host never divides one process's counter delta by an interval it was not measured over. The result is quantized by the tick rate: one tick is `100 / (CLK_TCK × interval)` percentage points, so at `USER_HZ` 100 a fully busy thread reads within about one point of 100% at the one-second default, but at the 50 ms minimum interval one tick is 20 points and the same thread honestly reads 80%, 100% or 120% from tick to tick. The value is not smoothed or capped at the host's CPU count: the CPUs a process can use are bounded by cgroup quotas and cpusets that the visible CPU count does not reflect, and the scanned mount need not be this machine's. There is no macOS process source: on a non-Linux host `--live-source` still reports an incomplete scan, and no CPU value is claimed there.

Resident memory is `/proc/<pid>/statm` field 2 (`resident`) in pages, multiplied by the page size the scanned mount reports through `AT_PAGESZ` in its own `self/auxv` — the interface `sysconf(_SC_PAGESIZE)` answers from, read through the scanned root rather than this machine's, so a fixture tree states its own page size and converts deterministically on any host. It is stored as an exact `u64` byte count and turned into text once, on the server, in IEC multiples (`KiB` is 1024 bytes, never 1000) with the fraction **truncated**: a count just below a multiple reads `1023.9 KiB` rather than a `1024.0 KiB` it never reached, and no step of the conversion leaves the integers, so a value too large for a `f64` is still published exactly. Shared pages are counted in full for every process that maps them, so these values do not sum to the memory a host has in use, and pages that are swapped out or were never faulted in are not counted at all. Proportional accounting is a later ticket.

How exact the page count is depends on the kernel, and the collector does not branch on its version (PX-005-G01). From Linux 6.16 `statm` is exact: `task_statm` (`fs/proc/task_mmu.c`) sums every resident counter across all CPUs with `get_mm_counter_sum` (commit `82241a83cd15`, "mm: fix the inaccurate memory statistics issue for users", first in v6.16 and backported to 6.15.7, 6.12.39 and 6.6.99). From 6.2, where commit `f1a7941243c1` made those counters percpu_counters, until that fix, `statm` reports the same approximate count as `stat` field 24: `percpu_counter_read_positive` leaves out every per-CPU delta smaller than the batch, `max(32, 2 × online CPUs)` pages (`compute_batch_value`, `lib/percpu_counter.c`), so each of the file, anonymous and shared-memory counters can be off, either way, by up to that batch per online CPU, and a just-started or small process can read `0 B` while it holds resident pages. `stat` field 24 is approximate on every kernel since 6.2 — `do_task_stat` (`fs/proc/array.c`) still fills it from `get_mm_rss` in v7.2 and in mainline — and is not read: nothing falls back to it. Kernels before 6.2 are approximate as well: on SMP builds each thread caches its own counter changes and adds them in only after more than 64 page-fault events (`SPLIT_RSS_COUNTING`, `TASK_RSS_EVENTS_THRESH`, `check_sync_rss_stat` in `mm/memory.c`, v6.1), and `stat`, `statm` and `status` all read those same counters, so `statm` is no worse there either. (`proc_pid_statm(5)` in man-pages 6.19 still calls `resident` inaccurate, which describes the kernels before the 6.16 fix.) The price is one more bounded read and one directory open per process per scan. On a 12-CPU Linux 6.10 VM with about 3,000 test-owned sleeping workers, every run recorded in the completion note put a scan at 11.6–14.0 ms before and 20.3–24.4 ms after, +64% to +100% (about 3.9–4.7 µs to 6.8–8.1 µs per process). Of the added 3–4 µs per process the `statm` read is about 1.5–2.0 µs and the pinned directory (described below) about 0.9–1.9 µs, a third to a half of the added cost: forcing reads by name in the same build was faster than pinning in 21 of 22 paired rounds. At the `MAX_RECORDS` bound of 65,536 records that extrapolates to roughly 0.25–0.31 s before and 0.44–0.53 s after per scan.

Both files of a record are read through one handle on its `/proc/<pid>` directory, opened once and reached again through the reader's own `/proc/self/fd/<n>` (`std` alone, no `openat`). A kernel procfs binds that handle to the process instance it was opened on, so once the instance is reaped a read through it fails with `ESRCH` or `ENOENT` instead of reaching a newcomer that took the PID between the two reads. By name, that misattribution needs the process to exit and be reaped between the two back-to-back reads and its number to be handed out again in the same instant. An ordinary fork gets a freed number only once the cyclic PID allocator comes back round to it, but a process with `CAP_CHECKPOINT_RESTORE` or `CAP_SYS_ADMIN` over the PID namespace can take it at once, with `clone3()`'s `set_tid` (Linux 5.5+) or `/proc/sys/kernel/ns_last_pid`, so the window is narrow but real; the pin rules it out rather than relying on timing, at the cost above. The binding is the kernel procfs's own: a scoped root given to `ProcFsSource::with_root` that is not a kernel procfs — a fixture, or a FUSE, 9p or sshfs mirror of another host's `/proc` — is read through the same handle with no such guarantee. Pinning needs the reader's own procfs: each scan checks that `/proc/self/fd/<n>` reaches the very directory it opened, and where it does not — on every system but Linux, and on a Linux reader whose own `/proc` is missing or unusable — every record is read by name, with that narrow but real window, and nothing reports the fallback. A pinned read also opens the record's directory for reading, where reading by name needed only search permission. A stock procfs grants both, so nothing changes there; but where a record directory may be searched and not read — a search-only mode, or a security policy that grants search but not read — the record is now skipped as `Denied` and the scan reported incomplete, where reading by name would have published it.

A value this scan could not read is published as `Unavailable`, or `Denied` when a permission refused it — never as zero, and a genuine zero stays `0 B`. Each cell carries its own availability: a record whose `statm` is refused (`Denied`), unreadable, or anything but the kernel's exact line of seven plain counts (`Unavailable`) is still a published record with an identity and a name, so an unreadable *metric* does not make the record *list* incomplete and does not add a clause to the status line. A process that ends between its `stat` and its `statm` read is counted as vanished, like one that ended before its `stat` was read, once its `stat`, read again through the same directory, is gone as well or names another instance under the same PID; a `statm` missing beside a `stat` that still reads as the same instance, which no kernel produces, or beside a line that names no instance, is an unread field of a published record. A record entry that is not a directory, a FIFO included, is refused without being opened and skipped as unreadable, and a task with no address space — a kernel thread, a zombie — reads the kernel's `0 0 0 0 0 0 0` and stays a known `0 B`. A mount that cannot state a believable page size — no `AT_PAGESZ` entry, a value that is not a power of two, or one outside 512 B 1 GiB — publishes every resident value as unread rather than attributing this machine's page size to records that were never measured on it, and a page count too large to convert is reported unread rather than wrapped. Each process gets a `ProcessKey` of source, host, boot and PID-namespace identity, the PID, and a creation token taken from `/proc/<pid>/stat` field 22 in kernel clock ticks since boot — not a rounded start-time second. The key resolves to an opaque session item ID, so a reused PID with a different creation token is a different row identity. The host, boot and PID-namespace components are facts about the source rather than about a record, so they are remembered for the session: a scan that cannot read one of those identity files is keyed with the last value that was read, and a transient failure therefore re-keys nothing (see Refresh). Identity that the kernel answers from the *reader's* namespaces is published only when the scanned mount is provably this process's own procfs: the hostname is a sysctl answered from the reader's UTS namespace, so a mount that cannot be proven reports its host identity as unavailable rather than stamping records with a hostname belonging to none of them, and a published hostname names the namespace it was read in (`host@uts:[inode]`) so two readers that disagree disagree visibly instead of both claiming to have named the same machine. A reader that cannot name its own UTS namespace publishes no hostname at all, since an unqualified name would let two readers in different namespaces claim the same identity. The boot identity is not gated that way, being one value per running kernel. The source identity is lossless in the root's bytes, so two roots differing only in invalid UTF-8 can never alias. The PID namespace comes from the scanned mount's own namespace init, `<root>/1/ns/pid`, whenever the scan may read it. An unprivileged scan usually may not, and then falls back to `self/ns/pid` — the reader's own namespace — only under both proofs that it describes these records: `<root>/self` names this process's own PID, and `<root>/self` and `/proc/self` are the same device and inode, since one procfs superblock belongs to exactly one PID namespace. A host `/proc` bind-mounted into a container fails the second proof, a nested namespace that inherited an outer `/proc` fails the first, and either way the namespace is reported unavailable rather than stamped with the reader's. A snapshot is either complete, where an empty list authoritatively means "no processes visible", or incomplete, where individually denied or unparsable records are skipped with a reason and an empty list never means "nothing is running". A process that exits between listing `/proc` and reading it was not unreadable — it no longer exists at sample time — so it is counted separately and does not degrade the scan; ordinary churn on a busy host therefore never leaves the shell labelled incomplete. The status line states what actually fell short: how many records were unreadable when some were, that the process list itself was unavailable and why when the root could not be listed at all, and that host identity is incomplete when only the identity files were missing, and how many entries were beyond the collector's own record limit when the scan stopped at that bound rather than at a read failure — it never publishes a count of zero unreadable, and never describes a record it declined to read as unreadable. Process names are sanitized once on the server: invalid UTF-8 plus every control (Cc), every `Default_Ignorable_Code_Point` including its reserved ranges, the format characters (Cf) outside that set, the line and paragraph separators, and the known blank-glyph characters — only the last group is enumerated by hand, since "renders as nothing" is a property of the glyph and not of any Unicode category — becomes U+FFFD, and every non-ASCII space separator is narrowed to a plain space so a name cannot fake width and the result is length-bounded, while spaces and parentheses stay literal text that is never interpolated into a command. A `stat` past the 64 KiB read bound is skipped with a reason rather than parsed from the bytes that fit, since a cut line still parses and would mint a wrong creation token. The status a source publishes states what it read and from where: only `--live-source` describes its data as live, and a scoped root claims neither liveness nor synthesis, because a path cannot tell a fixture tree from a bind mount of the host's real `/proc`. On a non-Linux host `--live-source` reports an incomplete scan rather than an empty one.

The socket directory must be private to the current non-root user. An existing socket is never replaced. Configure the existing `srui-ssh-bridge` subsystem to point to that socket and connect with the unchanged generic macOS client.

## System summary

Between the status line and the table the shell publishes a summary (PX-007), built from standard `Text` and `Progress` nodes in a `Column` with one `Row` per bar: no custom graph, no image and no drawing instruction, rendered by the unchanged generic client as native labels and `NSProgressIndicator` bars. Every figure becomes text once, on the server, in integer arithmetic; each bar is filled to exactly the truncated share its line prints, and the client derives nothing. Each figure is read through the scanned root — `<root>/stat`, `<root>/meminfo`, `<root>/uptime`, `<root>/loadavg` — so a fixture tree states its own and is deterministic on any host, and each file is read, and can fail, on its own.

- **Overall CPU** — `Overall CPU (100% = all 8 logical CPUs): 31.2%`. A share of *all* logical CPUs, where the table's `CPU (100% = 1 CPU)` column is a share of one, and the line always names its denominator. It is the first line of `stat` (`cpu`, in `USER_HZ` ticks summed over every CPU): busy is `user + nice + system + irq + softirq + steal`, idle is `idle + iowait`, and the share is the busy delta over the busy plus idle delta between two reads, truncated to a tenth of a point. `guest` and `guest_nice` are already counted in `user` and `nice` (`account_guest_time`, `kernel/sched/cputime.c`) and are not added again; fields after `steal` are not read; `iowait` may decrease between reads (K1), so idle and iowait are differenced as one sum. The `cpuN` lines that follow are counted as the logical CPUs online. Parsing stops at the first other line, after at most 4 KiB of it. The file is read through an 8 KiB buffer, so less than one buffer past that point is copied out of the kernel, and the rest of `stat` — an `intr` line that grows with the interrupt count among it — is neither parsed nor copied out (the kernel still renders the whole file when it is first read); a count that would need more than 2 MiB of `cpuN` lines is reported unknown (`all logical CPUs`) rather than as the lines that fit. The collector keeps one baseline of the host's counters, and the share is always measured between two consecutive successful reads: the first read is `Warming up`, and so is the first read after one that failed or held no usable `cpu` line, because such a read discards the baseline — an outage is never averaged into the figure published after it. Counters that went backwards, did not advance at all, or were read over a different number of CPUs leave no interval and read `Unavailable (no measurable interval since the previous sample)`, never 0% and never a spike; a different boot discards the baseline too.
- **Memory** — `Memory: 4.0 GiB used of 16.0 GiB (25.0% of total)`. Used is `MemTotal - MemAvailable` from `meminfo` (kB of 1024 bytes): the memory the kernel does not estimate as available for starting new applications without swapping. The percentage is used over `MemTotal`. A missing or malformed field, a `MemTotal` of 0 or a `MemAvailable` above `MemTotal` is unavailable, never zero.
- **Swap** — `Swap: 256.0 MiB used of 2.0 GiB (12.5% of total)`, used being `SwapTotal - SwapFree` over `SwapTotal`. A `SwapTotal` of 0 is a host with no swap and reads `Swap: none configured`, with its bar hidden: never 0% of 0 and never a division.
- **Load average** — `Load average (1, 5, 15 min): 0.52, 0.58, 0.59`, the first three fields of `loadavg` exactly as the kernel prints them: damped averages of runnable and uninterruptible tasks, not a percentage and not divided by the CPU count.
- **Uptime** — `Uptime: 3 days, 4 h 05 min`, the first field of `uptime` (the boot-time clock, so suspended time counts) truncated to whole minutes.
- **Processes** — `Processes visible to this reader: 3 listed · complete scan · no srtop filter`, the records the last successful scan listed, in the status line's own counts and words (`· 12 unreadable`, `· 5 beyond the record limit`, `· incomplete scan`). Every record is a process directory, never a thread, and a process that ended during the scan is not counted. The count's scope is what this reader can see in the scanned root, and srtop applies no filter of its own. That view is bounded without any error: a procfs lists only the PID namespace it was mounted for (K1 §4.1: by default the mounting process's, or the one `pidns=` names) — usually the reader's own, but an outer namespace's when the reader runs in a nested namespace that inherited that `/proc` — and procfs mount options (K1 §4.1) hide processes too — `hidepid=invisible` (2), which systemd's `ProtectProc=invisible` sets, and `hidepid=ptraceable` (4) drop other users' or unptraceable processes from the listing, while `hidepid=noaccess` (1) leaves them listed and unreadable, which the count reports. A `subset=pid` mount hides the system files instead, and their lines then say they could not be read. srtop detects neither a namespace boundary nor a mount option, so a complete scan is complete over this view and never a claim about the whole host.
- **Freshness** — `Last successful sample: 2027-01-15 08:00:00 UTC (server clock) · source: procfs:/proc`. The sample time is the collecting server's wall clock when the scan began, in UTC to the second, and the source is the scan's own identity, cut at 256 bytes. No generic renderer behaviour can turn a timestamp into a local age, so the time itself is published and the reader compares it with their own clock; no client logic was added.

A figure the collector could not state is never a number: its line says `Warming up`, `Not sampled`, `Unavailable (<file> could not be read)`, `Denied (reading <file> was refused)` or `Unavailable (<file> has no usable …)`, a collector error is set in the warning role, and its bar is hidden and carries no `VALUE` at all, because an empty bar reads as 0%. Every figure comes from the last successful sample: the last scan whose process list was read and accepted. A scan that cannot list its processes, or whose snapshot this app rejects, publishes no figure from that scan — every figure stays as it was, and the freshness line becomes `Collector error: could not list processes (permission denied) · last successful sample: …` in the warning role, so a stale figure is never shown as fresh. Nor is overall CPU, the one figure that is a difference: it is measured only between two consecutive successful reads of `stat`, so the first figure after an outage in which `stat` could not be read is `Warming up`, not the outage's average. The table, status and summary all stay usable, the next good scan replaces every figure at its own time, and a collector that stays broken republishes nothing, because neither the error nor the last sample changed. Transport loss is not this line's to report: the generic client shows its own connection state (`disconnected — resume will be attempted`), and a server cannot publish anything while disconnected, so the two never look alike. A first scan that already fails publishes no figure at all (`… · no successful sample yet · source: …`); that is what `--live-source` shows on every system but Linux, which has no process filesystem.

The summary is refreshed inside the refresh's own transactions, on the properties a client would see change and on no others: scalar `SET_PROPERTY` operations, which §12.1 lets a slow client's delivery queue coalesce, and — only on the tick a bar loses its value — one `CLEAR_PROPERTY` of that bar's `VALUE`, a rare state change that §12.1 delivers on its own revision rather than coalesced. The fake source's figures and sample time are constants, so once it is synchronized it publishes nothing at all. A live host's freshness line changes once a second, so it publishes that line on most ticks; its other lines change only when their figures do.

## Metric catalogue

Every field srtop publishes is an entry in one typed, server-side catalogue (PX-042, `src/catalogue.rs`): the four process columns `process.pid`, `process.name`, `process.resident_memory` and `process.cpu_usage`, and the seven summary figures `system.cpu_busy`, `system.memory_used`, `system.swap_used`, `system.uptime`, `system.load_average`, `system.process_count` and `system.sample_time`. Each entry states its stable key, its unit, the §6.5 value shape it is stored as (unsigned integer, string or a small typed record), the interface it is read from, how values of several processes may be combined (resident memory is non-additive: shared pages are counted once per process), its default formatter and typed sort order, the capability the reader needs, its sensitivity, its collection cost and the refresh tiers that may collect it. The catalogue refuses a malformed or duplicate key and any unit the rest of an entry cannot carry — a raw type, formatter, aggregation or sort that does not fit it, or a definition whose unit text names another unit. The table's headings and every row's cells are built from the same catalogued column list, so nothing on screen changes: the headings, cells and summary lines are byte-for-byte what they were.

One vocabulary covers every field's availability: present, warming up, permission denied (`Denied`), unsupported, stale and failed (`Unavailable`) are distinct, and only a present value carries a number. Every field published today is cheap and read with every sample, inside the scan's atomic snapshot. An expensive field may never be collected on every sample: the catalogue refuses one that claims to be, and `src/on_demand.rs` collects such fields only for the rows a client has selected or can see, only while they are asked for, on the runtime's blocking pool and never on the sample loop, with a bounded number of fields tracked and reads outstanding. Never-read fields are dispatched first and then the oldest reading, so every demanded field is read within a bounded number of samples. Every read answers: one that panics or is dropped unrun counts as failed, and one that hangs past its deadline is given up — its field reads failed and its slot is reused. A field never has more than one read outstanding, in flight or given up, however often its row is hidden and shown again: a row shown again while its read is in flight takes that read's answer, and a field whose read was given up is not read again until that read returns. So one wedged field holds exactly one worker; while fewer fields are wedged than there are in-flight slots every other field keeps being read, and if more wedge at once they fill the slots until the read deadline gives them up and frees the slots for the other fields. Reads still running, in flight or given up, never exceed a fixed bound, and limits that would let nothing be dispatched are refused at construction. The residual: if that many distinct fields wedge at once, nothing more is dispatched until one of their reads returns — fields with values turn stale, fields without one read failed once they have waited past the deadline (a field merely queued behind healthy reads stays warming up), and collection resumes by itself when any wedged read returns; a read that never returns keeps its worker for the life of the process. A wall clock set forward by at least the deadline gives up the reads in flight at that moment, and their fields read failed until read again. Each on-demand value carries the time its read started, on a clock that counts time the host spent suspended (the larger of monotonic and wall-clock progress, since `std` exposes no suspend-inclusive monotonic clock and srtop uses no FFI), so a value read before a sleep is stale after it; a completion that a newer read superseded is discarded, a value older than its freshness bound is reported as stale rather than current, and none is ever merged into the snapshot as if it had been read with it. No production field is expensive yet, so nothing is collected on demand in this revision; the first expensive collector and the selection or visible range that drives it connect there.

## Sorting

A row of four standard `Button`s between the summary and the table — `Sort by PID`, `Sort by Name`, `Sort by Resident`, `Sort by CPU` — sorts the list on the server (PX-009). A click is a standard `ACTIVATE`; the first click on a column applies its catalogued default direction (PID and name ascending, resident memory and CPU descending), the next one reverses it, and the active button's label carries `↑` or `↓`. Until the first click the rows stay in their source's order and no button is marked. The buttons are disabled when nothing is collected (the empty-shell fixture), so event validation refuses a click on them before any handler runs.

Values are compared as what they are, never as the text a cell shows: the PID, resident bytes and CPU share (tenths of one CPU) numerically, so `9` sorts below `10` and `9 B` below `1.0 KiB`, and the name by Unicode scalar value (case-sensitive, not a locale collation), so `Xorg` sorts before `a10`, and `a10` before `a9`. A value that is not present — `Denied`, `Unavailable`, `Warming up` — sorts last in both directions and is never treated as zero; a measured `0 B` or `0.0%` is a value. Equal values, and the missing ones among themselves, are ordered by the process-instance identity (source, host, boot, PID namespace, PID, creation token), the same way in both directions.

Sorting reorders; it never replaces a row. The protocol has no move operation for a collection model, so a row that changes place is deleted and reinserted under its own item ID, inside the same transaction, carrying its current cells. Only the rows off a longest run already in order move — a process that climbs the CPU ranking moves alone — and a reorder too large for one transaction commits as several, each a complete set of moves, so no revision a client receives ever lacks a row. The table offers a native single selection, which the generic client anchors to item IDs; it therefore stays on the same process through every sort and every refresh that changes the ranking. The server reads no user selection; only an explicit search promotes a selection (see Searching).

A click is applied, and its new order published, before the click is acknowledged. Clicks apply one at a time in arrival order, each against the order the last one left, and every later sample is published in the order active when it is published, so a scan that was already running when a click landed is published in the newer order and never brings back the older one. A click that resolves to the order already published sends nothing. A replayed click is answered from the session's record of it, as every event is, and changes nothing. A click always sorts by the values of the latest sample, including a change that did not alter a cell (bytes within one displayed `KiB`).

One limitation follows from the published-row ceiling (see Refresh). On a host past it, the published window is the leading rows of the active order, so under a CPU or resident sort it is chosen by rank: a process whose rank crosses the window's edge leaves the collection and, when it comes back, is a new row with a new item ID, and a selection on it is lost. Below the ceiling, which only hosts of tens of thousands of processes reach, every process stays in the collection under every sort. Past it, a click reorders the rows already published at once; the leading rows of the new order that were outside the window arrive with the next refresh, at most one interval later.

## Filtering

A native `TextInput` filter field and a status indicator line live above the table in their own row (PX-010). Editing the filter field sends `TEXT_EDIT` events to the server. Typing, caret navigation, and IME composition remain immediate and local in the client; the server receives committed values, evaluates them against process names and available command text, and publishes matching rows while updating the filter status.

- **Query grammar.** Filter queries match case-insensitively using Unicode case folding. Multiple search terms are separated by `|` (OR logic). Non-ASCII whitespace separators and control characters are sanitized to inert spaces. The raw query is capped at 512 bytes, and at most 16 non-empty OR terms are evaluated; terms beyond 16 are omitted and noted in the status. No regex or shell interpretation occurs.
- **Two-phase staging and monotonic generations.** Every filter query is assigned a monotonic `FilterGeneration` (`u64`). Edits stage a filter and update the filter status to show the pending query (`Pending filter (gen N): ...`). When the query commits, the filter status displays committed counts (`Committed filter (gen N): "query" · M of N rows matched`). Out-of-order generations from stale asynchronous processing or delayed events are rejected, ensuring older query results never overwrite newer ones.
- **Stable process identity and selection.** Filtering never invents new item IDs or alters process identity. The server retains the complete unfiltered set of rows (`unfiltered_rows`). Rows that are filtered out and subsequently restored when the filter is cleared retain their exact item IDs. The generic client's native table selection anchors to item IDs and follows matching rows as they move.
- **Sizing and frame reserves.** Filter controls and status reserve 2048 bytes (`FILTER_RESERVE_BYTES`) in catch-up snapshots and frame budget calculations, ensuring responsive filtering within configured protocol bounds.

## Searching and jumping to a PID

A second row below the filter holds the search controls (PX-011): a `Find processes` `TextInput`, `Previous match` and `Next match` buttons, a `PID to find` `TextInput`, a `Go to PID` button and a search status line. Search is not filtering: it locates rows and never hides, moves or changes one. Every control is a standard widget sending a standard `TEXT_EDIT` or `ACTIVATE`; the search runs on the server.

- **Same query rules as the filter.** A search query is parsed and matched by the filter's own rules: process name and available command text, Unicode case folding, `|` for OR, the 512-byte and 16-term caps, inert sanitization, no regex and no shell. Every edit takes the next monotonic generation.
- **Whole collection.** Matches are counted over every row the server publishes, in published order, and matches the filter or the published-row ceiling keep out of the table are counted and stated (`N more matches not shown`). The search never counts only what a client has cached.
- **Next and Previous.** A new query selects the first match in published order. `Next match` and `Previous match` move to the next or previous match and wrap around in both directions. The status names the current match by position, row, PID and name, for example `Search: "worker": 3 matches in 5 shown rows · match 2 of 3 at row 3 of 5 · PID 101 · worker`. With no match, the status says so (`no match for "zzz" in 5 shown rows; search hides no rows`) and both buttons are disabled, so event validation refuses a click.
- **Go to PID.** The PID field accepts one to ten ASCII digits; anything else disables `Go to PID` and the status says `PID field: digits only`. Typing never searches. `Go to PID` selects the published row the latest scan confirmed with that PID. A PID that no shown process has, one that the filter or the ceiling keeps out of the table, and one shown only because an earlier scan saw it are each explained instead of selected.
- **Identity, not position.** The current match is held by item ID, owned by one process-instance key, never by PID, row index or name. Sorting and refreshes recompute its position. When it stops being shown — its process ended, the filter hid it, or the ceiling dropped it — the status says so and the search moves to no other process. A reused PID is a different process instance with a different item ID. It is selected only by a new explicit search (`Go to PID` again, a new query, or `Next`/`Previous`, which continue from the place the old match held), never by a refresh. The status says when a different process now has the PID.
- **The table selects and reveals the match.** Every explicit search that sets a current match — a new query with a match, `Next match`, `Previous match`, a successful `Go to PID` — promotes it to the table's semantic selection by item ID (PX-011-G01: the table's `value` holds the `ItemId`). The generic client selects that row and scrolls it into view. Going to the match already selected promotes it again and reveals it again.
- **What moves the selection, and what does not.**
  - A search that selects nothing (no match, an empty query, a PID that is not shown, a malformed PID) leaves the promotion, and so the native selection, exactly as it was.
  - A refresh or a sort that moves the row keeps the promotion on its item ID.
  - When the row leaves the table — its process ended, the filter hid it, or the row limit dropped it — the SDK's settlement clears the promotion in the same commit that removes the row; srtop never withdraws it separately. A row shown again later is not re-promoted automatically: only an explicit search selects it again.
  - A reused PID is a different item ID and never inherits the promotion.
  - A row the user clicks stays a local selection. A later commit that promotes nothing keeps it, and `Next`/`Previous` continue from the server's current match, not from the clicked row.
- **Bounds.** The search status is at most 1024 bytes, the PID field keeps at most 32 bytes, and the search controls and the table's promoted `value` are charged a fixed 4096-byte reserve (`SEARCH_RESERVE_BYTES`) against the catch-up snapshot, so a long search status never shrinks the row budget. While a promotion is held, every plan that can remove rows leaves one operation and its bytes free for the `CLEAR_PROPERTY` settlement may add, so it still fits the §26 operation and frame bounds. A promotion counts as the two operations it records.
- **Fixture.** `--fake-repeated-names` publishes 60 constant processes, three of them named exactly `worker` at rows 10, 30 and 50, for the native search test.

## Filtering by user and PID set

A row between the filter and the search holds the user filter (PX-012): `Only my processes` and `All visible users` buttons, a `User` `TextInput` (a UID or an account name), a `PID set` `TextInput` and a status line. Every control is a standard widget sending a standard `ACTIVATE` or `TEXT_EDIT`; collection, owner resolution and filtering run on the server.

- **The UID is the owner.** On Linux a process's owner is the effective UID on its `/proc/<pid>/status` `Uid:` line, read through the same pinned `/proc/<pid>` directory handle as its `stat` and `statm` (PX-005-G01), so a PID recycled between the reads cannot lend its owner to the instance `stat` identified. The directory's own owner is not used, because the kernel reports a non-dumpable process's directory as root's. An owner that cannot be read is published as unread, never as UID 0 or `root`: a specific user filter hides it and the status counts it (`1 process with an unreadable owner hidden`).
- **Choices.** `All visible users` (the default, and what an empty user field means) shows every process the daemon's own OS account can enumerate. It is not a promise to bypass host permissions: what `hidepid` or a PID namespace hides is not in the collection to begin with. `Only my processes` shows the processes owned by the daemon's effective UID. Digits in the user field select exactly that UID, whether or not an account names it (`UID 4242 (no account name)`); digits past `u32` are refused as not a UID. Any other text is an account name, matched exactly against the names the server has resolved for the owners in the collection; several UIDs that share a name are all kept and listed (`name "ops", UIDs 1001, 1002 (2 accounts share this name)`). A button empties the user field.
- **Bounded, non-blocking name lookup.** Names come from the system user database (`getpwuid_r(3)` through `srui-unix-security`, so NSS sources such as LDAP or SSSD answer too) on one worker thread owned by a bounded cache: at most 1024 UIDs, least recently used evicted, at most 64 questions queued, a 2-second timeout after which a name is published as `name lookup timed out`, and a fresh question after 10 minutes. Publication never waits for the worker: a name that is not known yet is `name pending`, and a name filter keeps no row whose owner's name is still unresolved and says how many it is waiting for. A late answer is used by the next publication, at the latest on the next refresh tick. A hung lookup holds only that one worker thread.
- **PID set.** PIDs separated by commas or spaces, at most 64 distinct PIDs from at most 512 bytes of text; duplicates collapse, further PIDs are counted and ignored (`bounded to 64 PIDs, N more ignored`), entries that are not PIDs are named (`1 entry is not a PID: "abc"`) and a set of nothing but such entries shows nothing rather than everything. PIDs no visible process has are listed (`no visible process has PIDs 9998, 9999`). Text past 512 bytes is dropped together with any entry the bound cuts through, so a cut PID is never read as a shorter one; such a set keeps only its whole PIDs and says so. A user field longer than 64 bytes names no UID or account, and keeps nothing until it is shortened. A PID set selects by number on every scan, so a reused PID's new process matches it; identity is still the row's item ID.
- **How the filters combine.** A row is shown when the user filter, the PID set and the text filter all keep it, and then only within the published-row ceiling. The user-filter status counts what all of them keep (`2 of 6 processes match`); an empty result states what each active filter would keep on its own (`no process of 6 matches every filter: the user filter alone keeps 2, the PID set alone keeps 2, the text filter alone keeps 1`). While the user filter or the PID set is active, the text filter's own counts say they are counted after them. Search still counts matches over the whole collection and reports the ones these filters hide as not shown; a filter that hides the current match lets the SDK's settlement clear the table's promoted selection in the same commit that removes the row.
- **Sorting.** A sort applies every filter again and publishes the result through the same path as a filter edit, so a name resolved since the last publication takes effect with the sort, its statuses in the same commit.
- **Identity.** Changing any of these filters never creates a process identity: every row keeps its item ID whether hidden or shown, and clearing the filters restores the original rows and IDs exactly.
- **Bounds.** The user field keeps at most 64 bytes, a resolved name at most 64 bytes, the status at most 1024 bytes, and the six controls are charged a fixed 4096-byte reserve (`OWNER_RESERVE_BYTES`) against the catch-up snapshot.
- **Fixtures.** `--fake-source` gives PID 4101 to its own account (UID 1000, `alice`), PID 4102 to UID 1001 (`bob`), and the helper an unreadable owner. A source that states no accounts — a `/proc`-shaped tree that is not this host's, or a fixture — explains `Only my processes` and name filters instead of guessing; a UID still works.

## Inspecting a process

Four status lines under the table describe the selected process (PX-013): what is selected and whether its details are loaded; its name, PID and owner; its state, parent PID and start time; and its current CPU share and resident memory. They are standard `Text`s in a `Column`; selecting a row sends the standard `SELECTION_CHANGED`, and everything else happens on the server.

- **The selection is untrusted.** The server reads only the event's `ItemId` and resolves it against the rows it currently publishes. It never turns an item into a PID: the process instance is the published row's own identity (PID plus creation token). An item it does not publish — unknown, already gone, hidden by a filter, or not an item at all — is refused with a defined state (`Selected process: none · item 77 is not a row this server shows; nothing was read`), and nothing is read for it.
- **Highlight local, details asynchronous.** The native highlight is the client's own (§22.5); the server never selects a row because a user clicked one. Name, PID, owner, CPU and resident memory come from the server's own row at once; state, parent and start time are read by one bounded worker and arrive later (`· loading details` until then). Every read is tagged with the target's process identity and a selection generation, and a result for anything but the current target is dropped, so a slow read of an earlier selection never overwrites a later one. The worker runs one read at a time and keeps at most one waiting: a newer selection replaces the waiting one.
- **One current target.** A click and a search promotion (PX-011) both select: whichever the server applies last wins, and a click after a promotion replaces it, exactly as the native highlight does. A filter that hides the target, and so clears its promotion, shows that same process as `not shown (filtered out or beyond the row limit)`, never another one; it is described again when shown again.
- **Identity, not position.** A sort or refresh that moves the row keeps the inspector on it. A process that ends says `this process has ended; select another row`, with no details and no metrics. It says so only on evidence of an exit: the detail reader found the instance gone, or a scan entitled to account for it no longer lists it. A row that an incomplete scan kept but the published-row ceiling then dropped unconfirmed is `not confirmed by the latest scan; not shown`, never ended. Every field shown is the latest scan's: an owner that changes or becomes unreadable is published and never reverts. A PID reused by a new process is a new row with a new item ID, which the inspector does not adopt; the detail reader also refuses a record whose start time is not the selected instance's, so the newcomer's state, parent and start time are never shown.
- **Linux details.** State (`/proc/<pid>/stat` field 3, named as `proc_pid_stat(5)` documents, an undocumented code shown as unrecognized) and parent PID (field 4) are read on demand through the record's pinned `/proc/<pid>` directory, and accepted only if the line's start time (field 22) equals the selected key's creation token. The start time is derived from that same token: the root `stat`'s `btime` plus the token's clock ticks at the mount's own `AT_CLKTCK`, shown in UTC to the second (`btime` is whole seconds). It is re-read on every sample that confirms the row.
- **Unavailable is not zero.** Each state is distinct: no selection, loading, permission denied (the record, or the owner), details unavailable, not provided by this source, ended, and not shown. A parent PID 0 is the kernel's `none (PID 0: started by the kernel)`, never `root`; an unread boot time shows the start as seconds after boot.
- **Bounds.** Each line is at most 1024 bytes (cut and marked), and the five nodes are charged a fixed 6144-byte reserve (`INSPECTOR_RESERVE_BYTES`) against the catch-up snapshot.
- **Shared by the session.** Like the filters and the sort, the inspector is the session's: every client attached to the same srtop sees the last selection any of them made. The generic client sends no event when the user clears the native selection, so the inspector keeps describing the last selected process until another is selected.
- **Fixtures.** `--fake-source` states details for PID 4101 (sleeping, parent 1) and PID 4102 (running, parent 4101), and denies the helper's. `--fake-sequence` states constant details for its four processes. The other fixtures provide none, which the inspector says.

### Command line and executable

Under the four lines, one standard read-only `RichText` shows the selected process's command line, executable and working directory (PX-014). The generic client renders it as a non-editable, selectable native text view: select and copy it like any text; nothing in it is a link, a button or a file.

- **Read on selection, for that process only.** The arguments, executable and working directory are read by the inspector's detail worker with the state and parent, never by a scan, and only for the current target. On Linux, `cmdline` is read and `exe` and `cwd` are read with `readlink` through the record's pinned `/proc/<pid>` directory. The record's `stat` must carry the selected key's start time before and after those reads, so a reused PID's arguments are never shown. They are bound to the target's identity and selection generation like every inspector line, held only while it is the target, and never logged or saved.
- **An argument vector, not a shell command.** Each argument is shown on its own line with its index and exact byte length, for example `argv[1] · 13 bytes · --role=worker`. There is no joined or quoted "shell" form, and nothing shown is ever run.
- **Inert text.** Control characters (a newline shows as `\n`, ESC as `\x1b`), invisible format, line-separator and bidirectional-override characters (`\u{202e}`) and bytes that are not UTF-8 (`\xff`) are shown as visible escapes, and a backslash is doubled, so an argument cannot draw an escape it does not contain. Only the display is changed: the bytes read are kept exactly and never written back into the row, the filter or any identity.
- **Bounds.** The first 256 arguments within 16 KiB are kept; the rest of the area is counted, up to 2 MiB (`at least` beyond that), and dropped. Each argument shows at most 1024 bytes and each path 1024, and the whole view is at most 8192 bytes. Every cut says what it left out, in raw bytes (`argv[1] · 5000 bytes, first 1024 shown · …`, `… 245 more arguments not shown (73500 bytes)`). The node is charged a fixed 10240-byte reserve (`COMMAND_RESERVE_BYTES`) against the catch-up snapshot.
- **Distinct states.** A process started with no arguments, a zombie, a kernel thread, a denied `cmdline`, and an unavailable one each say so. The executable and working directory fail on their own: another account's process normally shows its arguments (`cmdline` is world-readable) and `permission denied` for both paths, which need ptrace read access. The paths are the server's, labelled `on the server`, and are never resolved or opened on this computer.
- **What the kernel reports.** A process can rewrite its own argument area (`setproctitle`); the view shows what the area holds now and flags an area without a final NUL as rewritten. The executable path can end in ` (deleted)` when the file was replaced; that is the kernel's text, shown as is.
- **Fixtures.** `--fake-source`'s PID 4101 has arguments with quotes, a newline, an escape sequence, shell metacharacters, a bidirectional override and a fixture secret (`--password=hunter2-SECRET`); PID 4102 shows its arguments and denies its paths.

## Choosing columns

A row of standard `Button`s between the sort controls and the table chooses the visible columns on the server (PX-068). For each column there are three buttons: `Hide <column> column` (or `Show <column> column` while it is hidden), `Move <column> column left` and `Move <column> column right`. A final `Restore default columns` brings back PID, Name, Resident and CPU in catalogue order. A shown column returns after the visible ones, which keep the order already chosen. A button that could change nothing is disabled, so event validation refuses the click: the first column cannot move left, the last cannot move right, the only visible column cannot be hidden, and the defaults cannot be restored while they are already shown.

A layout change is presentation, not identity. The server sets the table's `columns` and updates every row's cells in place, under its own item ID, with `MODEL_UPDATE`. When the change fits one transaction it commits as one. It never deletes, moves or recreates a row, the table or its model, so the native selection stays on its process. Every row keeps all of its catalogued cells and typed sort values server-side. The active sort therefore keeps ordering the rows by its column even while that column is hidden, and later samples are published in the chosen layout. Only the existing cheap columns are offered, and the layout is not saved between sessions.

## Pausing, the interval and manual refresh

A row under the system summary holds the sampling controls (PX-015): **Pause view**/**Resume view**, **Refresh now**, a **Refresh interval (ms)** field with **Apply interval**, and a sampling status line. All are standard `Button`s, a `TextInput` and a `Text`; every decision is the server's.

- **Pause view freezes this app's published view, not the connection.** From the pause on, the refresh loop takes no sample, and no row, cell or summary figure changes: they stay exactly what the session revision current at the pause held. Core transaction application and the transport are untouched, so every control keeps committing its own transactions, and a client attaching meanwhile is brought up on the frozen view.
- **Collection stops while paused.** srtop is a read-only observer, and a sample nobody is shown would be host work for nothing. The status says so: `Paused at 2026-11-08 12:00:05 UTC (server clock) · rows as of revision 7 · collection stopped: table and summary frozen; filters, sort, columns, search and the inspector act on the frozen rows · Resume view publishes a current sample, then every 1000 ms`. The data-freshness line starts with `Paused, not live · `, and Refresh now is disabled.
- **Controls work on the frozen rows.** The filter, the user filter and PID set, the sort buttons, the column chooser and search (with Go to PID) re-project the frozen collection and update their own status; nothing new is sampled for them. A filter cleared while paused brings back exactly the frozen rows.
- **The inspector reads nothing live while paused.** A row selected while paused is described from its frozen row, and its state, parent, start time and command line say `not read while the view is paused; Resume view reads them`. A read already running when the view was paused is dropped when it returns; details read before the pause stay shown. Nothing live is ever shown beside frozen rows.
- **Resume view publishes one current view.** It says `Resuming · sampling now`, takes one sample at once and publishes it through the ordinary diff: rows that survived keep their item IDs, ended processes are deleted, new ones inserted, all in the same bounded transactions as any refresh. No missed sample is replayed, because none was taken. A scan that was running when the view was paused or resumed is discarded.
- **The interval is checked on the server.** Apply interval reads the text the server kept for the field: whole milliseconds from 50 to 300000, digits only (`--refresh-interval-ms` uses the same validator). Anything else is refused with its reason on the sampling status, for example `interval "fast" refused: not a whole number of milliseconds; enter 50 to 300000 ms; keeping 1000 ms`, and the previous interval stays; the refusal is shown until the field is edited again. A new interval restarts the refresh loop's one ticker, so the next sample is one new interval later: no burst, and never two timers.
- **Refresh now takes one sample** through the same path as a tick, and the next tick follows one interval later. Presses the loop has not taken yet coalesce into that one sample.
- **One timer, owned by the loop.** No handler starts a timer or a thread; each records a request on the view and wakes the loop. The ticker, the wake and the loop end together on shutdown (SIGINT or SIGTERM) whatever the sampling state. A client disconnecting ends only its connection: the pause and the interval belong to the session, as the filters do, so every client of one srtop sees them.
- **Bounds.** The status is at most 512 bytes and the interval field keeps at most 32; the six nodes are charged a fixed 2048-byte reserve (`SAMPLING_RESERVE_BYTES`) against the catch-up snapshot.
- **No process-changing action exists.** When one is added, it must refuse every target while `ProcessView::frozen()` is `Some`: a paused view shows historical rows, not the host's current processes.

| ⇧⌘F | `primary+shift+f` | Follow selected process | the checkbox's click: turns follow on or off (PX-017) |
| ⌘T | `primary+t` | Show process tree | the checkbox's click: switches between the table and the tree (PX-018) |
| ⌘L | `primary+l` | Processes (the table), or Process tree | focuses whichever is shown; the shortcut moves with it |
| ⌘I | `primary+i` | Command line and executable | focuses the inspector's selectable command line |

- **A button's shortcut is its click.** The client sends the same `ACTIVATE` through the same target and action. A disabled button's shortcut therefore does nothing: Refresh now while paused, Next match with no match, a reset with nothing to reset. Event validation refuses a forged event to a disabled control.
- **A field's, the table's and the command line's shortcut only moves focus.** It sends nothing. Focus, table movement (arrows, Page Up/Down, Home/End), horizontal scrolling and text selection are the client's own. A selection made with the arrow keys is reported like a click, and the inspector follows it.
- **Typing is never a shortcut.** Every shortcut carries Command, so a letter typed into a field is text. While an input method is composing, no shortcut fires at all.
- **Reserved combinations stay the system's.** None of srtop's shortcuts is in the client's reserved table, which includes ⌘C, ⌘V, ⌘X, ⌘A, ⌘Z, ⌘Q, ⌘W, ⌘H and ⌘M. Copy, paste and select all keep working in every field and in the command line.
- **Sort shortcuts follow the sort buttons, not the column positions.** The sort buttons keep their order when the column chooser moves a column, so ⌘1 always sorts by PID. Per-column shortcuts are offered because Tab reaches buttons only when macOS Keyboard navigation (Full Keyboard Access) is on, which it is not by default.
- **Reset.** Focusing a field with its shortcut, or with Tab, selects its whole text, so ⌥⌘F then Delete clears the filter, and ⌘F then Delete clears the search. ⌥⌘U shows every user again, and ⌥⌘R restores the default columns.
- **Without a mouse:** ⌘F, type a name, ⌘G until the match is the one, ⌘L and the arrow keys to move the selection, ⌘I to read and copy the command line, ⌥⌘F and type a filter, then ⌥⌘F and Delete to reset.

## Following a process

A row between the column chooser and the table holds a standard **Follow selected process** checkbox (⇧⌘F) and a status line (PX-017). Follow is a server-side setting; the checkbox shows the value the server holds.

- **Selection and follow are separate.** With follow off, the client keeps a selected row on its process, under its item ID, when a sample or a sort moves it (§22.5). It never scrolls for it, so the table stays wherever you scrolled it, even if the selected process moves out of view. No sample ever selects or scrolls anything.
- **Turning follow on** follows the process the inspector describes, which is your own selection, and scrolls it into view at once. It does not select anything: the server names the process in the table's standard `keep_visible` hint (PX-017-G01), which only scrolls. The status says `Following PID 6010 · tracked · row 12 of 60 · …`. With nothing selected, or a selected process that is hidden or has ended, the server refuses with the reason (`Follow: off · nothing is selected; select a row, then turn follow on`) and the checkbox goes back to off.
- **While follow is on**, whenever a sample, a sort or a filter moves the followed process to another row, the client scrolls the least distance that shows it, because the hinted item moved. The server sends nothing for that, and never sets the selection: your selection stays on its process under its item ID, as with follow off. No row is added for it.
- **Scrolling yourself** is local. It never changes the selection and never turns follow off. The table stays where you put it until the followed process changes row; then follow brings it back into view. There is one exception. When follow retargets (a click, the arrow keys or a search match), the new hint reaches the client one round trip later and reveals the row it names, so a pan made within that round trip is undone once. To look elsewhere for longer, turn follow off.
- **Sticky, until you change it.** Selecting another row, with a click, the arrow keys or a search match, follows that row instead: the hint moves to it. Follow never selects a row for you, so fast arrow keys and clicks always end on your last press, even when a sample moves rows during the burst. During a fast burst each retarget's hint reaches the client one round trip late and scrolls to the row it names. On a short table your newest selection can be out of view by up to about (round trip ÷ key repeat) rows. After the burst it stays out of view until the last hint lands, one round trip later, which reveals it. The selection itself never changes.
- **One followed process.** While follow is on, the table's semantic selection names the followed process or nothing: turning follow on or selecting another row withdraws a search's earlier promotion of a different process (your own later selection stays). A client that attaches later restores no selected row, or the followed one when a search selected it, and scrolls to the followed process.
- **Deselecting stops follow** (PX-017-G02). When you leave the table with nothing selected (a click in empty space, or Command-click on the selected row), the client reports it as a `SELECTION_CHANGED` with no item. Follow, if on, stops with `Follow stopped: the selection was cleared; select a row and turn follow on again`, and its hint is cleared; the inspector says `Selected process: none · the selection was cleared; select a row to inspect it`. Turning follow on afterwards is refused (`nothing is selected`) rather than following the process you deselected. A collapse in a tree view that hides the selected row is not a deselection: the client sends only `EXPANSION_CHANGED`, never this `SELECTION_CHANGED`.
- **Follow stops by itself, and says why**, when the followed process ends (`Follow stopped: PID 6010 · tracked has ended · a new process that reuses its PID is not followed; …`) or is no longer shown because a filter hid it or the row limit left it out. The checkbox turns off and the hint is cleared. Follow never moves to another row by itself. A new process that reuses the PID is a different item, and it is never followed, selected or scrolled to.
- **Both views.** Follow carries over between the table and the process tree (PX-018): the switch moves the `keep_visible` hint to the shown collection under the same item ID, so the followed process stays followed and is revealed in the other view. In the tree, the hint never expands a collapsed parent and expanding one never scrolls, so the status says when the followed process is hidden under a parent you collapsed: `Following PID 310 · cc · hidden under collapsed PID 300 · make: expand it to see the followed process; …`.
- **Shared.** Like the filters, follow belongs to the session, so every client of one srtop sees the same setting and the same followed process.
- **Bounds.** The status is at most 512 bytes; the three nodes and the table's hint are charged a fixed 2048-byte reserve (`FOLLOW_RESERVE_BYTES`) against the catch-up snapshot.

`--fake-follow` is the deterministic fixture for this: 60 processes, where only `tracked` (PID 6010) changes CPU rank, one step per sample, and at the sixth sample it has ended and a new process reuses its PID.

## Process tree

A **Show process tree** checkbox (⌘T) and a view status sit in a row between the follow controls and the list (PX-018). The tree shows the same processes, under the same item IDs, arranged under their parents. The server builds the hierarchy; the client draws one native outline view from one model and never creates a node per row.

- **Parents are never guessed.** A process is shown under another only when the same scan holds exactly one record with its parent PID, both start times were read, the parent started no later than the child, and the filters keep the parent. On Linux the parent PID and the start time come from the same `/proc/<pid>/stat` read as the record's identity (fields 4 and 22). Everything else is a root, and its **Parent** column says why: `none: started by the kernel`, `root: parent 9999 not in this scan`, `root: parent 21 unreadable`, `root: parent 22 beyond the record limit`, `root: parent 20 not seen (incomplete scan)`, `root: parent 700 started later (PID reused)`, `root: parent 10 unverified (start time unread)`, `root: parent unread (permission denied)`, `root: parent 16 ambiguous`, `root: parent 300 hidden by the filters`, `root: row kept from an earlier scan` or `root: parent 40 kept from an earlier scan`. An attached row's Parent column is its parent's PID. When a parent exits, the kernel reparents its children to init or a subreaper, and the next sample shows them there.
- **Malformed lineage.** Parents that lead back to themselves (possible only when start times tie, or from a source that misreports) are cut at the cycle's member that orders first by process identity, whatever the sort: `root: cycle through parent 801 broken here`. A chain deeper than the §26 `max_model_tree_depth` (256 levels, the client's default) is cut where the next level would not fit: that child starts a new root right after the subtree it was cut from, `root: parent 1255 at the depth limit`.
- **Sorting** orders the roots and each parent's children by the active sort and never flattens a level.
- **Expand and collapse** are the client's own, with the disclosure triangle: nothing is requested and nothing is redrawn by the server. Every item starts expanded when the tree is shown. The client reports each change (`EXPANSION_CHANGED`), and the server only records it, for that client. A collapse that hides the selected process also clears the selection on that client, so the inspector clears too when it describes that client's selection; so does a sample, or a filter, that moves the selected process under a parent you collapsed (a sort only reorders siblings, and a switch shows a tree that starts expanded). A search or Go to PID that reveals a match under collapsed parents expands them on the client and on the server at once. A collapsed process stays collapsed while it is shown, even with no children for a while, and hides the children it gains again, as the client does. Left and right arrow keys do not expand or collapse: the generic client's outline has no keyboard disclosure yet.
- **The row limit** keeps the leading rows of the tree's preorder, under the same frame budget and 100,000-row limit as the table, each row also charged its Parent cell and two item properties. Every shown row's parents come before it, so the limit never orphans a shown process; it can only cut a subtree short. A tree row costs more bytes than a table row, so at the byte ceiling the tree can show fewer rows than the table: the status line and the filter status count the rows left out (`· 1 row beyond the publishable size limit`, `Filter: none · showing 19379 of 19380 rows; 1 beyond the publishable size limit`) in the commit that publishes them — the switch itself, paused or not, the switch back, a sort, a filter — not only at the next sample.
- **Selection** carries over by item ID in both directions: the server promotes the process the inspector describes in the view it switches to. A selection reported by the hidden view is ignored. Search selects and scrolls to its match in the tree, expanding the collapsed parents above it. Filters, the user filter, the PID set, pause, refresh, the inspector, the column chooser and every shortcut work the same in both views; a match or a row number in a status counts the tree in preorder, collapsed rows included.
- **One collection at a time.** Switching empties the hidden view's model in the same transaction that fills the other, so a client that attaches gets one collection, and the switch itself is one commit. The view switch, the tree node and its model are charged a fixed 4096-byte reserve (`VIEW_RESERVE_BYTES`) against the catch-up snapshot. Leaving the tree forgets what was collapsed.
- **Shared view, own disclosure.** Like follow and the filters, the view belongs to the session, so every client of one srtop shows the same view. Expand and collapse do not: each client discloses on its own, and the server keeps what each client instance reported apart (at most 64 clients' collapsed items at once; the least recently reporting one beyond that is treated as all expanded). A client that attaches later starts with every item expanded and inherits no other client's collapsed parents. The inspector and follow describe the selection of the client that made it, by clicking or by a search or Go to PID: only that client's collapsed parents hide it, clear the inspector or make follow say `hidden under collapsed`. Another client's collapse never rejects your selection.
- **Known limit.** srtop is not told when a client detaches or which client attaches, so what a departed client had collapsed is kept until those rows leave the tree, the view leaves the tree, or the client is evicted. That never affects another client's selection, but the follow status is one line for every client: while the client that made the selection keeps the followed process collapsed, every client reads `hidden under collapsed`, until someone selects a row.

`--fake-tree` is the deterministic fixture: twelve processes with an orphan, a parent PID reused by a newer process, a two-process cycle and a five-level chain, and at the second sample `make` ends and its two children are reparented to `init`.

## Refresh

Every collecting mode polls its source on a fixed schedule: `--refresh-interval-ms MS` configures it between 50 ms and 300 s, the default is one second, and the sampling controls can change it, pause it or take one sample at once (see above). The first snapshot creates the shell; every later tick publishes only the difference — inserts, deletes, the values of rows whose displayed cells changed, and the status text when it changed — so a row that did not change keeps its item identity and its native control. Deletions are emitted before insertions, so an insertion index is the row's final index, and a refresh larger than a §26 bound commits as consecutive atomic transactions rather than failing whole.

Three §26 bounds split a refresh, and they are independent. A transaction carries at most the store's operation bound, each model operation at most its items bound, and each transaction at most one 16 MiB frame of encoded payload — the frame ceiling is `DEFAULT_MAX_FRAME_SIZE` less a fixed allowance for the envelope the operations travel in, never a number of this app's choosing. The size bound is the one operation counting alone misses: a host that grows to tens of thousands of long names needs only four `MODEL_INSERT` operations, far inside the operation bound, and still carries more than one frame. Committing that as a single transaction would advance the server's revision and only then have the codec refuse the frame, detaching the client from a server that had already moved on — and the next identical tick would diff clean and republish nothing. Sizes are charged as upper bounds the encoder cannot exceed: every string counts its encoded UTF-8 bytes, not its characters, so a name of 128 four-byte characters is charged 512 bytes.

The collection itself is never larger than a client can be *sent*. Splitting the live mutations is not enough on its own: a client that attaches, or resyncs after a journal gap, is brought up by one catch-up snapshot transaction that carries every cached range of the model at once and is bounded only by its operation count, so a model that encodes past one frame is a collection nobody can attach to, however carefully each refresh was split. The rows that do not fit are therefore not published. The ceiling is the same derived number and the same upper-bound accounting the refresh planner uses, less a fixed allowance for the shell, a second fixed allowance for the status and a third, 8 KiB, for the system summary (every summary node with every line at its 512-byte bound, asserted on the protocol's own encoder), and it applies on the start path exactly as on every later tick — the start path is precisely the attach path this bound exists for. The rows kept are the leading ones of the published order — the source's own (`ProcFsSource` sorts by ascending PID) until a sort is chosen, then the active sort — so the published window is a deterministic function of the snapshot and that order alone: an unchanged host keeps exactly the rows it kept last tick, no row churns in and out, and an identical tick still publishes nothing. The status says what happened in counts and fixed wording, in its own clause (`· 6683 rows beyond the publishable size limit`) — those rows were read perfectly well, so they are never called unreadable, and they are not the entries the collector's own record bound never read (`beyond the record limit`) either. The runtime-side limitation this worked around — `sessiond` exported a catch-up snapshot as one unchunked transaction and checked only its operation count — was core protocol and runtime work affecting every SRUI application, and ticket PX-004-G01 has since given the runtime multi-envelope snapshot delivery (see `protocol/README.md`). This app's published-row ceiling is deliberately unchanged by that ticket; lifting it is a separate app decision.

The status is charged against that frame at a fixed reserve, never at its own current length. It travels in the same catch-up snapshot as the rows, so charging the text of the moment would let the longest status this app publishes — a failed scan's, which carries the failure, the retained-row clause and every degradation the scan reports — shrink the row budget and delete rows that same scan had just said it could not account for. The reserve covers every clause the status builder can emit with every count at its widest, plus the longest source label the status carries: a label is source-owned text of no fixed length, so it is cut at 256 encoded bytes and marked with an ellipsis rather than charged unbounded. A refresh that confirmed nothing and may delete nothing goes further and plans no row mutation at all — it publishes its status over the last-known rows and touches the collection not at all.

A tick whose snapshot holds nothing a client can see opens no transaction at all. Nothing that moves on its own is published: the issue counts and the source's internal state stay off the wire, so an unchanging source produces no traffic. The sample time is the one exception, because the freshness line shows it to the second (PX-007): a live host therefore publishes that one scalar property on most ticks, while a source whose figures and sample time are constants, like `--fake-source`, publishes nothing once synchronized. CPU usage is what a client sees, so a process whose published share changed between ticks updates its row in place on that tick (PX-006); idle processes that stay at `0.0%` publish nothing, and the counter baselines themselves never reach the wire. Sampling runs off the async runtime, since reading a host's process filesystem blocks.

A scan that fell short is not a collection that emptied, but it is still entitled to report the exits it did observe. A row is deleted only when the scan accounted for its absence: a scan that named the records it could not read has proven that every *other* absent process ended, so those rows go while the named record's row stays exactly where it is and keeps its item ID. Those identities are the scan's own knowledge — every record's PID is recorded as the scan leaves it out, in ledgers bounded by the scan rather than by the host — and never a reading of the bounded `EnumerationIssue` list, which only explains a degraded scan to a person and stops at 32 entries. A host with hundreds of unreadable records therefore still names every one of them and still deletes the rows of processes that really ended. The same holds for a host with more processes than one scan publishes: reaching the record bound stops the scan from reading each further record's detail, not from listing it, and a listing entry *is* a PID, so those entries are named too. Without that, every scan of a large host would be entitled to delete nothing and the collection would grow from the record bound until the model's cached-item limit refused the next refresh. That scoping is not a detail: one permanently denied `/proc/<pid>/stat` makes every scan on a shared host incomplete, and retaining every absence would then accumulate a stale row per exit until the model's cached-item limit refuses the next refresh.

Retention stays whole only where the uncertainty is whole because the identities themselves were never observed: the process list could not be listed or one of its entries could not be examined, the scan left out more records than the ledger naming them may hold, or the snapshot's identities were rejected. Then the last-known rows stay exactly where they are, keep their item IDs, and the status says what happened and how many rows are unconfirmed (`· process list unavailable: permission denied · 3 rows retained from an earlier scan`). A record an otherwise good scan could not read is also not a deletion; it keeps the place it already held, next to the same rows. A record that merely vanished between listing and reading is not uncertain at all and is deleted like any other exit. When the scan recovers, the status returns to the source's own label and no row moves. A host that stays broken republishes nothing, because the explanation has not changed either. The status is built from counts and fixed wording only: no process's own text ever reaches it.

What is retained is bounded by construction, in every case, including the ones no scan can enumerate. A host with more readable entries than one scan's ledger may name overflows it, so *every* tick reports itself unenumerable and keeps every absent row; short rows fit a frame in their tens of thousands, so the snapshot ceiling never stops that, and ordinary churn would grow the collection past the model's own §26 cached-item limit until inserts were refused and no refresh could converge again. No refresh therefore publishes more than 100,000 rows — the model's own item bound, lowered to whatever the session's store will cache — and the unconfirmed rows beyond it are evicted from the trailing end of the published order, which is where a row drifts for as long as it goes unconfirmed (under an active sort a retained row keeps the place its last published values give it, so the evicted rows are the trailing unconfirmed ones of that order). The eviction is a function of the published order alone, never of iteration order or of a clock, so the same ticks always publish the same rows; a row the scan confirmed is never evicted, and the status names the eviction in its own count-based clause (`· 1 unconfirmed row dropped to stay inside the published row limit`), which is not a process that ended, not a record that could not be read, not an entry beyond the collector's record bound, and not a row of this snapshot that would not fit.

Row identities are session-local and are never reused, and the allocator forgets an identity once its row leaves the collection, so a long-running poll does not accumulate one entry per process that ever ran.

The source's global identity — host, boot and PID namespace — is remembered across scans, because one unreadable identity file would otherwise re-key every record at once while skipping no PID, so retention would have nothing to keep and the whole table would be deleted and reinserted — twice, once on the failure and once on the recovery. A scan that could not read `sys/kernel/hostname`, `sys/kernel/random/boot_id` or the namespace link is keyed with the last value that was observed, so neither the degraded tick nor the recovering one deletes, inserts or moves a row, and every row keeps its item ID and its native control. Nothing remembered reaches the wire: the degradation is still published, from the scan's own issues and in the same count-based wording, on exactly the tick that saw it (`· incomplete scan · 3 processes listed · host identity incomplete`). A component that comes back as a *different* value is not a degradation but a different source: its records are different process instances and visibly take new row identities, and that newly observed value is what the next degraded scan is anchored to. A component never observed at all is never invented.

`--fake-sequence` runs a deterministic cyclic script — three processes, the same three a second later, then one ended, one renamed and one new, then a failed scan, then recovery — for tests that need every refresh case without a host. It is a fixture: it reads no process, no clock and no file, and says so in the status. Every step states the same system figures — with swap configured, where the fake snapshot has none — and its own sample time, one second after the step before: the repeated step publishes only that time, and the failed step keeps the previous step's figures and time under a collector error.

`--smoke-fixture` enables a local SIGUSR1 trigger for one deterministic title value. It updates the existing Surface label and heading through a normal atomic transaction. This is a test fixture, not a remote process action. The native test verifies retained window and table handles before and after that update.
