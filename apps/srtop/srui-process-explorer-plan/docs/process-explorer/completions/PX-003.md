## Bounded behavior

`--live-source` injects `procfs::ProcFsSource` at startup, which performs exactly one read-only scan of a `/proc`-shaped tree. The existing `--fake-source` and empty-shell paths are unchanged. No polling, no process controls, no signal delivery, no new transport, and no change to any other example.

### Collector choice (K1, S1)

The pinned collector in `examples/process-monitor` is `sysinfo` 0.39.6 (S1). Its `Process::start_time` returns **whole seconds since the UNIX epoch**, which this ticket explicitly forbids as the sole discriminator, and its pinned API exposes no boot identity, no PID-namespace identity and no higher-resolution creation token. `ProcFsSource` therefore reads `/proc` directly through `std` only (K1), which yields the boot-tick creation token, `boot_id`, the PID-namespace inode and the process list from **one** consistent source instead of stitching two enumerations together. No dependency was added: `apps/srtop/Cargo.toml` and `Cargo.lock` are untouched by this ticket.

### Instance identity

`source::ProcessKey` carries source identity, host identity, boot identity, PID-namespace identity, the PID, and a mandatory `CreationToken`. For Linux the token is `CreationToken::LinuxBootTicks`, taken from `/proc/<pid>/stat` field 22 (start time in kernel clock ticks since boot; `getconf CLK_TCK` is 100 on the test host, i.e. 10 ms resolution, never rounded seconds). Host, boot and namespace identity are `Observed`, so an unreadable component is an explicit missing value rather than a silent equality. The creation token has no missing variant on purpose: a source that cannot observe one must report an enumeration issue instead of publishing an unidentifiable row.

`projection::SessionItemIds` maps the whole `ProcessKey` to an opaque `ItemId`. IDs stay independent of row position and display name, are never equal to the PID, and are never removed or recycled within a session, so a reused PID with a different creation token always receives a new ID.

### Completeness and inaccessible records

`source::Completeness` is `Complete` or `Incomplete { skipped, issues }`, with issues bounded at `MAX_RECORDED_ISSUES = 32` while `skipped` still counts every record. An empty `Complete` snapshot is an authoritative "nothing is visible"; an `Incomplete` snapshot never is, whatever its record count. A denied, unparsable or PID-mismatched record is skipped with its own `EnumerationIssue` and reason and never fails the scan.

A record that *vanished* is not in that set. A process that exits between the directory listing and the read was never inaccessible — it no longer exists at sample time — so it is counted in `ProcessSnapshot::vanished` and does not degrade `Completeness`; `a_process_that_exits_during_the_scan_is_not_a_degradation` asserts exactly that. Folding ordinary churn into `skipped` would leave a busy host permanently labelled "incomplete scan" and make a genuinely denied record indistinguishable from a process that simply ended. Records beyond the scan's own bound are likewise counted apart, in `ProcessSnapshot::capped`, since they were never read rather than unreadable. Only a root that cannot be listed produces an empty result, and that result is `Incomplete`.

PX-002's `ProcessSource::status_text` contract is honored unchanged: the source states its own label, and only `ProcFsSource::live` returns `"Read-only · Live process snapshot"`. Any other root states what it read and from where without claiming liveness or synthesis — a path cannot tell a fixture tree from a bind mount of the host's real `/proc`, and calling the latter a fixture would label live processes as synthetic. `lib::published_status` appends a clause per actual degradation only when the scan was degraded: `· N processes listed · M unreadable` when records were unreadable, `· process list unavailable: <reason>` when the root itself could not be listed, `· M beyond the record limit` when the scan stopped at its own bound, and `· host identity incomplete` when only the identity files were missing. The fake path's string is byte-identical to before.

### Hostile names

`/proc/<pid>/stat` `comm` is raw bytes in parentheses and may contain spaces, parentheses, control bytes and invalid UTF-8. `parse_stat` locates it between the first `(` and the **last** `)` and requires the leading PID field to match the directory, so a hostile name cannot shift field indices. `DisplayName::sanitize` lossily decodes UTF-8, replaces every control, bidi-override and zero-width character with U+FFFD, trims surrounding whitespace, bounds the result at 128 characters and substitutes `(unnamed)` for an empty name. Names are published as ordinary `Value::String` table cells; nothing interpolates a name into a shell, a command or any evaluated content, and there is still no process-name-specific client code path.

## PX-002 test refinement

PX-002's `identity_survives_reorder_rename_pid_change_and_source_changes_do_not_alias` asserted that mutating a record's PID leaves its ItemId unchanged. Under PX-003 the PID is one component of `ProcessKey`, and a record whose PID changes while its creation token stays fixed describes a physically impossible process, so that clause was replaced rather than kept. The PX-002 invariants it protected are all still covered, and coverage is strictly larger: `identity_survives_reorder_and_rename_and_never_aliases_across_sources` keeps reorder, rename and cross-source behavior, `boot_host_namespace_and_pid_are_all_discriminators` proves each identity component individually discriminates, and `same_pid_with_a_different_creation_token_gets_a_new_item_id` proves a reused PID is a new instance. `fake_source_test.rs` was adapted to the new record shape only; its assertions were not weakened, and PX-002's `status_is_the_injected_source_description_not_a_fixed_fixture_label` and the native Swift expectation both pass unmodified.

## Review follow-up

Codex review of `05b97961` raised two findings on `procfs.rs`; both were real and are fixed in the follow-up commit.

**P1 — a snapshot larger than one model batch aborted initialization.** `MAX_RECORDS` is 65,536 while §26 bounds a single model mutation batch at `DEFAULT_MAX_ITEMS_PER_MODEL_OPERATION` = 10,000, and `initialize_rows` sent every row in one `MODEL_INSERT`. On a host with more than 10,000 readable processes the publishing transaction failed and `--live-source` exited with no window at all. `initialize_rows` now reads the session's own `max_items_per_model_operation` before opening the transaction (the session lock is held for the closure's duration) and inserts consecutive bounded batches inside that one transaction, so a large snapshot still arrives atomically. New test `a_snapshot_larger_than_one_model_batch_is_published_whole` publishes `limit * 2 + 1` records and asserts one revision, the full item count and five nodes.

**P2 — issue explanations were bounded only after the scan.** Every skipped record formatted and pushed a detail string; `Completeness::from_scan` truncated to `MAX_RECORDED_ISSUES` only at the end, so a host whose records are all unreadable allocated one string per process before 32 were kept. `source::record_issue` now takes the explanation as a closure and builds it only while the bound has room; every per-record arm in the scan uses it, and `skipped` still counts every record. New tests `issue_recording_stops_allocating_once_the_bound_is_reached` (asserts the closure is never called past the bound) and `a_wholly_unreadable_root_keeps_issue_memory_bounded_while_counting_every_record`.

## Limitations and open items

- One snapshot at session start. No refresh loop, diffing, sorting, filtering, typed metrics, actions or htop parity; those belong to PX-004 and later.
- The live host's scan was fully `Complete` (196 records, 0 skipped) for an unprivileged user, so the denied/vanished record paths have deterministic fixture coverage but no live-degraded sample. The live test accepts either outcome and asserts the explanation in the degraded case.
- PID-namespace identity was observed live (`4026531836`, the host namespace) and is asserted in fixtures, but no live cross-namespace comparison was run: `unshare --pid` needs privileges this unprivileged run deliberately does not take.
- Host identity comes from `/proc/sys/kernel/hostname`, which is a mutable label, not a durable machine identity. It is one component of the key alongside boot identity, not an authority on its own.
- Two records that both fail to observe boot, host or namespace identity compare equal in those components. Within one process-lifetime session that cannot span a reboot, and no ID is ever recycled; a durable cross-session identity is not claimed.
- The native macOS GUI evidence is the unchanged PX-001/PX-002 path over localhost SSH. There is no macOS live collector and none is claimed; on a non-Linux host `ProcFsSource::live()` reports an incomplete scan rather than an empty one.
- No push, PR, follow-on ticket, or self-declared independent verification. Build artifacts remain in the worktrees for the active delivery run; all logs stay outside every checkout.
