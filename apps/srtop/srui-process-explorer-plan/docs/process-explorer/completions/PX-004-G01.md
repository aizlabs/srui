## The defect

`server-rust/sessiond/src/session/snapshot.rs::export_snapshot_transaction` built one catch-up transaction carrying every cached range of every model and checked only `max_transaction_operations`. PX-004 round 6 measured a 34,000-row collection exporting an **18,259,393-byte** snapshot against the **16,777,216-byte** `DEFAULT_MAX_FRAME_SIZE`: `SruiCodec` refused the write, so no fresh client could attach and no resync could recover, and a reconnect reproduced the same failure byte for byte.

## Design decision and rationale

### What the design already defines (read-only, unchanged)

- §12.1 rules: a transaction is applied atomically, the client must not expose a half-applied transaction, and "if a connection drops mid-transaction, the incomplete transaction is discarded" — the design already contemplates one transaction whose delivery spans more than one unit and requires all-or-nothing visibility.
- §18 *Snapshot delivery form*: a snapshot travels in the transaction envelope with `base_revision = 0`, `new_revision = snapshot_revision`; it replaces the replica wholesale, is valid only while an outstanding continuity decision (`SERVER RESYNC_REQUIRED`, or the catch-up after `SERVER WELCOME`) calls for one, never regresses the revision and never enters the journal.
- §18 negotiation evolves through additive protobuf fields ("These are additive protobuf fields, so an older server can ignore them"); §19.2 lists "errors" as control-class server traffic; §26 makes maximum frame size and maximum transaction operations separate limits and forbids raising them ad hoc.
- No existing mechanism splits a snapshot or bounds its export by size, and §12.3 progressive first paint cannot help: it commits *new authoritative revisions*, while a snapshot must reconstruct one existing revision.

### Chosen: negotiated multi-envelope snapshot, announced by the continuity decision

1. **Client bound** — `ClientLimits.max_snapshot_parts = 7` (re-advertised on every HELLO and RESUME, like the rest of `ClientLimits`). Zero/absent means one: a legacy client is never sent a split.
2. **Explicit framing signal** — `ServerWelcome.snapshot_parts = 8` and `ServerResyncRequired.snapshot_parts = 10`: the decision that calls for the snapshot announces how many consecutive `Transaction` envelopes carry it. Zero/absent means one, so a snapshot that fits a frame is announced as `0` and its bytes, and the decision's bytes, are exactly the legacy form.
3. **Envelopes** — every envelope is `base_revision = 0`, `new_revision = snapshot_revision`, non-empty; operations concatenate in arrival order into the one snapshot transaction. No `Transaction` field was added, so every existing transaction literal, fixture and decoder is unchanged.
4. **Atomic apply** — the replica stages envelopes off to the side (`SnapshotAssembler`, Rust `server-rust/protocol/src/snapshot_framing.rs`, Swift `client-macos/Protocol/SnapshotAssembler.swift`) and applies the reassembled transaction once, through the existing §18 snapshot path, after the last envelope. A lost connection drops the assembler, i.e. the incomplete transaction is discarded (§12.1).
5. **Measured before writing** — `plan_snapshot_frames` computes the exact `framed_payload_len` of each envelope (unit-tested equal to `framed_payload_len` of the built `SruiMessage`) against the smallest of the codec limit, the server's advertised limit and the client's advertised `max_frame_size`, packs operations greedily, and runs inside bootstrap **before** subscription, cancellation side effects or any frame write.
6. **Loud refusal on both sides** — an undeliverable snapshot (more operations than `max_transaction_operations`, one operation larger than a frame, or more envelopes than the client stages) is a typed `SessionError` (`SnapshotUnrepresentable` / new `SnapshotUndeliverable(SnapshotFramingError)`) logged by the server, which writes a new control-class `ServerHandshakeRefused { reason = SNAPSHOT_UNDELIVERABLE, detail }` (`SruiMessage` field 16) instead of WELCOME/RESYNC_REQUIRED and closes. The Swift client reports `SessionFailure.handshakeRefused("snapshot undeliverable: …")` and logs that reconnecting will not recover.
7. **Operations stay splittable** — the exporter also ends a `MODEL_RESET_RANGE` at 1 MiB of encoded items (`SNAPSHOT_MODEL_RANGE_MAX_BYTES`), besides the existing 10,000-item bound, so wide rows cannot make a single operation outgrow a frame. The operation bound still applies to the *whole* snapshot: splitting lifts only the byte bound, because the envelopes are still one transaction.

### Why this does not trip the supercritical stop

- **No normative change to the design.** Every §18 snapshot rule holds per envelope and for the reassembled snapshot (base 0, `new = snapshot_revision`, wholesale replace, only under an outstanding decision, no regression, never journalled); §12.1 atomicity and incomplete-transaction discard are exactly the staging semantics; §26 limits are all still enforced and none is raised. The design document is untouched.
- **No unsanctioned compatibility break.** All wire changes are additive proto3 fields plus one new oneof member. New server + legacy client: the client advertises no `max_snapshot_parts`, so it is never sent a split; a snapshot that would need one is refused (previously the codec failed the write and the client saw a silent close, so behaviour only improves; the unknown refusal message is ignored by old decoders and the close follows). Legacy server + new client: no `snapshot_parts` is announced, so the client applies the single envelope as before. A fitting snapshot is byte-identical to the legacy form.

### Alternatives rejected

- *Size-bounded export only*: refuses rather than delivers, failing the ticket's acceptance that both paths deliver a > one-frame model.
- *A `snapshot_part {index, count}` field on `Transaction`*: also explicit, but touches the hottest message (dozens of struct literals across the workspace and examples), and per-envelope indexes add nothing on one ordered stream once the decision has announced the count.
- *`CommitOp` as the terminator*: §13 lists COMMIT, but a missing COMMIT is indistinguishable from a legacy single-envelope snapshot without negotiation, so it would still need the announcement and adds an operation every replica must special-case.
- *Raising the frame limit*: forbidden by the ticket and §26.

## Limitations

- The split lifts only the frame bound. A snapshot needing more than `max_transaction_operations` (10,000) operations is still refused — now loudly on both sides — because the envelopes form one atomic transaction and the replica's operation bound is a §26 limit this ticket must not raise. Node-heavy stores (more than ~10,000 nodes) therefore remain unattachable; lifting that needs a separate design decision about the snapshot's operation bound.
- The client stages at most `DEFAULT_MAX_SNAPSHOT_PARTS = 16` envelopes (≤ 256 MiB of wire bytes). Server-side, the snapshot is still built in memory in full before it is split, as before.
- A legacy client attaching to a session whose snapshot needs a split is refused rather than served; it does not understand `ServerHandshakeRefused` and sees the close, which is no worse than before.
- srtop's published-row ceiling (PX-004) is deliberately unchanged; whether to lift it now is an app decision for a later ticket.
- No live SSH/Linux run was needed: the change is platform-neutral protocol/runtime code exercised over in-process duplex connections and the existing Unix-socket integration suites.
