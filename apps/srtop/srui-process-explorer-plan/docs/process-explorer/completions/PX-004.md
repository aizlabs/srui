## Bounded behavior

Every collecting mode now polls. `ProcessView::start` publishes the shell and the first snapshot exactly as PX-003 did; `refresh::poll` then samples the same source on a fixed schedule and `ProcessView::apply` publishes the difference. `--refresh-interval-ms MS` configures the interval between `MIN_REFRESH_INTERVAL` (50 ms) and `MAX_REFRESH_INTERVAL` (300 s), defaulting to `DEFAULT_REFRESH_INTERVAL` = 1 s; a value outside that range, or a non-numeric one, is refused before the socket is published. The empty-shell fixture does not poll. No process is opened for control, no action handler exists, no dependency, transport or unrelated example changed.

### Only model data moves

A tick emits `MODEL_INSERT`, `MODEL_DELETE`, `MODEL_UPDATE` and, when it actually changed, one `SET_PROPERTY` on the existing status node. It never creates, deletes, moves or reorders a node: `assert_shell_intact` holds the store at five nodes with the same parents and the same model reference across the whole scripted sequence, and the client's `DirtyClassifier` classifies those operations as model content rather than structure, so the renderer mutates the table it already built.

Deletions are emitted before insertions, so an insertion index is the row's final index; a retained row is re-sent only when its displayed cells changed, and one that moved backwards relative to its neighbours is deleted and reinserted explicitly. The shape of this diff follows the collection diff already proven in `examples/process-monitor/src/diff.rs`; that example is not modified or depended on.

Batches obey both §26 bounds. Items per model operation are clamped by the store's own limit and by `DEFAULT_MAX_ITEMS_PER_MODEL_OPERATION`, as PX-003's publication path already did, and the operation count per transaction is bounded by the store's `max_transaction_operations`: a refresh that does not fit commits as consecutive atomic transactions. Each transaction's effects are recorded into the view as it commits, so a plan that stops partway leaves this app's idea of what the client holds equal to what the store holds.

### An idle host is an idle wire

When the plan is empty, no transaction is opened at all — not an empty one. Nothing self-changing is serialized: the sample time, the vanished/capped counts and the source's step counter never reach a published value, and the status line is built from counts and fixed wording only, so no process's own text can enter it either. The scripted fixture deliberately advances its sample time on every step, including the two steps whose records are identical, so a snapshot that only *looks* the same is not enough to pass.

### A failed scan is an error, not an empty host

Rows are deleted only on the word of a scan entitled to say a process ended, and that entitlement is scoped to the absences the scan could not account for (`ProcessSnapshot::retention`, see the review follow-up below). A scan that could not list the process filesystem, or whose records `SessionItemIds::project` rejects, cannot account for anything: it keeps every last-known row, its item ID and its place, and publishes an explanation instead:

~~~
Read-only · Fake process sequence · incomplete scan · process list unavailable: permission denied · 3 rows retained from an earlier scan
~~~

A degraded scan that still listed records is treated the same way for the records it named as unread: that row keeps the place it already held, anchored to the confirmed row that followed it, so a record missed for one tick does not travel to the end of the table and back. Every *other* absence in such a scan is a real exit and is deleted. Recovery converges without moving a row — only the status property changes — and a host that stays broken republishes nothing, because the explanation has not changed either.

### Identity over a long-running poll

`SessionItemIds` is now pruned to the identities that are still published (including rows a degraded scan failed to confirm). Without that, a poll loop on a host with ordinary churn accumulates one entry per process that ever ran. Pruning never lowers the counter, so a forgotten identity that somehow returned would receive a new ID rather than a retired row's: `forgetting_an_unpublished_identity_never_hands_its_id_back_out` and `churn_does_not_grow_the_allocator_without_bound` (200 ticks that replace every process) assert both halves.

Sampling runs on `spawn_blocking`, because reading a host's process filesystem blocks; the loop keeps serving the accept loop meanwhile and stops on the existing cancellation token.

## Review follow-up: scoped retention (PR #64)

### Round 1

**Finding (P1, `apps/srtop/src/refresh.rs`, "Scope incomplete scans before disabling deletions").** Retention was decided by one whole-snapshot boolean: `let authoritative = rejected.is_none() && snapshot.completeness.is_complete()`. When any single `/proc/<pid>/stat` is persistently denied or unparsable, `ProcFsSource::snapshot` marks the whole scan incomplete, so that flag stays false forever. On any shared host at least one process belongs to another user, so `Completeness::Incomplete` is the steady state: every deletion is suppressed, `retain_unconfirmed` restores the row of every unrelated process that exits, and ordinary churn accumulates permanently stale rows until the model's cached-item limit (§26, `max_cached_items_per_model`) refuses a refresh. Judged real; an independent PX-004 verifier had flagged the same behaviour as a limitation.

**Fix.** The source now hands the refresh loop the identities whose absence is genuinely uncertain instead of a bare boolean. `ProcessSnapshot::retention()` (`src/source.rs`) returns `Retention::Skipped(BTreeSet<u32>)` — exactly the PIDs named by the scan's own `IssueScope::Process` issues — or `Retention::Unenumerable` when the uncertain set cannot be named at all:

- the root could not be listed, entered or anchored: the missing records have no known PID.
- `capped > 0` (equivalently `IssueScope::Limit`): the entries beyond the collector's bound were never read, so their PIDs are unknown.
- a directory entry that could not be examined: that record has no PID either.

(Round 1 derived the first and third of those, and the PID set itself, from the scan's recorded `EnumerationIssue` list; round 2 below removes that derivation. The `capped` case above is round 1's and round 2's decision, **not** the current one: round 3 below names those entries instead, because the root listing that produced them is a PID.)

Identity-file issues (`HostIdentity`, `BootIdentity`, `PidNamespace`) degrade every record equally and hide none, so they no longer suppress deletions. A record that merely *vanished* is not uncertain and is deleted like any other exit (PX-003 already counted those separately). `retain_unconfirmed` now keeps an unconfirmed row only when `Retention::keeps` matches it — by PID, the only identity component an unread record has — and matching errs towards keeping a row, never towards deleting one whose fate is unknown. A rejected snapshot confirmed nothing, so it still retains globally. No wording, count or status clause changed; the status is still built from counts and fixed wording only.

The enumerable uncertain set is bounded by the scan's own ledgers (rounds 2 and 3), so a degraded scan holds back a bounded number of rows, never one per exit forever; §26 and the PX-003 bounded-memory properties are unchanged.

### Round 2

**Finding (P1, `apps/srtop/src/source.rs`, "Track skipped PIDs beyond the diagnostic cap").** Round 1 read the uncertain identities out of the scan's *explanations*: the PID set was built from the recorded `IssueScope::Process` issues, and `skipped > named` — more records skipped than explanations retained — fell back to `Retention::Unenumerable`. `MAX_RECORDED_ISSUES` is 32, so on a host with more than 32 persistently unreadable records — routine on a shared machine — that fallback fires on *every* scan: retention becomes global again, every unrelated exit is restored, and the collection grows by a stale row per exit until the model's cached-item limit stops refreshes. Judged real: the same unbounded growth round 1 fixed, moved to a higher threshold.

**Fix.** A skipped record's PID is known even when its explanation was dropped, so the scan now records it directly instead of inferring it. `SkippedRecords` (`src/source.rs`) is the scan's own ledger of what it could not read: `record(pid)` for a record whose PID it observed, `unnamed()` for a directory entry it could not even examine, `mark_unenumerable()` for a root it could not list or anchor. `Completeness::Incomplete` carries that ledger in place of a bare count (`skipped()` still returns the count, so no status wording changed), and `ProcessSnapshot::retention()` is now two questions with no reference to the issue list at all:

~~~rust
if self.capped > 0 || !skipped.is_enumerable() {
    return Retention::Unenumerable;
}
Retention::Skipped(skipped.pids().clone())
~~~

(Round 3 below replaces the `self.capped > 0` clause: a capped entry's PID is known, so it is named rather than made unknowable.)

`MAX_RECORDED_ISSUES` is unchanged at 32 and now bounds the human-readable `EnumerationIssue` explanations and nothing else; `record_issue` still builds a description lazily, so an explanation past the bound costs nothing (PX-003). Round 2 left `Retention::Unenumerable` for a failed or unanchored root, an unexaminable directory entry, and `capped > 0` / `IssueScope::Limit`; round 3 removes that last case.

**Bounded memory.** The PID set is bounded by the scan's own record bound, the same `record_limit` that bounds how many records it reads (`MAX_RECORDS` = 65,536 by default), not by the host: past that bound the scan stops naming and reports itself unenumerable, which retains globally — the safe direction — rather than growing. Round 3 puts a second, lower ceiling on the same set (`MAX_UNCERTAIN_PIDS`) so the two ledgers together cannot outgrow the model's own item bound. The skipped *count* is still unbounded, because it is a number.

### Round 3

**Finding (P2, `apps/srtop/src/source.rs` ≈ line 547, "Bound retention when scans hit the record cap").** `retention()` returned `Retention::Unenumerable` whenever `capped > 0`. On a host with more readable PIDs than one scan publishes (`MAX_RECORDS` = 65,536) *every* scan is capped, so retention is global on every tick: `ProcessView::apply` combines the newly confirmed rows with every row it ever published, ordinary churn can never delete anything, and the collection grows from the 65,536-row snapshot until the model's 100,000-item bound (§26) refuses the next insert. Judged real, and lower severity than rounds 1–2 because it needs a very large host — but it was the last global-retention path reachable in steady state.

**Fix (the capped case is enumerable, so it is scoped rather than global).** A capped record is not an unread *identity*. The record bound stops the scan from reading each further record's detail; it does not stop the root listing that produced the entry, and a `/proc` entry is exactly a PID — the collector already parses it (`parse_pid`) before deciding to cap. A capped record is therefore "identity known, detail unread", which is the scoped case round 2 already handles, and the collector now records it:

~~~rust
if records.len() >= self.record_limit {
    capped.record(pid);
    if capped.count() == 1 { /* one IssueScope::Limit explanation */ }
    continue;
}
~~~

`ProcessSnapshot::capped` changed from a bare `usize` to a second PID ledger beside the skipped one (`CappedRecords`; both are the same bounded `PidLedger` type under two names, so `count()` still answers the status line), and `retention()` unions the two ledgers:

~~~rust
if !self.capped.is_enumerable() {
    return Retention::Unenumerable;
}
let mut uncertain = self.capped.pids().clone();
if let Completeness::Incomplete { skipped, .. } = &self.completeness {
    if !skipped.is_enumerable() {
        return Retention::Unenumerable;
    }
    uncertain.extend(skipped.pids().iter().copied());
}
Retention::Skipped(uncertain)
~~~

`Retention::Unenumerable` now means only what was never observed: a root that could not be listed or anchored, a directory entry that could not be examined, or a ledger asked to name more identities than it may hold. Being capped is no longer one of them.

**The bound, stated.** `MAX_UNCERTAIN_PIDS` (`src/procfs.rs`) bounds the identities either ledger may name, and it is derived, not chosen:

~~~rust
pub const MAX_UNCERTAIN_PIDS: usize = (DEFAULT_MAX_CACHED_ITEMS_PER_MODEL - MAX_RECORDS) / 2;
const _: () = assert!(MAX_RECORDS + 2 * MAX_UNCERTAIN_PIDS <= DEFAULT_MAX_CACHED_ITEMS_PER_MODEL);
~~~

= 17,232 with today's constants. The skipped ledger keeps round 2's `record_limit` bound under the new ceiling (`record_limit.min(uncertain_limit)`); the capped ledger takes the ceiling alone, because capped entries are by definition beyond the record bound and that bound says nothing about how many of them a host has. `ProcFsSource::with_uncertain_limit` is the test seam for the ceiling, symmetric with the existing `with_record_limit`.

**Status text.** Unchanged wording, still counts and fixed strings only: a capped scan publishes `· incomplete scan · 2 processes listed · 2 beyond the record limit · 2 rows retained from an earlier scan`. ### Round 4

**Finding (P2, `apps/srtop/src/refresh.rs` ≈ line 207, "Split refreshes before they exceed the frame limit").** `commit` chunked a plan by `max_ops` only. Operation count and payload size are independent §26 bounds, and a single `MODEL_INSERT` may carry 10,000 items, so a source that grows from a small snapshot to tens of thousands of long names produces a refresh of only four operations — far inside the 10,000-operation bound — whose payload exceeds the 16 MiB frame limit. The store commits that transaction, `SruiCodec` then refuses to write the frame and the connection is detached, and because the next tick diffs clean nothing is ever republished: the client is dropped from a server whose revision has already moved on. Judged real and in scope — PX-004 already promises that a refresh larger than the §26 operation bound commits as consecutive atomic transactions, and frame size is the same §26 family.

**Fix (bound each transaction by its encoded size as well as by its operation count).** `commit` now walks the plan accumulating a per-operation byte cost and closes a transaction when the next operation would push it past the ceiling, as well as when it would push it past `max_ops`:

~~~rust
while end < plan.len() && end - start < max_ops {
    let cost = plan[end].bytes;
    if end > start && bytes + cost > max_bytes {
        break;
    }
    bytes += cost;
    end += 1;
}
~~~

The ceiling is derived from the protocol's own constant, never chosen:

~~~rust
const TRANSACTION_ENVELOPE_BYTES: usize = 64;
const MAX_TRANSACTION_PAYLOAD_BYTES: usize = DEFAULT_MAX_FRAME_SIZE - TRANSACTION_ENVELOPE_BYTES;
~~~

`TRANSACTION_ENVELOPE_BYTES` is the headroom for what the operations travel in — the `SruiMessage.transaction` tag and length prefix and the transaction's own `base_revision`, `new_revision` and `priority` fields, each a tag byte plus a varint of at most ten — so payload is never mistaken for frame.

**Why the accounting is a bound and not an average.** `Planned` now carries `bytes`, an upper bound on what the operation adds to an encoded transaction, computed from the values actually being published. Every length prefix is charged its widest varint and every field its tag, and **a string is charged its encoded UTF-8 length, never its character count**: a display name is bounded to `MAX_DISPLAY_NAME_CHARS` = 128 *characters*, and a character can encode to four bytes, so counting characters would understate a full-width name fourfold. `value_wire_bytes` recurses through lists and records and charges every other variant a fixed `SCALAR_VALUE_BYTES` = 64, which is above the widest one (a rectangle's four doubles).

`diff` applies the same ceiling per operation, not only per transaction: a transaction must hold at least one operation, so an operation that alone exceeded the frame bound could not be rescued by any later split. Insert and update runs now close on accumulated bytes as well as on `batch`, and the delete chunk length takes the ceiling as a second cap.

Nothing else moved. Deletions are still emitted before insertions, so an insertion index is still the row's final index; each committed transaction is still individually atomic and recorded as it commits; item identity is unchanged; an identical tick still publishes nothing; the status operation still leads the plan and still coalesces into the first transaction. No §26 limit was weakened, the frame limit was not raised, and no second transport or retry path was introduced.

### Round 5

**Finding (P2, `apps/srtop/src/refresh.rs` ≈ line 230, "Reject scans that temporarily lose global identity").** A scan reads the host, boot and PID-namespace identity once and stamps every record it publishes with the answer, and all three are components of `ProcessKey`. When one of those reads fails for a single tick — an unreadable `sys/kernel/hostname`, `sys/kernel/random/boot_id` or `1/ns/pid` — `project` still accepted the snapshot, but every record became a *new* key and therefore a new `ItemId`; meanwhile an identity failure skips no PID, so `snapshot.retention()` returned an empty scoped set and every last-known row was accounted for as ended. The refresh deleted and reinserted the whole table, losing native row identity and selection, and did it again when the identity file came back. Judged real and in scope: PX-004's first acceptance criterion is that unchanged rows retain their ItemIds and native controls.

**Fix (remember the source's global identity for the session, and key a degraded scan with it).** The three components are facts about the *source*, not about a record — one hostname per UTS namespace, one boot ID per running kernel, one namespace per procfs mount (PX-003) — and within one semantic session the source cannot legitimately become a different machine: a reboot ends the session. `SessionItemIds` therefore carries a `SessionIdentity` of the last value each component was *observed* to hold, and anchors every key it resolves against it:

~~~rust
fn anchor_component<T: Clone>(remembered: &mut Option<T>, observed: &mut Observed<T>) {
    match observed {
        Observed::Known(value) => *remembered = Some(value.clone()),
        Observed::Missing(_) => {
            if let Some(known) = remembered.clone() {
                *observed = Observed::Known(known);
            }
        }
    }
}
~~~

Anchoring happens before anything is looked up, on a *copy* of the session identity that is committed only once the snapshot survives the duplicate-identity check, so a rejected snapshot leaves the remembered identity exactly as it was. A component never observed at all stays missing: there is nothing to restore, and inventing one would be a claim rather than a memory. Both ways of not reading a component are the same event — `Unavailable` and `Denied` alike are a scan that lost sight of a fact that did not change.

**The honest exception.** A component that comes back as a *different* `Known` value is not a degradation: it is a different source, its records are different process instances, and they legitimately take new identities. That case is deliberately not smoothed over — the newly observed value replaces the remembered one and never overrides what the scan actually read — and it has its own test. The pre-existing PX-003 test `boot_host_namespace_and_pid_are_all_discriminators` still passes unchanged, and kills the mutation that would make a differing value behave as equal.

**Honesty and wording.** Nothing remembered reaches the wire. A `ProcessKey` is server-side row identity only — the published row carries a PID and a name — and the status line is still built from counts and fixed wording, still from the scan's own issues, so the degraded tick still publishes `· incomplete scan · 3 processes listed · host identity incomplete` on exactly the tick that saw the failure. No existing degradation clause changed. Scoped retention, `Retention::Unenumerable` for never-observed identities, the per-transaction encoded-size bound, deletions before insertions, per-transaction atomicity, an identical tick publishing nothing and every §26 limit are untouched: the fix is confined to how a key is composed, not to what a scan is entitled to delete.

### Round 6

**Finding (P2, `apps/srtop/src/refresh.rs` ≈ line 286, "Keep the resulting store within the snapshot frame limit").** Round 4 split the *live mutations* by encoded size, but left the *resulting collection* unbounded. `server-rust/sessiond/src/session/snapshot.rs::export_snapshot_transaction` builds one catch-up transaction carrying every cached range of every model and checks only `max_transaction_operations`, so after a refresh that leaves more than 16 MiB of model data — exactly what the round-4 acceptance test's 34,000 wide rows produced — `SruiCodec` refuses the catch-up frame for every fresh client and every resync. Nobody can attach at all. Judged real: measured on the real attach path, a 34,000-row collection exports a snapshot of **18,259,393 bytes** against the 16,777,216-byte limit.

**Scope ruling.** Chunked snapshot delivery is core runtime and protocol work (§18/§21 resync, a snapshot-framing signal on the wire, conformance coverage on both replicas). The standing contract forbids extending standard semantics ad hoc and requires a separate, narrowly scoped ticket for a missing generic facility, so **no file under `server-rust/` is touched here**. This round takes the reviewer's first alternative, which is inside this app's own boundary: *srtop must never publish a model larger than a client can be sent.* The core gap is filed as **PX-004-G01** and is explicitly **not fixed here**.

**Fix (bound the published collection, not just each transaction).** `bound_to_snapshot_frame` (`src/refresh.rs`) drops the trailing rows a catch-up snapshot of the resulting model could not carry, and returns how many:

~~~rust
fn bound_to_snapshot_frame(rows: &mut Vec<Row>, status_bytes: usize) -> usize {
    let budget = MAX_TRANSACTION_PAYLOAD_BYTES.saturating_sub(SNAPSHOT_SHELL_BYTES + status_bytes);
    let mut spent = 0usize;
    let mut kept = 0usize;
    for row in rows.iter() {
        let mut cost = row_wire_bytes(row);
        if kept.is_multiple_of(DEFAULT_MAX_ITEMS_PER_MODEL_OPERATION) {
            // This row opens another operation of the exported snapshot.
            cost += SNAPSHOT_RANGE_BYTES;
        }
        if spent + cost > budget {
            break;
        }
        spent += cost;
        kept += 1;
    }
    let dropped = rows.len() - kept;
    rows.truncate(kept);
    dropped
}
~~~

Every quantity is round 4's own accounting, reused rather than re-invented: `row_wire_bytes` charges each row the same upper bound the planner charges (a string at its encoded UTF-8 length, never its character count), the ceiling is still `DEFAULT_MAX_FRAME_SIZE` less the envelope allowance, and the two additions are the snapshot's own shape — one `MODEL_RESET_RANGE` operation per `DEFAULT_MAX_ITEMS_PER_MODEL_OPERATION` rows, and `SNAPSHOT_SHELL_BYTES` = 4 KiB for the `CREATE_MODEL` operation and the five `CREATE_NODE` operations that travel with the rows. The status text is not folded into that allowance but charged exactly, because it is the one property a scan can lengthen; the clause truncation itself adds is charged a fixed 64-byte allowance, so the count it states cannot move the budget that produced it.

**Both publishing paths.** The bound is applied where the rows are chosen — in `ProcessView::apply` on every tick *and* in `ProcessView::start`, the start path the round-4 note had flagged as still unbounded. That is precisely the attach path this finding is about: the first publication is one transaction, and every client that attaches later is brought up by one snapshot of that same model. `initialize_rows` (`src/lib.rs`) now documents that contract on its own signature.

**Truncation is honest, count-based and stable.** The status gains one clause of fixed wording and a count, in the existing style: `· 6683 rows beyond the publishable size limit`. It is deliberately distinct from every other shortfall — those rows were read perfectly well, so calling them `unreadable` would report a failure that never happened, and they are not the entries the collector's own record bound never read (`beyond the record limit`) either: this bound belongs to the wire, not to the scan. No process's own text reaches it. The rows kept are the *leading* ones of the order the source already publishes (`ProcFsSource` sorts by ascending PID), so the published window is a deterministic function of the snapshot alone: an unchanged host keeps exactly the rows it kept last tick, nothing churns in or out, and an identical tick still publishes nothing at all.

Everything from rounds 1–5 still holds: scoped retention and the two PID ledgers, `Retention::Unenumerable` only for never-observed identities, the per-transaction operation and size bounds, deletions before insertions, sticky session identity, item identity for every row that stays published, and every §26 limit. `retained` is recounted *after* truncation, so a row that was dropped is never also reported as retained.

### Round 7

Two findings, both P2, fixed in one change. No file under `server-rust/` is touched.

#### A — the status was charged against the rows it travels with

**Finding (`apps/srtop/src/refresh.rs` ≈ line 298, "Preserve retained rows when an error lengthens the status").** Round 6 charged the *current* status text against the snapshot frame before budgeting the rows: `bound_to_snapshot_frame(&mut target, provisional.len() + TRUNCATION_CLAUSE_BYTES)`. A rejected or unlistable scan produces the longest status this app emits — the failure, the retained-row clause, and every degradation the scan reports — so on a collection already at the ceiling that longer text shrank the row budget, truncated `target`, and the ensuing diff deleted last-known rows even though `Retention::Unenumerable` said the scan was no evidence that anything had ended. Judged real, self-inflicted by round 6, and a direct violation of PX-004 acceptance criterion 3.

**Fix (a fixed reserve, and an error-only refresh that plans no row mutation).** The status is now charged `STATUS_RESERVE_BYTES`, never its own length:

~~~rust
const MAX_STATUS_CLAUSE_BYTES: usize = 1024;
const STATUS_RESERVE_BYTES: usize = MAX_PUBLISHED_LABEL_BYTES + MAX_STATUS_CLAUSE_BYTES;
~~~

The allowance is derived from the status builder rather than from any one status. `published_status` was split into `ScanReport::of(snapshot)` — the counts and fixed categories one scan can report — and `published_status_from(label, &report)`, and the refresh clauses into `RefreshCounts { retained, rejected, evicted, truncated }`, so the reserve can be measured against the real builder with **every count at `usize::MAX`** instead of against the largest count a fixture happens to be able to construct. The source's own label is the one unbounded input left, so it is cut at `MAX_SOURCE_STATUS_BYTES` = 256 encoded bytes on a character boundary and marked with an ellipsis; `MAX_PUBLISHED_LABEL_BYTES` is that plus the mark. A rejection reason is bounded the same way at 128 bytes.

A refresh that confirmed nothing and may delete nothing now takes a path on which no row can be evicted at all — the reviewer's "make it unrepresentable":

~~~rust
if confirmed.is_empty() && retention.is_global() {
    return self.publish_status_only(session, source_status, snapshot, rejected);
}
~~~

`publish_status_only` plans exactly one `SET_PROPERTY` over the last-known rows: no row budget is computed, no target is chosen and no diff is taken, so there is nothing for a longer status to cost. An identical failure still republishes nothing.

The row budget is now a function of the rows alone, so the ceiling costs a little more: the 34,000-widest-row fixture publishes 27,315 rows rather than 27,317, and the status says `· 6685 rows beyond the publishable size limit`.

#### B — ledger overflow made retention unbounded again

**Finding (`apps/srtop/src/source.rs` ≈ line 579, "Prevent ledger overflow from enabling unbounded retention").** On a host with at least 82,769 readable PID entries the 17,233rd entry past `MAX_RECORDS` overflows the capped ledger, so `retention()` returns `Retention::Unenumerable` on *every* tick and every absent row is retained for ever. The round-6 frame ceiling does not stop the resulting growth — it bounds bytes, and short rows fit one frame in their tens of thousands — so ordinary churn grows the model past its 100,000-item §26 bound, after which insert transactions fail and refresh can no longer converge. Judged real: the last unbounded retention path.

**Fix (bound the published collection itself, in every case).** Retention is no longer bounded only by what a scan can name:

~~~rust
pub const MAX_PUBLISHED_ROWS: usize = DEFAULT_MAX_CACHED_ITEMS_PER_MODEL;
~~~

`ProcessView` carries that ceiling, lowered at `start` to whatever the session's store will cache, and every refresh evicts the unconfirmed rows beyond it:

~~~rust
let evicted = evict_unconfirmed_beyond(&mut target, &confirmed_ids, self.published_limit);
~~~

The rule is a function of the published order alone: the rows kept are the leading unconfirmed ones — the same deterministic window the snapshot ceiling keeps — so the trailing rows that go are the stalest, since `retain_unconfirmed` anchors an unconfirmed row behind the rows a scan did confirm. Nothing depends on iteration order or on a clock, a row a scan confirmed is never evicted, and an evicted row is never re-admitted from history. `bound_to_publishable_collection` applies the same ceiling as a row count beside its byte budget, so the two bounds are independent and neither can be traded for the other. `with_published_limit` can only ever *lower* the ceiling; it exists so a test can drive eviction without publishing a hundred thousand rows a tick.

The status names the eviction in the existing count-based style — `· 1 unconfirmed row dropped to stay inside the published row limit` — deliberately distinct from a process that ended (no clause: its row is simply deleted), from `unreadable`, from `beyond the record limit` and from `beyond the publishable size limit`. `MAX_UNCERTAIN_PIDS` keeps its meaning and its compile-time assertion for the *scoped* case; what bounds the unenumerable case is now `MAX_PUBLISHED_ROWS`, which no scan, ledger or retention decision can lift.

Everything from rounds 1–6 still holds: scoped retention by named PIDs, `Retention::Unenumerable` only for never-observed identities, sticky session identity, the per-transaction operation and encoded-size bounds, the snapshot ceiling with its deterministic leading-row window, deletions before insertions, atomic per-transaction commits, an identical tick publishing nothing, and every §26 limit.

## Limitations and open items

- `a_refresh_beyond_the_transaction_bound_is_published_whole` publishes 20,004 rows and needs 10,002 insertion operations to cross the real §26 bound, which no smaller collection can do. It dominates the app suite: about **46 s** on macOS and **154 s** on the Linux host, in debug. The cost is the engine's index shifting for ten thousand separate insertions, not this app's diff; the same behavior is also covered cheaply by the unit test `a_plan_is_committed_in_bounded_transactions_and_recorded_as_it_commits`.
- The size accounting is an upper bound, so it is conservative by roughly 15% on rows of this shape: the ceiling admits 27,316 widest-name rows, whose snapshot really encodes to about 14.5 MiB rather than the charged 16.7 MiB. A few thousand rows that would have fitted are therefore not published, and a refresh that would have fitted is occasionally split in two. The opposite error detaches every client, so the bound deliberately errs this way. (Round 6 supersedes round 4's version of this note, which described only the per-transaction split.)
- The published-collection ceiling is an app-level workaround, not a fix: `sessiond` still exports a catch-up snapshot as one unchunked transaction bounded only by its operation count, which every other SRUI application still meets. That core gap is tracked by **PX-004-G01** and is deliberately untouched here — no file under `server-rust/` is changed by this ticket.
- A row dropped for size is not remembered: the allocator keeps an identity only while its row is on screen, so a process that later fits is published under a fresh item ID. Nothing a client ever held changes, since that row was never published, and the allocator's counter only moves forward (`checked_add`, with exhaustion reported rather than wrapped).
- A host with more publishable processes than one frame can carry therefore shows a truncated table and says so, rather than showing all of them. The honest fix for such a host is virtualized ranges — the client asking for the window it is showing — which belongs to a later ticket, not a wider frame.
- `initialize_rows` is bounded by the same ceiling as every later tick (round 6), so the start path no longer publishes an unsendable first snapshot. It is still one atomic transaction: the shell and its first rows arrive together.
- Ordering is still the source's own: `ProcFsSource` publishes ascending PIDs. Sorting, filtering, virtualized ranges, typed metrics and process actions belong to later tickets, and none is claimed here.
- The live host's scans were complete, so the live run exercised insertion, deletion and update but not the degraded-live path; that path has deterministic fixture coverage on both platforms, and the live test accepts either outcome. The review follow-up's scoping is therefore also proven by fixtures rather than by a live denied record.
- One global-retention path remains — a scan that lists more than `MAX_UNCERTAIN_PIDS` = 17,232 entries past its record bound, a host of more than 82,768 processes, stops naming them and retains every absent row — and since round 7 it no longer grows the collection: retention is capped at `MAX_PUBLISHED_ROWS` and the excess is evicted and stated. What such a host still shows is a bounded, truncated view of itself; a collection that stays *complete* there needs the virtualized ranges of a later ticket, not a wider ledger.
- The published-row ceiling evicts the trailing unconfirmed rows of the published order. That order is a stable rule and the trailing rows are the stalest, but it is not a recency ranking: a row that goes unconfirmed drifts backwards only as confirmed rows are published ahead of it, so two rows unconfirmed since the same tick are evicted in publishing order rather than by any measure of how long each has been gone. An evicted row that reappears is published under a fresh item ID, exactly like a row dropped for size.
- A source's status label is cut at 256 encoded bytes, marked with an ellipsis, because the status is charged against the snapshot frame before the rows are and a label is source-owned text of no fixed length. Every label this repository ships is far shorter; a source that wanted a longer one would see it cut rather than see rows dropped to pay for it.
- Scoped retention matches a skipped record by the PID the scan recorded when it skipped it, because a record the scan could not read has no other observable identity component. A retained row carrying that same number from an earlier boot or another namespace would therefore be kept one tick longer than strictly necessary; matching deliberately errs towards keeping a row rather than deleting one whose fate is unknown.
- A global identity component the session has *never* observed is not back-filled when it first becomes readable: the keys stamped `Missing` while the file was unreadable are genuinely different keys from the ones stamped with the value, so a source that starts degraded and recovers re-keys its records once. That is deliberate — the alternative is deciding retroactively that a value that was never read is the value those records were running under — and it costs one churn at the start of a session rather than a churn per degradation, which is what round 5 fixed.
- The remembered identity lives in `SessionItemIds`, so it is per semantic session: a reconnect that mints a new view starts with nothing remembered, exactly as it starts with no rows.
- Acceptance item 4 is asserted in ticks, not in wall-clock seconds: the worker was observed on the first tick after it appeared and the first tick after it was reaped, and the measured elapsed times are printed as evidence rather than asserted, so a loaded host cannot make the test flaky in the direction of a false pass.
- The refresh loop is one poll per source per process. There is no adaptive interval, no coalescing under backpressure and no per-client pacing; §12.2 pacing stays the renderer's business, as before.
- A snapshot whose identities are rejected is published as an error and retried on the next tick. There is no escalation if a source stays broken forever beyond that unchanging status line.
- The native evidence is the unchanged PX-001/PX-002 localhost SSH path on macOS. There is no macOS collector and none is claimed.
- No push, PR, follow-on ticket, or self-declared independent verification. All logs stay outside every checkout.
