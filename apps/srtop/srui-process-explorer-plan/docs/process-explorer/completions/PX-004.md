## Bounded behavior

Every collecting mode now polls. `ProcessView::start` publishes the shell and the first snapshot exactly as PX-003 did; `refresh::poll` then samples the same source on a fixed schedule and `ProcessView::apply` publishes the difference. `--refresh-interval-ms MS` configures the interval between `MIN_REFRESH_INTERVAL` (50 ms) and `MAX_REFRESH_INTERVAL` (300 s), defaulting to `DEFAULT_REFRESH_INTERVAL` = 1 s; a value outside that range, or a non-numeric one, is refused before the socket is published. The empty-shell fixture does not poll. No process is opened for control, no action handler exists, no dependency, transport or unrelated example changed.

### Only model data moves

A tick emits `MODEL_INSERT`, `MODEL_DELETE`, `MODEL_UPDATE` and, when it actually changed, one `SET_PROPERTY` on the existing status node. It never creates, deletes, moves or reorders a node: `assert_shell_intact` holds the store at five nodes with the same parents and the same model reference across the whole scripted sequence, and the client's `DirtyClassifier` classifies those operations as model content rather than structure, so the renderer mutates the table it already built.

Deletions are emitted before insertions, so an insertion index is the row's final index; a retained row is re-sent only when its displayed cells changed, and one that moved backwards relative to its neighbours is deleted and reinserted explicitly. The shape of this diff follows the collection diff already proven in `examples/process-monitor/src/diff.rs`; that example is not modified or depended on.

Batches obey both §26 bounds. Items per model operation are clamped by the store's own limit and by `DEFAULT_MAX_ITEMS_PER_MODEL_OPERATION`, as PX-003's publication path already did, and the operation count per transaction is bounded by the store's `max_transaction_operations`: a refresh that does not fit commits as consecutive atomic transactions. Each transaction's effects are recorded into the view as it commits, so a plan that stops partway leaves this app's idea of what the client holds equal to what the store holds.

### An idle host is an idle wire

When the plan is empty, no transaction is opened at all — not an empty one. Nothing self-changing is serialized: the sample time, the vanished/capped counts and the source's step counter never reach a published value, and the status line is built from counts and fixed wording only, so no process's own text can enter it either. The scripted fixture deliberately advances its sample time on every step, including the two steps whose records are identical, so a snapshot that only *looks* the same is not enough to pass.

### A failed scan is an error, not an empty host

Rows are deleted only on the word of a scan entitled to say a process ended: `Completeness::Complete`, with every record identified. A scan that could not list the process filesystem, or whose records `SessionItemIds::project` rejects, keeps every last-known row, its item ID and its place, and publishes an explanation instead:

~~~
Read-only · Fake process sequence · incomplete scan · process list unavailable: permission denied · 3 rows retained from an earlier scan
~~~

A degraded scan that still listed records is treated the same way for what it did not see: the unconfirmed row keeps the place it already held, anchored to the confirmed row that followed it, so a record missed for one tick does not travel to the end of the table and back. Recovery converges without moving a row — only the status property changes — and a host that stays broken republishes nothing, because the explanation has not changed either.

### Identity over a long-running poll

`SessionItemIds` is now pruned to the identities that are still published (including rows a degraded scan failed to confirm). Without that, a poll loop on a host with ordinary churn accumulates one entry per process that ever ran. Pruning never lowers the counter, so a forgotten identity that somehow returned would receive a new ID rather than a retired row's: `forgetting_an_unpublished_identity_never_hands_its_id_back_out` and `churn_does_not_grow_the_allocator_without_bound` (200 ticks that replace every process) assert both halves.

Sampling runs on `spawn_blocking`, because reading a host's process filesystem blocks; the loop keeps serving the accept loop meanwhile and stops on the existing cancellation token.

## Mutation verification

Every edited file was touched before each incremental run; each mutation was reverted and the suite re-run green afterwards. `mutations.log`.

1. **Believe every scan** (`let authoritative = true`). → exit 101; four tests fail, including `a_failed_scan_keeps_every_row_and_says_so_and_recovery_converges` — the failed scan deletes every row, which is exactly what the ticket forbids.
2. **Let the sample time reach the status** (append `snapshot.sampled_at`). → exit 101; the repeated-snapshot tick publishes `Refreshed { … status_changed: true, transactions: 1 }` instead of nothing, and four integration tests plus one unit test fail.
3. **Never forget an unpublished identity** (drop the body of `SessionItemIds::retain`). → exit 101; `churn_does_not_grow_the_allocator_without_bound` and `forgetting_an_unpublished_identity_never_hands_its_id_back_out` fail.
4. **Ignore the transaction bound** (`plan.chunks(usize::MAX)`). → exit 101 with `Store(OperationError("maximum transaction operations exceeded (limit: 10000, actual: 10001)"))` — the precise §26 failure the chunking exists to prevent; the unit test fails too.
5. **Hand every row a fresh identity on every projection**. → exit 101; the scripted tick reports `inserted: 3, deleted: 3` for three processes that did not change — the full rebuild the ticket forbids — and three projection tests fail.

The native test also failed for real during development, on a torn sample that paired a new revision with the previous rows; it now records a state only when the native controls already show what the client holds, which is itself the assertion that the table mirrors the model.

## Limitations and open items

- `a_refresh_beyond_the_transaction_bound_is_published_whole` publishes 20,004 rows and needs 10,002 insertion operations to cross the real §26 bound, which no smaller collection can do. It dominates the app suite: about **46 s** on macOS and **154 s** on the Linux host, in debug. The cost is the engine's index shifting for ten thousand separate insertions, not this app's diff; the same behavior is also covered cheaply by the unit test `a_plan_is_committed_in_bounded_transactions_and_recorded_as_it_commits`.
- Ordering is still the source's own: `ProcFsSource` publishes ascending PIDs. Sorting, filtering, virtualized ranges, typed metrics and process actions belong to later tickets, and none is claimed here.
- The live host's scans were complete, so the live run exercised insertion, deletion and update but not the degraded-live path; that path has deterministic fixture coverage on both platforms, and the live test accepts either outcome.
- Acceptance item 4 is asserted in ticks, not in wall-clock seconds: the worker was observed on the first tick after it appeared and the first tick after it was reaped, and the measured elapsed times are printed as evidence rather than asserted, so a loaded host cannot make the test flaky in the direction of a false pass.
- The refresh loop is one poll per source per process. There is no adaptive interval, no coalescing under backpressure and no per-client pacing; §12.2 pacing stays the renderer's business, as before.
- A snapshot whose identities are rejected is published as an error and retried on the next tick. There is no escalation if a source stays broken forever beyond that unchanging status line.
- The native evidence is the unchanged PX-001/PX-002 localhost SSH path on macOS. There is no macOS collector and none is claimed.
- No push, PR, follow-on ticket, or self-declared independent verification. All logs stay outside every checkout.
