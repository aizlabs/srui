So: from 6.16 (and 6.15.7, 6.12.39, 6.6.99) `statm` is exact while `stat` is not; from 6.2 until that fix both read the same approximate counter, where each of the three counters `resident` adds up can be off, either way, by less than `max(32, 2 × online CPUs)` pages per online CPU, and a just-started or very small process can read 0; before 6.2 all three files read one counter too, approximate by each thread's changes not yet added in. Reading `statm` is therefore exact where the kernel can be exact and never worse than `stat` anywhere, without asking the kernel's version. The ticket's own probe (Docker, 6.10.14-linuxkit, 12 CPUs) found `stat` rss 0 while `smaps_rollup` Rss > 0 in 13% of reads right after exec, 37% under 16 busy loops, and 0/500 for a settled `sleep`; on that kernel `statm` is the same counter, so those numbers are what 6.2–6.15 still publish. The man pages lag the kernel: `proc_pid_statm(5)` in man-pages 6.19 (2026-02-08) still says "resident … (inaccurate; same as VmRSS in /proc/pid/status)", which describes the kernels before the fix.

### Strict parsing, bounded reads, checked conversion

`statm` is read through `read_bounded` (the scan's 64 KiB bound) and parsed by `parse_statm_resident`: exactly seven plain decimal counts, each fitting a `u64`, separated by single spaces and ended by one newline — the kernel's own format — or nothing. A field too many or too few, a sign, a non-digit in any field, a count past `u64`, a doubled, leading or trailing space, a tab, a CR or a missing newline refuses the whole line, which is then an unread metric (`Unavailable`), never a zero and never a partial read. The page count is multiplied by the mount's page size with `checked_mul`, as before. `stat` field 24 is no longer parsed at all (`StatFields::resident_pages` is gone), so there is nothing to fall back to.

### When `statm` fails after `stat` succeeded

The decision follows the existing record and field states rather than inventing a new one:

| `statm` read | Published | Why |
| --- | --- | --- |
| Ended: `ENOENT` by path, `ESRCH` through the pinned directory | No record; counted in `vanished`; no CPU baseline kept; `Completeness` untouched | The process no longer exists at sample time — the same event as a `stat` that is already gone, which PX-004 counts as vanished churn. Publishing it with half a sample would put a row on screen for a process the scan has just proved ended. |
| Refused (`EACCES`/`EPERM`) | Record published, `resident` = `Denied` | One refused field of an identified record, as PX-005 treats a refused `auxv` |
| Any other failure, oversized, or a line that is not the kernel's | Record published, `resident` = `Unavailable` | One unreadable field, as PX-005 treats an unparsable field 24 |
| Seven zeros (no address space) | `0 B`, a known zero | What PX-005 published from field 24 = 0 for the same tasks |

No case falls back to `stat` field 24: that would publish an approximate number beside exact ones with nothing to say which is which. The record's own reason is published before the mount's page-size reason. `ESRCH` is matched by number (3 on every Linux architecture) because `io::ErrorKind` has no stable variant for it, and is now counted as an exit for the `stat` read too: through a pinned directory it is the kernel's report of exactly the event `ENOENT` reported by path. A process that becomes a zombie between the two reads reads seven zeros and is published as `0 B` for that one scan, which is true of that instance at that instant.

### Same process for both reads: the directory is pinned

`stat` (identity, name, CPU ticks) and `statm` are separate reads, and by path the second reaches whichever process holds the number then. On Linux the scan now opens each record's `/proc/<pid>` directory once and reads both files through the reader's own `/proc/self/fd/<n>` link to that handle (`std` alone; no `libc` dependency exists in this crate, so no `openat`). procfs binds the handle to the `struct pid` it was opened on, so after that instance is reaped every lookup through it fails with `ESRCH` (`proc_pid_permission`) and can never reach a newcomer under the same number. `record_access` decides once per scan whether the reader can do this — it opens the root and checks that `/proc/self/fd/<n>` reaches the very directory it opened (same device and inode) — and otherwise reads by name, so a reader without that link (every system but Linux, or a Linux reader whose own `/proc` is missing or unusable) never mistakes a missing link for every process having ended. That fallback is silent: nothing reports that a scan read by name. A pinned read opens the record's directory for reading, where reading by name needed only search permission; stock procfs grants both, and the consequence elsewhere is under Limitations.

Why pin rather than rely on PID allocation: Linux allocates PIDs cyclically, so by name a misattribution needs the process to exit and be reaped and the allocator to come back round to its number, all within the microseconds between two back-to-back reads — vanishingly unlikely, but the plan's identity rule is that a numeric PID is not process-instance identity, and the pin turns "unlikely" into "impossible" at a cost measured below (about 0.9–1.9 µs per process, a third to a half of what this change adds). Live demonstrations on the 6.10 kernel (`probe/*.log`):

- `pin-probe-container.log`, uid 1000: through a pinned directory, after the process was killed and reaped, `statm` and `stat` fail with "No such process"; by name, "No such file or directory". A zombie's `statm` is `0 0 0 0 0 0 0` and its `stat` rss 0.
- `kthread-probe.log`, a read-only `--pid=host` container: `kthreadd` and `pool_workqueue_release` have `statm` `0 0 0 0 0 0 0` and `stat` rss 0.
- `reuse-probe.log`, a disposable `--privileged` container writing `ns_last_pid` in its own PID namespace: PID 9 was reused by a second instance (start time 16801419, then 16801420); the read through the directory pinned on the first instance failed with "No such process", while the read by name returned the newcomer's `557 256 256 8 0 88 0`.

## Correction to PX-005's claims

PX-005's history is not rewritten; its record is corrected here and in `feature-ledger.px005-g01.json` (SRUI-PX005G01-005):

- "Exact" in PX-005 — the commit subject's "exact bytes" and SRUI-PX005-001's "exact u64 byte count" — is true of how the count is stored and converted (an integer product, no `f64`). The count it converted, `stat` field 24, was the kernel's approximate `get_mm_rss` on every kernel since 6.2, so the published bytes were not an exact measurement there.
- PX-005 described `stat`'s `rss`, `statm`'s `resident` and `status`'s `VmRSS` as "the same inaccurate number". That holds before 6.16 and the stable backports; from 6.16 `statm` and `status` are exact and only `stat` is not.
- SRUI-PX005-002's interface, `/proc/<pid>/stat` field 24, is superseded by `/proc/<pid>/statm` field 2.
- PX-005's live cross-check ("equalled `VmRSS` to the byte") compared two reads of the same approximate counter on 6.10. It verified the page-size conversion, not exactness. On 6.16 or later `stat` field 24 and `VmRSS` can differ; `statm` and `VmRSS` cannot, since both now use `get_mm_counter_sum`.

## Limitations

- No kernel at or after 6.16 was available, so the exact regime is established from the kernel sources above, not observed. The live run is 6.10, where `statm` and `stat` read the same approximate counter; the change is never worse there, and the README states the bound.
- On 6.2 up to the fix (6.16, or 6.15.7 / 6.12.39 / 6.6.99 on those stable lines; distribution kernels may carry it under other version numbers) the value is still approximate: each of the three counters can be off, either way, by up to `max(32, 2 × online CPUs)` pages per online CPU, and a fresh or very small process can show `0 B`. The collector cannot tell which regime it is in without branching on the kernel version, which this ticket rules out.
- The pin is Linux-only. A Linux reader whose own `/proc` is missing or unusable reads by name and keeps the theoretical reuse window described above; nothing reports that it did. Fixture tests on macOS exercise the by-name path and the pinned path is exercised on Linux, but the Linux fallback itself has no automated test: the verification demonstrated it by hand, with the reader's own `/proc` covered by an empty tmpfs (`logs/foreign-mount.log`).
- Before 6.2 the value is approximate as well: each thread adds its cached counter changes in only after more than 64 page-fault events. There `statm`, `stat` and `status` read the same counters, so the change is never worse.
- A pinned read opens the record's directory for reading, where reading by name needed only search permission. Stock procfs (`/proc/<pid>` is `r-xr-xr-x`) is unaffected, but a search-only record directory, or a security policy that grants search and not read, now yields a record skipped as `Denied` and an incomplete scan where reading by name would have published it. The verification reproduced that (`logs/searchonly-dir.log`).

- The performance numbers come from a shared Docker Desktop VM under other load; they are relative evidence, not a budget.
