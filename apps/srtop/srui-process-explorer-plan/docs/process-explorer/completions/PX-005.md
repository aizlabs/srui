## Bounded behavior

The read-only collection gains one metric: resident memory, as a third column beside PID and name. Nothing else moved. No process is opened for control, no action handler exists, no sorting, no further memory field, no dependency, transport or unrelated example changed — and the collector still reads `/proc` through `std` alone, with no new crate.

### One metric, defined where it is produced

`apps/srtop/src/metric.rs` holds the definition and the only conversion. `RESIDENT_MEMORY` states the interface (`/proc/<pid>/stat` field 24, `rss`, in pages, times the page size the scanned mount reports), the unit of the stored value (`bytes`), and what the number does *not* account for: shared pages counted in full for every process that maps them, so these values do not sum to a host's used memory; swapped-out and never-faulted pages not counted at all; and the kernel's own caveat that `stat`'s `rss`, `statm`'s `resident` and `status`'s `VmRSS` are the same inaccurate number. Proportional accounting is PX-046's, and is not claimed here. The column heading is taken from the definition rather than written out again, so a column cannot be labelled as something other than what was published into it.

Interpretation stays server-side: the client renders the text this module produced and never scales a unit or decides what an absent value means, so no process-specific client policy was added.

### Bytes stay integers

`ProcessRecord::resident` is an `Observed<u64>` of **bytes**, never a formatted string, and the text is derived once, at projection. The conversion to IEC multiples is pure integer arithmetic — the whole part is a shift, the fraction an exact remainder scaled by ten before shifting back — so there is no `f64` anywhere in the path. That is not decoration: `u64::MAX` divided by 2^60 as a float rounds to `16.0`, and `u64::MAX / 2` to `8.0`, each publishing a value *larger* than the one measured, at a unit boundary it never reached. The formatter also **truncates** rather than rounds, so one byte below a mebibyte reads `1023.9 KiB` and never the `1024.0 KiB` that rounding produces.

The widest cell this app can publish is `"Unavailable"` at eleven bytes — wider than the widest number, `1023.9 PiB` — and that bound is asserted, then used by `refresh`'s widest-row fixture, so the §26 frame ceiling PX-004 proved is still measured against a row as wide as the real one. One consequence is recorded rather than hidden: a row is now 18 planned bytes wider, so the largest collection that fits a single catch-up snapshot frame is smaller, and the two "just inside the frame" tests moved from 27,000 rows to 26,000.

### Unavailable is not zero, and zero is not unavailable

Every cell carries its own availability. A resident value the scan could not read is published as `Unavailable`, or `Denied` when a permission refused it; a process that genuinely holds no resident pages stays `0 B`. The two are independent of the record's other fields: the fake fixture's third row has an unavailable PID beside a denied metric, and its second a readable PID beside a known zero.

A record whose metric is unreadable is still a record. Its identity and name are intact, so it is published with that one field reported unread, and `Completeness` — which answers whether the record *list* is authoritative — is deliberately **not** degraded by it. A per-field gap is reported in the field, visibly, in every affected row; it adds no clause to the status line, because "incomplete scan" is a claim about which processes exist.

### The page size belongs to the mount, not to this machine

Pages become bytes through `AT_PAGESZ` in the scanned root's own `self/auxv` — the interface `sysconf(_SC_PAGESIZE)` answers from, read through the injected root exactly as the hostname and boot identity already are. Reading it through the root rather than from the real `/proc` is what keeps the fixtures deterministic on any host: a canned tree states its own page size, so the same fixture publishes the same byte count on a 4 KiB Linux host and a 16 KiB macOS one. The fixtures state 8192 deliberately, which is neither platform's, so a conversion that silently borrowed the host's page size fails the suite.

The value is refused unless it is a power of two between 512 B and 1 GiB, and the multiplication is checked. A mount that cannot state a believable page size publishes every resident value as unread rather than attributing another kernel's page size to records never measured under it, and an absurd page count is reported unread rather than wrapped into a small confident number.

## Limitations

- Resident memory is the kernel's `rss`, which the kernel itself calls inaccurate: shared pages are counted in full for every mapper, so the column does not sum to a host's used memory. Proportional and shared-page accounting is PX-046.
- The page size is believed only when the scanned mount states one. A `/proc` bind-mounted from a kernel with a different page size than its own `self/auxv` reports would be converted with the reader's — same-kernel mounts cannot differ, and a cross-kernel mount is not a case this collector claims to support.
- The live acceptance is asserted with one-sided tolerances (growth at least what was touched less 16 MiB; agreement with `VmRSS` within 32 MiB) and the measured numbers are printed as evidence, so a loaded host cannot turn a real regression into a pass.
- The live evidence is a Linux VM kernel on this machine, not the separate physical Linux host PX-003 and PX-004 used; that host was not reachable for this run. Both are real kernels with a real `/proc`, and page size 4096 was confirmed, but nothing here claims coverage of another architecture's page size.
- A row is 18 planned bytes wider, so the largest publishable collection is correspondingly smaller. The ceiling is unchanged; what it admits is not.
- No push, pull request, follow-on ticket, or self-declared independent verification. All logs stay outside every checkout.
