## Bounded behavior

The read-only collection gains one metric: sampled CPU usage, as a fourth column after PID, name and resident memory. Nothing else moved: no process is opened for control, no action handler, no sorting, no graph, no host-normalized display, no dependency, transport, protocol or unrelated example changed, and the collector still reads `/proc` through `std` alone. No shared protocol or runtime semantics were needed.

### The convention is in the heading

`metric::CPU_USAGE` defines the metric and labels the column `CPU (100% = 1 CPU)`: one fully used logical CPU is 100%, so a multithreaded process may exceed it — the convention S1 documents for `Process::cpu_usage` ("might be bigger than 100 if run on a multi-core machine"). A percentage normalized to the whole host is left for the later display option the ticket names. The heading is taken from the definition, as PX-005's is, so the column cannot be labelled as something other than what was published into it.

### Interfaces, verified for this kernel

| What | Interface | Reference |
| --- | --- | --- |
| CPU time | `/proc/<pid>/stat` field 14 `utime` + field 15 `stime`, clock ticks, "divide by `sysconf(_SC_CLK_TCK)`"; neither is a `[PT]` ptrace-gated field, so an unprivileged read is real, not the substituted 0 | `proc_pid_stat(5)`, man-pages 6.19 (2026-02-08), https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html; K1 |
| Tick rate | `AT_CLKTCK` (17) in the scanned mount's own `self/auxv`: "The frequency with which times(2) counts. This value can also be obtained via `sysconf(_SC_CLK_TCK)`" | `getauxval(3)`, man-pages 6.19, https://man7.org/linux/man-pages/man3/getauxval.3.html |
| Interval | `std::time::Instant` — `clock_gettime(CLOCK_MONOTONIC)` on UNIX, never goes backwards barring platform bugs; `checked_sub` is used so a violated monotonicity is detected rather than saturated | https://doc.rust-lang.org/std/time/struct.Instant.html ("Underlying System calls", "Monotonicity") |
| Convention | per-process share "might be bigger than 100 if run on a multi-core machine"; "a process needs to be refreshed twice" | S1, https://docs.rs/sysinfo/latest/sysinfo/struct.Process.html#method.cpu_usage |

The app does not depend on `sysinfo` (none is pinned in `apps/srtop/Cargo.lock`); S1 was consulted for the convention only. `CLOCK_MONOTONIC`, like `utime` and `stime`, does not advance across a suspend, so a suspend does not dilute an interval with time nobody could have been scheduled in. The tick rate is read through the scanned root exactly as PX-005 reads `AT_PAGESZ`: fixtures state their own rate deterministically, and a mount that states none publishes no CPU value rather than borrowing this machine's.

### A persistent collector, and process-instance identity

CPU usage is a difference between two samples, so `ProcFsSource` is the persistent collector: `main` already moves one instance into the refresh loop for its whole life (`refresh::poll` hands the same source to and back from `spawn_blocking`), and it now holds one `CpuBaseline` per record its previous scan published. The map is rebuilt from each scan's records, so it is bounded by the record bound and forgets every process that ended; a scan whose root listing failed read no counter and keeps the baselines as they were.

The key is the PID **and** the creation token (`/proc/<pid>/stat` field 22) — PX-003's process-instance identity, not a PID. A reused PID is a different key and warms up instead of subtracting the counters of the process it replaced. Start ticks are only comparable within one boot and PID namespace, so a boot ID or namespace that comes back *different* discards every baseline; one a scan merely could not read discards nothing (mirroring PX-004's session identity anchoring).

### Never zero, never a spike

`CpuUsage` is `Measured(CpuInterval)`, `WarmingUp` or `Missing(MissingReason)` — deliberately not an `Observed`, because "seen once" is neither a value nor unreadable.

| Case | Published | Baseline kept |
| --- | --- | --- |
| First sample of an instance (new process, reused PID) | `Warming up` | current |
| Counter went backwards (reset) | `Unavailable` | current |
| Monotonic interval zero | `Unavailable` | **previous**, so the next scan measures across both |
| Monotonic interval negative (injected clock only) | `Unavailable` | current |
| `utime`/`stime` absent, negative, non-numeric or overflowing | `Unavailable` | none (next readable sample warms up) |
| Tick rate absent, zero, > 1,000,000/s | `Unavailable` on every scan, not an endless warm-up | current |
| `self/auxv` unreadable | `Denied` | current |
| Delta implying > 65,536 logical CPUs, or an overflowing divisor | `Unavailable` | current |
| Real measurement of zero ticks | `0.0%` | current |

The percentage is `ticks × 10¹² / (rate × elapsed_ns)` tenths, in checked `u128` arithmetic, truncated — like PX-005, a value is never displayed as larger than it was measured. The widest CPU cell is `6553600.0%` (10 bytes) and `Warming up` is 10, both inside the existing `MAX_CELL_BYTES` = 11, which is asserted. A per-field CPU state never degrades `Completeness`.

### Frame ceiling

A row is one string cell wider, so `refresh`'s widest-row fixture now carries the widest metric cell in both metric columns, and the two "just inside the snapshot frame" tests moved from 26,000 rows to 25,000 — the ceiling working, not a regression. The ceiling itself is unchanged.

## Limitations

- **Pre-existing flake, not introduced here:** PX-005's `live::live_snapshot_locates_the_test_owned_sleeping_worker` sometimes reads `rss` = 0 for a `/bin/sleep` it has just spawned (`a running process holds resident pages`). On the unchanged base `3f1a9b5e`, running the `live::` module 20 times in the same container failed 3/20 (`linux-base-flake.log`); run alone it passed 20/20. On this branch it failed 1/8 module repeats and 1 of 2 full-suite runs. Not fixed here (PX-005's test, outside this ticket); it needs its own follow-up — most likely the kernel's lazily folded per-CPU RSS counters right after `execve`.
- No macOS process source exists (`--live-source` on macOS reports an incomplete scan, as before), so there is no macOS CPU interface to mirror; no macOS CPU value is claimed.
- Tick quantization (review round 1, W3): one tick is `100 / (CLK_TCK × interval)` percentage points. At `USER_HZ` 100 that is ≈ 1 point at the 1 s default (a busy thread read 99.3%–100.3%) but 20 points at the 50 ms minimum, where a fully busy thread honestly reads 80%, 100% or 120%. Documented and pinned by a test; not smoothed, and not capped at the host CPU count (see Review round 1).
- `utime + stime` only; waited-for children's `cutime`/`cstime` are excluded, as in `top`/`htop`'s per-process figure.
- A busy host updates every row whose share changed on every tick; this is the metric doing its job, not churn, and idle rows publish nothing.
- The live evidence is a Linux VM kernel on this Mac (aarch64, `USER_HZ` 100), not a separate physical host or another architecture's tick rate.
- No push, pull request, follow-on ticket, or self-declared independent verification. All logs stay outside every checkout.

## Later change (5 October 2026)

The CPU test's workers recorded above, the `/bin/sh` builtin loop and `/bin/sleep 47`, have been replaced by the one worker every live test now uses: the test binary itself, re-executed to run a single ignored test, which reports ready on its stdout only once a scan can see it (branch `codex/srtop-live-worker-ready`, PR #77). `Worker::burn()` starts it in a mode that, after reporting ready, spins one thread while libtest's main thread only waits, within the same 60 s lifetime and parent-exit bounds as the sleeping worker `Worker::start()` starts; its setup happens before it reports ready, outside the sampled interval. The PX-005 flake listed under Limitations was that sleeping worker's readiness race. The evidence above was recorded with the old workers.

The same test no longer asserts the 30.0%–115.0% band and the 5.0% cap. Its floor assumed the scheduler gives the burner at least 30% of a CPU, which a loaded host does not owe it: under 16 busy loops on 12 CPUs the burner read 28.9% once in 40 runs on this branch, and once in 20 on `main` with the old `/bin/sh` burner. Instead the test reads each worker's own `utime + stime` and an `Instant` just before and just after each scan, and requires the published share to lie between the smallest tick delta over the longest interval and the largest delta over the shortest, less the 0.1 point srtop truncates, at the `AT_CLKTCK` rate srtop also reads. That holds whatever share the burner is given, and the burner must still have used more CPU than the sleeper.
