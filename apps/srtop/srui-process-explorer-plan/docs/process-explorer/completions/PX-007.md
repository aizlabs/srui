## Bounded behavior

The shell gains a system summary and a data-freshness indicator between the status line and the process table. Nothing else moved: the table, its columns and cells, retention, the record bounds, the CPU and resident-memory metrics, the protocol, the runtime, the SDK, the generic renderer and the client are unchanged; no dependency was added (`apps/srtop/Cargo.lock` is untouched) and the collector still reads `/proc` through `std` alone. The only change outside `apps/srtop` is the native test, `client-macos/Tests/SRUITests/ProcessExplorerShellTests.swift` (expectations only). No process is opened for control and no action is installed.

### What the summary is

Fourteen nodes, all standard and all required tier (D1 §7.2, §7.3): a `Column` (node 6) holding three `Row`s of a `Progress` bar and its `Text` line — overall CPU (7–9), memory (10–12), swap (13–15) — and four `Text` lines: load average (16), uptime (17), processes (18) and freshness (19). The shell's own nodes 1–5 keep their IDs. There is no custom graph, image, resource or drawing instruction; the unchanged generic AppKit renderer shows them as `NSTextField` labels and `NSProgressIndicator` bars (D1 §22.4). Each bar comes first in its row, so the bars stay aligned whatever the lines say.

### Definitions, and where each is read

Every figure is read through the scanned root (`<root>/stat`, `<root>/meminfo`, `<root>/uptime`, `<root>/loadavg`), so a fixture tree states its own and is deterministic on any host; each file is read, and can fail, on its own. Every figure is stored as the exact integer the kernel wrote and turned into text once, on the server, in integer arithmetic, and each bar is filled to exactly the truncated share its line prints (`summary::Bar::tenths`). The definitions also live in `metric::SYSTEM_CPU`, `MEMORY_USED`, `SWAP_USED`, `UPTIME`, `LOAD_AVERAGE`, `PROCESS_COUNT` and `SAMPLE_TIME`, and in the README's "System summary" section.

| Figure | Interface and computation | Denominator, as published |
| --- | --- | --- |
| Overall CPU | `stat` first line (`cpu`), USER_HZ ticks summed over every CPU. Busy = `user + nice + system + irq + softirq + steal`; idle = `idle + iowait`; share = Δbusy / (Δbusy + Δidle) between two reads, truncated to a tenth. `guest`/`guest_nice` are already in `user`/`nice` and are not added again; fields after `steal` are not read. The `cpuN` lines that follow are counted as the logical CPUs online. | `Overall CPU (100% = all N logical CPUs)` — a share of all of them, never the column's `CPU (100% = 1 CPU)` |
| Memory | `meminfo` `MemTotal`, `MemAvailable` (kB = 1024 bytes). Used = `MemTotal − MemAvailable`. | `(x% of total)`, total = `MemTotal` |
| Swap | `meminfo` `SwapTotal`, `SwapFree`. Used = `SwapTotal − SwapFree`. `SwapTotal` 0 → `Swap: none configured`. | `(x% of total)`, total = `SwapTotal` |
| Load average | `loadavg` first three fields, exactly as printed (`%lu.%02lu`). Not a percentage, not divided by the CPU count. | none — not a share |
| Uptime | `uptime` first field (seconds on the boot-time clock), truncated to whole minutes. | none |
| Processes | The last successful scan's records, in the status line's counts and words (`listed`, `unreadable`, `beyond the record limit`, `complete`/`incomplete scan`); processes, never threads; `unfiltered`, since no filter exists yet. | none |
| Freshness | The collecting server's wall clock when the last successful scan began, UTC to the second, and that scan's `SourceId` (cut at 256 bytes). | none |

### Never zero, never stale as fresh

| State | Line | Bar |
| --- | --- | --- |
| Measured | the figure and its denominator | shown, at the truncated share |
| First read of this boot (CPU) | `Warming up` | hidden, no `VALUE` |
| Counters went backwards, did not advance, or another CPU count (CPU) | `Unavailable (no measurable interval since the previous sample)` | hidden, no `VALUE` |
| File refused | `Denied (reading <file> was refused)`, warning role | hidden, no `VALUE` |
| File unreadable | `Unavailable (<file> could not be read)`, warning role | hidden, no `VALUE` |
| File malformed, or values no kernel writes (`MemAvailable > MemTotal`, `MemTotal` 0, `SwapFree > SwapTotal`) | `Unavailable (<file> has no usable …)`, warning role | hidden, no `VALUE` |
| No swap (`SwapTotal` 0) | `Swap: none configured` | hidden, no `VALUE` — never 0% of 0, never a division |
| Nothing sampled yet | `<label>: Not sampled` | hidden, no `VALUE` |
| A measured zero (an idle host, unused swap) | `0.0%`, `0 B used` | shown, empty |

A bar without a value is hidden (`visibility = hidden`, which keeps its layout space) and its `VALUE` is cleared, because an empty bar reads as 0%. Parsing is strict: a `cpu` line needs at least eight plain counts and at most 64 fields and is refused whole otherwise; a `meminfo` field must be `<key>:`, spaces, a count and ` kB`; `uptime` and `loadavg` must be the kernel's exact formats. The `cpuN` lines are read one bounded line at a time and the read stops at the first other line, so the `intr` line is never read; more than 2 MiB of `cpuN` lines reports the count unknown (`all logical CPUs`) rather than the lines that fit. The CPU baseline is kept across an unreadable `stat` and discarded when the boot changes.

### Freshness, collector errors and transport loss

Every figure comes from the last successful sample: the last scan whose process list was read and accepted (`summary::Sample::of`). A scan that cannot list its processes, or whose snapshot this app rejects, publishes no figure from that scan: every figure stays as it was, and the freshness line becomes, in the warning role,

```
Collector error: could not list processes (permission denied) · last successful sample: 2027-01-15 08:00:02 UTC (server clock) · source: fake-process-sequence-v1
```

so stale figures are never presented as fresh. A file that fails alone, within a successful scan, marks only its own line. The table, status and summary stay usable; the next good scan replaces every figure at its own time; a collector that stays broken republishes nothing, because neither the error nor the last sample changed. A first scan that already fails shows `… · no successful sample yet · source: …` and no figure — what `--live-source` shows on macOS, which has no `/proc`.

No generic renderer behaviour derives a local age from a timestamp (the registry has no timestamp or duration value type), so the ticket's "otherwise" applies: the time itself is published, as UTC on the server's clock, and no client logic was added. Transport loss is the generic client's own indicator (`ConnectionManager`, "disconnected — resume will be attempted"); the app's text never claims transport status, and a server cannot publish anything while disconnected.

### Traffic and the snapshot frame

The summary is published with the shell in the start transaction (one `CREATE_NODE` per node, every property inline — exactly what a catch-up snapshot carries) and refreshed inside the existing refresh transactions (D1 §12.1) as scalar `SET_PROPERTY` on the properties a client would see change and no others (`summary::changes`); the one exception is a bar that loses its value, whose `VALUE` is cleared by a `CLEAR_PROPERTY`, a rare state change that §12.1 delivers on its own revision rather than coalesced. Status first, then the summary, then the row operations, so a failure explains itself even if a later batch does not commit. A source whose figures and sample time are constants — the fake source — publishes nothing once synchronized; PX-008's frozen-source gate is not implemented here, but `a_frozen_fake_source_publishes_nothing_after_its_first_transaction` already holds. A live host's freshness line changes once a second, so it publishes that one line on most ticks; the live sample time is taken on an injected `WallClock` (`SystemTime::now` in production), so fixture tests are deterministic.

The summary is charged a fixed `SUMMARY_RESERVE_BYTES` = 8 KiB against the catch-up snapshot, beside the shell's and the status's allowances, never its current length: lines are cut at `summary::MAX_SUMMARY_TEXT_BYTES` = 512 bytes (the widest line the builder can emit, with a 256-byte source identity, is asserted to fit uncut) and bar descriptions at 128. The widest possible summary — every line at its bound, every bar shown — is planned at 6,902 bytes and encodes, on the protocol's own encoder, to 4,771 (`the_summary_reserve_covers_the_widest_summary_on_the_real_encoder`); a session with the widest status, the widest summary and no row exports a fresh-client snapshot of 6,312 bytes against the 13,571 bytes of allowances (`the_shell_status_and_summary_fit_their_snapshot_allowances`). The row ceiling is therefore 8 KiB lower: about a dozen of the widest rows. `a_collection_just_inside_the_snapshot_frame_is_published_whole` still publishes 25,000 widest rows whole.

## Changed existing expectations

Each change follows from the summary being part of the shell, or from its sample time being on screen; none weakens what the test proved.

- **Node count 5 → 19** (`lib.rs` structure tests, `fake_source_test`, `refresh_test::assert_shell_intact`, five Linux live tests) and **the column's children** `[HEADING, STATUS, TABLE]` → `[HEADING, STATUS, SUMMARY, TABLE]`: the summary is fourteen nodes of the shell. `SHELL_NODE_COUNT` names the number; the empty-shell test asserts the summary's whole structure explicitly, and the no-action check now walks all 19 nodes.
- **Scripted step 1 now publishes one transaction** (`refresh_test::a_scripted_sequence_inserts_deletes_and_renames_without_rebuilding_the_tree`): it publishes exactly one operation, `SET_PROPERTY` of the freshness line's text with the new sample time, and still no row and no status. Later revisions shift by one, and step 2's transaction also carries that line.
- **Failed scan and recovery operations** (`a_failed_scan_keeps_every_row_and_says_so_and_recovery_converges`, `a_failed_scan_at_the_snapshot_ceiling_deletes_no_row_however_long_its_status`): the failure now publishes the status plus the freshness line's text and warning role (asserted exactly), and recovery costs three scalar properties — status, freshness text, freshness role — instead of one (asserted exactly). Both still publish no row operation.
- **`a_refresh_beyond_the_frame_bound_commits_as_frames_a_client_accepts`**: the second operation is no longer necessarily the first deletion, because the process count changed too and its `SET_PROPERTY` follows the status; the test now asserts the status leads, the scalar properties come next, and every deletion still precedes every insertion.
- **`the_first_publication_is_warming_up_and_a_refresh_publishes_the_measured_value`** (PX-006): its fixture source now stamps a fixed sample time through the injected `WallClock`. On the system clock two scans straddling a second would change the freshness line and flake its "nothing changed" assertion, which is about the CPU column.
- **Native: one five-tick cycle costs five transactions, not four** (`scriptedRefreshUpdatesTheSameNativeTableInPlace`). The repeated tick now shows its own sample time, so it publishes exactly that line; the test asserts the repeated tick's rows and status are unchanged and only its freshness line differs. Cycle starts are therefore detected as the first state of each run of the initial rows (the repeated tick is now its own recorded state), and `coversTwoScriptedCycles` waits for two of them. The recorder also compares the native summary lines with the client's model.
- Struct literals of `ProcessSnapshot` in `retention_test` and `refresh_test` gain `system: SystemSample::not_provided()`; `refresh::commit` takes one `Published` record instead of rows and status, and its two unit-test call sites follow.

## Limitations

- Overall CPU, memory and swap describe the kernel behind the scanned mount, not a container's cgroup: inside a container they are the VM's or host's figures (the live run publishes the Docker VM's 12 CPUs and 15.5 GiB). cgroup-scoped figures are not this ticket's.
- "Used memory" is one documented definition (`MemTotal − MemAvailable`); `MemFree`, buffers and caches are not shown separately, and swap used is `SwapTotal − SwapFree` without separating `SwapCached`.
- Overall CPU counts `steal` as busy, as time the host's CPUs were not idle; a reader who wants it apart has no separate figure yet. The tick quantization PX-006 documents applies too, though across all CPUs it is finer: one tick is `100 / (CLK_TCK × interval × CPUs)` points.
- The sample time is the server's wall clock; a client in another zone, or with a skewed clock, must do its own arithmetic to find the age. No age is displayed, because no generic facility derives one.
- `uptime` includes a time namespace's offset (`timens_add_boottime`), as the kernel reports it.
- A system file whose path is a FIFO stalls the scan in `open(2)`, as the record files already do (PX-005-G01's limitation); a kernel procfs has no FIFO there.
- The live evidence is one Linux VM kernel (6.10, aarch64, `USER_HZ` 100) on this Mac. No macOS source exists, so on macOS `--live-source` publishes the collector error and no figure.
- The screenshots render the progress bars and the table but not the labels' text (`cacheDisplay` of the content view); the native assertions read the controls directly. PX-008 owns the release screenshot.
- No push, pull request, follow-on ticket, or self-declared independent verification. All logs stay outside the repository.
