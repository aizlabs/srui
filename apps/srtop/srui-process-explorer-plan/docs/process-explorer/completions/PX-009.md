## Design

- **Reorder by documented operations, identity kept.** §13 has no model move and §8 offers insert/delete by item identity, so a row that changes place is `MODEL_DELETE` by its item ID and `MODEL_INSERT` of the same item ID, in the same transaction. No new item ID is ever minted to sort, and no `MODEL_UPDATE` is sent for a pure reorder. `MODEL_RESET_RANGE` was rejected: a permutation larger than one operation's item bound collides with the store's duplicate-ID check between ranges. No generic runtime facility was missing, so no prerequisite ticket was raised.
- **Selection.** The generic client's `TableCollectionAdapter` restores selection by item ID after each applied transaction, but `ControlFactory.refreshCollection` calls `deselectAll` on every update of a table whose selection mode is `none` (srtop's until now). The table therefore declares `selection_mode = Single`: a native, local selection (§22.5) that survives reorders. The server installs no selection handler; a `SELECTION_CHANGED` is validated and acknowledged with no effect (semantic selection is PX-013).
- **Stale results.** A click is applied synchronously in its `ACTIVATE` handler under the shared view's lock, so the acknowledgement's `revision_after_effect` already holds the new order and clicks apply strictly one at a time. The poll loop samples without the lock and sorts its target under the view's order when it publishes, so a scan begun before a click is published in the click's order. Event replay is answered from the session's dedupe record (§18.2).
- **Initial order.** Until the first click the collection keeps the source's order and PX-004's retained-row placement exactly; no button is marked. Under an active sort, a retained (unconfirmed) row sorts under the values it was last published with.

## Limitations

- Name order is by Unicode scalar value, case-sensitive; no locale collation.
- Clicks toggle relative to the order applied before them; there is no explicit ascending/descending control or generic sort-header event.
- A refresh under an active sort moves rows ahead of its deletions and insertions; a refresh too large for one transaction may still split its non-move operations (pre-existing PX-004 behaviour), but never a move.
- A store whose transactions hold a single operation cannot carry a move atomically; there each operation travels alone.
- Under an active sort, eviction of unconfirmed rows takes the trailing ones of the sorted order rather than the stalest.
- The selection is local presentation only; the server does not use it (PX-013).
- No Linux runtime run and no dev-box scenario in this ticket.
- Above the published-row ceiling (on the order of 100,000 rows, or one snapshot frame — about 25,000 of the widest rows), the published window is the leading rows of the active order. Under a CPU or resident sort it is therefore chosen by rank: a process whose rank crosses the window's edge leaves the collection and comes back as a new row with a new item ID, losing any selection on it (also in the README's Sorting section).

## Correction round 1

The independent verification of `130fdb58` failed it on two blocking findings (B1, B2) and two non-blocking ones (N3, N4); the report and probes are under `verify/` in the run directory. One commit on top fixes them and nothing else: `apps/srtop/src/refresh.rs`, `apps/srtop/tests/sort_test.rs`, the README's Sorting section and this note. Where this section and the text above differ, this section holds.

- **B1, clicks sorted by stale values.** A row's order values were recorded only when it was inserted. An in-place `MODEL_UPDATE` recorded the new cell but kept the old values, and a value that changed without changing its cell (bytes within one `KiB`) was not recorded at all. `set_sort` then ordered the rows by those old values. In a live session the first CPU click ordered by the all-missing values of the warming-up first sample until the next poll. Fix: `Effect::Update` records the row's order values with its value. After every refresh, committed, partly committed or with nothing to send, `refresh_sort_values` gives every published row the order values its target row holds: the latest sample's, or a retained row's last published ones. Order values never reach the wire, so this costs no transaction.
- **B2, the view's record diverged from the store.** `record_committed` merged every run of consecutive inserts into one `insert_run`, which assumes indices that ascend past the rows inserted before them. Under a sort, a move's reinsertion at a high index can be followed in the same transaction by an arrival at a lower index. The store applied both correctly; the view recorded `[2,3,1,4]` against a store holding `[4,2,3,1]`. Fix: a run is merged only while each index is at least the previous index plus its row count. An insertion below that starts a new run, applied after the first, exactly as the store applied it.
- **N3, tests.** In `tests/sort_test.rs`:
  - `a_click_after_an_in_place_update_sorts_by_current_values`: CPU warming up and then measured at 10% and 90%; resident 1,024 B and then 1,100 B, both shown as `1.0 KiB`.
  - `a_move_and_an_arrival_in_one_refresh_keep_the_view_equal_to_the_store`: the verifier's `[4,2,3,1]` case, then a refresh with nothing to do.
  - `a_random_walk_of_samples_and_clicks_keeps_the_view_equal_to_the_store_and_sorted`: a fixed-seed LCG, 400 steps over 8 processes with tied names and memory, every missing state and random clicks. After every step it asserts that the view's item IDs equal the store's, that the published rows are exactly the sample's, and that they are in the active order computed by a test-local comparator.

  Against the unfixed `refresh.rs` (from `130fdb58`), 3 of the 12 tests fail. With only B1 reverted, the click test and the random walk fail. With only B2 reverted, the move-and-arrival test and the random walk fail. Files restored, SHA-256 checked.
- **N4.** The rank-based window above the row ceiling is now listed under Limitations and in the README.
