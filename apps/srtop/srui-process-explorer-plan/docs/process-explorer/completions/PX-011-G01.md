## Design reading and the chosen semantics

- §6.3: presentation state is local "unless explicitly promoted to semantic state". §7.6 and §22.5: List/Table/Tree selection highlight is local and the client sends `SELECTION_CHANGED`. §7.4 lists `selected` under common state and `value` under content. §8: collections are models of stable item IDs, partially replicated, filled by asynchronous range requests and server-pushed ranges. §22.7: scrolling stays local. §22.8: native accessibility for standard controls. §26: decode limits. §32: conformance suites. Nothing in these sections forbids a server-owned selection, so the build did not need to contradict the design.
- **Property.** The promoted selection is the standard `value` property (registry id 13, value type `value`, "Current value of an input or control") of a `List`, `Table` or `Tree`, holding `Value::ItemId` (wire `Value.item_id_value`, field 8). Absent `value` means no promotion. No new property, operation or enum value; no `protocol/registry.yaml`/`srui.proto` change, so no codegen and no registry-count change.
- **Why not property 10 `selected`.** On the collection node it is a `bool` and cannot name an item. Per item (`ModelItem.properties`) it fails three acceptance items: a client re-hydrating an evicted range cannot tell an old `selected=true` from a new promotion, so "reveal only when the promotion changes" breaks; apps re-emit sorted rows from their own data, silently dropping it, so "moving the item keeps the selection" breaks; and single-selection uniqueness would need a model scan. One `ItemId` on the node has none of these problems.
- **Store rules (Rust `SemanticStore` and Swift `SemanticStore`, identical, conformance vectors 50–53).** For a List/Table/Tree, `value` must be an `ItemId` (an integer, string, list or null is refused — a row index is never a selection), and it may be held only while `selection_mode` is `single` or `multiple`. The rule is evaluated on the resulting property set of `CREATE_NODE`, `SET_PROPERTY`, `CLEAR_PROPERTY` and `BATCH_PROPERTY_SET`, so setting `selection_mode` to `none` or clearing it while promoted is refused too. Error: `StoreError::InvalidCollectionSelection`, conformance code `invalid_collection_selection`; the whole transaction rolls back (§12.1). Item presence is deliberately **not** a store rule: a sparse replica may not cache the item, and a replica-side rejection would force resync loops.
- **Authoritative rules (SDK `UiTransaction::promote_selection`, `List/Table/Tree::promote_selection`).**
  - Unknown `ItemId` (not in the authoritative model): `StoreError::ItemNotFound`, nothing recorded, no row-index fallback.
  - `selection_mode` none or absent, non-collection node, or no `model_ref`: `StoreError::InvalidCollectionSelection`; missing node `NodeNotFound`; dangling `model_ref` `ModelNotFound`.
  - Success records a one-item `MODEL_RESET_RANGE` carrying the authoritative item at its index (the same commit type as range fulfilment and `push_visible_model_range`, §8, §12.1), then `SET_PROPERTY(value = ItemId)`. The promotion itself names only the `ItemId`; the index travels as ordinary model content so a replica that does not cache the target can place it.
  - `clear_promoted_selection` withdraws it (`CLEAR_PROPERTY value`); `promoted_selection` reads it.
  - **Deletion.** A `MODEL_DELETE` (by id or by range) that removes the promoted item clears the promotion in the same commit, unless the same transaction re-inserts that `ItemId` (a move under sorting). `settle_promoted_selections` runs on the SDK `Session::transaction`/`transaction_custom`, sessiond `transaction_with_result` and sessiond range commits. `MODEL_RESET_RANGE` never clears a promotion: a replaced window does not prove deletion.
- **Renderer rules (generic, every List/Table/Tree, no application path).**
  - A committed operation that sets or clears a collection's `value` is a promotion. It is applied after that commit's model refresh: it selects the item's native row (replacing any local selection, without emitting `SELECTION_CHANGED` — the server already knows), scrolls it into view once, refreshes row accessibility and posts `NSAccessibility.Notification.selectedRowsChanged` (§22.8). Promoting the same `ItemId` again is a new promotion and reveals again. Withdrawal clears the native selection.
  - `ItemId` absent from the replica (unknown, deleted, or outside the cached range): the selection is cleared and **no row index is guessed**; the promotion waits, and is applied and revealed when the item arrives through the range machinery (`MODEL_RESET_RANGE` from the SDK promotion, a range fulfilment, or any later commit). After the reveal, the neighbouring rows of the new viewport are requested through ordinary `ClientModelRangeRequest`s. A user click cancels a waiting promotion.
  - Local selection after a promotion stays local, emits `SELECTION_CHANGED`, and is not overwritten by unrelated commits — including structural remounts, because the renderer now remembers a collection's local selection across remounts.
  - Reveal only on change: commits without an operation on `value` never select or scroll. A remount (structural commit, resync, reconnect) restores the selection from semantic state and reveals only when the promotion differs from the one this renderer last applied; a fresh renderer (reconnect/new client) therefore reveals it.
  - `selection_mode` none: the adapter ignores a promotion (defence in depth; the store already refuses the state).
  - `multiple` mode: the promotion replaces the whole native selection with that one item.
- **§26.** No new decode path: `Value.item_id_value` already decodes on both sides under the existing frame, depth, string and item limits, so no new negative vector is required. The SDK promotion adds one item and two operations to a transaction and is bounded by `max_transaction_operations` like any other operation.

## Limitations

- One promoted `ItemId` per collection. `multiple` mode accepts it but a promotion cannot name several items.
- Inline (`items`-property) collections carry no ItemIds, so a promotion on them never resolves to a row and leaves no selection.
- Model-backed trees are flat in this client, so reveal never needs to expand ancestors; hierarchical disclosure is not addressed.
- A promotion waiting for an uncached item is cancelled by a user click but not by user scrolling; if the item arrives later it is selected and revealed then. The SDK path always sends the item with the promotion, so this window only exists for raw `SET_PROPERTY` promotions or a replica that evicts the item within the same commit.
- Deletion settlement covers `MODEL_DELETE` in SDK and sessiond commit paths. A promotion naming an item that disappears through `MODEL_RESET_RANGE`, or one committed through a hand-built `UiTransaction` that skips `settle_promoted_selections`, stays semantically set; the renderer then shows no selection rather than guessing.
- The deletion tracker scans the node graph once per transaction that deletes model items (`lc-debt` in `sdk/src/selection.rs`).
- The native tests run offscreen in the test process (no SSH, no `srtop`); PX-011 must add its own live end-to-end evidence when it adopts the API.
- Independent verification is pending.
