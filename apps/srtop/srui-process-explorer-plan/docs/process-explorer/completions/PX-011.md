## Behaviour when matches change or a PID is no longer visible

- Every publication that changes the rows (refresh, sort, filter) re-counts the matches and the target's position against the rows the client is about to hold.
- A target that stops being published (process ended, filter hid it, row ceiling dropped it) is reported as `PID p · name is no longer shown; the search moved to no other process`. Previous and Next continue from the place it last held.
- If the same item ID is published again (for example, the filter is cleared), the target is that same process instance again. That is not a retarget.
- A reused PID is a new `ProcessKey` and so a new `ItemId`. A refresh never moves the target to it. The status adds `a different process now has PID p: Go to PID selects it`, and only an explicit new search (Go to PID, a new query, Next or Previous) selects it.
- An unresolved Go to PID re-explains itself on every publication: no shown process, not shown (filtered out or beyond the row limit), shown only from an earlier scan, or `was not shown when searched and is now: Go to PID selects it`. It never selects on its own.

## Limitations

- First-candidate limitation, resolved in round 1: native selection and reveal needed a generic facility, which PX-011-G01 now provides. The round-1 bullets below are the current limitations.
- A row hidden and later shown again (for example, by clearing the filter) is the same target, but its promotion was cleared with it and is not re-promoted automatically. The status shows the match again; only an explicit search selects the row again.
- Search does not read the user's native selection. Next and Previous start from the server's current match, not from a row the user clicked, because the server receives no table `SELECTION_CHANGED` handler (the PX-008 audit refuses one).
- After a malformed PID the last unresolved Go to PID result stays on the status beside `PID field: digits only`, until the next explicit search.
- Matching cost is one linear pass over the server-side collection per publication while a query is active (the same order of cost as the filter). When search is idle, the fast path does nothing.

### B1: the native table selects and reveals the current match

- `apps/srtop/src/refresh.rs`:
  - New `Effect::Promote(Box<Row>)`. `commit` records it through `UiTransaction::promote_selection(TABLE, item_id)`, which records a one-item `MODEL_RESET_RANGE` carrying the row followed by `SET_PROPERTY(value = ItemId)`.
  - Every srtop commit already goes through `Session::transaction`, which runs `settle_promoted_selections`.
  - After each committed transaction, `ProcessView.promoted` is read back from the store, so a promotion that settlement cleared is recorded as cleared.
  - `ProcessView::promotion` plans the promotion for the row an explicit search just selected. `promoted_selection()` exposes the record.
- `apps/srtop/src/search.rs`: `set_query`, `step` and `go_to_pid` return the item they selected, or `None` when they selected nothing.
- **Budgets.**
  - A promotion weighs two operations in `commit`'s chunking (`Planned::operations`). Its planned bytes include the second operation and the carried row; the encoded transaction is asserted not to exceed them.
  - While a promotion is held, the row-mutating paths (`apply`, `set_sort`, `commit_filter`, `publish_layout`) plan with `planning_limits`: `max_transaction_operations - 1` operations and `MAX_TRANSACTION_PAYLOAD_BYTES - PROMOTION_CLEAR_BYTES` bytes. The `CLEAR_PROPERTY` that settlement adds when a commit removes the promoted row therefore still fits.
  - The table's promoted `value` in the catch-up snapshot is covered by `SEARCH_RESERVE_BYTES`. The ceiling test now promotes a row before checking that the widest snapshot fits one frame.

### Promotion semantics

| Event | Promotion |
| --- | --- |
| New query with a match, Next, Previous, successful Go to PID | Promoted to the selected match's `ItemId`. The client selects the row, replacing any local selection, and scrolls it into view. Promoting the item already promoted is a new promotion and reveals it again. |
| A search that selects nothing (no match, empty query, missing, hidden, retained-only or malformed PID) | Unchanged. The native selection stays where it was; the status explains. |
| Refresh or sort that moves the row | Kept on its `ItemId`: a move is a delete and re-insert of the same item in one transaction, which settlement keeps. |
| Match no longer shown because the filter hid it or the row limit dropped it | Cleared by the SDK's settlement in the same commit that deletes the row. srtop does not withdraw it separately; it reads the result back from the store. |
| Process exits | Cleared by settlement in the same commit that deletes its row. |
| Row shown again (for example, the filter is cleared) | Not re-promoted automatically. The search target is the same instance and the status shows it, but only an explicit search selects the row again. |
| Reused PID | A new process instance has a new `ItemId`, so it never inherits the promotion. The old one is cleared with its row, and only an explicit search promotes the new one. |
| User clicks another row | The click stays local (PX-011-G01): a later commit that promotes nothing keeps it. Next/Previous continue from the server's current match, not from the clicked row. srtop installs no `SELECTION_CHANGED` handler. |

### Round 1 limitations

- With `max_transaction_operations` at 1, no transaction can hold both a row deletion and settlement's `CLEAR_PROPERTY`. `planning_limits` keeps at least one operation, so a refresh that removes the promoted row would be refused under that limit. The default limit is 10,000.
- The reserve depends on the view's record of the promotion, which is read back from the store after every srtop commit. A promotion made by another writer to the same session would not be seen until srtop's next commit. srtop is the only writer of its session.
