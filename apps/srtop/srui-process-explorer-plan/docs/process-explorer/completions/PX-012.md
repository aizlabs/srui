### Scope broadening

srtop's PX-008 audit refuses `unsafe`, `extern` and `libc` in srtop's own sources and admits only tokio and the SRUI runtime crates as dependencies. An NSS-aware name lookup therefore cannot live in srtop. It was added to the existing runtime crate `srui-unix-security` (already a normal dependency of srtop, already `libc`-based, and already the home of the effective-UID helper). It is a read-only OS query, not SRUI semantics, so no protocol facility was needed. That crate was therefore added to the verification profile: its `cargo test`, `clippy -D warnings` and `fmt --check`, on macOS and Linux.

## Semantics

| Choice | Rows kept |
| --- | --- |
| All visible users (default; empty user field) | every row: every process the daemon's own OS account can enumerate. Not a promise to bypass host permissions: what `hidepid` or a PID namespace hides is not in the collection at all. |
| Only my processes | rows whose owner is the daemon's effective UID, as the source states it (`effective_uid()` for the live source, a constant for a fixture). A source that states none keeps nothing and says so. |
| Digits in the user field | rows owned by exactly that UID, whether or not an account names it. |
| Any other text | rows whose owner UID the cache resolved to exactly that name. Several UIDs sharing the name are all kept and listed. Owners whose names are still pending, timed out or failed are hidden and counted. |

- **Combination.** A row is shown when the user filter, the PID set and the text filter (PX-010) all keep it, and then only within the published-row ceiling. The user-filter status counts what all of them keep. An empty result names what each active filter keeps alone, for example `no process of 6 matches every filter: the user filter alone keeps 2, the PID set alone keeps 2, the text filter alone keeps 1`.
- **Search (PX-011).** Search still counts matches over the whole collection; the ones these filters hide are "not shown (filtered out or beyond the row limit)". A filter that hides the promoted match removes its row, and PX-011-G01 settlement clears the promotion in that same commit. This is tested: exactly one transaction carries the `CLEAR_PROPERTY`, and it is the one with the `MODEL_DELETE`. The search target keeps its `ItemId` and reports "no longer shown".
- **Unreadable owners.** An owner that is unreadable or denied is `Observed::Missing`, never UID 0. A specific filter hides it, and the status says `N processes with an unreadable owner hidden`.
- **Identity.** Changing any filter never mints an item ID. Every row keeps its `ItemId` hidden or shown, and the collection's identity allocator keeps every unfiltered row. A refresh under an unchanged filter publishes nothing.
- **When a delayed name arrives.** Publication never waits for the worker. A name answered later changes the status (and a name filter's rows) at the next publication, at the latest on the next refresh tick.

## Limitations

- **No owner column.** The owner is a filter input, not a displayed field. A User column is catalogue work for a later ticket (PX-043 owns process fields).
- **One worker thread.** Name lookup has one worker. A lookup that never returns, such as a hung NSS backend, holds that thread for the daemon's life. Every later name then times out, while UIDs still filter immediately. At most 64 further questions queue behind it.
- **Name filters need forward lookups.** A name filter asks the cache about every distinct owner in the collection: UID to name, not `getpwnam_r`. A host with more than 1024 distinct owners cycles the cache (`lc-debt` in `owner.rs`). A name filter cannot select an account that owns no visible process, which is a correct empty result.
- **Name changes.** Names are re-asked only after 10 minutes, so a renamed account keeps its old name until then. The UID is unaffected.
- **Effective UID.** The owner is the effective UID, as `ps -o user` and `top` show it. Real-UID selection (`ps -U`) is not offered.
- **PID sets select by number.** On every scan, so a reused PID's new process matches the set. Identity is still the `ItemId`, and the old instance's row is deleted as it ends.
- **Pinning is Linux-only.** Read by name (non-Linux, a tree that is not a kernel procfs), `status` has the same no-pinning caveat as `statm`.
- **The macOS fixture is not the host.** The fake source's account (UID 1000, `alice`) is a fixture constant, not the Mac user running the test.

### F1: a sort keeps the table, the filters and the search in agreement

- **Defect.** `set_sort` resolved every filter again (`visible()`) but published only moves (`plan_moves`). An account name that resolved after a name filter was applied, and before the next refresh, changed the filter's result: the target held rows the table did not, a `debug_assert_eq!` tripped in debug builds, and a release build kept the old rows while the search was counted against the new ones. A different leading window under the published-row ceiling in the new order had the same shape.
- **Fix (full publication path).** `set_sort` now sorts the server-side collection, plans the sort-button labels, and hands them to `republish()` — the path filter, user-filter and PID-set edits already take. Rows that stay are moved under their own item IDs, rows that joined or left are inserted or deleted, and the filter status, user-filter status, summary match count and search are planned against exactly those rows, in one plan. The moves-only assertion is gone because a sort may now change membership. The doc comment of `set_sort` states this.
- **Other non-refresh paths checked.** Column layout (`publish_layout`) re-lays out `self.rows` and resolves no filter. Search (`set_search`, `step_search`, `go_to_pid`, `set_pid_input`) reads `self.rows` and resolves no filter. Filter, user-field, button and PID-set edits already use `republish()`. `publish_status_only` resolves no filter. `set_sort` was the only path that resolved the filters and published a partial plan.
- **Test.** `owner_test::a_sort_after_a_name_resolves_publishes_the_new_membership_with_its_statuses` uses a gated resolver. It applies the name filter `alice` while the lookup hangs (nothing shown, "not resolved yet"), releases the lookup, waits for the cache, and clicks the PID sort with no refresh in between. Afterwards the table holds exactly PIDs 100 and 101 under their original item IDs, the view records the same rows, the user-filter status says `name "alice", UID 1000 · 2 of 6`, and the search status counts `in 2 shown rows` and matches the view's record. It runs in a debug build.

### F2: a bounded field is never cut into a different PID or UID

- **Defect.** `PidSet::parse` cut the text at 512 bytes and then tokenized it, so 510 spaces and `4102` read as PID 41. The same cut-then-parse pattern was in the user field (`OwnerFilter::set_input`, 64 bytes: 60 spaces and `10001` read as UID 1000) and in PX-011's search PID field (`Search::set_pid_input`, 32 bytes: 30 spaces and `4102` read as PID 41).
- **Fix.** `owner::whole_entries(text, limit, separator)` keeps text within the bound whole. Past the bound it cuts on a character boundary and then back to the last separator, dropping the entry the bound cut through, and reports the cut.
  - PID set: a cut set is active and keeps only its whole PIDs, possibly none, never everything. The status adds `text past 512 bytes ignored, with any entry the bound cut through`, and the field keeps only the whole entries.
  - User field: text past 64 bytes is `OwnerChoice::TooLong`. It keeps nothing and says `the user field is longer than 64 bytes, so it names no UID or account; shorten it`. `OwnerChoice::parse` refuses overlong text itself as well.
  - Search PID field: text past 32 bytes names no PID. Go to PID is disabled and the status says `PID field: longer than 32 bytes, not a PID`.
- **Other bounded inputs checked.** The text filter and the search query (512 bytes, PX-010 grammar) are cut before parsing, but a cut term is a prefix of what was typed, matched as a substring, and the status already says `query bounded`.
