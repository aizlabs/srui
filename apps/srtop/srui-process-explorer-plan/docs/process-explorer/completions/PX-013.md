## Bounded change

- `apps/srtop/src/inspector.rs` (new):
  - `SelectionGeneration`: monotonic, advanced by every accepted selection and every refusal.
  - `ProcessState` (one printable ASCII code, named as `proc_pid_stat(5)` documents, otherwise "unrecognized state"), `StartTime` (time after boot and, where the boot time is known, the wall-clock time), `ProcessDetails` (state, parent, start, each `Observed`), `DetailRead` (`Read`, `Ended`, `Unreadable(reason)`), the `DetailSource` trait and `FixtureDetails`.
  - `DetailReads`: one worker thread (`srtop-inspector`) and a one-slot mailbox. At most one read runs and at most one waits; a newer request replaces the waiting one (counted as superseded). A panicking read is an unreadable record. Dropping it closes the mailbox; the worker ends after its current read. `DetailReadsIdle` observes it for tests.
  - `Inspector`: the current selection (`None`, `Refused(item)` or one process with its row, generation and details), `select`, `refuse`, `reread`, `completed` (accepts a result only if its `ProcessKey` and generation are the current target's, and counts every dropped one), and `view`, which renders the four lines, each bounded to `MAX_INSPECTOR_LINE_BYTES` = 1024 bytes plus the cut mark.
- `apps/srtop/src/procfs.rs`:
  - `StatFields` gains `state` (field 3) and `parent` (field 4), parsed after the last `)` like every other field. A state that is not exactly one printable character, or a parent that is not a plain count within `u32`, is `Observed::Missing`, never 0.
  - `ProcFsDetails` (`ProcFsSource::details_reader`, `ProcessSource::details`): reads only a key this source minted, with a known PID and a `LinuxBootTicks` token. It opens `/proc/<pid>` through `RecordDir` (pinned where the reader can pin it, PX-005-G01), reads `stat` through it, and accepts the line only if its start time equals the key's token; otherwise, or if the record is gone, the instance has ended. A refused read is `Unreadable(Denied)`.
  - The start time is derived from the key's own token: `StartTime::from_ticks(start_ticks, AT_CLKTCK, btime)`. The tick rate is the mount's own `self/auxv` `AT_CLKTCK` (`read_auxv_entry`, now shared with the scan). `read_boot_time` reads exactly one `btime` line from the root `stat`, line by line through a bound, examining at most 64 bytes of each line, so a long `intr` line is skipped.
- `apps/srtop/src/source.rs`: `ProcessSource::details()` (default: none). `FakeProcessSource` and `ScriptedFakeSource` state constant details; `FIXTURE_BOOT_TIME`.

## Selection and promotion rules

| Input | Inspector |
| --- | --- |
| `SELECTION_CHANGED` on `TABLE` naming the `ItemId` of a published row | That row's process instance becomes the target, under a new generation. Name, PID, owner, CPU and RSS show at once from the server's row; `· loading details` until the worker answers. |
| `SELECTION_CHANGED` naming an item the server does not publish (unknown, ended, hidden by a filter, beyond the row limit) | Refused under a new generation: `Selected process: none · item N is not a row this server shows; nothing was read`. No detail read. |
| `SELECTION_CHANGED` without an `ItemId` argument (none, a number, a string) | Refused: `Selected process: none · the selection named no row; nothing was read`. No detail read. |
| A search promotion (new query, Next, Previous, Go to PID; PX-011, PX-011-G01) | The promoted row becomes the target under a new generation, exactly like a click. |
| A click after a promotion | The click wins: it is applied later. The promotion stays the server's (the click does not clear it), and the native highlight is the client's. |
| A promotion after a click | The promotion wins, as it does for the native highlight. |
| A filter hides the target (settlement clears its promotion in the same commit) | The same instance, `not shown (filtered out or beyond the row limit)`, with no details or metrics. Never another process. Shown again, it is described again. |
| A sort or refresh moves the row | Unchanged: the inspector follows the `ItemId`. |
| The row leaves the collection, or the detail reader finds the instance gone or another instance under its PID | `this process has ended; select another row`, with no details and no metrics. Not read again. A reused PID's new record is a new item, which the inspector never adopts. |
| The user clears the native selection | Nothing: the generic client sends no event for a cleared selection, so the inspector keeps its target. |

Every detail result is tagged with `(ProcessKey, SelectionGeneration)` and dropped unless both still name the current target.

## Limitations

- **One worker, no deadline.** Details are read by one thread. A read that never returns, such as a wedged procfs, holds that thread for the daemon's life, and every later selection then shows `loading details` while its name, PID, owner, CPU and RSS still show (`lc-debt` in `inspector.rs`). A `stat` read is not known to block in practice.
- **The inspector is the session's.** Every client attached to one srtop session shares it, like the filters and the sort. The last selection any client made is shown, and `client_instance_id` is not consulted.
- **A cleared native selection is not reported.** The generic client emits no event when the user deselects, so the inspector keeps describing its last target. Adding a deselection event would be a generic client and protocol change, not this ticket's.
- **Start time to the second.** `btime` is whole seconds, so the wall-clock start can be up to a second off what `ps` shows with more precision. The time after boot is exact to the tick.
- **Re-read on confirmed samples only.** State and parent are re-read on each refresh that confirmed the selected row; a row kept from an earlier scan keeps its last details and says `row kept from an earlier scan`.
- **No owner column, no advanced fields.** The inspector shows what the ticket names. Command line, threads and other fields are later tickets (PX-043 and on).
- **Pinning is Linux-only.** Read by name (non-Linux, or a tree that is not a kernel procfs), `stat` has the same caveat as in PX-005-G01; the start-time check still refuses a reused PID.

## Rebase onto the PX-012 review fix

PX-012's PR-review fix `61e2f6a2` landed on `909cac4a` after this ticket branched. It routes `set_sort` through the full `republish()` path, so a sort can change membership (a resolved account name, or a different leading window under the published-row ceiling), and adds `owner::whole_entries` so bounded fields are no longer cut before they are parsed. `git rebase --onto 61e2f6a2 909cac4a codex/PX-013-inspector` conflicted in one hunk of `apps/srtop/src/refresh.rs`, in `set_sort`.

- **Resolution.** The upstream side was kept: `set_sort` ends in `self.republish(session, plan)`. The PX-013 side was dropped: its own `plan_moves`, search and inspector effects and commit inside `set_sort`. Nothing was lost, because `republish()` already plans `inspector_effects(&target, &self.unfiltered_rows, &self.unconfirmed)` after the search effects, against exactly the rows it publishes. The comment in `set_sort` now says the inspector is re-planned there. The inspector follows its `ItemId` across a sort, and a row the sort's ceiling drops is shown as `not shown` for that same instance. No other file conflicted, and `whole_entries` needed no change here.
- **Reserves.** `INSPECTOR_RESERVE_BYTES` is unchanged, and the snapshot test still measures the inspector at its widest within it, beside PX-012's reserves. The fix changes no reserve. `republish()` plans with `planning_limits`, so a sort that deletes the promoted row still leaves room for settlement's `CLEAR_PROPERTY`. The inspector's effects are ordinary one-operation `SET_PROPERTY`s that `commit` chunks under `max_transaction_operations`.
- **New test.** `a_sort_that_drops_the_selected_row_under_the_ceiling_shows_it_as_not_shown` (see Tests). Mutation check: removing `inspector_effects` from `republish()` fails it and `the_inspector_follows_a_search_promotion_…` (`rebase/mutant-R1.log`). The file was restored byte-identically.
