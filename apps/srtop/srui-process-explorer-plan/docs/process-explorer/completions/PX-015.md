## Semantics

### Pause view

- **What it freezes.** The click is applied before its acknowledgement. It records `Frozen { revision: session.current_revision(), paused_at: now }`, advances the epoch and wakes the loop. Every row, cell and summary figure stays exactly what that revision holds.
- **What the pause commit carries.** It contains only the sampling status, the button label (`Resume view`), `SAMPLING_REFRESH.enabled = false`, the freshness line's label and the inspector's lines. It never touches a row.
- **What keeps running.** Core transaction application and the transport are untouched (§12.2: commits are state-consistency boundaries, not frames). Every other control keeps committing, a client keeps receiving, and a fresh client attaches to the frozen view through the normal snapshot.
- **Collection stops.** The loop polls no ticker while paused and takes no sample. A sample that still reaches the view is refused: one already running when the pause landed, or one passed to `ProcessView::apply` directly. It is counted in `Sampling::discarded`.
- **Status.** `Paused at 2026-11-08 07:14:33 UTC (server clock) · rows as of revision 2 · collection stopped: table and summary frozen; filters, sort, columns, search and the inspector act on the frozen rows · Resume view publishes a current sample, then every 300 ms` (native run).
- **Freshness (PX-007).** The line becomes `Paused, not live · Last successful sample: …`. It never implies live data.
- **Controls while paused.** Filter, user filter, PID set, sort, column chooser, search and Go to PID re-project the frozen collection (`unfiltered_rows`), and each publishes its own status. This is the chosen rule: re-project, not defer. Re-projection recomputes the processes line for the filter's match count, as PX-010 does, and keeps the paused label. Clearing a filter restores exactly the frozen rows.
- **Inspector while paused.** It shows frozen data only, never a live read beside frozen rows:
  - A row selected while paused is described from its frozen row. Its details and command line say `not read while the view is paused; Resume view reads them`.
  - A detail read (PX-013, PX-014) already running at the pause is dropped when it returns.
  - Details read before the pause stay shown.
- **Process-changing actions.** None exist. `ProcessView::frozen()` is the queryable state. Its documentation requires a future action to refuse every target while it is `Some`.

### Resume view

- **The click.** It clears `Frozen`, sets resuming, advances the epoch, asks for one sample now and restarts the ticker. The status is `Resuming · sampling now, then every N ms`, the freshness line is `Resuming, not yet refreshed · …`, and Refresh now is enabled again. A deferred inspector read is asked for at once.
- **The resume sample.** The loop takes one sample and publishes it through the ordinary `apply` diff, under the same PX-004/PX-010-G01 transaction, frame, row-ceiling and snapshot budgets as any refresh:
  - surviving rows keep their item IDs;
  - ended processes are deleted, and new ones are inserted;
  - the active sort and filters apply;
  - the status returns to `Live · sampling every N ms`.
- **No replay.** No sample missed while paused was taken, so none is replayed.
- **Stale scans.** A scan running across a pause and resume belongs to an earlier epoch and is discarded, so it never stands in for the resume sample.

### Interval

- **Valid values.** Whole milliseconds, ASCII digits only, from 50 to 300000 (`MIN_REFRESH_INTERVAL`..=`MAX_REFRESH_INTERVAL`, unchanged from PX-004). Surrounding spaces are ignored. The command line uses the same validator.
- **Applying.** `TEXT_EDIT` on the field only keeps the text, at most 32 bytes. Apply interval validates the kept text. This avoids applying the debounced intermediate values a typist produces.
- **Refusals.** These are refused, never rounded or clamped:
  - empty;
  - a sign;
  - a fraction;
  - a unit;
  - full-width digits;
  - fewer than 50 or more than 300000;
  - an overflow;
  - more than 32 bytes.

  The status explains the refusal and keeps the previous interval, for example `interval "fast" refused: not a whole number of milliseconds; enter 50 to 300000 ms; keeping 300 ms`. Editing the field clears the refusal.
- **Taking effect.** An accepted change sets `retime`. The loop replaces its one ticker with one whose first tick is one new interval after the change: no burst, and no drift from the old phase. Applying the current interval restarts nothing.
- **While paused.** An interval applied while paused takes effect on resume.
- **New nodes.** They are charged `SAMPLING_RESERVE_BYTES`, measured on the encoder at 1/2 to 1× of the reserve.

### Manual refresh

- **One sample.** Refresh now sets one coalesced request and wakes the loop. It takes one sample through the same `spawn_blocking` + `apply_sampled` path as a tick, then restarts the ticker, so the next periodic sample is one interval later. There is no new frame or protocol.
- **Coalescing.** Presses the loop has not taken yet are one sample. A press during a running scan gives at most one more.
- **While paused.** It is disabled. Event validation rejects the click, and the handler also refuses. A paused view is refreshed only by Resume view.

### Timers and shutdown

- **One timer.** The ticker is a local of `poll` and the only timer. Handlers start no timer or thread. Replacing the ticker drops the old one, so two never run.
- **Ending.** Cancelling the shutdown token ends `poll` in every sampling state (live, paused, resuming, retimed). The ticker and the `Notify` wait go with it, and nothing keeps the view alive afterwards (tested with a `Weak`).
- **Disconnect.** The ticker belongs to the session's refresh loop, not to a connection. A client disconnect ends only its own connection task (runtime `handle_connection`), as before. The pause and the interval are session state, like the filters, and a reattaching client sees the paused view. The binary test drives this through a real socket and then stops the instance with SIGTERM and SIGINT.

## Limitations

- **Collection stops; it does not continue.** This is the documented choice. A paused view therefore cannot report "N changes since pause" or compare the frozen and current views. Resume shows only the current state.
- **The inspector after resume.** A deferred read is asked for when Resume view is applied, which can be a few milliseconds before the resume sample lands. Briefly, live details may show beside rows that are still frozen. The status says `Resuming · sampling now` throughout that window.
- **Pause is the session's.** Like the filters and the sort, every client of one srtop session shares the pause, the interval and the refusal note.
- **A filter applied while paused recomputes the summary processes line without a collector error.** This is the pre-existing `summarize_with_matches` behavior of PX-010/PX-012. A pause itself never changes any figure: it relabels only the freshness line of the published summary.
- **Timer tests use real time** with wide margins (0 vs about 24 samples, 0 vs 1). They are not virtual-time tests; tokio's `test-util` is not a dependency.
- **No macOS live reader.** As in PX-013 and PX-014, the real-worker pause test runs on Linux only. The native macOS test uses the scripted source.
