## Why

PX-017 kept the followed process visible by re-promoting it through PX-011-G01's `value`. The server cannot see the client's newer local selection, so promote-backs overwrote rows the user had already left (a 20-press SSH burst ended 10 rows short; the PX-017 verifier reports in the PX-017 run directory `verification-result-pr-review.json` and `verification-result-withdraw.json` record the cascade, including the store-apply/render window in `SessionController`). `keep_visible` scrolls without ever touching selection, so after turn-on follow needs no promotion and that race has nothing left to overwrite.

## Design reading

§4 inv. 13 (optional semantics need a documented fallback), §6.3 (presentation state is local unless explicitly promoted; the server owns committed semantic state), §7.4 (common properties), §8 (collections of stable item IDs, partial replicas, asynchronous ranges, viewport hints never required for correctness), §12.1 (atomic commits), §22.5 and §22.7 (scrolling and selection highlight are local; uncached ranges load asynchronously), §26 (decode limits), §32 (conformance). Nothing contradicts a server-owned hint that scrolls once per set or move and never touches selection: it is the same one-shot reveal PX-011-G01 already uses, minus the selection.

## Semantics implemented

- **Property.** New standard property `keep_visible` (id 32 at this base; value type `value`, category `control_specific`), added through `protocol/registry.yaml` → `srui.proto` (`PROPERTY_KEEP_VISIBLE`) → `./protocol/generate_proto.sh`. Code refers to it only through generated constants (`PropertyRef::KEEP_VISIBLE`, `.keepVisible`). Property count 31 → 32 (`build.rs` assert, `semantic_types_test.rs`, `spec/registries.md`, `CLAUDE.md`).
- **Store rules (Rust `SemanticStore` and Swift `SemanticStore`, same order and messages).** The value must be an `ItemId`; it may be held only by a `List`, `Table` or `Tree` that has a `model_ref`. Evaluated on the resulting property set of `CREATE_NODE`, `SET_PROPERTY`, `CLEAR_PROPERTY` and `BATCH_PROPERTY_SET`, so clearing `model_ref` while the hint is held is refused (clear the hint first). Error `StoreError::InvalidKeepVisible` / `.invalidKeepVisible`, conformance code `invalid_keep_visible`; the whole transaction rolls back. Item presence is not a replica rule (sparse caches). Independent of `value` and `selection_mode` (admitted with `selection_mode` none).
- **Authoritative settlement (extends PX-011-G01's `sdk/src/selection.rs`).** `affects_promotions` also fires on `keep_visible`; the tracker records `(node, property)` assignments; `settle_promoted_selections` settles promotions and hints independently: an assignment naming an item the model does not hold → `ItemNotFound`, whole transaction discarded; an earlier hint whose item this commit removed (delete by id or range, range reset replacing it, positional update, `model_ref` change to a model without it) → `CLEAR_PROPERTY keep_visible` recorded in the same commit. A move under sorting keeps it. New `dangling_keep_visible` and `first_dangling_item`; sessiond `commit_transaction` refuses a pre-built commit that would leave a dangling promotion or hint. Runs on SDK `transaction`/`transaction_custom`, sessiond `transaction_with_result` and range fulfilment (`commit_ops_locked`).
- **SDK.** `UiTransaction::{set_keep_visible, clear_keep_visible, keep_visible}` (`sdk/src/keep_visible.rs`) and `List/Table/Tree::{set_keep_visible, clear_keep_visible, keep_visible}`; `KEEP_VISIBLE` constant. `set_keep_visible` records a one-item `MODEL_RESET_RANGE` carrying the authoritative item, then `SET_PROPERTY(keep_visible)`, so a sparse replica can place the row (same shape as `promote_selection`). Errors: `NodeNotFound`, `InvalidKeepVisible` (not a collection, no `model_ref`), `ModelNotFound`, `ItemNotFound`.
- **Client (generic, every List/Table/Tree).** `Collections/CollectionKeepVisible.swift` holds per-adapter state (`itemID`, `shownRow`). `TableCollectionAdapter.applyKeepVisible` and `OutlineCollectionAdapter.applyKeepVisible` reveal with `CollectionPromotion.reveal` (`scrollRowToVisible`, the minimum scroll) and touch nothing else. `RendererAppKit/CollectionKeepVisibleRendering.swift` routes from `ControlFactory`; `LayoutRenderer` computes `keepVisibleTargets` per transaction, skips the generic property path for it, and applies hints after the model refresh and after promotions, for every collection the commit refreshed or hinted; on mount/remount for every collection. Rules: a commit that sets it (even to the same item) reveals; a later commit reveals only if the item's row index changed from the last revealed one; an unchanged index never scrolls (a local pan persists); an uncached item, or one without a displayed row, scrolls nothing, requests nothing, and is revealed when it arrives at a row other than the last shown; clearing never scrolls; no selection change, no accessibility selection notification, no `SELECTION_CHANGED`, no change to the promotion memory. A remount builds fresh views whose viewport is at the origin, so the hinted row is revealed there once. Disclosure is never changed (model-backed trees are flat at this base).
- **Fallback.** A client without support ignores the property and keeps its viewport where the user put it (registry description, `spec/registries.md`).
- **§26.** No new decode path: `Value.item_id_value` already decodes under the existing frame, depth, string and item limits on both sides. The SDK set adds one item and two operations, bounded by `max_transaction_operations`.

## Limitations

- One hinted `ItemId` per collection.
- An item that is moved and returns to the same row index between two commits is not seen as moved; only the row index the renderer last revealed counts.
- While the user navigates, a commit that moves the hinted item scrolls to it. That is the property's meaning; the server retargets the hint when follow follows the user (PX-017's job).
- A remount reveals the hinted row in the rebuilt view even when it did not move, because a remount already resets every collection viewport to the origin.
- Model-backed trees are flat at this base. With hierarchical trees (PX-018-G01) an item without a displayed row is simply not scrolled to and no ancestor is expanded.
- Inline (`items`) collections carry no ItemIds and are refused by the store.
- Settlement shares PX-011-G01's O(nodes) scan per commit that touches a model, a promotion or a hint (`lc-debt` in `sdk/src/selection.rs`).
- The native tests run offscreen in the test process (no SSH, no `srtop`); PX-017 must add live end-to-end evidence when it adopts the property.
- Rebase onto PX-018-G01 will renumber the property (34) and the suite 1 vectors; code uses only the generated constants and names, and numbering lives in the vector file names, the manifest count and the suite README.
- Independent verification is pending.
