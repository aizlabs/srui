## Root cause (re-checked at the base)

- `client-macos/Collections/TableCollectionAdapter.swift` `tableViewSelectionDidChange` recorded the empty selection locally (`onLocalSelection(nodeID, [])`, which PX-011-G01 withdrawal relies on) and then returned at `guard selectedIDs.isEmpty == false else { return }`.
- `OutlineCollectionAdapter.outlineViewSelectionDidChange` looped over the selected items and sent nothing when there were none.
- `Event.selectionChanged`, `SemanticInteraction.selectionChanged`, `SemanticAction.selectionChanged`, `SessionController` and `EventOutbox` all carried exactly one `ItemId`.
- No document defined an empty selection. The design doc §7.6 gives `SELECTION_CHANGED(node_id, item_id, edit_seq)`, the registry entry for event 3 has no argument schema, and `spec/registries.md` mentioned `SELECTION_CHANGED` only in the promotion rules.
- Servers: `examples/ui-gallery` rejected an event with no item (`InvalidInput`). `examples/process-monitor` logged and ignored it, so its "Kill Selected" could still target a process the user had deselected. srtop's `selection_changed` already refused an itemless event (`select_item(None)`), which stopped follow and cleared the inspector, but under the "named no row" wording.

## Wire semantics (specified in `spec/registries.md` §4.2 and §4.4)

- **Cleared.** When a user action leaves a `List`, `Table` or `Tree` with no selected item, the client sends exactly one `SELECTION_CHANGED` with no `value` argument. It means "nothing is selected now". Examples of such actions: a click in empty space, Command-click on the only selected row, or an assistive-technology deselect. Servers treat it as clearing that client's selection, never as malformed.
- **Malformed.** A `value` that is present but is not an `ItemId` stays malformed, and is never read as a clear.
- **A collapse is not a deselection (fix round 1).** A user collapse of a `Tree` item that hides the selected rows sends `EXPANSION_CHANGED` only, never `SELECTION_CHANGED`. The server learns of it from that event; PX-018 mirrors the collapsed set on the server, clears the inspector without a `SELECTION_CHANGED` and keeps follow on with "hidden under collapsed …", which a client clear would contradict.
- **Server-caused deselection sends nothing.** Withdrawing a promotion, a commit that removes the selected row, a promotion waiting for an uncached item, and a restore on remount all change the selection without an event. A collection with `selection_mode` none sends neither form.
- **Multiple selection is unchanged.** It sends one event per selected item whenever the selection changes and at least one item stays selected. Which items were deselected is never reported, so a partial deselection in multiple mode has no event of its own.
- **Interaction with promotion (PX-011-G01).** A user deselect after a promotion is reported, and it makes the empty selection local. A later withdrawal leaves it alone and sends nothing, as before.
- **Compatibility.** Nothing changes in the registry, protobuf or framing: the cleared form is an `Event` with an empty `arguments` list, which every decoder already accepts. `generate_proto.sh` leaves no diff. The registry's event 3 description gained one sentence, and description text is not generated into any output.
  - An older server handles the new event exactly as it handled an itemless `SELECTION_CHANGED` before, and that varies: at the base, ui-gallery rejected it with `PolicyRejected`, process-monitor ignored it and kept the earlier selection, and srtop treated it as naming no row, which cleared the inspector and stopped follow.
  - An older client never sends the cleared form, so a server that relies on it still sees a stale selection from such a client.

## Implementation

- **Rust core and SDK.**
  - `semantic_tree::SelectionChange { Item(ItemId), Cleared }`.
  - `Event::selection_cleared(event_seq, event_id, observed_revision, node_id)` builds an event with no arguments.
  - `Event::selection_change()` returns `Some(Item)` for an `ItemId` value and `Some(Cleared)` for no value. It returns `None` for any other value type, or for any event that is not `SELECTION_CHANGED`.
  - Both are re-exported by `srui-sdk`, and the `SELECTION_CHANGED` constant's doc points to them.
  - The module doc lists the rule.
- **Swift.**
  - `Event.selectionCleared(...)`.
  - `SemanticInteraction.selectionCleared(nodeID:)`.
  - `SemanticAction.selectionCleared` (its event type is `EVENT_SELECTION_CHANGED`), plus `SemanticHandle.clearSelection()`.
  - `EventOutbox.sendSelectionCleared(...)`, which allocates, retains and replays the event like any other.
  - `SessionController` routes the native `.selectionCleared` through `enqueueNativeSemanticAction`. The private `sendSelectionChanged` takes `itemId: ItemId?`, where `nil` means the outbox's cleared send.
  - The `selection_mode` none refusal now keys on the event type, so it covers both forms.
- **Adapters.**
  - **Table.** `TableCollectionAdapter.onSelectionCleared` fires from `tableViewSelectionDidChange` when `selectedRowIndexes` is empty, after `onLocalSelection(nodeID, [])`.
  - **Outline.** `OutlineCollectionAdapter.onSelectionCleared` fires from `outlineViewSelectionDidChange` when the selection is empty.
  - **Tree collapse.** `setExpanded` never reports a clear, even when the collapse hides every selected row: it reports `EXPANSION_CHANGED` only (fix round 1 removed the first commit's collapse clear).
  - **Suppression.** Every server-driven path already runs under `isSuppressingSelectionEvents`: `update(rows:)`, `update(model:)`, `applyPromotion` and its withdrawal, the pending-promotion clear, `restoreLocalSelection`, and the disclosure reload. They report nothing.
  - **Wiring.** `ControlFactory` wires `onSelectionCleared` to `.selectionCleared` for List, Table and Tree.
- **Examples.**
  - **ui-gallery.** A cleared event forgets that collection's recorded selection and shows `List selection cleared · nothing is selected` (or the Table equivalent). A non-`ItemId` value is still rejected.
  - **process-monitor.** `MonitorState::clear_selection_for_client` removes only that client's entry, so "Kill Selected" answers `NoSelection` ("Select a process first").
  - Both keep accepting a bare unsigned integer as an item, as before.
  - **coding-agent-demo and counter.** Checked: the demo's single-selection list registers no `SELECTION_CHANGED` handler, and counter has no collection. Nothing changed.
- **srtop.**
  - `refresh::selection_changed` reads `selection_change()`. A cleared event goes to the new `ProcessView::clear_selection`, while an item, or a malformed value, keeps its `select_item` path.
  - **Inspector.** `Inspector::clear` advances the selection generation, so no earlier read can land, and reads nothing. It publishes `CLEARED_SELECTION_STATUS` ("Selected process: none · the selection was cleared; select a row to inspect it") and the "no process selected" command line.
  - **Follow.** `Follow::cleared` stops follow with `SELECTION_CLEARED_FOLLOW_STATUS` ("Follow stopped: the selection was cleared; select a row and turn follow on again"), and the shared `publish_selection` clears the hint. Turning follow on afterwards is refused with the existing "nothing is selected" reason.
  - The README's follow section says so.

## Limitations

- **Partial deselection in multiple mode** is not reported by design: the server learns the remaining items, not the removed ones. No in-repo server uses multiple selection today.
- **Older peers.** An older server handles a user deselect as it handled an itemless selection before, which varies by server (see Compatibility). An older client never sends the clear.
- **Tree collapse** that hides the selection is never reported as a clear; servers that care read `EXPANSION_CHANGED` (PX-018 does).
- **process-monitor.** An unknown or malformed selection is still ignored and keeps the earlier selection. That behaviour was unchanged by this ticket, but a later fix could treat it as a clear.
- **srtop tree view.** Not exercised over SSH, because it does not exist at this base.
