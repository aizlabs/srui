## Do the existing generic facilities suffice?

Yes. Before writing code, each thing follow needs was checked against what the base already provides.

- **Re-reveal on demand.** PX-011-G01 treats every committed operation on a collection's `value` as a new promotion, including a promotion of the same `ItemId` (`client-macos/RendererAppKit/CollectionSelectionPromotion.swift:40`, `let changed = explicit || memory.promoted != promoted`). The SDK records the `SET_PROPERTY` even when the value is unchanged (`server-rust/sdk/src/session.rs:337-341`). So srtop can ask for one more reveal by promoting the followed item again.
- **The reveal is minimal and one-shot.** It is `NSTableView.scrollRowToVisible` (`client-macos/Collections/CollectionPromotion.swift:28`): no scroll when the row is already visible, the least scroll otherwise. Nothing persists after it, so a later pan is the user's.
- **Ordinary selection preservation already exists and never scrolls.** `TableCollectionAdapter.update(model:modelID:tableView:)` re-selects the selected item IDs after every model refresh without scrolling (`client-macos/Collections/TableCollectionAdapter.swift:294`, `:326`). Follow therefore adds nothing to non-follow mode.
- **The server can tell an overridden click.** A promotion replaces the client's local selection (G01). Every event carries `observed_revision`, the revision the client held when it generated the event (`protocol/srui.proto:458`, design §7.7). A `SELECTION_CHANGED` observed before the latest promotion was therefore replaced by that promotion on the client, and the server can promote the user's row back. Follow never steals a selection for longer than one round trip.
- **What is not available, and is not needed for the chosen mode.** The server never learns of a manual scroll: scrolling is local (§22.5, §22.7), and a fully cached table sends no range request. So "a manual pan cancels follow" cannot be implemented without a new generic facility. This ticket lets the mode be chosen; the chosen mode (below) needs no such signal. No persistent "keep in view" hint is needed either: re-promotion only when the row moves gives the same effect with existing semantics.

Re-promoting is an honest use of G01: each promotion is the server's statement that this item is selected, and the client reveals it once, as specified. Follow promotes only when the followed row's index changes, never on an unchanged sample, so it does not fight a pan, and with follow off nothing is promoted.

## Follow semantics

- **Explicit setting.** A standard checkbox `Toggle` "Follow selected process" (node 68, shortcut `primary+shift+f`, ⇧⌘F) and a status `Text` (69) in a `Row` (67) between the column chooser and the table. It is off in the creating commit, and disabled with `Follow disabled: process collection not started` in the uncollected shell. Its `VALUE_CHANGED` boolean is the only thing read from the event.
- **Turning on** follows the process the inspector describes (the server's resolved selection) and promotes it at once, so it is revealed. Nothing selected, a selected process that is not shown, or one that has ended is refused, with its reason. The handler always publishes the toggle's value, so a refused request puts the client's checkbox back (§6.3).
- **Sticky follow.** While on, every plan that changes the rows (a sample, a sort, a filter) ends, after every row operation, with the followed item's promotion if and only if its row index changed since it was last shown. The status says `Following PID 6010 · tracked · row 56 of 60 · …`. The item ID never changes and no row is created.
- **Pan without changing the selection.** Scrolling is local, never changes the selection and never stops follow. The view stays where the user put it until the followed process changes row; then the client scrolls the least distance that shows it again. This is the mode the status and the toggle's description state.
- **Cancellation.**
  - The user turns the checkbox off (status back to `Follow: off · …`).
  - Selecting another shown row (click, arrow keys, or a search match) **retargets** follow to that row, without a promotion, because the client already shows it.
  - A `SELECTION_CHANGED` that names no shown row stops follow with its reason.
- **Filtering-out and disappearance.** Follow stops itself, turns the checkbox off and says why:
  - `Follow stopped: PID 6010 · tracked has ended · a new process that reuses its PID is not followed; select a row and turn follow on again`;
  - `Follow stopped: PID 6010 · tracked is no longer shown (filtered out or beyond the row limit); …`.

  It never moves to another row, and showing the row again does not restart it.
- **PID reuse.** The target is an item ID, which names one process instance (PX-003). A new process with the same PID has another item ID, so it is never followed, selected or revealed, whether it appears in the same sample as the exit or later.
- **A selection a promotion replaced.** While on, a `SELECTION_CHANGED` whose `observed_revision` is older than the latest committed promotion is promoted back, so the user's later choice wins. With follow off, nothing is promoted on a selection, as before.
- **Cross-view navigation.** srtop has one view, the process table. Follow is bound to it. PX-018 (tree view) must carry follow over or stop it explicitly; nothing here pretends to cover it.
- **Shared state.** Follow belongs to the session, like the filters and the inspector, so every client of one srtop sees the same setting and followed process.

## Limitations

- **A pan does not cancel follow.** The server cannot see a local scroll without a new generic facility. The chosen mode keeps the pan until the followed row moves, and says so in the status and the toggle's description.
- **Any row change triggers a reveal.** A followed row that shifts by one because a row above it left is revealed again. If it is already visible, `scrollRowToVisible` does not move.
- **A flash before an overridden click is restored.** A click that crosses a follow promotion in flight is replaced by it on the client for one round trip, and then promoted back.
- **Each reveal re-posts selection.** Each follow promotion re-selects the row without emitting `SELECTION_CHANGED`, and posts `selectedRowsChanged` (G01).
- **One shared follow per session.** Two clients of one srtop share one follow setting and one followed process, as they share the inspector.
- **The test pan is programmatic.** The native "pan" is `scrollRowToVisible` on the client's own table, not a trackpad gesture. Either way it is a local clip-view scroll the server never sees.
- **The test host never activates.** As in PX-016, the router's `isWindowKey` seam is set for the test window.
- Independent verification is pending.

## Rework on keep_visible (PX-017-G01)

- Base: `45586452fae9e91aa7adb1bb85edf93ed70e7c9c` (PX-017-G01 head; stacked on PX-018-G01 `2ff26c9a` and the original PX-017 `51a80297`). Branch: `codex/PX-017-follow-keep-visible`. - Why. Every promotion-based design lost a race against the user. At `747a7fe6` each retarget promoted, and the replies overwrote fast arrows (`verification-result-pr-review.json`). At `dd641099` retargets withdrew instead, but a sample landing mid-burst promoted a stale target, and the promote-back rule chained (`verification-result-withdraw.json`). Separately, a store-apply/render gap in `SessionController` could undo a click. The Codex PR #98 finding (`follow.rs:225`): after following A and clicking B, `TABLE.VALUE` still named A, so a relaunched client restored A while follow, the inspector and the checkbox described B.
- Scope. Only `apps/srtop`, its tests and the native test file changed. No protocol, registry, SDK, renderer, client source or dependency changed; none was needed.

### Semantics

- **Only `keep_visible`.** Follow keeps its target visible through the table's standard `keep_visible` hint and nothing else. Follow never sets `value`, at turn-on or later. The renderer reveals the hinted item whenever a commit sets the hint or changes the item's row, and never touches the selection (PX-017-G01).
- **Turn-on promotes nothing (decision).** Turning on follows the process the inspector describes. That is the user's own selection as the server resolved it, from a click, an arrow or a search match, so the client already shows it selected. The turn-on commit carries one `keep_visible` set (its one-item `MODEL_RESET_RANGE` and `SET_PROPERTY`), the checkbox and the status. A refusal (nothing selected, hidden, ended) sets nothing.
- **Retarget.** While on, a `SELECTION_CHANGED` naming another shown row (click or arrow), or a search match, makes that row the target and sets the hint to it once. A selection of the current target sets nothing. A search keeps its own PX-011 promotion of the match, which then names the target.
- **Samples, sorts and filters put nothing of follow's on the wire.** The hint is never set again for an unmoved or moved target, because the client reveals the item when its row changes. The status still names the row.
- **Removed.**
  - `Follow::track` promotions and `Followed::shown_at`.
  - `Follow::forget_shown`.
  - `ProcessView::last_promotion`, `select_item_at`, the `observed_revision` stale-click rule, and the promote-back of an overridden click.
  - The turn-on promotion.

  `selection_changed` calls `select_item` again.
- **The selection is the user's.** No follow commit contains a `SET_PROPERTY(TABLE, value)`. So no reply can replace a newer local selection, whatever the round trip, and the store-apply/render gap in `SessionController` has nothing to undo. Rapid arrows and clicks end on the last press, with or without samples moving rows mid-burst (measurements below).
- **One followed process (Codex finding).** While follow is on, `value` names the target or nothing. When follow turns on or retargets and `value` names another process, for example an earlier PX-011 search promotion, follow withdraws it (`CLEAR_PROPERTY(value)` through `UiTransaction::clear_promoted_selection`). The withdrawal is joined to the hint in one transaction (`joins_next`). On a live client, the PX-011-G01 withdrawal rule keeps any selection made after the promotion.
- **What a fresh client sees.**
  - While following:
    - selection: none, or the target when a search promoted it (never another process);
    - viewport: revealed to the target, because the snapshot carries `keep_visible` and a newly mounted collection starts with the hinted row revealed (PX-017-G01).
  - After follow stops or is turned off: no hint.
  - Measured by `bootstrap_fresh_client` after a turn-on, a retarget, a burst, a search, a click after a search and samples (Rust), and by a second native client over SSH after a retarget (selected `[]`, rows `{45, 5}` showing row 50).
- **Self-repairing.** `follow_table_effects` derives what is needed from the store's own record of `keep_visible` and `value`, read after every commit. It sets the hint when it names anything but the target, withdraws when `value` names another process, and clears the hint when follow is off. A set that did not commit is therefore made by the next plan, and a settled clear is never repeated.
- **Ending follow.** When the target ends, is filtered out or is left out by the row ceiling, follow stops, and the hint is cleared in that plan: explicitly, or by PX-017-G01 settlement in the commit that deletes the row, in which case the explicit clear records nothing. The checkbox turns off and the status gives the reason. A selection that names no shown row stops follow and clears the hint too. A reused PID is another item ID and is never followed, hinted or selected.
- **Follow off.** No hint is held, and nothing is hinted or promoted on a sample or a selection. Turning off clears the hint, and `value` is left to its owner (search).
- **Pause (PX-015).** A paused view publishes no sample, so nothing changes. A user sort while paused that moves the target commits only the row moves. The hint stays on the target, so the client reveals it at its new row.
- **Budgets.**
  - `FOLLOW_RESERVE_BYTES` (2048) now also covers the table's hint, measured on the encoder with the widest item ID: `encoded=1178`.
  - `planning_limits` leaves one operation and its bytes free for each settlement clear the store may add: one for a held promotion and one for a held hint.
  - A hint costs two operations, like a promotion.
- **Cross-view (PX-018).** Appended to the PX-018 ticket's hand-off: carry follow over by setting `keep_visible` on the tree node. `keep_visible` does not expand collapsed ancestors, and a local disclosure change never scrolls.

### Limitations

- **The hint lags every retarget by one round trip** (verification note N1).
  - Each retarget's hint (click, arrow or search match) reaches the client one round trip after the retarget, and setting it reveals the row it names.
  - **Panning.** A pan made within that round trip after a click is pulled back to the clicked row once; the verifier saw this in 4 of 4 live tries. So "the view stays where you put it until the followed process changes row" holds only once the retarget's hint has landed. The toggle's description (`FOLLOW_DESCRIPTION`) and the `follow.rs` module doc state the rule without this exception; this docs-only change leaves them as they are.
  - **During a burst** the newest selection can be up to about RTT ÷ key-repeat rows out of view. The verifier measured up to 14 rows on a 5-row viewport at yield spacing. This implementation's native run saw the selected row out of view after 3 of 20 gaps at yield and 1 ms spacing, and 0 at 30 and 80 ms.
  - **After a burst** the selection stays out of view until the last hint lands: 39–91 ms on loopback, one RTT in general. That hint reveals it.
  - The selection itself never changes. Avoiding the lag would need a client or renderer change (for example not revealing a hint set for a row the user has since left), which this ticket does not make.
- **A failed search promotion while following (N2).** If the commit carrying a search's promotion fails while follow is on, follow has already retargeted to the match. The next plan's repair sets the hint to it, and the client scrolls to a row it never selected. The repair never promotes and never restores another process.
- **Known test gap: the hint and the withdrawal are not proven atomic (N3).** Mutant M13, which removes `joins_next` in `follow_table_effects`, survives. The hint and the withdrawal are three operations in a control-only plan and always fit in one transaction under the default limits. No test forces a split at the operation limit: `SessionConfig` has no store-limit override, and srtop's start path needs the default limit. I recorded this instead of adding a test.
- **Native RTT is loopback.** Real SSH over loopback has sub-millisecond RTT. The 50–100 ms RTTs are covered by the model test, which drives the real view and journal.
- **With follow off, a search promotion survives a later click.** That is PX-011/PX-011-G01 behaviour, so a fresh client then restores the search match. Follow withdraws it only when it turns on or retargets.
- **Tree.** `keep_visible` on a `Tree` never expands collapsed ancestors (PX-017-G01). See the PX-018 hand-off.
- **Inherited from PX-017-G01.** One hint per collection. A hinted item that moves and returns to the same row between two commits is not seen as moved.
- **One shared follow per session**, as before. The test pan is programmatic, and the test host never activates, as before.
- Independent verification of this rework is pending. Every ledger entry stays `in_progress`.

## CI race: the selected row showed the next PID (PR #101)

- **Failure.** CI macOS run 43061183831, job 130678011721 (merge ref main+#101): `rapidArrowKeysWhileFollowingEndOnTheLastPressWithASampleMidBurst`, `ProcessExplorerShellTests.swift:1302`, `30 ms key repeat: no commit changed the selection: ["press 11: 6048 instead of 6047"]`. It did not reproduce locally in 50 unforced runs of the test (10 idle, 20 with one `yes` per core, 20 with three per core).
- **The selection never moved.** The burst ended on row 57, PID 6057, exactly as in a passing run. Had the selection really moved to 6048, press 11 would have started one row lower and the burst would have ended on row 58. So the displacement was a display defect, not a selection change. Hypotheses (a)–(d) are refuted: no restore by row index, no stale remembered item, no scroll that selects, no promotion.
- **Root cause: a generic client defect, present on `main`.** `TableCollectionAdapter.update(model:modelID:tableView:)` handles a commit that keeps the row count, such as a re-sort, by reloading only the rows in `visibleRect` (`reloadVisibleRows`, since `24c8ed41`). AppKit can also hold cell views for rows outside `visibleRect`:
  - rows it prepared around the viewport;
  - any view realized on demand by `view(atColumn:row:makeIfNecessary:)`. Accessibility realizes views this way, and so does this test's `nativeRows` on every `selectedPID()`.

  Those views kept the previous commit's cells. Scrolling such a row into view reuses the stale view, so the user sees another process's cells.
- **Order of events.**
  1. Press 10 selects row 46, PID 6047, the bottom visible row (visible rows 42–46).
  2. The measurement realizes views for all 60 rows.
  3. Refresh now is clicked.
  4. The sample commit lands before a layout pass discards the off-screen views. A slower runner makes this order more likely.
  5. The sample moves `tracked` from row 56 to row 41. The selection correctly follows ItemId 6047 to index 46 (row 47). That row is below the viewport and was not reloaded, so its view still shows 6048.
  6. The next check reads 6048.
- **Native proof.** With temporary instrumentation (removed before commit), the test polled `selectedPID()` every 1 ms after the tenth press until the sample landed, which forces the CI order. It then printed `selectedRow=46 nativePID=6048 modelPID=6047 … mismatchedRows=["40:6042/6010", "46:6048/6047", …, "55:6010/6056"]`. The model and the selected index were right; 11 views outside the visible rows `{41, 5}` were stale.
- **Fix (Collections, generic).** The content reload now covers every row AppKit holds a view for, plus the visible rows: `reloadRealizedRows` uses `enumerateAvailableRowViews`, and `lastRowUpdate` reports those rows. The cost is bounded by the views AppKit keeps. No protocol, registry, SDK, renderer, srtop or process-specific code changed, and the native test is unchanged.
- **Deterministic test.** `CollectionAdaptersTests.aResortReloadsEveryRealizedRowNotOnlyTheVisibleOnes`:
  1. A 60-row model-backed table in a 90-point viewport, with the selection on the bottom visible row (row index 45).
  2. The row below the viewport is realized with `makeIfNecessary`.
  3. A delete and insert moves ItemId 100 from row 55 to row 41.
  4. The test asserts: the selection is on ItemId 46 at row 46, no `SELECTION_CHANGED` is emitted, every realized view shows its model row, and rows 40–47 show their model rows when scrolled into view.

  Before the fix it fails exactly like CI (`shown(46) → "6047"`, model `"6046"`). It also fails on `origin/main` `911539ad`, run in a temporary detached worktree that was then removed. So the defect is pre-existing, generic client behaviour, not introduced by #98–#101.
