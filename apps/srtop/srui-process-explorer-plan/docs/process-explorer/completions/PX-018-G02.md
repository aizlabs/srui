## Design reading

- §7.6, §7.7: a List/Table/Tree reports `SELECTION_CHANGED` and a Tree `EXPANSION_CHANGED`; every event carries `observed_revision`, the state the user acted on.
- §12.2: a commit is not a frame. The client publishes a commit to its replica (`TransactionApplier`) several suspensions before the main-actor turn that renders it (`SessionController.updateRenderer`). A click in between acted on the rows of the earlier commit.
- §22.5: selection highlight and disclosure are local interaction state; only their semantic outcome goes to the server, so the outcome should name the state the user saw.
- §18.2: an event whose `observed_revision` is ahead of the server's is rejected. The stamp is never ahead of the client's own replica, which is never ahead of the server.
- §6.3, §12.1, §22.7, §4 inv. 13 and §32: unchanged; nothing here changes a transaction, a collection model, a range request, or a conformance vector.

## Root cause (re-checked at the base)

`SessionController.enqueueNativeSemanticAction` stamped every native semantic action with `semanticInspectionSourceSnapshot().transaction.revision`, the applier's published snapshot. `handleTransaction` publishes a commit in `outbox.commitLiveRender`, then awaits the terminal pump, the resource lease and the outbox fences before `updateRenderer` mounts or applies it on the main actor. A collapse made in that window carried the commit's revision. With a revealing Go to PID promotion, srtop's `expansion_changed_at` took such a collapse for one made after the promotion and cleared the inspector, and the render then expanded the parent and selected the match with selection events suppressed (PX-018 verification V6-F1).

The existing `lastRenderedRevision` could not be reused: the transaction lane records it after `updateRenderer` returns and after `outbox.completeLiveRender`, so a click in the main-actor turns right after the render would still carry the earlier revision, and srtop would undo a genuine post-render collapse (mutant M6 below).

## Implementation (`client-macos/Session/SessionController.swift`)

- **`nativeRenderedRevision`**, a `@MainActor` `Revision`, starts at `.initial`. `updateRenderer`'s main-actor closure sets it to the snapshot's revision immediately before `renderer.attach`/`layoutRenderer.mount` (first mount, catch-up or resync snapshot, resume recovery remount) or `renderer.apply` (live commit). That happens inside the synchronous turn guarded by the resource-owner and render-token fences. If the render throws, the earlier value is restored. It is reset to `.initial` with the replica in `resetSharedStateForReplacement` and in the abandoned-session discard, in the main-actor blocks that already reset `lastRenderedRevision`.
- **Stamping.** `enqueueNativeSemanticAction` uses `renderedObservedRevision(rendered: nativeRenderedRevision, published: source.transaction.revision)`, which is `min` of the two, when `stampsRenderedRevision(action, on: nodeType)` holds. That covers `SELECTION_CHANGED` in both forms on a `List`, `Table` or `Tree`, and `EXPANSION_CHANGED` on a `Tree`. `ACTIVATE`, `VALUE_CHANGED`, `TEXT_EDIT` (its own path, `enqueueNativeTextEdit`, untouched), the selection of a `Select`, `ChoiceGroup` or `Tabs`, and every in-process automation action (`performSemanticAction`, which keeps its handle's snapshot revision) are unchanged.
- **Unchanged:** `event_seq`, event IDs, the outbox, retention, acknowledgement, replay, validation (still against the published snapshot), and which events are sent with which arguments.
- `nativeRenderedRevisionForTesting` exposes the value to tests. The file's spec header lists the rule.

### Why it is safe

- **Never ahead of the applier.** It only takes the revision of a snapshot the applier has published. The `min` at stamping time covers the one window where it could be: `applier.resetReplica()` runs before the main-actor block that resets it. Event dispatch is closed in that window anyway, because the replacement waits for its snapshot. So §18.2 future-revision rejection cannot fire on it.
- **Exactly one boundary.** Native callbacks run on the main actor and a render is one synchronous main-actor turn, so a user action is either before it (stamped with the earlier revision) or after it (stamped with this one).
- **Reports a render makes itself** carry the revision being rendered. A revealing promotion's `expandCollapsedAncestors` reports `EXPANSION_CHANGED(true)` from inside `renderer.apply`. This is why the value moves before the apply, not after (mutant M4).
- **A new controller** (reconnect) starts at `.initial`. It always remounts the committed replica (`renderCommittedSnapshotBeforeResumeIfNeeded`, `hasMountedInitialTree` is per controller) before dispatch opens. A catch-up snapshot opens dispatch only after its mount.
- **A failed live render** leaves the value at the last revision actually shown, so later events are stamped older, never newer, until the next mount.

## Compatibility

- **A server that ignores `observed_revision` for these events** (ui-gallery, process-monitor, counter, and srtop for `SELECTION_CHANGED`) behaves exactly as before: the event's type, node, arguments, `event_seq` and `event_id` are unchanged, and only the revision can be lower. It is never ahead of the client's replica, so the §18.2 future-revision rejection is unaffected. No repository server rejects an older revision.
- **An older client** keeps today's stamping (the applier's published snapshot). With srtop it keeps the documented PX-018 window: a collapse made between a promotion's delivery and its render clears the inspector. The srtop README says so.
- **An older srtop with a new client.** A srtop that ignores `observed_revision` (before PX-018 round 5) sees no difference. The PX-018 srtop undoes a collapse only when it is stamped at or before the revision before the latest revealing promotion. With a new client that is exactly a collapse the outline made before it applied the promotion, the case it already meant to undo. A collapse made after the render carries the promotion's revision or later, as before, and is applied. Expand reports are applied regardless of revision. Nothing is lost.
- No wire or registry change: `generate_proto.sh` was not needed (no source touched), and nothing in `protocol/` changed.

## Limitations

- **Events made by the in-process automation API** (`SemanticInspector` handles) keep the revision of the handle's snapshot, as before; they are not native interactions.
- **A failed live render** leaves the stamp at the last revision shown until the next mount, so a collapse in that state can be read by srtop as made before a promotion that never rendered. This is the conservative side: the client did not show the promotion.
- **Older clients** keep the V6-F1 window (Compatibility).
