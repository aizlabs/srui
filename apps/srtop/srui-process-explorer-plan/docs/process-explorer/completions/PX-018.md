## Do the generic facilities suffice?

Yes, for every build item. PX-018-G01 provides the hierarchical model (preorder index space, the two item properties, exact shape validation on every replica, local disclosure, `EXPANSION_CHANGED`, Tree `columns`, the SDK `TreeModel`); PX-017-G01 provides `keep_visible` on a `Tree` with the hidden-interval mapping; PX-011-G01 provides promotion on a `Tree`, which reveals through collapsed ancestors and reports each with `EXPANSION_CHANGED(true)`. Two generic limits remain and are recorded as limitations, not worked around: the outline has no keyboard disclosure (left/right arrows), and `sessiond` answers a range request for rows it holds with `AlreadyCached` and sends nothing (srtop pushes every row, so its clients hold no gap). See Limitations.

## Tree semantics

- **Model.** The tree is a second projection of the rows the table publishes: the same process instances under the same item IDs, arranged on the server into one `Tree` (node 73) over its own model (2) whose index space is the forest's preorder. The SDK's `TreeModel` stamps every item's `tree_depth` and `descendant_count` (`tree::stamp`) and refuses a forest deeper than the depth limit. No semantic node is created per row. Each tree row's value is the table's cells in the current layout and a last **Parent** cell.
- **Lineage.** Every record carries `Lineage { parent, started }`. On Linux both come from the same `/proc/<pid>/stat` read as the record's identity: field 4 (parent PID, `0` for the kernel's tasks, an unusable field unread, never 0) and field 22 (start time in clock ticks, the record's `LinuxBootTicks` creation token). A source that collects none states `Lineage::NOT_COLLECTED`.
- **Parent rule.** A shown row is placed under another only when: its own row was confirmed by the current scan; its parent PID was read and is not 0; exactly one **confirmed** record of the same generation holds that PID; both start times were read and the parent started **no later** than the child (equal ticks count); and the filters keep the parent. The parent cell then holds the parent's PID.
- **Explicit roots.** Anything else is a root whose Parent cell says why, in fixed wording and numbers only: `none: started by the kernel`; `root: parent unread (<reason>)`; `root: row kept from an earlier scan`; `root: parent P not in this scan`; `root: parent P unreadable` (the scan's skipped ledger names P); `root: parent P beyond the record limit` (its capped ledger names P); `root: parent P not seen (incomplete scan)` (a ledger that cannot name what it missed); `root: parent P kept from an earlier scan`; `root: parent P ambiguous` (two records hold P); `root: parent P unverified (start time unread)`; `root: parent P started later (PID reused)`; `root: parent P hidden by the filters`; `root: cycle through parent P broken here`; `root: parent P at the depth limit`.
- **Reparenting.** When a parent exits, the kernel reparents its children to init or a subreaper; the next sample reads their new parent PID and shows them there, under their own item IDs (fixture `--fake-tree` step 1, and the Linux live test).
- **Cycles.** Parent links that lead back to themselves (possible only when start times tie, or from a source that misreports; a self-parent is a cycle of one) are broken at the cycle's member that orders first by `sort::process_key_order`, whatever the active sort; the other members stay attached under it.
- **Depth limit.** The tree is arranged under the store's `max_model_tree_depth`, at most the wire default 256 levels every client enforces (`ProcessView::tree_levels`; `with_tree_levels` can only lower it, for tests). A row with children may sit at most at depth `levels − 2` (the store's rule), so a chain of exactly `levels` processes fits; the next level's process starts a new root, emitted right after the top-level subtree it was cut from, and says `root: parent P at the depth limit`. Its own subtree continues under it.
- **Siblings.** The roots and every parent's children keep the order of the rows they come from — the active sort (PX-009), or the source's (ascending PID) — so sorting orders every level and never flattens one.
- **Row ceiling.** The tree keeps the **leading rows of its preorder** under the same frame budget and row limit as the table (`bound_to_publishable_collection`), each tree row also charged its Parent cell and its two item properties. A prefix of a preorder is a forest and every kept row's ancestors precede it, so the ceiling never orphans a shown process: it cuts a subtree short, and the status counts the rows left out (`· 6 rows beyond the publishable size limit`). Descendant counts are stamped after the cut.
- **Edits.** A hierarchical model is judged whole after a transaction's last operation on it, and a sparse replica cannot place an identity delete. Every tree edit is therefore index-based and one joined unit: the shared leading and trailing runs stay, updated in place by indexed `MODEL_UPDATE` where a cell or a place changed; the middle is one range `MODEL_DELETE` and `MODEL_INSERT`s under the same item IDs. When that exceeds the store's operation or byte bound the whole preorder is replaced, which is no larger than a catch-up snapshot. A client keeps its selection and its collapsed set across such a commit (both anchored to item IDs; measured natively).
- **View switch.** A standard checkbox **Show process tree** (node 71, ⌘T) and a view status (node 72) in a Row (node 70) between the follow controls and the collections; disabled in the uncollected shell. Its one handler is the toggle's `VALUE_CHANGED`. One switch is one transaction: the shown collection's model emptied by one index range, the other filled, the two collections' `visibility` swapped (`collapsed` takes the hidden one out of the layout), the list-focus shortcut `primary+l` moved to the shown collection, the switch's value, the view status, and the selection and follow carry-over. The emptied model takes its collection's promotion and hint with it (SDK settlement). The Tree is created with the shell, its headings included (`refresh::tree_headings`), collapsed; the column chooser updates both collections' headings.
- **Selection.** Carried over by item ID both ways: in the switch commit the server promotes, on the shown collection, the process the inspector describes (the user's own last selection), and only the followed process while follow is on. A `SELECTION_CHANGED` from the hidden collection is ignored (`select_item_in`), so it neither clears the inspector nor stops follow. A selection in the tree is the inspector's input exactly as in the table.
- **Disclosure.** Local (PX-018-G01): the client expands and collapses, and reports `EXPANSION_CHANGED`; the server records it (`ProcessView::collapsed`, pruned to rows that still have descendants on every publication, emptied by a switch) and publishes no row. A collapse that hides the inspector's process has also deselected it on that client without a `SELECTION_CHANGED`; the server clears the inspector to match (`Inspector::clear`, `Selected process: none · select a row to inspect it`). A report for an item without children, not in the tree, from the table, or that changes nothing publishes nothing.
- **Follow.** Carried over: the switch hints the followed item on the shown collection (`follow_after` with a fresh collection), so it is revealed there; a selection in the tree retargets follow as in the table; samples and sorts set no hint. The tree's follow status says `item N of M in the tree`, and, while the followed process is under a parent the client reported collapsed, `Following PID 310 · cc · hidden under collapsed PID 300 · make: expand it to see the followed process; the tree never expands it for you, and expanding never scrolls` (the outermost collapsed parent). Follow stops by itself as before when its process ends or is not shown.
- **Search, filters, pause, inspector, shortcuts.** A search or Go to PID promotes its match on the shown collection; in the tree the client expands exactly the collapsed parents above it (PX-018-G01) and reports them, which the server records. Filters, the user filter and the PID set filter the rows first; a shown row whose parent they hide is a root saying so. A paused view switches over its frozen rows and publishes no sample. Counts and "row N" in the search and follow statuses count the tree in preorder, collapsed rows included. Every shortcut works in both views; `primary+t` is unique and in no client reserved table.
- **Budgets.** `VIEW_RESERVE_BYTES` = 4096 covers the view row, toggle, status (`MAX_VIEW_STATUS_BYTES` 512), the Tree node with its headings, its model's `CREATE_MODEL`, and its promotion and hint at the widest item IDs: measured 1,437 bytes on the encoder.

## Limitations

- **No keyboard disclosure.** Left and right arrows neither expand nor collapse: the generic outline is a flat data source (`OutlineCollectionAdapter.swift:706-712` returns no children, `:727-729` makes no item expandable) with its own disclosure button and no key handling. Adding it is a client change, outside this ticket.
- **Range requests.** srtop pushes every published row, so a client's tree holds no gap and disclosure requests nothing (natively measured: 0). A range request for rows the server holds is answered `AlreadyCached` and sends nothing (`server-rust/sessiond/src/session/model_range.rs:209-216`); srtop installs no range provider (PX-008 audit). The asynchronous loading of a missing range is the generic client's (PX-018-G01 evidence).
- **Tree edits resend the moved middle.** A reorder in the middle of a large tree resends every row between the first and the last that moved (`lc-debt` in `plan_tree`): under a CPU sort a 10,000-process tree sends about 0.7 MB per sample, where the table moves only the rows that changed place. Still one transaction, one frame and inside the 3 s budget.
- **Server-side disclosure knowledge is what the last client reported.** The collapsed set is shared by the session, like follow; with two clients disclosing differently the follow status and the inspector clearing follow the last report. Leaving the tree forgets it, and a newly shown tree starts expanded, because the hidden collection's model is emptied.
- **A collapse clears the inspector, not follow.** Follow is not a selection; it stays on its process and says where it is hidden. Expanding the parent does not reselect the row on the client (the outline never selects a row it does not show), so the inspector stays empty until the user selects again.
- **Inherited.** A switch promotes the selection on the shown collection; as with a search promotion (PX-011-G01), a later click stays local and the promotion survives it with follow off, so a client that attaches later restores the promoted row. `keep_visible` lags a retarget by one round trip (PX-017). One hint per collection.
- **Live PID reuse is not forced.** An unprivileged test cannot make the kernel hand out a given PID (`ns_last_pid` and `clone3` `set_tid` need `CAP_SYS_ADMIN` or `CAP_CHECKPOINT_RESTORE`); the reuse rule is exercised by the procfs fixture, the Rust fixtures and the randomized oracle, and the live test checks it over every link of a real host's tree.
- **Status and row numbers count the preorder.** "row N of M" in the search status and "item N of M" in the follow status count collapsed rows too.
- Independent verification is pending.
