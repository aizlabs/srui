## Design decisions

### 1. Multi-selection: app-level tags, not native multiple selection

The generic facility was checked and is not one this ticket can use as "stable multi-selection":

- `Table`/`Tree` accept `selection_mode = multiple`, and the AppKit adapters then allow a multiple native selection, but in that mode `TableCollectionAdapter` emits **one `SELECTION_CHANGED` per selected item** and nothing for an emptied selection (`client-macos/Collections/TableCollectionAdapter.swift:485-506`). The server can neither tell an added item from a replaced set nor learn of a deselection: the event carries no set.
- The promoted `value` is **one `ItemId`** (registry `value`, PX-011-G01): the server can never restore or carry a set of selected items to a client.
- A native selection cannot hold rows a filter hides or a process that has ended, which the ticket requires (hidden tags counted; exits historical), and it is the keyboard-highlighted row the ticket says tags are independent of.

The ticket's build items do not need native multi-selection: htop's tagging (H5) is a set kept apart from the highlighted row. So tags are **server-side application state** keyed by process instance, shown in a **Tag** column, and changed by buttons that act on the existing single selection. This is the "stable multi-selection" of the title: a set of processes the user chose, stable across sorting, filtering, the view switch and samples, independent of the selection. A PX-020-G01 is not needed; a later need for native multi-row selection with set semantics (a `SELECTION_CHANGED` carrying the whole set and a multi-item promotion) would be its own prerequisite, and this ticket does not extend the standard semantics.

### 2. Threads

A thread row (PX-019) cannot be tagged: a tag marks a process instance, and a thread is part of its process. A request on a thread row is refused with `TID 201 of PID 200 · worker-1 is a thread: tags mark processes, so select its process row`. "Tag selected and descendants" never includes threads (`tree::descendants` walks process rows only), a tagged process's thread rows carry no tag, and hiding or showing user threads changes no tag. A kernel thread is a process row and can be tagged. Tested by `threads_are_never_tagged_and_a_hidden_kernel_thread_tag_is_counted`; the mutant that tags a thread by its process key (M8) fails it.

### 3. Exit: historical, bounded

A tagged process instance that leaves the server-side collection — it ended, or no scan lists it any more (eviction past the row limit) — keeps a **historical tag**: the PID and name it was last shown with, listed in the tags status as `N no longer listed: PID 300 · make, …` (the three newest named, `and K more`). The wording does not claim an exit: PX-021 owns "exited" versus "no longer observed". A historical tag is terminal: it is never put back on a row, even if the same instance were listed again. A scan that cannot account for absences (a rejected snapshot, an unenumerable ledger) keeps the rows (PX-004), so their tags stay live. Retention: at most `MAX_HISTORICAL_TAGS` = 64, oldest forgotten first and counted (`(6 forgotten)`); Clear tags removes live and historical tags and the forgotten count. Removal on exit was rejected: the user would lose the fact that a tagged process went away, which a later bulk action (PX-035) must not hide.

### 4. Interactions

- **Collapsed mirror (PX-018).** A collapse that hides the selected row clears the inspector, so the buttons and the shortcut have no selection: `Nothing tagged: select a process row first`. A tagged row under a collapsed parent stays tagged and is not counted hidden (it is in the model). Test: `a_row_hidden_under_a_collapsed_parent_cannot_be_tagged_and_is_not_counted_hidden`.
- **Search, follow, the inspector.** A tag request publishes only tag cells (`MODEL_UPDATE` by identity, in place) and the tags status: no promotion, withdrawal, `keep_visible`, inspector or follow change. Asserted on the committed operations (`assert_only_tag_cells_and_status`) and on the store's `value`, `keep_visible`, inspector and follow status before and after Clear tags. A search promotion, follow and the inspector keep working on tagged rows unchanged.
- **Filters, sort, column chooser, view switch, pause.** Every publication marks the rows it publishes from the tag set (`visible_in`), so tags survive all of them; a paused view tags its frozen rows and descendants from the frozen sample.
- **Row and byte ceilings.** Every row gains one cell. The ceiling charges each row an empty tag cell, whatever its tag, so tagging never changes which rows fit; the tagged cells' extra bytes are one fixed reserve, `TAG_CELLS_RESERVE_BYTES` = `MAX_TAGGED` × 6 = 6,144 bytes. `MAX_TAGGED` = 1,024 tagged processes at once; a request beyond it is refused whole (`Nothing tagged: PID 1000 · root and 1024 sampled descendants would make 1025 tags, above the limit of 1024`), untagging never. A first design charged every row the tagged width; it cost 6 bytes per row (about 150 KB at the ceiling) and pushed `a_refresh_beyond_the_frame_bound_commits_as_frames_a_client_accepts` into one frame (its vanishing rows would have had to grow from 8,000 to 22,000, 27 s → 203 s on the store's per-id delete path), so it was replaced by the bounded set and the one reserve.
- **Failed commits (PX-018/PX-019 pattern).** The tags status is planned after the rows whose cells it describes and carries the tag set's generation, recorded as it commits (`Effect::TagsStatus`). A request holds the set before it and `settle_tags` puts it back when the status's generation never committed; a sample that retires departed tags does the same. Tests through the `commit_fault` seam: `a_failed_tag_request_keeps_the_set_and_the_status`, `a_failed_clear_keeps_every_tag`, `a_failed_sample_keeps_an_ended_process_tagged_until_one_commits`. A plan that committed its rows only in part leaves cells the next publication restates from the set put back.

## Tag model

- **Identity.** A tag is the whole `ProcessKey` of a process instance (source, host, boot, PID namespace, PID, creation token; `thread: None`), anchored by the session identity like every row key. It is never a PID, row index, item ID or name. A newer instance reusing a tagged PID is a different key: `descendant_tags_are_frozen_survive_filters_and_turn_historical_when_a_process_ends` (reuse after exit) and `a_newcomer_beside_a_kept_earlier_instance_of_its_pid_is_not_tagged` (the ended instance still shown beside its successor by an unenumerable scan; the mutant that matches tags by PID, M6, fails it).
- **Freezing.** "Tag selected and descendants" inserts the selected process and each descendant `tree::descendants` finds in the current generation, each as its own key, at the request. Nothing is recorded about the group: a process started later is just an untagged row (`late` in the fixture, a late worker live).
- **History and retention.** Departure is computed in `apply` against the collection the sample keeps (`Tags::departed`), named from the previous collection or else the tag-time name; `retire` moves them to history under a new generation. Bounds: ≤ 1,024 live tags, ≤ 64 historical, names ≤ 64 bytes, status ≤ 1,024 bytes; Clear removes all.

## Limitations

- **No native multiple selection.** Tags are marked in a column, not by native row highlighting; the generic client has no per-item style for it, and none was added. Tagging a range of rows takes one click per row or Tag selected and descendants.
- **Not htop's "children".** htop tags the shown children of the highlighted row; srtop tags the sampled descendants whatever the filters hide, and counts the hidden ones. Space and `c`/`U` are not bound: every srtop shortcut carries Command (PX-016).
- **Historical tags say "no longer listed"**, not "exited": PX-021 owns exit versus no longer observed and the tombstone details.
- **Limits.** 1,024 tagged processes; 64 historical tags. Tags are session state: they do not survive a restart of the server, and a reconnecting client receives them with the rows.
- **No action uses tags yet** (bulk actions are PX-035).
- The `inspector_test::the_inspector_stays_on_its_process…` name-cache flake (pre-existing) failed in two of four full macOS runs; alone 5/5 and its target 15/15 pass; see Verification.
- Independent verification is pending.
