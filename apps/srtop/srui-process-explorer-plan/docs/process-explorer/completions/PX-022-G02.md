## Design reading

- D1 §18: "The client MUST retain pending events but MUST NOT replay them or generate new semantic events until the server provides a machine-readable continuity decision." A selection made in a detached window therefore cannot be reported.
- D1 §22.5: the selection highlight is local, and "Only semantic outcomes are sent to the server". A local selection the server was never told of is a divergence, not a preference.
- D1 §6.3 and §7.6, as PX-011-G01 reads them: committed semantic UI state belongs to the remote session and the client keeps a non-authoritative replica, while presentation state such as the List/Table/Tree selection highlight is local "unless explicitly promoted to semantic state", and only the user's change is reported, as `SELECTION_CHANGED`. A server promotion of the selection (PX-011-G01), its withdrawal and a `selection_mode` of none are therefore committed state the renderer follows, not user changes, and the gate must not hold them back. D1 §22.7 only says how `NSTableView`/`NSOutlineView` are fed from the replicated model (row reuse, range requests); it says nothing about promotions.
- D1 §17: a lost transport must reach the client, which then shows DETACHED as client chrome (PX-022-G01).
- D1 §20.1: the bridge "attach[es]/detach[es] a connection from a session" and "does not own semantic state". A connection the daemon ended is over, and the bridge has nothing left to forward.
- D2 T17 and T19: the Unix-socket bridge and its SSH binding. D2 T28: collections and local selection. D2 T22–T24: attach, detach and resume, unchanged.

## Fix 1: a stale window takes no user selection change

**Defect.** This was found natively by PX-022's SSH test, in `PX-022/impl2-probe-run-1.log`.
- A Down Arrow in a detached srtop window moved the native highlight from PID 4101 to 4103.
- Its `SELECTION_CHANGED` was dropped (`sessionInactive`).
- The renderer's `collectionSelectionMemory` kept 4103 through a `RESUME_OK` replay, and through a same-session snapshot remount.
- So the table highlighted 4103, while the server's inspector, and the tag buttons that act on the process it describes, stayed on 4101.

**Fix.**
- `TableCollectionAdapter` and `OutlineCollectionAdapter` implement `selectionShouldChange(in:)`. AppKit asks this before every user-initiated selection change: mouse, keyboard, Cmd-A, type-select, the `deselectAll(_:)` action and accessibility. It never asks for `selectRowIndexes`, but it does ask for a programmatic `deselectAll(nil)` (shown by mutant MR5 below). The method answers `isSuppressingSelectionEvents || allowsUserSelectionChange()`. The adapter sets `isSuppressingSelectionEvents` around each of its own server-driven selection changes, so those always pass and only the user is held back. Those changes are a promotion's withdrawal, a promotion to an item absent from the replica, a reload restoring the selection, and a remount restoring a local selection.
- `TableCollectionAdapter.applySelectionMode(.none, to:)` is static, has no adapter flag, and is shared by Table, List and Tree. It clears with `selectRowIndexes(IndexSet(), byExtendingSelection: false)` instead of `deselectAll(nil)`. The adapter's `selectionMode` is already `.none` by then, so the clear reports nothing.
- Audit of the programmatic selection calls in `client-macos/Collections` and `client-macos/RendererAppKit`. Each `selectRowIndexes` call runs with suppression set, and AppKit does not ask the gate for it. Of the `deselectAll(nil)` calls, the two in `clearSelectionForPromotion` and the two in `restoreSelection` run with suppression set. The one in `applySelectionMode(.none)` is replaced as described above. Nothing in `RendererAppKit` calls them directly. `CollectionSelectionPromotion` goes through `applyPromotion` and `restoreLocalSelection`.
- `ControlFactory.allowsUserSelectionChange` holds the gate. Every List, Table and Tree adapter it builds reads it, including the adapters a remount builds.
- `LayoutRenderer.setSessionWindowStatus(_:)` sets the gate: closed while a status is shown, open when it is cleared or empty.
- Scrolling, copying and tree disclosure are unchanged.

## Fix 2: `srui-ssh-bridge` ends when its daemon closes

**Defect.** This was also found natively, in `PX-022/impl2-probe-run-3.log`. After `SIGTERM` of srtop, an idle client stayed `connected`, with no stale status, for the whole 30 s wait. Its Connections row offered Open, not Connect. Reproduced by hand: the bridge logged "srui-ssh-bridge exited cleanly." and its process stayed alive. There were two causes:
- `bridge_streams` used `tokio::io::copy_bidirectional`, which returns only when both directions reach EOF. On daemon EOF it shut down the write half of tokio's stdout, which does not close fd 1, and then waited for the SSH side.
- After `bridge_streams` returned, `main` returned into a tokio runtime shutdown that waits for the blocking thread reading stdin. That thread returns only when the SSH side writes or closes.

**Fix.**
- `bridge_streams` forwards the two directions separately.
- Daemon EOF ends the bridge once what the daemon sent is flushed.
- SSH EOF shuts down the daemon's write half and keeps forwarding until the daemon closes, which is the existing half-close behaviour.
- `main` leaves with `std::process::exit(0)`, or `exit(1)` after logging a forwarding error.

## Tests

`client-macos/Tests/RendererAppKitTests/StaleWindowSelectionTests.swift` is a new swift-testing suite. Each test runs on a real `NSTableView` and a real `NSOutlineView`, mounted through `LayoutRenderer`.
1. *A stale Table or Tree keeps its selection against the user's arrow key, and moves once live.*
   - With a status set, `selectionShouldChange(in:)` is false.
   - A real Down Arrow key-down leaves row 2 selected and reports nothing.
   - After the status is cleared, the next Down Arrow selects row 3 and reports `SELECTION_CHANGED` for ItemId 4.
2. *A server promotion still selects in a stale window.*
3. *The gate follows the status through a remount.* The new adapter refuses, and an empty status clears the gate.
4. *A promotion's withdrawal still clears in a stale window* (round 2). Commit `value=ItemId(3)`, set a status, then commit `clearProperty(value)`. No row is selected and nothing is reported.
5. *A promotion to an item absent from the replica still clears in a stale window* (round 2). Commit `value=ItemId(3)`, set a status, then commit `value=ItemId(999)`. No row is selected.
6. *A selection_mode of none still clears a stale window's selection, and the user's deselect stays refused* (round 2). Row 2 is selected live. A status is set. The user's `deselectAll(collection)` action leaves row 2 selected. Then a `selection_mode` none commit, with no promotion involved, leaves no row selected and reports nothing.

Round 3 adds `Harness.expectUserStillFrozen(at:)` at the end of tests 2, 4, 5 and 6, on Table and Tree. After the server-driven change it checks that the gate refuses again, that a real Down Arrow leaves `selectedRowIndexes` as the server left it, and that no interaction was emitted. A suppression flag left set by a promotion or a clear would open the gate. The arrow would then move the row, and nothing would be reported.

`server-rust/ssh-bridge/tests/bridge_failure_test.rs` has two new tests:
- `daemon_eof_ends_the_bridge_while_the_ssh_side_stays_open`: the library bridge delivers the daemon's last frame, returns within 5 s after the daemon side closes while the SSH side is still open, and the SSH side then reads EOF.
- `binary_exits_when_the_daemon_closes_while_stdin_stays_open`: the real binary is connected to a test listener with its stdin piped and held open. The daemon sends one frame and closes. The bridge exits with status 0 within 5 s, and its stdout reads the frame and then EOF. The test is skipped as root, like `binary_stderr_contains_no_protocol_bytes`, and was run as uid 1000 on Linux.

The existing bridge tests all still pass.

## Limitations

- Pre-existing and not a regression (verifier O2, probe P12 in `verify2-probes-Verify2StaleSelectionProbes.swift`). A multiple-selection collection has rows 2 and 4 selected. A `selection_mode` single commit then makes AppKit trim the selection to one row, and AppKit does not ask the gate. `tableViewSelectionDidChange` (`TableCollectionAdapter.swift`) runs unsuppressed, so it emits `selectionChanged` and stores local selection memory, both live and stale. The Tree path is the `.selectionMode` branch of `ControlFactory.applyProperty`, which runs `applySelectionMode(adapter.selectionMode, to: outlineView)`. This behaviour has not changed since `e101eb76`. A candidate follow-up is to apply a mode change with selection events suppressed. It is not fixed here.

- Pre-existing and not a regression (verifier F2): if the client is still writing when the daemon closes, `to_daemon` fails with EPIPE. `bridge_streams` then returns an error before `to_ssh` has drained what the daemon already sent. The tail of the daemon's output is lost and the bridge exits 1. The base `copy_bidirectional` bridge behaves the same way: on Linux both lose the tail in 5 of 5 runs, and on macOS the base loses it in 7 of 18 runs and this ticket in 6 of 18. Repro: `python3 -I verify-bridge_probe.py <bin> close_while_client_mid_write_daemon_never_reads` (also `close_while_client_mid_write_daemon_drains`); see `verify-bridge-probes-compare.log` and `verify-linux-docker-bridge-compare.log`. A follow-up could keep draining `to_ssh` after a `to_daemon` write error. It is not fixed here.

- The gate follows the client-owned status, which `ConnectionManager` sets when it handles an attempt's event. A selection made in the few milliseconds between the transport ending and that event is still dropped and kept locally. A host that drives `SessionController` without `ConnectionManager` shows no status and gets no gate.
- Tree disclosure stays local while a window is stale, and is not reported. An application that mirrors a client's disclosure lags until that client's next report.
- After `bridge_streams` returns, the bridge exits without running destructors. Everything it forwarded has been written and flushed by then, and it owns no other state (§20.1).
