## Design reading

- D1 §18: "The client MUST retain pending events but MUST NOT replay them or generate new semantic events until the server provides a machine-readable continuity decision." A selection made in a detached window therefore cannot be reported.
- D1 §22.5: the selection highlight is local, and "Only semantic outcomes are sent to the server". A local selection the server was never told of is a divergence, not a preference.
- D1 §22.7: server promotions are applied by the renderer (PX-011-G01). They are not user changes and are not affected.
- D1 §17: a lost transport must reach the client, which then shows DETACHED as client chrome (PX-022-G01).
- D1 §20.1: the bridge "attach[es]/detach[es] a connection from a session" and "does not own semantic state". A connection the daemon ended is over, and the bridge has nothing left to forward.
- D2 T17 and T19: the Unix-socket bridge and its SSH binding. D2 T28: collections and local selection. D2 T22–T24: attach, detach and resume, unchanged.

## Fix 1: a stale window takes no user selection change

**Defect.** This was found natively by PX-022's SSH test, in `PX-022/impl2-probe-run-1.log`.
- A Down Arrow in a detached srtop window moved the native highlight from PID 4101 to 4103.
- Its `SELECTION_CHANGED` was dropped (`sessionInactive`).
- The renderer's `collectionSelectionMemory` kept 4103 through a `RESUME_OK` replay, and through a same-session snapshot remount.
- So the table highlighted 4103, while the server's inspector, and the tag buttons that act on the process it describes, stayed on 4101.

**Fix.**
- `TableCollectionAdapter` and `OutlineCollectionAdapter` implement `selectionShouldChange(in:)`. AppKit asks this before every user-initiated selection change, whether by mouse, keyboard or deselection. It never asks for `selectRowIndexes`, which promotions use. The method answers `allowsUserSelectionChange()`, a closure.
- `ControlFactory.allowsUserSelectionChange` holds the gate. Every List, Table and Tree adapter it builds reads it, including the adapters a remount builds.
- `LayoutRenderer.setSessionWindowStatus(_:)` sets the gate: closed while a status is shown, open when it is cleared or empty.
- Scrolling, copying and tree disclosure are unchanged.

## Fix 2: `srui-ssh-bridge` ends when its daemon closes

**Defect.** This was also found natively, in `PX-022/impl2-probe-run-3.log`. After `SIGTERM` of srtop, an idle client stayed `connected`, with no stale status, for the whole 30 s wait. Its Connections row offered Open, not Connect. Reproduced by hand: the bridge logged "srui-ssh-bridge exited cleanly." and its process stayed alive. There were two causes:
- `bridge_streams` used `tokio::io::copy_bidirectional`, which returns only when both directions reach EOF. On daemon EOF it shut down the write half of tokio's stdout, which does not close fd 1, and then waited for the SSH side.
- After `bridge_streams` returned, `main` returned into a tokio runtime shutdown that waits for the blocking thread reading stdin. That thread returns only when the SSH side writes or closes.

**Fix.**
- `bridge_streams` forwards the two directions separately.
- Daemon EOF ends the bridge once what the daemon sent is flushed.
- SSH EOF shuts down the daemon's write half and keeps forwarding until the daemon closes, which is the existing half-close behaviour.
- `main` leaves with `std::process::exit(0)`, or `exit(1)` after logging a forwarding error.

## Tests

`client-macos/Tests/RendererAppKitTests/StaleWindowSelectionTests.swift` is a new swift-testing suite. Each test runs on a real `NSTableView` and a real `NSOutlineView`, mounted through `LayoutRenderer`.
1. *A stale Table or Tree keeps its selection against the user's arrow key, and moves once live.*
   - With a status set, `selectionShouldChange(in:)` is false.
   - A real Down Arrow key-down leaves row 2 selected and reports nothing.
   - After the status is cleared, the next Down Arrow selects row 3 and reports `SELECTION_CHANGED` for ItemId 4.
2. *A server promotion still selects in a stale window.*
3. *The gate follows the status through a remount.* The new adapter refuses, and an empty status clears the gate.

`server-rust/ssh-bridge/tests/bridge_failure_test.rs` has two new tests:
- `daemon_eof_ends_the_bridge_while_the_ssh_side_stays_open`: the library bridge delivers the daemon's last frame, returns within 5 s after the daemon side closes while the SSH side is still open, and the SSH side then reads EOF.
- `binary_exits_when_the_daemon_closes_while_stdin_stays_open`: the real binary is connected to a test listener with its stdin piped and held open. The daemon sends one frame and closes. The bridge exits with status 0 within 5 s, and its stdout reads the frame and then EOF. The test is skipped as root, like `binary_stderr_contains_no_protocol_bytes`, and was run as uid 1000 on Linux.

The existing bridge tests all still pass.

## Limitations

- The gate follows the client-owned status, which `ConnectionManager` sets when it handles an attempt's event. A selection made in the few milliseconds between the transport ending and that event is still dropped and kept locally. A host that drives `SessionController` without `ConnectionManager` shows no status and gets no gate.
- Tree disclosure stays local while a window is stale, and is not reported. An application that mirrors a client's disclosure lags until that client's next report.
- After `bridge_streams` returns, the bridge exits without running destructors. Everything it forwarded has been written and flushed by then, and it owns no other state (§20.1).
