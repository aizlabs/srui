## Design reading

- D1 §17, D2 T22: the session is srtop's, not the connection's. A lost transport moves it to DETACHED and srtop keeps sampling; only the client can know its transport is gone, so the window's connection state is client chrome (G01), and no srtop text claims a live connection.
- D1 §18, D2 T23: the server decides continuity. `RESUME_OK` replays the journal, `RESYNC_REQUIRED{SAME_SESSION}` sends a snapshot of the same incarnation, `RESYNC_REQUIRED{REPLACED}` sends a new incarnation's snapshot, and only the newest resume generation may act. srtop adds nothing to these decisions; it only configures the §18.1 window (`--journal-capacity`). A restart mints a new token and restores nothing, so it is always `REPLACED` (§17's incarnation rule).
- D1 §18 ("MUST NOT … generate new semantic events until the server provides a machine-readable continuity decision"), D1 §22.5 (local selection is reported): while detached, an interaction cannot be sent. The generic client already drops non-text interactions then; a dropped selection left the native highlight on a row the server never heard of (fixed by PX-022-G02).
- D1 §18.2, D2 T24: an event allocated in one incarnation is never replayed against another; a press made while detached is not allocated at all.
- D1 §18.3, D2 T29: a pending text edit is replayed only when the same session resumes; after a full resync unresolved local edits are discarded, not merged.
- D1 §20.1: the bridge is an ephemeral proxy; when the daemon goes, the transport is over (fixed by PX-022-G02).

## Implementation

### srtop (`apps/srtop/src/main.rs`)

- `--journal-capacity N` builds the session with `Session::mint_with_config(SessionConfig { journal_capacity: N, .. })`. Without it the runtime's default applies. As `srui-sessiond --journal-capacity`, a window that retains nothing is refused rather than clamped: `0`, `-1`, `many`, an empty or missing value, and a repeated option all exit non-zero before any socket is published. The module doc states that the continuity decision is the runtime's.
- Nothing else in srtop changes. The explorer's selection, follow, tags, last-observed records and per-client mirrors already live in the srtop process and are keyed by process instance and client instance, so they belong to the incarnation: a same-session reconnect keeps them, a restart loses them, which is exactly what §§17–18 require. The inspector, tags and follow need no reconnect hook (none is approved: no SDK attach/detach notice).

### What PX-022-G02 provides, and why this ticket needs it

Both were found by this ticket's native SSH test and are recorded in `docs/process-explorer/completions/PX-022-G02.md`:

- **A stale window takes no user selection change.** Without it, a Down Arrow in a detached window moved the native highlight from 4101 to 4103 while the dropped `SELECTION_CHANGED` left the inspector, and with it the tag buttons' target, on 4101 after a `RESUME_OK` replay or a same-session snapshot (`impl2-probe-run-1.log`: `selectedPIDs() → ["4103"]`). That is not safe cached inspection. G02 gates `selectionShouldChange(in:)` on the G01 status.
- **`srui-ssh-bridge` ends when its daemon closes.** Without it, after `SIGTERM` of srtop an idle client stayed `connected`, with no subtitle, for the whole 30 s wait (`impl2-probe-run-3.log`), so the REPLACED-after-restart case could not be reached and the window showed frozen data as live.

## What a session window shows (all over real localhost SSH, the generic client, `ConnectionManager`)

| State | Subtitle and accessibility help | Data | Input |
| --- | --- | --- | --- |
| live | none | live | everything |
| transport lost | `disconnected — showing data from revision N (stale)` | the cached replica at N, unchanged | no button press sent; no selection change; text kept locally |
| reconnecting | `connecting — showing data from revision N (stale)` | as above, then the catch-up | as above |
| same-session snapshot | `resynchronizing — showing data from revision N (stale)` | old N until ready, even after the snapshot is in | as above |
| replaced | `session replaced — rebuilding` | the new incarnation's snapshot in a new window | as above |
| ready | none | caught up | everything |

## Tests

### `apps/srtop/tests/continuity_test.rs` (new; the real binary over its private socket, a minimal replica)

1. `a_reconnect_within_retention_replays_the_missed_commits_and_keeps_every_identity`: select and tag 4101, lose the transport, let an independent observer see three more commits, `CLIENT_RESUME` → `RESUME_OK` naming the same token and frontier; the replay is contiguous from the client's revision with no snapshot; every PID keeps its item; inspector and tag unchanged; the freshness line moved on.
2. `a_reconnect_outside_retention_resynchronizes_the_same_session_with_the_same_identities` (`--journal-capacity 1`): `RESYNC_REQUIRED{SAME_SESSION}` with the same token and this client's frontier; the snapshot keeps 4101's item, the inspector target and the tag; the next commit applies.
3. `a_reconnect_after_a_restart_is_replaced_and_inherits_no_selection_or_tag`: stop srtop, start a new one on the same socket, resume → `RESYNC_REQUIRED{REPLACED}`, a new token, frontier 0; inspector `Selected process: none · select a row to inspect it`; tags `Tags: none · …` (no live and no historical tag, so no last-observed record either); no tagged row.
4. `an_unusable_journal_capacity_is_refused_without_publishing_a_socket`.
5. `live_procfs_identities_follow_every_continuity_decision` (Linux only, `--live-source`): srtop's own process through `RESUME_OK` (default window) and `SAME_SESSION` (window 1) keeps its item and the inspector; each restart is `REPLACED` with no selection.
6. `a_journal_capacity_replays_exactly_that_many_missed_commits_and_no_more` (round 2): with `--journal-capacity 1`, exactly 1 missed commit → `RESUME_OK` and exactly 2 → `RESYNC_REQUIRED{SAME_SESSION}`; with `--journal-capacity 3`, exactly 3 → `RESUME_OK` and exactly 4 → `SAME_SESSION`.
7. `the_default_journal_capacity_is_the_runtime_default_exactly` (round 2): without the flag, exactly `SessionConfig::default().journal_capacity` (1024) missed commits → `RESUME_OK` and one more → `SAME_SESSION`, so srtop's default is the runtime's, not merely large.

Tests 6 and 7 share `continuity_after_exactly`, which makes the missed-commit count exact rather than "at least": srtop runs with `--refresh-interval-ms 300000`, so after its first sample it commits nothing on its own. A second client selects 4101 and waits for the inspector's details (`Selected process: PID 4101 · worker`, without `loading details`); the detaching client is then at exactly that revision. Each missed commit is one `TAG_TOGGLE` by the second client, whose `ServerEventAck.revision_after_effect` must be exactly one more than the last. On `RESUME_OK` the replay must start at the client's revision and be exactly the missed `(base, base + 1)` commits; on a resync the snapshot must be at exactly the revision reached. Either way 4101 keeps its item and its tag state is the parity of the toggles. A stray commit fails the test rather than shifting the count. All 2,059 toggles of both tests take about a second.

The runtime's `RESUME_OK.replay_from_revision` is the client's own `last_applied_revision` (`srui_sessiond` handshake), the base of the first replayed commit; D1 §18's example shows `last_applied_revision + 1`. Test 1 asserts the runtime's value; the discrepancy is pre-existing and outside this ticket.

### `client-macos/Tests/SRUITests/ProcessExplorerShellTests.swift` (new test)

`detachedWindowsSayTheyAreStaleAndEveryContinuityDecisionReachesTheExplorer`: srtop `--fake-sequence --refresh-interval-ms 200` behind a real sshd and `srui-ssh-bridge`, opened through `ConnectionManager` with `makeSessionControllerAttempt` over `SSHTransport`. 2. 3. Resumed (`RESUME_OK`, events `connecting, ready`): held at ready the window says `connecting — … revision N (stale)` with replayed data in; after ready the subtitle clears, the token is the same, newer samples are in, 4101 keeps its item, it is still tagged (the detached untag was never sent), sampling is still live (the detached pause was never sent), and the highlight is the inspector's process.

5. Replaced: srtop is stopped with `SIGTERM` (the client now sees `disconnected …`, through PX-022-G02's bridge fix) and a new one with `--journal-capacity 1` started on the same socket; `4103` typed while detached. Events `connecting, replaced, ready`; held at ready the new window (the old one closed) says `session replaced — rebuilding` and the alert is `sessionReplaced`; after ready: a new token, no selection, `Selected process: none …`, `Tags: none …`, no tagged row, and 600 ms later the PID set is empty and all 3 rows shown (the old incarnation's edits are abandoned).
6. Same-session snapshot: select and tag 4101 in the new incarnation, detach, type `4101`, wait a second (several commits past a one-commit journal), then two overlapping `connect(id:)` calls, the first held (round 3) after its `CLIENT_RESUME` is sent and before its receive loop exists, so the overlap is deterministic. The newer attempt's events are `connecting, resynchronizing, ready`; held at ready, with the first still held, its window says `resynchronizing — showing data from revision N (stale)` with the snapshot already in; the first is then released and runs to its `stop()` with no `ready`, no status or subtitle change, no rollback and the same token; the superseded attempt's end never put `disconnected …` on the window; after ready: the same token, 4101's item, selection, inspector and tag kept; the PID set edit discarded (field empty, every row shown; D2 T29).

## Limitations

- The stale-window selection freeze is PX-022-G02's and follows the G01 status, so a selection made in the few milliseconds before `ConnectionManager` handles a transport end is still dropped and kept locally (G02 note).
- Tree disclosure stays local while detached and is not reported; srtop's mirror of that client's collapsed items then lags until its next disclosure report, which only affects srtop's "selection hidden under a collapsed parent" handling.
- srtop's own status lines are server text at the revision shown: `Live · sampling every 1000 ms` stays visible in a detached window under the `(stale)` subtitle. It describes srtop's sampling, not the connection.
- "Revision N" in the subtitle is the applier's revision at the transition (G01): after a same-session snapshot is in, the line still names the old revision until ready.
- The runtime's `replay_from_revision` differs from D1 §18's example by one (see Tests); unchanged here.
- `58d1c6f8`, which first carried the shared fixes, stays in this branch's history (a rewrite was refused by the environment's permission policy); its shared hunks are superseded byte for byte by G02's merge.
