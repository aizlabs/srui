## Design reading

- D1 §17, D2 T22: the session is srtop's, not the connection's. A lost transport moves it to DETACHED and srtop keeps sampling; only the client can know its transport is gone, so the window's connection state is client chrome (G01), and no srtop text claims a live connection.
- D1 §18, D2 T23: the server decides continuity. `RESUME_OK` replays the journal, `RESYNC_REQUIRED{SAME_SESSION}` sends a snapshot of the same incarnation, `RESYNC_REQUIRED{REPLACED}` sends a new incarnation's snapshot, and only the newest resume generation may act. srtop adds nothing to these decisions; it only configures the §18.1 window (`--journal-capacity`). A restart mints a new token and restores nothing, so it is always `REPLACED` (§17's incarnation rule).
- D1 §18 ("MUST NOT … generate new semantic events until the server provides a machine-readable continuity decision"), D1 §22.5 (local selection is reported): while detached, an interaction cannot be sent. The generic client already drops non-text interactions then; a dropped selection left the native highlight on a row the server never heard of (see "Shared fix 1").
- D1 §18.2, D2 T24: an event allocated in one incarnation is never replayed against another; a press made while detached is not allocated at all.
- D1 §18.3, D2 T29: a pending text edit is replayed only when the same session resumes; after a full resync unresolved local edits are discarded, not merged.
- D1 §20.1: the bridge is an ephemeral proxy; when the daemon goes, the transport is over (see "Shared fix 2").

## Implementation

### srtop (`apps/srtop/src/main.rs`)

- `--journal-capacity N` builds the session with `Session::mint_with_config(SessionConfig { journal_capacity: N, .. })`. Without it the runtime's default applies. As `srui-sessiond --journal-capacity`, a window that retains nothing is refused rather than clamped: `0`, `-1`, `many`, an empty or missing value, and a repeated option all exit non-zero before any socket is published. The module doc states that the continuity decision is the runtime's.
- Nothing else in srtop changes. The explorer's selection, follow, tags, last-observed records and per-client mirrors already live in the srtop process and are keyed by process instance and client instance, so they belong to the incarnation: a same-session reconnect keeps them, a restart loses them, which is exactly what §§17–18 require. The inspector, tags and follow need no reconnect hook (none is approved: no SDK attach/detach notice).

### Shared fix 1: a stale window takes no user selection change (generic renderer)

Native finding, confirming the risk the earlier attempt named: in the native test, a Down Arrow pressed in a detached window moved the native highlight from 4101 to 4103 (`impl2-probe-run-1.log`: `selectedPIDs() → ["4103"]`). The `SELECTION_CHANGED` was dropped (`sessionInactive`), so after a `RESUME_OK` replay, and equally after a same-session snapshot (which restores the local selection memory), the table highlighted 4103 while the inspector, and with it the tag buttons' target, still described 4101. That is not safe cached inspection.

Fix, in the generic client and keyed only on G01's client-owned status:

- `TableCollectionAdapter` and `OutlineCollectionAdapter` implement `selectionShouldChange(in:)`, which AppKit asks before every user-initiated selection change (mouse, keyboard, deselection) and never for `selectRowIndexes`. It answers `allowsUserSelectionChange()`.
- `ControlFactory.allowsUserSelectionChange` is set by `LayoutRenderer.setSessionWindowStatus(_:)`: false while a status is shown, true when it is cleared. Every List/Table/Tree adapter reads it through a closure, so a remount's new adapters keep the gate.
- Server promotions still apply (they are not user changes). Scrolling, reading and copying cached text are unaffected. Tree disclosure stays local.

Size: 35 lines across `client-macos/Collections/TableCollectionAdapter.swift`, `Collections/OutlineCollectionAdapter.swift`, `RendererAppKit/ControlFactory.swift`, `RendererAppKit/LayoutRenderer.swift`.

### Shared fix 2: the bridge ends when its daemon closes (srui-ssh-bridge)

Native finding: after `SIGTERM` of srtop, the client stayed `connected`, with no subtitle, for the whole 30 s wait (`impl2-probe-run-3.log`). An idle client was never told the daemon had gone, so the window showed frozen data as live and offered "Open" rather than "Connect". Two defects in `server-rust/ssh-bridge`, reproduced by hand (`srtop` stopped under a bridge whose stdin stays open: "srui-ssh-bridge exited cleanly." logged, process still alive):

- `bridge_streams` used `copy_bidirectional`, which returns only when both directions reach EOF. Daemon EOF shut down the write half of tokio's stdout, which does not close fd 1, and the bridge then waited for the SSH side to close.
- After `bridge_streams` returned, `main` returned into a tokio runtime shutdown that waits for the blocking thread reading stdin, which returns only when the SSH side writes or closes.

Fix: `bridge_streams` splits the two directions. Daemon EOF ends the bridge at once (everything forwarded is flushed); SSH EOF shuts down the daemon's write half and keeps forwarding until the daemon closes, as before. `main` leaves with `std::process::exit` (0, or 1 on a forwarding error) instead of returning. The `//!` spec list is unchanged (§20.1).

Size: about 60 lines in `server-rust/ssh-bridge/src/lib.rs` and `src/main.rs`, plus two tests.

## What a session window shows (all over real localhost SSH, the generic client, `ConnectionManager`)

| State | Subtitle and accessibility help | Data | Input |
| --- | --- | --- | --- |
| live | none | live | everything |
| transport lost | `disconnected — showing data from revision N (stale)` | the cached replica at N, unchanged | no button press sent; no selection change; text kept locally |
| reconnecting | `connecting — showing data from revision N (stale)` | as above, then the catch-up | as above |
| same-session snapshot | `resynchronizing — showing data from revision N (stale)` | old N until ready, even after the snapshot is in | as above |
| replaced | `session replaced — rebuilding` | the new incarnation's snapshot in a new window | as above |
| ready | none | caught up | everything |

## Tests

### `apps/srtop/tests/continuity_test.rs` (new; the real binary over its private socket, a minimal replica)

1. `a_reconnect_within_retention_replays_the_missed_commits_and_keeps_every_identity`: select and tag 4101, lose the transport, let an independent observer see three more commits, `CLIENT_RESUME` → `RESUME_OK` naming the same token and frontier; the replay is contiguous from the client's revision with no snapshot; every PID keeps its item; inspector and tag unchanged; the freshness line moved on.
2. `a_reconnect_outside_retention_resynchronizes_the_same_session_with_the_same_identities` (`--journal-capacity 1`): `RESYNC_REQUIRED{SAME_SESSION}` with the same token and this client's frontier; the snapshot keeps 4101's item, the inspector target and the tag; the next commit applies.
3. `a_reconnect_after_a_restart_is_replaced_and_inherits_no_selection_or_tag`: stop srtop, start a new one on the same socket, resume → `RESYNC_REQUIRED{REPLACED}`, a new token, frontier 0; inspector `Selected process: none · select a row to inspect it`; tags `Tags: none · …` (no live and no historical tag, so no last-observed record either); no tagged row.
4. `an_unusable_journal_capacity_is_refused_without_publishing_a_socket`.
5. `live_procfs_identities_follow_every_continuity_decision` (Linux only, `--live-source`): srtop's own process through `RESUME_OK` (default window) and `SAME_SESSION` (window 1) keeps its item and the inspector; each restart is `REPLACED` with no selection.

The runtime's `RESUME_OK.replay_from_revision` is the client's own `last_applied_revision` (`srui_sessiond` handshake), the base of the first replayed commit; D1 §18's example shows `last_applied_revision + 1`. Test 1 asserts the runtime's value; the discrepancy is pre-existing and outside this ticket.

### `client-macos/Tests/SRUITests/ProcessExplorerShellTests.swift` (new test)

`detachedWindowsSayTheyAreStaleAndEveryContinuityDecisionReachesTheExplorer`: srtop `--fake-sequence --refresh-interval-ms 200` behind a real sshd and `srui-ssh-bridge`, opened through `ConnectionManager` with `makeSessionControllerAttempt` over `SSHTransport`. A `RecordingConnectionAttempt` records each attempt's events and can hold its ready event, so the window is read with the decision's data in and the chrome not yet cleared; a `ContinuityRecorder` records every subtitle by KVO. A lost network is `SIGKILL` of the bridge serving this socket (`pgrep -f "srui-ssh-bridge <socket>"`); srtop is not told.

1. Connected: events `connecting, resynchronizing, ready` (the catch-up after WELCOME); no subtitle; select 4101, tag it.
2. Detached: `disconnected — showing data from revision N (stale)` on subtitle and accessibility help, title untouched; Tag (untag) and Pause pressed, Down Arrow pressed; the highlight stays on 4101; one second later revision, rows, freshness line and inspector are unchanged.
3. Resumed (`RESUME_OK`, events `connecting, ready`): held at ready the window says `connecting — … revision N (stale)` with replayed data in; after ready the subtitle clears, the token is the same, newer samples are in, 4101 keeps its item, it is still tagged (the detached untag was never sent), sampling is still live (the detached pause was never sent), and the highlight is the inspector's process.
4. Detached again, `4101` typed into the PID set: nothing filters locally; resumed, the edit is replayed and the table shows only 4101 (§18.3).
5. Replaced: srtop is stopped with `SIGTERM` (the client now sees `disconnected …` thanks to fix 2) and a new one with `--journal-capacity 1` started on the same socket; `4103` typed while detached. Events `connecting, replaced, ready`; held at ready the new window (the old one closed) says `session replaced — rebuilding` and the alert is `sessionReplaced`; after ready: a new token, no selection, `Selected process: none …`, `Tags: none …`, no tagged row, and 600 ms later the PID set is empty and all 3 rows shown (the old incarnation's edits are abandoned).
6. Same-session snapshot: select and tag 4101 in the new incarnation, detach, type `4101`, wait a second (several commits past a one-commit journal), then two overlapping `connect(id:)` calls. The newer attempt's events are `connecting, resynchronizing, ready`; held at ready its window says `resynchronizing — showing data from revision N (stale)` with the snapshot already in; the superseded attempt's end never put `disconnected …` on the window; after ready: the same token, 4101's item, selection, inspector and tag kept; the PID set edit discarded (field empty, every row shown; D2 T29).

## Limitations

- The selection gate follows the client-owned status, which `ConnectionManager` sets when it handles the attempt's event. A selection made in the few milliseconds between the transport ending and that event is still dropped and kept locally. A host that drives `SessionController` without `ConnectionManager` shows no status and gets no gate.
- Tree disclosure stays local while detached and is not reported; srtop's mirror of that client's collapsed items then lags until its next disclosure report, which only affects srtop's "selection hidden under a collapsed parent" handling.
- srtop's own status lines are server text at the revision shown: `Live · sampling every 1000 ms` stays visible in a detached window under the `(stale)` subtitle. It describes srtop's sampling, not the connection.
- "Revision N" in the subtitle is the applier's revision at the transition (G01): after a same-session snapshot is in, the line still names the old revision until ready (native evidence: `revision 9` shown with the replica at 17).
- Two shared fixes are included because the ticket's acceptance cannot pass without them (fixes 1 and 2 above). Both are small and tested; the bridge fix is in `server-rust`, not in the client.
- The runtime's `replay_from_revision` differs from D1 §18's example by one (see Tests); unchanged here.
