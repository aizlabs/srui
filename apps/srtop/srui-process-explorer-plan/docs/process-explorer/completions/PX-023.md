## Design reading

- D1 §19, §19.1: SSH provides host-key verification and user authentication; the client uses a fixed subsystem, never a shell-interpolated command, relies on the user's `ssh`/agent/`known_hosts`, and fails closed on host-key changes "according to normal SSH policy". The form therefore produces argv elements only and keeps `StrictHostKeyChecking=yes`.
- D1 §25: "SRUI does not weaken host-key checks and does not define an 'accept unknown host silently' mode." The alert explains and stops; it never offers to trust.
- D1 §22.1: the client is SSH adapter plus renderer; remote data never drives local behaviour. The form is local chrome. No remote app can open it, prefill it or choose a destination: `SavedConnection`/`ConnectDraft` are written only by the user's form and the local file.
- D2 T19–T20: `SSHTransport` and the capability handshake are reused unchanged. D2 T38: host, optional port, remote user and Connect, relying entirely on existing SSH credentials, with host-key behaviour "visible to the user, not silently bypassed".

## Implementation

### `client-macos/ConnectionManager/ConnectionEndpoint.swift` (new)

- `ConnectionEndpoint.parse(host:user:port:)` returns `Result<ConnectionEndpoint, ParseError>`. Only leading and trailing whitespace is dropped. The Host field also accepts `user@host`, `host:port`, `[v6]` and `user@[v6]:port`; a user or port given in both places must agree (`conflictingUser`, `conflictingPort`).
- Host: ASCII `[A-Za-z0-9._-]`, not starting with `-` or `.`, at most 253 characters (RFC 1035 text form). It may be an `ssh_config` alias. IPv6 must be bracketed and pass `inet_pton(AF_INET6)`, with an optional `%zone` of `[A-Za-z0-9._-]`; the brackets are stripped for `ssh`. A bare IPv6 address (`::1:22`) is refused because its end is ambiguous. `://` is refused as a URL.
- User: ASCII `[A-Za-z0-9._-]`, not starting with `-` or `.`, at most 64. Port: one to five ASCII digits, 1–65535; `+22`, `-22`, full-width digits and `000022` are refused. Name: local only, at most 128; an empty name defaults to `user@host[:port]`.
- Every `ParseError` has a user-facing `description`, which is what the form shows. A space or control character is named by its code point.
- `validate(savedHost:user:)` re-checks a stored entry. `displayString` brackets IPv6 for the Connections list.

### `client-macos/ConnectionManager/HostKeyRejection.swift` (new)

- Classifies OpenSSH's own `sshconnect.c` text: `changed` (`REMOTE HOST IDENTIFICATION HAS CHANGED`, `has changed and you have requested strict checking`, `POSSIBLE DNS SPOOFING DETECTED`), `revoked`, `unknown` (`host key is known for … you have requested strict checking`), or `unverified` (`Host key verification failed`). Anything else is not a host-key failure.
- `alertMessage(for:sshMessage:)` names the endpoint and the known_hosts name (`[host]:port` for a port other than 22), says SRUI never adds or replaces a key, says how to check it outside SRUI (`ssh-keygen -R '…'`, connect once from Terminal), and appends OpenSSH's text, which includes the offered fingerprint for a changed key.

### `client-macos/ConnectionManager/ConnectionManager.swift`

- `ConnectDraft.endpoint`, `validationMessage` and `savedConnection` use `ConnectionEndpoint`.
- `ConnectionManager.sshConfiguration(for:)` (nonisolated, pure) is the one configuration every attempt uses, extracted unchanged from `beginAttempt`. The production factory still builds `SSHTransport(configuration: request.configuration)`.
- `connect(id:)` refuses an entry whose stored host/user no longer validate (`invalidInput`, "This saved connection’s endpoint is invalid: …"), before any attempt or argv exists.
- `recordFailure` turns a host-key failure into `ConnectionAlert.Kind.hostKeyRejected`, titled "Host Key Not Trusted". It reads the entry before `markDisconnected` forgets a never-connected draft. Other failures keep "Connection Failed" with the original message. `presentAlert` folds a host-key failure into a pending REPLACED disclosure exactly as it does a connection failure.

### `client-macos/ConnectionManager/ConnectionManagerView.swift`

- `ConnectSheet` (now internal, for the native test): Host (prompt `host, user@host:port or [::1]`), Remote User, Port (`optional`), Name (`optional`); the validation reason in red; Cancel and Connect at the bottom as the cancel and default actions. Connect is disabled and `submit()` re-checks validity. The NavigationStack and toolbar were replaced by a plain stack so the buttons are the sheet's own controls. The row endpoint uses `ConnectionEndpoint.displayString`.

- `apps/srtop/README.md`: srtop from the Connections window, through the same form and configuration as counter.

## Limitations

- The native form test drives `ConnectSheet` hosted directly in a window rather than through **Add Connection** in the full Connections window, and reaches Connect by its Return key equivalent: SwiftUI draws its buttons without `NSButton`s, and the in-process accessibility tree of the hosting view is empty without an assistive client. The sheet-to-`manager.connect(_:)` wiring in `ConnectionManagerView` is one unchanged line; the manager path is covered by the live tests. Manual check: run `client-macos/.build/debug/RendererDemoApp` with no arguments, click **Add Connection**, type `host;id` (expect the inline message and a disabled Connect), then a real host.
- The live tests substitute only the identity file and known_hosts path in the manager's configuration, because the ephemeral sshd's key cannot be in the user's `~/.ssh/known_hosts`. Every other option is asserted equal to `sshConfiguration(for:)`. The user's own `~/.ssh/config` still applies to every `ssh` the form starts, as before.
- Host-key classification reads OpenSSH's English diagnostics. A future OpenSSH wording change degrades to the generic "Host key verification failed" case, or to the plain "Connection Failed" alert; neither ever connects. Text a remote server writes to stderr after authentication could also mimic these phrases: that only shows a blocking alert.
- The `RendererDemoApp --ssh/--user/--port` developer command line (used by `apps/srtop/run.sh ssh`) still passes its arguments as given, behind the existing `--`. It does not go through this form's validation.
- One connection window, no fleet management, no stored secrets, no new retry or reconnect semantics, as the ticket requires.
