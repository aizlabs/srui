## Round 3

- **R2-1, the scenario:**
  1. A context has been ready.
  2. A reconnect gets REPLACED, which resets the applier to revision 0 (`SessionController.swift`, the REPLACED replica discard).
  3. The transport drops before the replacement's snapshot.
  4. Round 2 then sent `CLIENT_RESUME(new session)@0`, because it gated the resume on `hasBeenReady` alone.
  5. `RESUME_OK` emitted ready over an empty replica, so the window read live with no roots until the replay landed.
- **The fix** (`ConnectionManager.swift`, client only):
  - `ConnectionAttemptRequest.resumeSessionID` now requires `ConnectionSessionContext.hasCommittedReplica`, which is `hasBeenReady && applier.lastAppliedRevision > 0`.
  - In `beginAttempt`, a context with `needsFreshContext` (`hasBeenReady` with the applier back at revision 0) is dropped, and its windows are closed. A new one is created, exactly as for a cold relaunch.
  - An attempt still running on the old context is superseded by the token as before, and its `runAttempt` tail closes that context's windows again.
- **Why a fresh identity, not just HELLO on the old outbox:**
  - After REPLACED, the old outbox is bound to the replacement incarnation, and its frontier is whatever that decision reported. `EventOutbox.confirmFreshSession` (the WELCOME path) keeps the outbox's sequence counters and retained intents. HELLO on that outbox would therefore continue numbering from state the client no longer has a replica for.
  - The cold-path rule (§18: no reuse of a `client_instance_id` without its frontier state) gives the same answer: a new outbox, so a new identity at frontier 0.
  - Nothing is lost by this. The REPLACED decision already abandoned every unresolved event and text edit, and new events stay disabled until a snapshot commits. So between the REPLACED decision and the drop, the old outbox has nothing to keep.
- **Kept:** a warm reconnect with a real replica (revision > 0) still sends `CLIENT_RESUME` at its committed revision. "a context that has been ready resumes with CLIENT_RESUME at its committed revision" pins this, at revision 1. Generation supersession and all token guards are unchanged.
- **Tests:**
  - Rewritten: "interrupted replacement reattaches with HELLO from a fresh context, ready only with the snapshot" (previously "… resumes the new session from an empty replica"), run with REPLACED on the original connection and on a later resume.
  - Its scripted server answers whichever handshake arrives, as srtop would: `CLIENT_HELLO` gets WELCOME plus the snapshot; `CLIENT_RESUME` gets `RESUME_OK` with the replay held back.
  - At the moment ready is observed, the test asserts that the replica has roots at revision 1 and that the frame was `CLIENT_HELLO`. It also asserts a new context and a client identity different from the emptied context's.
- **The 4096-byte session-ID bound** (R2-3) is kept as defence in depth. 128 scalars already cap an ID at 512 bytes. The byte check is O(1) on a native string and runs first, so a hostile multi-megabyte ID is refused before its scalars are counted.

### Findings and fixes

- **F1 (medium): a cold relaunch with srtop's default journal was shown live over an empty, then historical, replica.**
  - The cold `CLIENT_RESUME` at revision 0 got `RESUME_OK`, replaying from revision 1. `SessionController` emits `ready` at revision 0 before the replay is applied. `ServerResumeOk` carries no replay target, and no protocol field was added.
  - Round 1's live test forced the snapshot path with `--journal-capacity 1`, so the replay path never ran. The README claimed "either way the window is built from srtop's complete current state", which was wrong for that path.
  - Fix, `ConnectionManager.swift`:
    - `ConnectionSessionContext.hasBeenReady` is set when a session is first ready in the context.
    - `ConnectionAttemptRequest.resumeSessionID` is the saved session ID only once `hasBeenReady` is set, and `nil` otherwise. `makeSessionControllerAttempt` passes it as the controller's `sessionId`.
    - A context with no committed replica (a cold relaunch, or attempts that never became ready) therefore attaches with `CLIENT_HELLO` and its fresh identity. This is §18's documented attach path: the cold `CLIENT RESUME` is a MAY.
    - `ready` then comes only after the WELCOME catch-up snapshot is applied, as for any fresh attach. A warm context (one that has been ready) resumes exactly as before.
  - Replacement on the HELLO path: `SessionControllerConnectionAttempt` gets `rememberedSessionID`, the saved ID, only for a HELLO attach.
    - If the WELCOME (`.resynchronizing(.fresh(sessionID:))`, or `.ready` for a session at revision 0) names a different session, it yields the existing `.replaced(previousSessionID:newSessionID:)`.
    - The manager's REPLACED handling is unchanged: it saves the new ID with revision 0 before the snapshot, shows the blocking "Session Replaced" alert naming both IDs, and sets the window chrome.
    - The same ID gives `.resynchronizing` and no alert.
  - Generation supersession and every token guard are unchanged for both paths. In the live double connect, the superseded HELLO attempt now ends `failed`, because its WELCOME lost the outbox binding to the newer attempt. That is ignored by the token guard, as before.
- **F2 (low): two mutants survived round 1's tests.**
  - `superseded-writes-store` survived every test. A new unit test, "a superseded attempt's late replaced and ready never reach the row or the file", holds the older attempt's start, lets the newer attempt save, then releases the older one with its `replaced` and `ready` queued.
  - `forget-resurrect` was killed only by a PX-022-G01 test. A new PX-024 test, "a forgotten entry is not brought back when its running session becomes ready", covers it.
- **F3 (low): an unreadable saved file was destroyed by the next save.**
  - `SavedConnectionStore` now writes `{"connections": [...], "version": 1}` (`currentVersion`). A bare JSON array is the pre-versioned form of version 1 and still loads.
  - Anything else fails `load()`: truncated, empty, another shape, an out-of-range or negative revision, or an unknown version. The file is then moved aside with one `rename(2)` to the fixed `<name>.unreadable` (`backupURL`). The rename replaces any earlier backup, so at most one is kept.
  - It then throws `LoadError.movedAside(reason:backup:)`. Its description, shown in the "Couldn’t Load Connections" alert, names the backup path.
  - If the move itself fails, `LoadError.leftInPlace` is thrown and every later `save` throws `UnreadableFileInPlace`, so the file is never written over.
- **F4 (low): saved and server-reported session IDs were never validated, and duplicate entry IDs loaded as two rows.**
  - `SavedConnection.validSessionID` accepts an ID only if it is:
    - non-empty;
    - at most 4096 UTF-8 bytes, checked before scalars are counted;
    - at most `maximumSessionIDScalars = 128` scalars;
    - free of every scalar `ConnectionEndpoint.firstDisallowedScalar` refuses (control including NUL, newline and ESC; format; separators; surrogate; private-use; unassigned).
  - Bound: `srui-sessiond` mints 32 lowercase hex characters (`mint_session_id`, `server-rust/sessiond/src/session.rs`). §17 makes the ID opaque, so 128 leaves room for another server's format (a 36-character UUID string, a prefixed token) and refuses anything longer.
  - On load, an invalid ID is dropped together with its revision. The entry keeps its endpoint and label and has no remembered session.
  - Server-reported IDs in `.ready` and `.replaced` pass the same rule before they are stored or shown. An invalid one is not stored, and the alert says "a session with an invalid ID" instead of echoing it.
  - Duplicate entry IDs: `SavedConnectionStore.normalized` keeps the first of each ID and drops the rest.

## Audit: what already existed

Most of what this ticket asks for was already in `client-macos/ConnectionManager/` (the D2 T38 work, hardened by PX-022-G01 and PX-023). It had never been exercised against srtop across a relaunch.

| Requirement | Before this ticket | Gap |
| --- | --- | --- |
| Endpoint labels persist locally | `SavedConnectionStore` (one JSON file, atomic replace) holds `id`, `label`, `host`, `port`, `user`, `sessionID`, `lastKnownRevision`. PX-023 re-validates a loaded entry before argv. | None; reused, no second store. |
| Remembered revision is not resume authority | `ConnectionSessionContext` is created per manager, so a relaunch gets an empty `TransactionApplier` at revision 0. `lastKnownRevision` is written only from a ready replica (`persistableRevision`) and is never read by the attempt path. | Proof only. The row captioned it `Session <id> · revision N`, which reads like a resume point. |

| Double connect | Attempt tokens per entry. A newer `connect` cancels the older task, and every handler checks the token. The shared outbox's resume generation latch supersedes the older controller. | Proof only (cold relaunch). |
| Forget is local | `remove(id:)` drops the entry and saves; a running attempt is left to end on its own (PX-022-G01). | Proof only. |

No generic protocol, SDK or runtime facility was needed. Every behaviour sits on the existing `CLIENT_RESUME` path. §18 explicitly allows the cold form: a fresh `client_instance_id`, `last_applied_revision = 0`, `last_acked_event_seq = 0`, and empty terminal, text and event continuity.

## Design reading

- D1 §6.3: the client keeps a non-authoritative replica, and render objects are disposable. Nothing durable on the client is authoritative.
- D1 §17: the session's lifetime is independent of the connection. A detached session stays alive, and `session_id` is an incarnation token.
- D1 §18: without an atomic durable checkpoint, a relaunched client "MUST NOT claim a persisted last-known revision and MUST NOT reuse the former `client_instance_id`". It "MAY still send `CLIENT RESUME` for the persisted `session_id` with a fresh `client_instance_id`, `last_applied_revision = 0`, `last_acked_event_seq = 0`". A persisted revision is "presentation metadata only". Resume attempts are generation-bound per outbox. REPLACED abandons the old retry set.
- D1 §18.1–18.2: the journal is bounded, so a gap means a snapshot. The server's receive window refuses `event_seq <= last_processed_event_seq` for a bound identity (`OutsideReceiveWindow` in `server-rust/event-dedupe/src/lib.rs`). Reusing an identity without its frontier would therefore collide.
- This ticket implements no literal revision-N cold resume. That would need the atomic checkpoint §18 describes (replica, outbox, text, terminal offsets, resources, negotiation), and nothing partial is persisted to imitate it.

### `SavedEndpointRelaunchLiveTests` (new; real localhost sshd, real `srui-ssh-bridge`, real srtop)

Each launch is a `ConnectionManager` with its own production attempt factory; only the test key and known_hosts are substituted, and the configuration is asserted equal to `ConnectionManager.sshConfiguration(for:)`. The quit is `shutdown()`. Only the saved file passes between launches. The fixture (`LiveSSHD`) outlives every client. It is stopped from a dedicated `Thread` (`OwnedFixture.shutDownOffMainActor`), never the main actor or the cooperative pool, and every spawned process sets its stdio before `run()`. A `HandshakeRecordingTransport` wraps `SSHTransport` and keeps the first frames, so the test reads the `CLIENT_RESUME` actually on the wire.

1. **"a relaunch rebuilds srtop's complete current state with a fresh identity, and forgetting leaves the session alive"**. srtop runs `--fake-sequence --refresh-interval-ms 200 --journal-capacity 1`.
   1. **First launch.**
      - It connects through `ConnectDraft`, sees at least three updates, and clicks **Pause view**. That is its event 1, acknowledged (`lastAckedEventSeq == 1`). The test then quits.
      - The file holds the id, label, endpoint and session ID, and `lastKnownRevision ==` the frozen revision (8 in the recorded run).
   2. **Relaunch: a new manager over the file.**
      - The entry is listed unchanged with status `unknown`.
      - Two `connect(id:)` calls overlap. The first is held by the controller's own `handshakeSendDidFinishForTesting` seam after its `CLIENT_RESUME` is sent and before it can read the answer. Both attempts share one session context.
      - Both `CLIENT_RESUME` frames carry the saved session ID, revision 0 (not the remembered 8) and frontier 0. They carry no text or terminal state and the new launch's identity, which differs from the first launch's.
      - The newer attempt's events are `connecting, resynchronizing, ready`: revision 0 is outside a one-commit journal, so the same session sends a snapshot.
      - The held attempt is released and runs to its end without `ready`. Status, alert, window subtitle and revision are unchanged.
   3. **Complete current state.** srtop is paused, so nothing has been published since the quit. Even so:
      - the rebuilt model rows and item IDs equal the first launch's frozen rows and IDs;
      - the sampling status still says `Paused at …`;
      - the whole tree (82 nodes), the rows, the item IDs and the revision equal what an independent fresh `ConnectDraft` attach of another client receives.
   4. **No sequence collision.** The relaunched client clicks **Resume view**:
      - its event 1 is acknowledged;
      - srtop samples again (`Live …`);
      - revisions advance.
      Under the first launch's identity, sequence 1 would be refused as outside the receive window.
   5. **Forget is local.** After `remove(id:)`:
      - the entry and its file record are gone;
      - the forgotten entry's still-open transport keeps receiving commits;
      - the srtop process is running;
      - the observer stays connected to the same session ID.

## Limitations

- No literal revision-N cold resume. A relaunch always attaches as a new client (`CLIENT_HELLO`). Anything typed or queued but unsent when the app quit is lost by design (§18: no atomic durable checkpoint). Window geometry, scroll position and local selection are not restored across a relaunch.
- Round 1's claim here was wrong: a cold revision-0 `RESUME_OK` against srtop's default journal was not "long gone in any real session". It is the common case for a relaunch within the journal's 1024 commits, and it showed live chrome over an empty, then historical, replica (verifier F1). Round 2 removes that path for cold contexts; see "Round 2".
- Round 2's limitation is closed in round 3. It read: "a warm context emptied by REPLACED still resumes at revision 0, and closing that needs a protocol or Session change". The second half was wrong: the client-only fix in "Round 3" closes it. `CLIENT_RESUME` is now sent only from a context with a committed replica. Any context without a committed replica attaches with `CLIENT_HELLO`, so no window is declared ready over an empty replica on any path this manager drives. A context that has been ready and was then emptied is replaced by a fresh context, with a new outbox and identity. A context that has never been ready keeps its context and identity: its outbox has never been bound to a session (round 3 verifier, V3-3).
- Round 3 verifier V3-4 (present before this ticket): if Connect is pressed while the `.replaced` handler is still awaiting its save, the token guard drops that attempt's "Session Replaced" alert. The saved session ID is still updated. The window is one file write.
- Replacement detection on the HELLO path compares the WELCOME's session ID with the saved one. That is exact for a server that serves one session per socket (sessiond's `connection.rs` binds every connection to its one `Session`, and srtop is one session per process), which is the only deployment the runtime has.
- The `<name>.unreadable` backup is one file, replaced by the next unreadable file and otherwise kept until the user removes it. Nothing else reads or evicts it.
- A forgotten entry's running session keeps its window and transport until the connection ends (PX-022-G01 behaviour, unchanged). Forgetting never closes or detaches anything remote; to stop watching, the user closes the window or quits.
- Two saved entries for the same endpoint are independent clients of one srtop session. That is intentional, and no fleet administration is implied.
