### Log audit: the "connection ended" lines

- **What is printed, and where.**
  - srtop logs `srtop: connection ended: {error}` to stderr (`apps/srtop/src/main.rs`).
  - The standalone `srui-sessiond`, which R1 does not run, logs `Connection ended: {e}` at WARN
    through `tracing_subscriber::fmt()` to stdout (`server-rust/sessiond/src/main.rs:455`).
  - For an unsupported version, the error is `SessionError::UnsupportedCoreVersion`
    (`session.rs:215`): `unsupported core protocol version {requested:?}; this server speaks
    {supported:?}`. The live box logged, for example, `srtop: connection ended: session error:
    unsupported core protocol version "1.5.0"; this server speaks "0.5.0"`.
- **It is escaped.** `{:?}` escapes newlines, ESC and bidirectional controls, so a client cannot
  inject lines.
- **It is unbounded.** One 2.5 MiB version gives a WARN line of about 2.5 MB, repeatable once per
  connection up to the 16 MiB frame limit.
- **It is pre-existing.** It is identical at `e549ee8a`.
- **Nothing was changed here.** It is recorded in R1.md's known gaps, with a follow-up: bound
  sessiond's "Connection ended" line, and srtop's matching one.
- **Both streams are audited.** The box's entrypoint, `restart-srtop` and the live test all send
  srtop's stdout and stderr to `/var/log/srtop.log`. `docker logs` carries both container streams,
  and the test writes each source into one file. `live-checks.sh` says so beside the audit.

### Findings and fixes

- **F1 (high): incompatible versions do not fail clearly.**
  - **The finding.** When the server refuses a client, the user sees only "transport ended:
    receive stream closed by peer". Core-version compatibility is a symmetric major.minor match,
    and the server checks the CLIENT HELLO first, so this is the refusal a real version skew
    produces.
  - **The fix.** The user approved a server-side fix: sessiond will send the existing
    `ServerHandshakeRefused{UNSPECIFIED, bounded detail}` before closing. It is built separately
    as PX-026-G02, in branch `codex/PX-026-G02-handshake-refusal`. This round touches neither
    sessiond nor the protocol.
  - **Preparing the gate for it.** The live compatibility test is split in two:
    - `compatibleProfilesConnectAndTheClientRefusesAnIncompatibleServerClearly` covers the
      compatible client and the client's own refusals. It passes.
    - `theServerRefusesAnIncompatibleClientWithItsReason` covers a client offering only
      `standard-widgets/2` and a client of core 1.5.0. It requires that each failure starts with
      "server refused the handshake:" and names `org.srui.standard-widgets/1` or `1.5.0`, and that
      the connection manager's alert holds the same text and never "transport ended".
  - **Against today's base the second test fails, as intended.** Five of five runs failed it with
    4 issues each, reading `failure="transport ended: receive stream closed by peer"`. It is not
    skipped.
  - **For PX-026-G02.** The detail must contain the requested version, or the required profile's
    `name/version`. `SessionError::UnsupportedCoreVersion` and `NegotiationError` already print
    both. The client shows it as "server refused the handshake: reason 0: <detail>".
  - **Plan.** `PX-026-G02` is added to this ticket's `depends_on` in task-index.json, the ticket,
    IMPLEMENTATION_PLAN.md and TASK_INDEX.md. `validate_plan.py` now reports exactly two failures
    until G02's own task entry merges: "Unknown dependency PX-026-G02 for PX-026-G01" and
    "Execution order violates PX-026-G02 -> PX-026-G01". Expect a task-index.json conflict on the
    rebase; keep both sides.
- **F2 (medium-high): the live compatibility check is flaky.** The `handshake()` helper waited
  for `isHandshakeComplete && revision >= 1`, but asserted `isEventDispatchEnabled`, which the
  controller enables only after the snapshot is rendered and finalized. It now waits for all
  three.
  - I audited the suite's other waits. The package and privacy tests already wait for
    `isEventDispatchEnabled`. The continuity and host-key tests wait on the connection manager's
    status or alert, and assert nothing sampled before it.
  - `live-checks.sh` ran ×5 under `caffeinate -u -d`. All six other checks passed in every run.
- **F3 (high): the walkthrough deletes user data outside a fresh account.**
  - **Freshness refusal.** Before any write, the walkthrough refuses, with exit 4, an account
    that already holds any of these. It names each one it finds and writes nothing.
    - the install prefix;
    - `saved-connections.json` or `saved-connections.json.unreadable`;
    - `~/.codex/srtop-devbox`;
    - a `srtop-devbox` container.
  - **Override.** `--allow-existing-srui-data` overrides the refusal and is documented as
    dangerous.
  - **No purge of what it did not create.** `--purge-settings` is passed only when the run itself
    created the saved connections, so ones that existed before survive even under the override.
    The verify step checks them by digest.
  - **Stop on early failure.** A failed preflight or prerequisites step ends the run with
    `STOPPED after …` and `SUMMARY FAIL`, before anything is planted, built or installed.
  - **Docs.** CLEAN_ACCOUNT_WALKTHROUGH.md says all this, and says to run the walkthrough only on
    a revision that includes PX-026-G02.
- **F4 (medium): `checklist-session.sh`'s teardown is not byte-exact.** The `~/.ssh/config` edit
  moved into `apps/srtop/r1/ssh-config-alias.sh`.
  - **Refusals.** It refuses a symbolic-link config or `~/.ssh`, an existing block, and an
    existing `srtop-devbox` host.
  - **Backup and append.** It backs up with `cp -p` into a private `mktemp -d`. It appends in
    place, adding a separating newline only when the last line lacks one.
  - **Restore.** If the file still equals the original plus the block, it restores the original
    in place (`cat` into the file), byte for byte, and resets the original mode. An originally
    absent file is removed, along with a `~/.ssh` it created. An originally empty file stays
    empty.
  - **Edited during the session.** If the file was edited, it removes only the block's lines and
    says so.
  - **Signals.** The checklist session now traps HUP as well as INT and TERM.
- **F5 (low-medium): R1.md was wrong that a new enum is needed.** R1.md and this note now say the

- **F6 (low): the envelope overstated what is enforced.**

   version, kernel, Rust toolchain and binary digests (below).
2. **The user runs the clean-account walkthrough.** It is
   `apps/srtop/r1/clean-account-walkthrough.sh`, with instructions in `CLEAN_ACCOUNT_WALKTHROUGH.md`.

   linker's ad-hoc signature, nothing is notarized and no Apple credentials are involved. The R1
   notes say signed or notarized distribution is out of scope.

   `apps/srtop/r1/voiceover-keyboard-checklist.md`, set up by `checklist-session.sh`, and holds the
   four outstanding manual checks.

## Limitations and follow-ups

- **A server refusal gives no reason yet.** When the server refuses an incompatible client offer,
  the client can say only that the connection closed. The fix uses the existing
  `ServerHandshakeRefused{UNSPECIFIED, bounded detail}`. It needs no new message, enum value or
  registry entry, and it lands in PX-026-G02. (Round 1 wrongly said a new enum value was needed;
  verifier F5.)
- **Window identity across a resume.** In the connection manager, the resumed session's window is
  a different `NSWindow` (`same NSWindow: false`). This is recorded, not asserted. Checklist item 9
  watches its effect.
- **CI.** The live checks and the walkthrough need Docker and are not in CI. `selftest.sh` runs
  in `apps/srtop/test.sh`, the Darwin pre-push path, not in a CI job.
- **Tooling not run.** `shellcheck` is not installed here. The devbox's apt packages are not
  pinned.
- **Known follow-ups.** They are listed in R1.md: the `SSHTestSupport.terminate` wedge risk, the
  AF_UNIX lost-FIN audit, the pre-push hook's display, the load-sensitive PX-025 and PX-010-G01
  timing tests, PX-023's `posix_spawn` lc-debt, G02 O2 and the T35 capability-only check.
