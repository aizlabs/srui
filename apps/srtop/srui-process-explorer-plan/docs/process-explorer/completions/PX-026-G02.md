# PX-026-G02 implementation evidence

- Ticket: PX-026-G02, "Refuse incompatible clients with the existing handshake refusal". It is a generic `srui-sessiond` change and an R1-prerequisite.
  - It is added in this commit: ticket file, `task-index.json` entry (`depends_on: ["PX-026"]`, refs D1 §§15, 18, 19.2, 26, 32.7), master-plan block and queue row.
  - It is placed before PX-026-G01 in `execution_order`. PX-026-G01's own entry is not edited here; that happens on its branch.
- Why: the R1 gate PX-026-G01 requires that incompatible versions fail clearly. An independent verifier found that sessiond closed the connection without a frame in two cases:
  - a HELLO or RESUME core version it cannot serve (`SessionError::UnsupportedCoreVersion`);
  - an offer that does not satisfy the session's required profiles (`SessionError::Negotiation`).
  - Both sides use the same `major.minor` rule (`server-rust/sessiond/src/session/handshake.rs` `core_version_is_compatible`, `client-macos/Session/SessionController.swift` `sruiCoreVersionIsCompatible`), and the server checks the HELLO first. Real core-version skew therefore always took the silent-close path.
- User decision (approved): sessiond sends the existing `ServerHandshakeRefused { reason: HANDSHAKE_REFUSAL_REASON_UNSPECIFIED, detail }` before closing. There is no change to `protocol/srui.proto`, `registry.yaml`, codegen, generated files or enum values.

## Design reading

- D1 §18: "The server validates the core version and negotiates the offered profiles against the current session before it subscribes the connection or emits replay, snapshot, resource, or Terminal data. … A newer server MUST fail closed when the core version is absent/incompatible or the offer does not satisfy the session's required profiles."
  - Sending one diagnostic refusal and then closing is still failing closed. No session data is sent and nothing is subscribed.
- D1 §15: the active set is the server's required profiles plus the matching optional ones. A missing required profile is therefore a negotiation failure.
- D1 §19.2: the refusal is control-class. `logical_class_for_server_envelope` (`server-rust/sessiond/src/outbound/scheduler.rs`) already maps `ServerHandshakeRefused` to `Control`; it is unchanged and correct.
  - The refusal is written directly on the handshake writer, as the PX-004-G01 snapshot refusal is, before the active-session scheduler exists.
- D1 §26: every string sent to the client is bounded. The detail is at most 256 bytes, far below any `max_string_length` a real client advertises. It never reflects peer bytes verbatim.
- D1 §32.7 (suite 7, extension negotiation): see *Conformance* below.
- The design document has no `ServerHandshakeRefused` message. It is the PX-004-G01 protocol extension (`protocol/README.md`, *Snapshots larger than one frame*). This ticket reuses it and does not change the read-only design.

## Change

`server-rust/sessiond/src/connection.rs`:
- `refuse_undeliverable_snapshot` becomes `refuse_handshake`. It keeps the same `WRITE_TIMEOUT`-bounded `framed_write.send` (which flushes) and the same best-effort warning on failure, and it is still called from the existing HELLO and RESUME `Err` arms before `return Err(error.into())`. That return drops both socket halves, which closes the stream.
- A pure `handshake_refusal(&SessionError) -> Option<ServerHandshakeRefused>` decides what is sent:
  - `SnapshotUnrepresentable` / `SnapshotUndeliverable` → `SNAPSHOT_UNDELIVERABLE`, `error.to_string()` bounded to 1024 bytes. This is unchanged.
  - `UnsupportedCoreVersion { requested, .. }` → `UNSPECIFIED`, `unsupported core protocol version <echo> (this server serves <major.minor>)`.
  - `Negotiation(UnsatisfiedRequiredProfiles { missing })` → `UNSPECIFIED`, `client offer does not satisfy required profiles: [<p1>, …]`.
  - Anything else → `None`, so the existing close-only behaviour is kept.
- How the detail is bounded:
  - `<echo>` is at most 32 characters of the client's `core_version`. Any character outside `[A-Za-z0-9.+_-]` becomes `?`, `...` marks truncation, and an empty version (the proto3 default) reads `(none)`.
  - `<major.minor>` is derived from `CORE_VERSION` (`0.5`).
  - The profile list names the server's missing required profiles (sorted, because `CapabilitySet` is a `BTreeSet`): at most 8, then `+N more`. It never names the client's own offer.
  - The whole detail then goes through `bound_diagnostic_string(_, 256)`.
  - It contains no path, session ID or other secret.
- Doc comment of `refuse_handshake`: states when the refusal is sent, which reason each case uses, and that every other failure stays close-only.

No subscription or frame precedes the refusal. Both errors come from `negotiate_client`:
- HELLO: `negotiate_hello` at the top of the bootstrap loop.
- RESUME: the first statement of the bootstrap loop, after only the identity, terminal-map and pending-text-edit input checks.
- Both run before snapshot export, replay collection, `subscribe_client_locked`, `attach_terminals` and any frame write (`server-rust/sessiond/src/session/handshake.rs`).
- The transport attachment guard taken at connect (§17) drops on return. The new tests assert `attached_count() == 0` afterwards.

### Handshake failure kinds and what each does now

| Failure | Error | Behaviour |
| --- | --- | --- |
| HELLO/RESUME `core_version` absent or of another `major.minor` | `UnsupportedCoreVersion` | **new:** one `ServerHandshakeRefused{UNSPECIFIED, detail}`, then close |
| Offer lacks a required profile (HELLO or RESUME, same or replaced incarnation) | `Negotiation` | **new:** one `ServerHandshakeRefused{UNSPECIFIED, detail}`, then close |
| Catch-up/resync snapshot undeliverable within client limits | `SnapshotUnrepresentable` / `SnapshotUndeliverable` | unchanged: `ServerHandshakeRefused{SNAPSHOT_UNDELIVERABLE, detail}`, then close |
| No first message within 5 s | `HandshakeTimeout` | unchanged: close only |
| EOF before the first message | `ConnectionClosed` | unchanged: close only |
| Malformed or oversized first frame | `Framing` | unchanged: close only |
| First message is not HELLO/RESUME | `UnexpectedMessage` | unchanged: close only |
| Session already terminating/expired at attach | `TerminalState` | unchanged: close only |
| Invalid `client_instance_id`, too many `terminal_stream_offsets`, invalid pending text-edit refs | `InvalidInput` (and the text-edit validation errors) | unchanged: close only |
| Server namespace contract misconfigured | `InvalidConfiguration` | unchanged: close only (a server fault, not a client incompatibility) |
| Lock poisoned, outbound hub closed, resource error | `LockPoisoned`, `OutboundClosed`, `Resource` | unchanged: close only |
| Shutdown during the handshake | — | unchanged: `Ok(())`, close |
| Write timeout or lag while sending WELCOME/RESUME_OK/snapshot/replay | `WriteTimeout`, `LaggedResyncRequired` | unchanged |

`client-macos/Session/SessionController.swift` (the `.serverHandshakeRefused` case): a minimal generic change.
- The client already failed as `.handshakeRefused` and logged `Reconnecting will not recover (§18, §26).`; it never said "Reconnect and resume to recover" for a refusal.
- It used to prefix an `UNSPECIFIED` refusal with a meaningless `reason 0:`. For `UNSPECIFIED` it now shows the detail alone, or `no reason given` when the detail is empty.
- `SNAPSHOT_UNDELIVERABLE` and unrecognized reasons are formatted as before, and `boundedRefusalDetail` still applies.
- `ConnectionManager` shows `SessionFailure.description` in its "Connection Failed" alert and is unchanged.

The core-version case is formatted the same way. The text the real server sends to a `1.5.0` client is `unsupported core protocol version 1.5.0 (this server serves 0.5)` (live raw-wire test). The native client cannot offer another core version without a code change, because `SRUICoreVersion` is a constant. Its rendering of that refusal is therefore covered over `PipeTransport` with the skew reversed.

It asserts the exact detail, the `UnsupportedCoreVersion` result and `attached_count() == 0`.

## Conformance (§32.7)

No vector was added.
- Suite 7 has no vector directory. It is a set of test runners.
- The message adds no new wire shape. Its encoding and decoding are already pinned in all three languages by `golden_handshake_refused.bin` (PX-004-G01). An `UNSPECIFIED` refusal is the same message with the default reason.
- What changed is when the server sends the message, and a fixture cannot express that.

Instead, suite 7's Rust runners in `protocol/conformance-vectors/suites/manifest.json` gain `cargo test -p srui-sessiond --test connection_failure_test`. `scripts/run-conformance --suite 7` therefore exercises the server refusal. Its Swift runners already include `HandshakeNegotiationTests`, which holds the new client case. Vector counts and `expected.json` are unchanged.

## Compatibility

- Clients since PX-004-G01 already decode `ServerHandshakeRefused`. They fail with `handshakeRefused` and do not reconnect. Before this change they showed `server refused the handshake: reason 0: <detail>`; the `reason 0:` prefix is now dropped for `UNSPECIFIED`.
- A client older than PX-004-G01 has no such `oneof` case and ignores the frame (`guard let payload = message.msg else { return }`). It then sees the same close it sees today.
- These notes are recorded in `protocol/README.md`, *Incompatible clients are refused, not silently closed (PX-026-G02)*.

## Limitations
- Pre-existing, unchanged here: `srui-sessiond`'s accept loop logs `Connection ended: {e}` through `tracing_subscriber::fmt()`, which writes to **stdout**, not stderr. The independent verifier corrected this; it found the line on stdout with stderr empty (`server-rust/sessiond/src/main.rs:455`, `session.rs:215`).
  - For `UnsupportedCoreVersion` the `Display` includes the full requested string (`{requested:?}`). That form escapes newlines, ESC and bidi characters, so there is no line or ANSI injection.
  - A hostile client can still make one long WARN line: 2,500,219 bytes for a 2.5 MiB version, repeatable per connection up to the 16 MiB frame limit. The line is identical at the base `e549ee8a`.
  - The bound in this ticket applies to the wire detail only. PX-026-G01's log and diagnostic disclosure audit should decide whether to bound that log line, and must read stdout as well as stderr.
- Info (verifier):
  - The 256-byte cap can cut mid-name when 8 or more long required profiles are missing. The registry's six profiles total about 190 bytes, so this does not happen today.
  - `refuse_handshake` ignores the shutdown signal, so a client that never reads can delay daemon shutdown by up to `WRITE_TIMEOUT` (30 s). This predates this ticket.
  - The client's `boundedRefusalDetail` bounds length only. This server now sends only sanitised ASCII.
- Pre-existing, not changed: `srui-sessiond`'s accept loop logs `Connection ended: {e}` on stderr. For `UnsupportedCoreVersion` the `Display` includes the full requested string (`{requested:?}`), so a hostile client can still make one long server log line. The bound in this ticket applies to the wire detail only. PX-026-G01's log/diagnostic disclosure audit should decide whether to bound that log line.
- The client's log line for any refusal still cites `(§18, §26)`. It is generic text from PX-004-G01, and §26 is about the snapshot case. It is left unchanged to keep the client change minimal.
- The native client cannot offer an incompatible core version without a code change. The live core-version check is therefore on the wire, and the native rendering of that message is checked over `PipeTransport`.
