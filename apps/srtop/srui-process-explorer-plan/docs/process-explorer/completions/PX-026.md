## Round 2 (verifier finding 1, low)

**Finding.** No test checked that the outbox keeps an automated event until it is settled. The verifier's mutant `automation-no-settlement-wait` removes an automated event from `pendingEvents` right after the send in `EventOutbox.allocateAndSend`. All three tests still passed, because they checked only the final `pendingCount == 0` and `lastAckedEventSeq`. Under that mutant, an automated event would be missing from reconnect replay (§18.2) and no test would fail.

**Fix (test-only).** Every one of test 1's four actions (native, automated, automated, native) now runs through `whileSettlementIsHeld`.

- `AutomationWireTap.holdInbound()` stops delivering inbound chunks to the client. The tap still decodes them, so the test sees srtop's PROCESSED `ServerEventAck` on the wire before the client applies it.
- While the ack is held, the test asserts `pendingCount == 1`, `lastAckedEventSeq == seq - 1` and `eventSeq == seq`. The event's frame is on the wire and its seq is allocated, but it is still retained and not settled.
- `releaseInbound()` then delivers the held chunks in order, and the event settles (`pendingCount == 0`, `lastAckedEventSeq == seq`).
- The check is the same for native and automated actions. The stream's end and the fixture teardown also release held chunks.
- No product hook was added. `pendingCount`, `lastAckedEventSeq` and `eventSeq` are existing public `EventOutbox` properties.
- Measured (`r2/impl2-probe.log`): `native seq 1: pending=1 lastAcked=0`, `automation seq 2: pending=1 lastAcked=1`, `automation seq 3: pending=1 lastAcked=2`, `native seq 4: pending=1 lastAcked=3`, all while the ack was held.

**Replay after a transport drop: not added.** This suite's fixture is one `SSHTransport` and one `SessionController`. Dropping and resuming the transport needs the PX-022/PX-024 continuity harness (`ConnectionSessionContext`, `ContinuityRecorder`, a restarted bridge). That is not a cheap addition here. Replay of retained events in their original identity is the existing `EventOutbox.resendPendingEvents` path, and it is the same for every pending event whatever its origin. That generic property is covered by the existing outbox replay tests (`EventOutboxRetryTests`, `PendingEventReplayLoopTests`), not by a PX-026 test.

## Design reading

- **D1 §22.9.** The client keeps a read-only semantic-tree API with stable node identities, roles, labels, values, hierarchy, state and advertised actions. A local consumer writes `find(role=button, label="Restart").activate()`, never `click(x, y)`. The surface is semantic: it MUST NOT expose `NSView` pointers or classes as identity. Automation actions MUST travel through the normal SRUI event path and the server's authorization checks. They MUST NOT mutate the authoritative tree directly or bypass `enabled` or capability state. An XPC surface SHOULD stay disabled until its authorization model is specified.
- **D2 T35.** T35 is the in-process API: `client-macos/Accessibility/Accessibility.swift` (`SemanticInspector`, `SemanticTreeSnapshot`, `SemanticNodeSnapshot`, `SemanticNodeHandle`), served by `SessionController.makeSemanticInspector()`. Its handles call `performSemanticAction`, which uses the same `enqueueSemanticAction` → `validateSemanticAction` → `send*` → `EventOutbox` path as `enqueueNativeSemanticAction`, the native renderer trampoline (`renderer.onInteraction`). Validation checks the epoch, that the session is active, the negotiated `standardWidgetsV1` capability, that the node exists, `enabled`, the registry emits matrix and the selection mode. T35 has no XPC or IPC surface. T35 already covers what PX-026 needs, so no generic facility, protocol message or SDK change was added.
- **D2 T24.** T24 covers event settlement: `event_seq` is contiguous per client instance, and each event is settled by `ServerEventAck` (`settled_event_seq`, status, echoed `event_id`). PX-026 proves that settlement is identical at the wire for automated and native actions.
- **The existing T35 coverage.** `SemanticInspectionAutomationTests` and `SemanticInspectorTests` prove the generic properties over a pipe fixture. PX-026 applies them to srtop over real SSH, in the unchanged generic client.

### No external endpoint

## Limitations

- **An automated selection does not move the native highlight.** It is a semantic event: the server inspects B while the native table still highlights A, which the user selected. This is T35's existing behaviour. srtop, as in PX-013, never selects rows server-side. PX-026 makes no claim that the native highlight follows automation.
- **The disabled-control native refusal is unobservable at the client.** The client classifies `nodeDisabled` as a race and reports nothing either way. So "identical" for a disabled control is proved by the same thrown error on the automated path, no frame, no consumed `event_seq` and an unchanged server state on both paths, not by comparing two reported errors. For `unsupportedAction` the two reported errors are compared directly.
- **The lsof check covers this process only.** Mach and XPC services are invisible to lsof. Their absence rests on `scripts/check-client-no-listener-api.sh` (see Codex review) and on no product source changing. The process-wide diff is asserted only in the isolated invocation; a full run reports it without asserting it.
- **`SemanticAutomationError.description` prints an event TypeRef with the node-type name of the same local ID**, for example `TypeRef(standard:1/Surface)` for ACTIVATE. The cause is the existing `TypeRef.description` precedence, and it is cosmetic: the errors compare by value. The report uses `standardEventName` and is unaffected. Not changed here (out of scope).
- **No external automation surface exists.** That remains future work that needs its own reviewed permission model (§22.9), as the standing contract requires.
