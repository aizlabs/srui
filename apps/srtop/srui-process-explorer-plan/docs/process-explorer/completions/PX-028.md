## What was built

`apps/srtop/src/actions.rs` (new), wired by `install_actions` (`src/lib.rs`), `--actions` (`src/main.rs`) and `impl ActionTargets for ProcessView` (`src/refresh.rs`).

- **`ActionIntent`** — immutable (private fields, getters only, no setter): `IntentId` minted by the gate (increasing), the exact targets (`ActionTarget`: whole `ProcessKey`, PID, owner, a bounded "PID 4101 · worker"), `ActionOperation::Terminate` (a graceful termination *request*; PX-030 makes it real), `ActionParameters { scope: SelectedProcess }` fixed by the button, `ActionContext` (the account the daemon acts as, as the source states it — the daemon's effective UID for the live source, which §27 binds to the SSH-authenticated user — and the preparing `client_instance_id`), `created_at` and `expires_at` on a suspend-aware monotonic clock (`on_demand::SuspendAwareClock`, so a suspend shortens rather than extends an intent's life). Default lifetime 30 s.
- **`ProcessActions`** — the server-only interface an authorized action reaches: `supports(operation)` and `execute(&Authorized) -> Execution`. `Authorized` has a private field: only `ActionGate::confirm` constructs it, after `authorize` re-checked everything, so nothing else can reach an executor. **The only implementation is `DryRunExecutor`**, which returns `Requested` for an operation it offers and sends nothing; it holds no handle and names no signal API. A new audit rule (`the_only_production_action_executor_is_the_dry_run_executor` in `tests/no_process_control_test.rs`) fails on any other production `impl ProcessActions for …`; the existing token, import and binary audits still hold for every module, so the executor cannot name `kill`, `libc`, `nix`, `Command`, `pidfd_*`.
- **Outcomes** — `ActionOutcome::{Refused{reason: Refusal}, Unsupported, Requested{dry_run}, ObservedComplete, Failed, OutcomeUnknown}`. An executor answers only `Execution::{Requested, Unsupported, Failed, OutcomeUnknown}`: it has no way to claim an observed completion, which only a later observation can establish (PX-031). The dry-run status is `Dry run #1 requested (terminate PID 4101 · worker): nothing was sent to the process, and whether it ends is not observed`.
- **Read-only mode on the server** — `ActionMode::{ReadOnly, DryRun}`. `ActionGate::writable` is checked at Prepare and at Confirm. In read-only the controls are published disabled (event validation rejects a click, §7.4), and a click that reaches a handler anyway — the button enabled in the store — is refused, and the controls are republished disabled. `publish` diffs against what the *store* holds, not what the gate last wrote, so anything that enabled a control is put back.
- **Eligibility** (`ActionGate::admit`, at Prepare and again for every target at Confirm), answered by `ProcessView` from its own rows: the target must be the latest scan's own instance by whole `ProcessKey` (`TargetState::Current`); a row kept unconfirmed from an earlier scan, a last-observed record (PX-021), another instance under the same PID (same source/host/boot/PID namespace), or nothing at all are refused as `Unconfirmed`, `Historical`, `Replaced`, `Unknown`. It must be a process, not a thread; its PID known; its owner `Known(account)` — another owner and an unread owner are both refused; and not a protected PID (`DEFAULT_PROTECTED_PIDS = [1]`; PX-030 adds the support chain, and this list is never the only boundary). A paused view is refused (its rows are not the latest scan), as is a source that states no account.
- **Intent-specific freshness** (`ActionGate::authorize`) — accepted only when the Confirm click's `observed_revision` is at or after `confirmable_from`, the revision of the commit that first published this intent's confirmation (taken from `transaction_with_result`, so it is the exact commit, not a later one); by the preparing client instance; before `expires_at`; with the account unchanged; and every target eligible now. Telemetry commits between Prepare and Confirm change none of these. An intent whose confirmation never committed is discarded. A confirm consumes the intent whatever the result; redelivery of the same event is answered by the runtime's dedupe cache without re-running the handler (§18.2).
- **What a click carries** — nothing is read but `client_instance_id` (bound by the session to its connection) and `observed_revision`. Event arguments are never read, so a forged item ID, PID text or list cannot widen or change the target set, and a new selection after Prepare does not retarget the intent (the intent holds the key, not the selection).
- **The controls** — only with `--actions read-only|dry-run` (and a process source): a `Row` (node 83) under the inspector with `Prepare dry run: terminate selected` (84), `Confirm` (85, relabelled `Confirm dry run: terminate PID 4101 · worker` while an intent is pending), `Cancel` (86) and a status `Text` (87). Without `--actions` no action node or handler exists and the R1 shell has exactly its old nodes; the only change it sees is a row ceiling 4 KiB lower (below). An unknown mode, a missing or repeated value, and `--actions` without a source are refused before the socket is published. The row ceiling charges `ACTIONS_RESERVE_BYTES` (4 KiB) whether or not the controls exist, so they never change which rows fit; `the_widest_action_controls_fit_their_snapshot_reserve` measures the widest controls (status 1024 B and Confirm label 512 B, both with the cut mark) on the encoder. The PX-008 audit's handler allowance gains exactly `ACTION_PREPARE`/`ACTION_CONFIRM`/`ACTION_CANCEL` with bare `ACTIVATE`, with five new refusal self-tests (another event type, the status, the row, a computed target, a path).
- **T21 code** (`examples/process-monitor/src/terminator.rs`) was read and not reused: it signals by PID with a check-then-act window, which is exactly what PX-029's handle work replaces. Nothing in this ticket signals.

## Limitations

- **Nothing is executed.** The only executor is the dry run. Handle resolution (PX-029), graceful termination and the support-chain denylist (PX-030), and observing what a request did (PX-031) are not implemented; `ObservedComplete` exists as a type only.
- **Expiry is enforced at Confirm, not shown proactively.** An expired intent keeps Confirm enabled until it is clicked (then refused and disabled); no timer republishes it. PX-030's confirmation panel is where expiry, navigation and identity replacement invalidate it visibly.
- **One pending intent per instance**, shared by every client of the session: a Prepare replaces any pending one; another client's Confirm is refused but consumes it, and any client's Cancel discards it without a client check (both fail-safe: neither can make anything execute). An intent left pending by a client that disconnects stays until it is replaced or a click meets its 30 s expiry.
- **The account is the one the source states** (`Accounts::current`): the daemon's effective UID for the live source; a fixture's own account for fixtures. A source that states none refuses every action.
- **Not checked here:** a target whose PID is reused between the latest scan and execution. The dry run executes nothing; PX-029 resolves a handle and re-checks identity at acquisition.
