## Design decisions

- **Navigation, defined.** The server's resolved selection (the inspector's selected process instance) no longer naming the intent's process instance: selecting another row, clearing the selection, or a filter, search, user-filter, thread or view change that moves or clears it. Sorting, column changes, telemetry samples and the tree's disclosure keep it as long as the same instance stays selected. Pause and resume are not navigation: the intent is **held** (its Confirm disabled, Cancel available) while the rows are not the latest scan, as PX-028 established; expiry and navigation still withdraw a held intent.
- **Prepare A, select B, confirm: the old intent is rejected.** Of the two outcomes the acceptance allows, PX-030 takes "rejected", because it makes "navigation invalidates" literal. PX-028 kept an intent across a selection change; that is now a withdrawal. The selection change's own handler revalidates the gate (`ProcessView::sync_actions` → `ActionGate::revalidate`), which withdraws the intent and deletes its panel in the same handler, so A's Confirm is gone for every client and a click on it still in flight is rejected by event validation (`NodeNotFound`). Independently, `authorize` refuses a navigated intent at Confirm (`Refusal::Navigated`), so no ordering of commits and clicks can confirm A while B is selected.
- **Acquire at Confirm, not at Prepare.** The handle is opened by the terminator only after the gate re-checked the intent in full, checked against the intent's key after `pidfd_open` (PX-029), checked again with `key_of(id) == intent key` (`terminate::signal_held`) and settled at once. Justification: (1) no descriptor is held while a person reads the confirmation, so Cancel, expiry, navigation, withdrawal and a new Prepare have nothing to close and cannot leak one; (2) binding at Prepare adds no safety, because the key already pins the instance by its start time, which the post-open check compares, so a PID reused between the clicks is refused (`Replaced`) and the newcomer receives nothing; (3) the window between the identity check and the signal is the two system calls. The terminator owns exactly **one** `ProcessHandles` table, which PX-008's audit now pins.
- **Node-ID scheme.** A prepared intent's panel takes three fresh node IDs, `PANEL_ID_BASE + 3n` (row), `+ 3n + 1` (question) and `+ 3n + 2` (Confirm), for the `n`-th intent of the run (`actions::PanelIds`), `PANEL_ID_BASE = 1_000_000`, far above every fixed node (≤ 87). A slot is never used twice, even if its commit failed. At most `DEFAULT_CONFIRMATION_PANELS` = 4096 panels per run; past that Prepare is refused (`Refusal::PanelsExhausted`: "restart srtop to prepare more"). All 4096 Confirm handlers are registered once in `install_actions`, before the socket is served, each bound to its slot; a click on slot `n` confirms only the intent shown in slot `n` (`ActionGate::confirm_panel`), never a later one. The old panel is deleted in the commit that consumes, cancels, replaces or withdraws its intent. Node 85 (PX-028's generic Confirm) is never created any more.
- **Support chain, derived on the server** (`src/support.rs`, `ServerSupportChain`): srtop itself (`std::process::id()`; srtop embeds the session runtime, so it is the session daemon too) and its ancestors by `/proc/<pid>/stat`'s parent field up to the namespace root; and every connected client's transport — the accepted socket's peer PID (`SO_PEERCRED` through tokio's `peer_cred()`, registered in `main`'s accept loop for as long as the connection lasts) — with its ancestors (the `sshd: user@notty` session and the monitor above it). Read afresh at every Prepare, Confirm and revalidation. It is consulted only for keys from the live `/proc` source (a fixture's PID names no process of this host). It **fails closed**: if any member's record cannot be read, or the kernel reported no peer PID, every live target is refused (`Refusal::SupportChainUnknown`). It is checked after PX-028's owner, identity and freshness checks, never instead of them.
- **Configured protected targets.** `--protect-pid PID` (repeatable, at most 64, positive, only with `--actions`), added to `DEFAULT_PROTECTED_PIDS = [1]` (PID 1 in the reader's namespace, the only one handles are opened in), in every source. Minimal by intent: no file, no names.
- **How actions are enabled.** Only `--actions terminate` (with a process source) sends anything; `--actions dry-run` still uses `DryRunExecutor`, and `--actions read-only` disables everything. Without `--actions` the package is unchanged: no action node or handler, read-only. For the devbox: `SRTOP_ARGS="--live-source --refresh-interval-ms 1000 --actions terminate" apps/srtop/devbox/devbox.sh up`.
- **Unsupported hosts.** `PidfdTerminator` probes once at start (`ProcessHandles::probe`, which opens and closes a handle on srtop itself and sends nothing). `Unsupported` (not Linux, `ENOSYS`, a filter's `EPERM`, `ENODEV`) makes `ProcessActions::unavailable` report the reason; the gate publishes Terminate… disabled with `Terminate unavailable: <reason>; nothing can be sent to any process`, and a click that gets through is `Unsupported`. There is no PID-addressed fallback anywhere.

## What was built

- `src/actions.rs` — `ActionMode::Terminate`; `PanelIds`, `PanelView`, the panel in `ActionsView`, `create_panel`, the panel diff in `publish_view` (delete the old panel and create the new in one commit; confirmable from that commit's revision); `confirm_panel`; `ActionIntent::still_selected`; `revalidate`/`withdrawal` and `Report::Withdrawn` (`Withdrawn #1 (…): <reason>; nothing was requested`); `SupportChain`/`SupportRole` and `Refusal::{SupportChain, SupportChainUnknown, Navigated, Withdrawn, PanelsExhausted, NotHeld}`; `Execution::Refused`; `ProcessActions::unavailable`; mode-dependent labels ("Terminate…", `Confirm: terminate PID 4101 · worker`), the question (`Terminate PID 4101 · worker (UID 1000)? Confirm sends it SIGTERM, which asks it to exit; it may handle or ignore it.`) and the requested status (`Requested #1 (…): SIGTERM was sent; the process may handle or ignore it, and whether it exits is not yet observed`).
- `src/terminate.rs` (new) — `PidfdTerminator` (one `Mutex<ProcessHandles>`, probe at start), `signal_held` (the `key_of` check and the one `settle`), and the mapping of every acquisition and settlement result to `Requested`, `Refused` (`Replaced`, `NotHeld`), `Unsupported` or `Failed`, each saying nothing was sent where nothing was.
- `src/support.rs` (new) — `ServerSupportChain`, `Transport` (a guard that unregisters on drop), bounded ancestry (`MAX_ANCESTRY` 64; a cycle is refused).
- `src/lib.rs` — `pub mod support; pub mod terminate;`, `ACTION_CONFIRM` removed, `install_actions` registers Prepare, Cancel and one `on(panel_confirm, ACTIVATE, ..)` per slot.
- `src/refresh.rs` — `sync_actions` revalidates, and runs after every republication and inspector publication too (so a selection change withdraws in its own handler).
- `src/main.rs` — `--actions terminate`, `--protect-pid`, the executor choice, the support chain and the per-connection transport registration.
- `tests/no_process_control_test.rs` — the PX-008 audit, adjusted minimally (below).

### The PX-008 audit, adjusted minimally

- `src/terminate.rs` (`EXECUTOR_MODULE`) alone, besides `src/handle.rs`, may name the handle module, and only `ProcessHandles`, `HandleSignal`, `SignalOutcome`, `AcquireError`, `HandleId` (`EXECUTOR_HANDLE_ITEMS`); the seam (`PidfdSystem`, `Pidfd`, `LivePidfds`) stays refused there.
- Across all production code (`handle_reach_violations`): exactly one handle-table construction, `ProcessHandles::live()`, in `src/terminate.rs` (`EXECUTOR_TABLE`); exactly one settlement, `.settle(id, HandleSignal::Terminate)`, there (`EXECUTOR_SETTLE`); exactly one `PidfdTerminator::live()`, in `src/main.rs`. Any `ProcessHandles::`/`PidfdTerminator::` associated function named elsewhere, called or taken as a value, is reported.
- The production `ProcessActions` are exactly `DryRunExecutor` (`src/actions.rs`) and `PidfdTerminator` (`src/terminate.rs`) (`PRODUCTION_EXECUTORS`).
- `kill`, `libc`, `unsafe`, `syscall`, `extern`, `nix`, `Command` remain refused in `src/terminate.rs` as everywhere but `src/handle.rs`, which stays the only system-call site; its pinned `unsafe` blocks and signal mapping are unchanged.
- The handler allowance gains exactly `on(panel_confirm, ACTIVATE, ..)` in `src/lib.rs` (`PANEL_CONFIRM`); `ACTION_CONFIRM` leaves `ACTION_BUTTON_CONSTANTS`.
- New self-tests (`the_termination_executor_is_the_one_reach_into_the_handle_module`): a second identical settlement, a settlement elsewhere, of another handle or by path; a second table in `main` or in the module, one over another system, a constructor taken as a value; a second terminator in `main`, one built in `lib.rs`; the settlement removed (0); the seam in the executor module; `libc::kill`, `kill`, `unsafe`/`libc::syscall`, `nix`, `Command` in the executor module; the panel registration in `actions.rs` or `terminate.rs`, under `VALUE_CHANGED`, computed, another identifier, a path, `ACTION_CONFIRM`. The PX-029 self-test now also refuses the handle module's real constructs in `src/terminate.rs`. `the_production_action_executors_are_the_dry_run_executor_and_the_pidfd_terminator` replaces the dry-run-only rule.
- The nm import comment says the binary now reaches `syscall` through the terminator of `--actions terminate`; the forbidden import list is unchanged (no `kill` import is attributed, no `pidfd_*` import exists).

## Limitations

- **Requested is not exited.** `Sent` means the kernel accepted SIGTERM for that instance; it may handle or ignore it, and a zombie accepts it too. The status says so, and nothing reports completion; observing the outcome, a deadline and "still running" are PX-031's.
- **Each panel is a structural commit, and the generic client remounts on structural commits** (§23's conservative classifier, `LayoutRenderer.apply`): every Prepare, withdrawal and Confirm rebuilds the window's native views. The selection survives it (asserted natively); no client code changed. A client that mutated in place on a node insertion would avoid the remount; that is a renderer improvement, not PX-030's.
- **A bounded number of confirmations per run.** 4096 panels; then Prepare is refused until srtop restarts. The 4096 Confirm handlers are registered at start because the runtime cannot remove a handler, and the session never reuses a node ID, so its used-ID set grows by three per Prepare (at most 12 288).
- **One pending intent per instance, and one selection.** PX-028's single pending intent stays; the inspector's selection is the server's one resolved selection, so another client selecting a row withdraws the first client's intent (fail-safe: nothing is sent).
- **Proactive expiry is at the next sample or selection.** An expired panel is withdrawn at the next refresh tick (at most the refresh interval, also while paused) or view change; a click before that is refused at Confirm.
- **Support chain limits.** Protection is by PID within srtop's PID namespace; a member that exits leaves the chain at the next read. The transport is the socket peer (the bridge); a process the bridge or the SSH session started is not part of the chain unless it is an ancestor. With `/proc` mounted `hidepid` so that ancestors' records are unreadable, every live target is refused (fail closed). It is never the only boundary.
- **PX-029 residues carry over:** a replacement started in the same clock tick under the same PID is indistinguishable by start time; `EPERM` at the signal is reported as a failure without telling permission from a filter.
- **The devbox native test is opt-in.** It needs a box started with `--actions terminate` and `SRTOP_PX030_TERMINATE_BOX=1`, is not part of `test.sh` or `live-checks.sh` (whose read-only package test it must not disturb), and was run against an isolated box as recorded above.
