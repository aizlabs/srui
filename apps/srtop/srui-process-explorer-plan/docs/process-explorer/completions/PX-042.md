## Design

- **Catalogue shape.** Validation is per entry and then across entries (`Catalogue::new`): well-formed dotted key (≤ 64 bytes), the definition's unit text must equal the typed unit's `describe()`, `Unit::carries(raw)`, the formatter's single accepted `(unit, raw)` pair, aggregation only on a quantity, sort that fits the unit; tier policy (non-empty, no repeats, `Expensive` or `ProcessContent` never `EverySample`, `System` never `OnDemand`); duplicate key; at most `MAX_ENTRIES` (512).
- **Scheduling.** Cheap fields stay in the atomic snapshot read every sample (unchanged path). Expensive fields are only collected through `OnDemandFields::demand(wanted)`, where `wanted` is the complete current set of (process instance key, field) pairs for selected/visible rows: fields not in it are forgotten (never read again), sampled or unknown keys are refused and counted, at most `max_fields` tracked and `max_in_flight` reads outstanding (superseded by correction rounds 1–3: a stuck read holds its slot until `read_deadline`, then counts against `max_abandoned` until it returns, and its field is never read again while it is outstanding). A field with a value younger than `min_interval` is not re-read.
- **Not blocking the loop.** `demand` only enqueues; `collect_completed` drains a channel with `try_recv`. Production reads run on tokio's blocking pool, as the scan already does.
- **Ordering.** Each read gets a sequence number; a completion is accepted only when it answers the read its slot is currently waiting for. Since correction round 3 a field never has more than one read outstanding (a field shown again adopts its in-flight read), so a newer read is only dispatched after the older one answered; a stray or repeated older completion is discarded.
- **Staleness / timestamps.** A value is stamped with the monotonic time its read started (`SourceTime`, distinct from the snapshot's `SnapshotTime`). Stamps must satisfy `issued_at ≤ started ≤ finished ≤ drain time`, otherwise the read is `Failed`. A value older than `max_age` is `Stale`, never `Present`. A value of the wrong raw type for its entry is `Failed`.

## Correction round 1

Candidate `0b434b08` passed independent verification; an adversarial review reproduced two defects in `on_demand.rs` and raised a third. All three are fixed in one commit on top; only `on_demand.rs`, the README's catalogue section, the ledger entry SRUI-PX042-004 and this note changed. This section supersedes the Design text above where they differ.

- **C1 — starvation (reproduced).** `demand` dispatched in the caller's order every call, so with more demanded fields than `max_in_flight` and a re-read interval no longer than the loop period, the front fields were re-read forever and the rest stayed warming up. Fix: the fields due for a read are sorted by (last reading's time, last reading's sequence, position in `wanted`) with never-read fields first, so equal ages rotate instead of favouring the front. Test `every_demanded_field_is_read_within_a_bounded_number_of_ticks`: 6 fields, `max_in_flight` 1, 2 and 4, `min_interval` 1 s and a 1 s tick; every field leaves warming up within `ceil(6/k)` ticks, no value is ever older than `ceil(6/k)` s afterwards, and read counts stay within one of each other over `4 * ceil(6/k)` further ticks.
- **C2 — leaked in-flight slot (reproduced).** `in_flight` only fell when a completion arrived, so a read that panicked, was dropped unrun or hung held its field warming up and its slot forever. Fix: (a) every job owns a `Reply` guard that sends `Err(Failed)` on drop if no result was sent, covering a panic (unwinding drops it) and a job dropped by the pool; (b) every dispatched read is recorded by sequence with its issue time, and a read outstanding past `Limits::read_deadline` (30 s default, on the injected clock) is given up — its field becomes `Failed` if still waiting for it, its slot is reclaimed, and a later completion for it is discarded because its sequence is no longer outstanding; (c) given-up reads that have not returned are bounded by `Limits::max_abandoned` (16), and dispatch pauses while that many are outstanding, so a source that hangs every read occupies at most `max_in_flight + max_abandoned` workers. Tests: `a_panicking_read_fails_its_field_and_frees_its_slot`, `a_dropped_read_fails_its_field_and_frees_its_slot`, `a_hung_read_is_given_up_at_its_deadline` (failed at the deadline, slot reused by a newly shown field, the late answer ignored), `given_up_reads_are_bounded`.
- **C3 — suspend.** `InstantClock` did not advance across a suspend. A suspend-inclusive kernel clock (`CLOCK_BOOTTIME`, `mach_continuous_time`) needs FFI, which PX-008's audit refuses in production code (`libc`, `nix`, `unsafe`), and no dependency was added. Fix: `SuspendAwareClock` replaces it; each reading advances by the larger of the `Instant` and the wall-clock progress since the previous reading (`ElapsedTracker`). A suspend is counted through the wall clock; a wall clock set back never stops or reverses it; a wall clock set forward ages values early, the safe direction. Remaining gap, documented in the module and README: a suspend across which the wall clock itself did not advance is not seen. The per-process CPU interval keeps `procfs::SystemMonotonicClock`, which deliberately excludes suspend. Test: `freshness_time_counts_a_suspend_and_never_runs_backwards`.

Mutation checks, each applied alone: dispatch by caller position only (C1) — caught by the fairness and hung-read tests; reply guard that never sends (C2) — caught by the panic and drop tests; `expire` disabled (C2) — caught by the hung-read and bound tests; `max_abandoned` ignored (C2) — caught by `given_up_reads_are_bounded`; wall-clock progress ignored (C3) — caught by the suspend test. The catalogue and on-demand tests passed 20 of 20 consecutive runs (26 tests each).

## Correction round 2

A fresh verifier failed candidate `326b8d26` on one blocking defect (all profile commands, C1 and C3 passed). Fixed in one commit on top; `on_demand.rs`, the README's catalogue section, ledger entry SRUI-PX042-004 and this note changed. This section supersedes the C2 text of round 1 where they differ.

- **B1 — one wedged read eventually disabled all on-demand collection (reproduced).** `expire` stamped the given-up field's failed reading with the read's issue time, which made it the oldest reading, so `demand` re-dispatched the same field first to the same wedged source; one more read was abandoned per deadline until `max_abandoned` was reached, after which nothing was dispatched again and other fields went stale and new ones stayed warming up forever. Fix:
  - (a) Fields with a given-up read still outstanding are tracked (`wedged`, a count per field). Such a field is never dispatched again until every given-up read of its own has returned (it stays `Failed`), [superseded by correction round 3: the "two" case was itself a defect] so one wedged field holds one worker — two only if it was hidden and shown again while its first read was still in flight — and is re-read once that read returns. No backoff was added: re-reading is already gated on the previous read returning.
  - (b) A demanded field without a value reads `Failed`, not `WarmingUp`, once it has waited `read_deadline` since it was first demanded, or while a given-up read of its own is outstanding. If the bound is saturated by distinct wedged fields, fields with values turn stale, fields without read failed, and dispatch resumes by itself as soon as any wedged read returns.
  - (c) The module doc's "never stops collection for good" claim is replaced by the precise guarantee and residual: if `max_abandoned` distinct fields wedge at once, nothing more is dispatched until one returns, and a read that never returns holds its worker for the life of the process. Same disclosure in the README.
- **N1 — `max_abandoned` overshoot.** Expiry could take the given-up count to `max_abandoned + max_in_flight - 1`. The bound is now exact: a read is dispatched only while in-flight plus given-up reads are fewer than `max_abandoned`, which expiry preserves, so given-up reads, outstanding reads and occupied workers never exceed it (the doc says to keep it at least `max_in_flight`; defaults 16 and 4).
- **N2 — forward wall-clock jump.** Disclosed in the module doc and README: a wall clock set forward by at least `read_deadline` gives up every read in flight at that moment; their fields read failed until read again. No code change.

Tests (manual clock and dispatcher; a test helper keeps chosen fields' jobs unrun, matching queued jobs to reads by dispatch sequence):
- `one_wedged_field_never_stops_the_others` — the verifier's scenario over 1,000 one-second ticks: the hung field is dispatched exactly once, stays `Failed` (including after being hidden for 100 ticks and shown again), never more than one read is given up, the other field is `Present` on every tick, a field shown at tick 500 is `Present` from then on; when the wedged read finally returns it is discarded and the field is read again.
- `saturation_by_wedged_fields_is_reported_and_recovers` — two wedged fields saturate `max_abandoned` 2: nothing is dispatched from the fifth tick on, no field is dispatched twice, a newly shown field reads `Failed` after the deadline, a field with a value turns `Stale`; one wedged read returns and the next `demand` dispatches the never-read field, which becomes `Present`.
- `running_reads_never_exceed_the_bound` — N1: with one read already given up, only one more is dispatched, so in-flight plus given-up reads and outstanding entries never exceed `max_abandoned`.
- `given_up_reads_are_bounded` now also asserts that a field which waited a full deadline under the bound reads `Failed` and then `Present` once read.

Mutation checks, each alone: no wedged check in dispatch, or wedged never recorded — caught by `one_wedged_field_never_stops_the_others`; wedged count never cleared — caught by the same test's final re-read; overdue/wedged `Failed` state removed — caught by the saturation, bound and wedged tests; old gate (`abandoned >= max_abandoned`) — caught by `running_reads_never_exceed_the_bound` and the saturation test. ## Correction round 3

A fresh verifier failed candidate `9116079f` on one blocking finding (B1 itself held: its scenario passed, and a randomised probe of 600 seeds × 500 operations kept every invariant). Fixed in one commit on top; `on_demand.rs`, the README's catalogue section, ledger entry SRUI-PX042-004 and this note changed. This section supersedes earlier rounds where they differ.

- **B2 — a field hidden and shown again while its read was in flight got a new read each time (confirmed).** Dispatch looked only at the slot's pending read and the wedged set; hiding dropped the slot, and the earlier read joined the wedged set only at expiry. A wedged row flickering at the viewport's edge took every in-flight slot, starved the other fields for about 24 s, and left four given-up reads behind; four such fields stopped all dispatch for good. The round-2 claim "one worker, two at most" was false. Fix: a strict invariant of at most **one** outstanding read per (process instance, field), in flight or given up, kept in `reading_of` independently of the slot's lifetime. A demanded field with an outstanding read is never dispatched. If that read is in flight, the re-created slot adopts it (its answer is accepted under the usual request-to-drain window and staleness rules). If that read was given up, the field reads `Failed` until the read returns. The per-field `wedged` count is gone: it was this invariant restricted to given-up reads. The claims in the module doc, README and ledger now say exactly this.
- **N3 — a healthy queued field read `Failed`.** A field merely waiting behind healthy reads read `Failed` once it passed `read_deadline` without a first read. Now a field without a value reads `Failed` only when its own given-up read is outstanding, or when dispatch is closed by given-up reads — at least one given-up read, room for another read in flight, and in-flight plus given-up reads at `max_abandoned` (`saturated_by_wedged_reads`) — and it has waited `read_deadline` since it was demanded. Queued behind healthy reads, it stays `WarmingUp` however long it waits.
- **N4 — `Limits` were never validated.** `Limits::validate` refuses a zero `max_fields`, `max_in_flight`, `max_abandoned`, `max_age` or `read_deadline` (`LimitsError::Zero`), and a `max_abandoned` below `max_in_flight` (`LimitsError::AbandonedBelowInFlight`). `OnDemandFields::new` now returns `Result<_, LimitsError>`, as `Catalogue::new` rejects bad input. `min_interval` may be zero.

The field never has more than one outstanding read, it is dispatched exactly once, at most one read is ever given up, the other field is read on every tick, and the wedged field reads `WarmingUp` before the deadline and `Failed` after it.
- `a_field_shown_again_adopts_its_outstanding_read` — a field shown again adopts its in-flight read and takes its answer; a read answering while its field is hidden is discarded, and the field is read anew when shown again.
- `an_older_completion_never_overwrites_a_newer_result` (rewritten) — repeated or stray completions of earlier reads arriving after a newer reading are discarded.

## Verification round 4

A fresh verifier passed `e6e8250098015d0fbc0befa58cb792f3c8f108c7`.
- The scoped profile passed, and the on-demand and catalogue tests passed 10 runs out of 10.
- The round-2 (hung, then hidden) and round-3 (flickering wedged field) probes no longer reproduce.
- A randomised probe of 800 seeds × 500 operations held every invariant:

  - `in_flight + abandoned ≤ max_abandoned`;

Its non-blocking findings:
- **N5 (fixed in the docs).** "Every other field keeps being read" holds only while fewer than `max_in_flight` fields are wedged. With that many or more, they fill the in-flight slots until `read_deadline`. The module doc and README now say so.
- **N7 (fixed).** The round-1 scheduling bullet above is marked as superseded.
- **N6 (open).** `Limits::validate` accepts `min_interval ≥ max_age`, so a healthy field can turn stale before it may be read again. This does not stop dispatch; it is left for the first expensive collector, which chooses real limits.
- **I1 (as documented).** With `max_abandoned == max_in_flight`, a single given-up read counts as saturation, so a long-queued healthy field can read failed.
