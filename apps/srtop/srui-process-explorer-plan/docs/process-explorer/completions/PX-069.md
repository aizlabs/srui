## Bounded change

- `apps/srtop/src/settings.rs` (new): the saved view model and the versioned format.
  - `SavedView`: name, column layout, sort (`None` keeps the active order), committed command filter, user filter (`AllVisible`, `Mine`, or the user field's text), tree on/off, thread settings. No field can hold a PID set, search, selection, tag, process key, intent or confirmation, endpoint, credential, geometry or appearance. No meters: srtop has none yet (PX-070).
  - `Settings`: the source the views are scoped to, 1–8 views with distinct names, and the active view (`None` after the active view is deleted).
  - Format `srtop-settings 2`: one `key value` per line, every value percent-escaped (printable ASCII only), app line, source line, active line, `view`…`end-view` blocks, and a final `checksum <FNV-1a 64>` over every byte before it.
  - Versions: a newer version is refused from its first line alone (`Problem::NewerVersion`) and never interpreted. Version 1 (columns and sort per view, no active view) is read and migrated in memory; defaults fill the rest.
  - Bounds: 64 KiB, 256 lines, 4096-byte lines, 8 views, 64-byte names, 32 column entries, 64-byte keys, the filter's 512 bytes and the user field's 64. Exceeding any refuses the whole file.
  - Compatibility: structure is strict (unknown, missing or malformed key refuses the file). Well-formed values this build cannot honour are dropped and explained in notes: an unknown column or sort key (catalogue keys, PX-042), a duplicate column. A view left with no column gets the default layout.
- `apps/srtop/src/settings_file.rs` (new): `SettingsStore`, the only module that writes.
  - Reads: `symlink_metadata` first; only a regular file is opened; its size is checked before it is opened, then at most 64 KiB + 1 bytes are read.
  - Load: missing file gives defaults and writes nothing. A damaged file (truncated, oversized, checksum, malformed, bad version) falls back to a valid `settings.bak` of the same source, else defaults. A newer version, another app's file, another source's file, an unreadable file or a non-file makes the store read-only with defaults shown.
  - Save: re-reads the current file; refuses when read-only. When the current file is valid it is copied to `settings.bak` through a temporary file and rename. A damaged file never becomes the backup. The new file is written to `settings.tmp.<pid>` (`create_new`, mode 0600; directory created 0700), `sync_all`, renamed into place, and the directory is flushed. Stale temporaries (older than 10 minutes, at most 256 entries examined) are swept after a successful save.
  - `default_path()`: `$XDG_CONFIG_HOME/srtop/settings` (absolute only), else `~/Library/Application Support/srtop/settings` on macOS, `~/.config/srtop/settings` elsewhere. `default_path_from` is the pure rule.
  - Test seam `interrupted_at(SaveStep)` stops a save at backup-replaced, half-written, written or renamed, as a crash would.
- `apps/srtop/src/saved_views.rs` (new): `SavedViews`, the switcher.
  - Controls (created only with a settings store): Row 89, eight slot Buttons 90–97 (`View: <name>`, `(active)`; empty slots disabled and collapsed), `View name` TextInput 98, `Save as new view` 99, `Rename active view` 100, `Delete active view` 101, `Restore default views` 102, status Text 103. All mutations are disabled while the store is read-only.
  - Apply: `apply()` sets columns, sort, user filter, command filter, tree and thread controls through `ProcessView`'s existing setters (`set_columns`, `set_sort`, `choose_owner`/`set_owner_input`, `set_filter`, `set_view`, `set_user_threads`, `set_kernel_threads`), only for what differs. Rows keep their item IDs, and a pending intent is kept or withdrawn as those controls would (PX-030).
  - Create captures the presentation (`capture()`, read-only access to the view). Rename and Delete never receive the process view or the gate. Delete leaves no view active and applies nothing. Restore defaults saves and applies the one `Default` view (catalogued columns, PID ascending, no filter, every user, the table).
  - A change is kept only if the file took it; a failed or refused save keeps the views and says why on the status.
- `apps/srtop/src/lib.rs`: node constants 89–103, `SAVED_VIEW_SLOTS`, `SAVED_VIEWS_NODE_COUNT`, and `install_saved_views()`: creates the controls under `COLUMN`, applies the active view, installs 8 slot `ACTIVATE`s, the name field's `TEXT_EDIT` and 4 button `ACTIVATE`s, each on a bare node constant. Lock order: saved views, then the process view, then the gate.
- `apps/srtop/src/refresh.rs`: `SAVED_VIEWS_RESERVE_BYTES` = 6 KiB, charged in the row ceiling whether or not the controls exist (as `ACTIONS_RESERVE_BYTES` is), so they never change which rows fit.
- `apps/srtop/src/main.rs`: `--settings-path PATH` and `--no-settings` (mutually exclusive, each at most once; `--settings-path` needs a process source and must name a file). The default is the per-user path for `--live-source` only. Fixture sources keep no settings unless a path is given. The store is scoped to the first snapshot's source identity; the views are installed before the actions and before the socket is served.
- `apps/srtop/tests/no_process_control_test.rs` (PX-008 audit): `src/settings_file.rs` alone may name `OpenOptions`, `OpenOptionsExt`, `DirBuilder`, `DirBuilderExt`, `fs::rename`, `fs::remove_file` and call `.write`/`.write_all`. The writes are pinned by `settings_write_violations`: exactly one `OpenOptions::new()` and one `create_new`, and no `truncate`, `append` or `.create(true)`. The saved views' node constants are admitted with `ACTIVATE` and the name field with `TEXT_EDIT`. A new self-test proves the same writer is refused in any other file, the pin catches an in-place rewrite and a second open, every other rule (`Command`, `kill`, `fs::write`, `File::create`, `set_permissions`, a handler) still holds in the settings module, and a computed or wrong-event registration is refused.
- Existing tests that start `--live-source` now pass `--no-settings` (`tests/shutdown.rs`, `tests/continuity_test.rs`, `tests/outcomes_wire_test.rs`, `tests/actions_wire_test.rs`, `demo/tests/scenario_test.rs`, `demo/tests/churn_range_test.rs`), so no test reads or writes the real user's settings.
- `apps/srtop/README.md`: a Saved views section (contents, controls, location, format, write steps, damage, never-overwritten cases, reset, limits) and the input-handler list.

## File lifecycle (what you create, you close)

- **Writer:** only `SettingsStore::save`, called on Save as new view, Rename, Delete, a switch of the active view, and Restore default views. Reading never writes.
- **Files:** `settings` (replaced by rename only), `settings.bak` (the previous valid file; one), `settings.tmp.<pid>` / `settings.bak.tmp.<pid>` (removed on failure; a crash leftover is never read and is removed by a later save once it is 10 minutes old).
- **Reset:** `Restore default views` (keeps the previous file as the backup), or delete the `srtop` settings directory. srtop never deletes the settings file or the backup. Tested: `restore_defaults_saves_and_applies_the_default_view_and_keeps_the_previous_file_as_backup`, and the native test's restart.

## Verification round 1 fixes

The second commit on top of `f283c1f9`. Its code is identical to `6cd97bd5`, the tree the round-2 mutants and the Linux run used; that commit was amended with documentation only (README, this note and the ledger). The verifier's probes in `verify1-probes/` became the committed tests named below.

- **F1 (medium, blocking): an oversized newer-version file was overwritten.**
  - Cause: the size was refused before the version was read.
  - Fix in `settings.rs`: `parse` now reads the file's head first. `declared_version` looks at at most `HEAD_BYTES` (the magic, a space and up to 11 bytes); `names_another_app` looks only at a complete second line. Only then are the size and line bounds applied.
  - Fix in `settings_file.rs`: `read_bounded` no longer refuses on `metadata.len()`. It reads at most 64 KiB + 1 bytes and lets the parser decide.
  - An oversized or over-long `srtop-settings 3` file is `ReadOnly::NewerVersion`. An oversized `app other` file is `ReadOnly::ForeignApp`. Neither is ever replaced.
  - The backup is checked the same way whenever a save would replace it (a valid settings file is in place). A newer, foreign, non-settings or unreadable `settings.bak` gives `ReadOnly::Backup(..)` at load and refuses the save. A damaged settings file is replaced without touching the newer backup.
  - An oversized file that cannot be read is now `ReadOnly::Unreadable`. It was refused as oversized before without being opened; now it is never replaced.

## Limitations

- **Version 1 is defined here.** No released srtop wrote version 1. It is the minimal layout record (columns and sort), kept readable so the migration path is real and tested from the first release.
- **No locking.** Two srtop instances of the same user saving at once are not serialized: the last rename wins, whole.
- **One source per file.** A file saved for another source makes the store read-only, so a fixture run with `--settings-path` at the live file cannot overwrite it. A user who switches source must reset or use another path.
- **Sort `none`.** A view saved before any sort keeps the active order when applied, because srtop has no way back to "unsorted". The `Default` view therefore sorts by PID ascending.
- **Application order.** The active view is applied after the first snapshot commits, in a few transactions, before the socket is served. The first client attaches to the applied state.
- **No hand editing.** The checksum line means a hand-edited file is refused and the backup is used.
- **Not covered by the views:** the PID set and search are not saved; meters do not exist yet (PX-070).
- **Devbox and R1 live runs.** The devbox's default `SRTOP_ARGS` (`--live-source`) now gives the box's own user a settings file inside the container and shows the switcher row. The R1 devbox scripts were not rerun here.
- **Permissions are not repaired.** They are set at creation (directory 0700, files 0600) and not checked or changed later.
