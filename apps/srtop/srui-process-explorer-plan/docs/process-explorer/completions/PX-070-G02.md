## What changed

**Registry and codegen.** `protocol/registry.yaml` gains property 35 `split_axis` (`control_specific`, value type `enum`, `enum_types: [SplitAxis]`) and enum 13 `SplitAxis` (1 `side_by_side`, 2 `stacked`). `protocol/srui.proto` mirrors them. `server-rust/semantic-tree/build.rs` now asserts 35 properties and 13 enums. `./protocol/generate_proto.sh` regenerated `client-macos/Protocol/srui.pb.swift` and `client-macos/SemanticModel/RegistryTables.swift`; a rerun leaves both byte-identical (checksums compared). The `Split` node type entry (id 25, tier `should`, `emits: [VALUE_CHANGED]`) is unchanged. The registry count also changed in `CLAUDE.md`, `spec/registries.md` and `protocol/README.md`.

**Store rules (Rust `server-rust/semantic-tree/src/split.rs` and `store/`; Swift `client-macos/SemanticModel/Split.swift` and `SemanticStore.swift`).** Both stores use the same order and the same codes:

- `split_axis` must be `SplitAxis` value 1 or 2. Anything else is `invalid_split_axis`: another enum's token, value 0 or 3, or a non-enum. This value check runs first, as for `shortcut`.
- `split_axis` is admitted only on `Split`; any other node type is `split_axis_not_admitted`. Both checks run on `CREATE_NODE`, `SET_PROPERTY` and `BATCH_PROPERTY_SET`. Clearing it restores the `side_by_side` default.
- A `CREATE_NODE` or `MOVE_NODE` that gives a `Split` a ninth child is `max_split_panes_exceeded` (`MAX_SPLIT_PANES` / `maxSplitPanes` = 8). A move within the same `Split` and `REORDER_CHILDREN` add no pane.
- Every refusal discards the whole transaction.
- Nested `Split`s count toward `max_tree_depth`.
- Swift excludes `split_axis` from its generic registry value-type check, so a non-enum value reports `invalid_split_axis` exactly as Rust (which has no generic check) does.

**Decode paths.** Rust `validate_decoded_split_axis` sits beside `validate_decoded_shortcut` (combined as `validate_decoded_property`) on the same paths: `Property::try_from`, which covers node records, `CREATE_NODE` and `BATCH_PROPERTY_SET`, and `SET_PROPERTY`. Swift adds `ProtocolDecoder.checkDecodedSplitAxis` and `validateDecodedSplitAxis`, called at every site the shortcut check is called. The reason text is byte-identical in both languages: `invalid split_axis: split_axis must be SplitAxis side_by_side (13:1) or stacked (13:2), got enum 13 value 3`. A stateless decoder cannot know a parent's type, so the pane limit is enforced at apply, like `max_tree_depth`.

**SDK (`server-rust/sdk`).** `Split` and `SplitBuilder` (`impl_widget_boilerplate!`) provide:

- `axis`/`set_axis`/`clear_axis` and their op forms (`SplitAxis`, re-exported), plus `effective_axis` (side by side when absent);
- `label`, `accessible_description`, and the common state and layout props;
- `panes(store)` in child order, and `Split::MAX_PANES`.

The SDK also exports `SPLIT_AXIS` and `MAX_SPLIT_PANES`. Panes are ordinary children created with `parent(split_id)`. There is no divider position and no `VALUE_CHANGED` handler for a `Split`.

**Renderer (`client-macos/RendererAppKit/SplitRendering.swift`, `ControlFactory.swift`, `LayoutRenderer.swift`, `DirtyClassifier.swift`).**

- **Mapping.** `Split` maps to `SemanticSplitView`, an `NSSplitView` with thin dividers. `side_by_side` (and an absent axis) gives `isVertical == true`, which means vertical dividers. `stacked` gives horizontal dividers.
- **Panes.** Each child is mounted in a `SplitPaneView`, in child order. The child is pinned to the pane's leading and top edges. Its trailing and bottom edges fill the pane at priority 249.5 and stay inside it at 249.8. Both are just below NSSplitView's default holding priority (250), so no hugging, compression or `preferred_size` constraint of the child ever moves a divider. The child's `minimum_size` is repeated on the pane as a required constraint, so a divider stops there.
- **Initial lengths.** Until the user moves a divider, lengths come from the hints at every split-view length. A pane's `preferred_size` along the axis claims that length. The rest is shared by `grow` (absent or zero counts as 1).
- **Row/Column panes.** A Row/Column pane's stack hugging is lowered to 249, so it fills its pane.
- **Visibility.** A child whose `visibility` is `collapsed` takes its pane out of the arranged subviews; un-collapsing puts it back in child order without a remount. `hidden` keeps the pane's space.
- **Fill in a stack.** In an enclosing stack the split view fills the cross axis at priority 750.
- **Divider positions are local.** A divider move is a drag, a `setPosition(_:ofDividerAt:)`, or an accessibility splitter adjustment. AppKit marks such a resize with `NSSplitViewUserResizeKey`. The move records the proportions in `ControlFactory.splitProportionMemory[splitID]`, at most one entry per pane. That memory is pruned with the mounted node set on every mount, so it is dropped with its `Split`. Nothing is sent: no `SemanticInteraction`, so no event and no frame.
- **What keeps the proportions.** A non-structural commit leaves the split view in place. A remount restores the proportions. When panes are added or removed, the remaining panes keep their relative proportions and a new pane takes an equal share. A window resize scales the panes and keeps the user's proportions.
- **Accessibility.** The split view is an `AXSplitGroup` labelled from `label`. AppKit's own `NSSplitViewSplitter` elements expose a value, but their `accessibilityPerformIncrement` reaches an unimplemented `accessibilityPerformAction:` and raises an exception (reproduced in a scratch AppKit script). The split view therefore replaces them with `SplitDividerAccessibilityElement`s: role `AXSplitter`, value is the divider position in points, min and max values, and orientation. Increment and decrement move the divider by 5% of the length, and `setAccessibilityValue` sets it.
- **Dirty classification.** `DirtyClassifier` classifies `split_axis` (`SET`/`CLEAR`/`BATCH`) as `.structureAffecting` for that `Split`'s operation. Pane hints stay `.layoutAffecting`.

**Examples.** `examples/ui-gallery` no longer lists `Split` as a type the renderer cannot build. Its comment and README say the gallery does not show it yet. No gallery content changed. **No srtop change** (PX-073-G01 adopts `Split`).

## Design decisions

1. **`max_split_panes_exceeded` is a fixed constant, not a negotiated `StoreLimits` field.** The ticket fixes the value at 8, and no capability negotiation is added.
2. **The over-limit malformed vector is refused at apply.** It decodes on every path (Rust, `ProtocolDecoder`, `Transaction(wire:)`), and applying the decoded transaction refuses operation 10 with nothing committed. `expected.json` records `expected_error_code`, `failed_op_index` and `refused_at: apply`. A decode-time pane count would see only Splits created inside the same transaction; that would be partial and misleading.
3. **Holding priority stays at AppKit's 250.** At 300, a holding priority outranks the enclosing NSStackView's 250 edge constraints, and every divider move landed short by the stack's edge inset: 20 points inside a Surface, measured in the renderer and reproduced in a scratch script. Moving left lands short on a left inset, moving right on a right inset.
4. **Seeded lengths are never stored.** Only user divider moves are remembered. A first layout at the window's default size therefore cannot freeze hint-derived proportions.
5. **Tests never post mouse events into NSSplitView's drag loop.** In the swift-testing process that nested tracking loop stopped the main run loop. `swift_task_asyncMainDrainQueue` then called `exit(0)`, ending the run with exit status 0 and no results; an `atexit` backtrace showed this. Tests move the divider with `setPosition(_:ofDividerAt:)`, which is where a drag lands, and through the accessibility splitter. A real posted-event drag was exercised only in scratch AppKit scripts. With the window at the screen origin it honoured `minimum_size`: a drag of -400 stopped at 150 points.

## Native AppKit evidence (real `NSWindow`, `SplitRenderingTests`, 14 tests)

- **Toolkit mapping.**
  - `side_by_side` and absent map to vertical dividers; `stacked` maps to horizontal ones.
  - Eight panes mount with seven splitters.
- **No traffic.** Setting a divider position, and accessibility increment and set, emit no interaction, range request or terminal traffic. The positions are remembered locally.
- **Divider kept.**
  - A commit updating a pane's `Text` keeps the divider within 1 point of where the user put it. It mutates in place: same split view, non-structural.
  - A remount with the same panes restores the proportion within 0.01.
- **Pane set changes.**
  - Inserting a third pane keeps the first divider's A:B proportion within 0.01, and the new pane gets 1/3.
  - Removing a pane keeps A:C.
  - A window resize to 1240 and to 640 points keeps the user's proportion.
- **Pane hints.**
  - A pane's `minimum_size` (260 and 180 points) holds when the divider is pushed 600 and 900 points past it, and holds against an accessibility value of 0.
  - `preferred_size` (150 points) and `grow` 3 seed the lengths. A divider move past the preferred size is honoured.
  - A collapsed child collapses its pane and comes back in child order on a non-structural commit; `hidden` keeps the space.
- **Accessibility tree.** An `AXSplitGroup` holds two `AXSplitter`s, with no duplicated native splitters. Each splitter has the parent, the orientation, increment and decrement allowed, a value equal to the divider position, and a non-empty frame. Increment moves the divider and decrement moves it back.
- **Classification and pruning.**
  - A `split_axis` change is `[.structureAffecting(operation:)]`, rebuilds the panes on the other axis and keeps the proportions. `minimum_size` is `.layoutAffecting`. A `BATCH` gives `contentOnly(label)` plus `structureAffecting`.
  - Remembered proportions are dropped with their `Split`.

Suite 4, on the wire (`SplitFrameIndependenceTests`):

- The real `SessionController` and `AppKitRenderer` run over a `PipeTransport`. Both runs (still, and moved three times plus increment and decrement) send 0 frames between mount and the Button press, and exactly 1 frame after it.
- The two streams are byte-identical once each event's random `event_id` and `client_instance_id` are blanked.

## Reference lookup (verified at implementation time)

The AppKit behaviour this relies on was checked on macOS 26.4.1 / SDK 26.2 with scratch scripts outside the repository:

- **Collapsing.** A hidden arranged subview reports `isSubviewCollapsed`. The renderer removes collapsed panes instead.
- **Splitters.** `NSSplitViewSplitter` is an `NSAccessibilityElement` subclass whose increment raises `unrecognized selector accessibilityPerformAction:`.
- **Resize notifications.** A user drag's `splitViewDidResizeSubviews` carries `NSSplitViewUserResizeKey: 1` and a `setPosition` carries `0`. Layout-driven resizes carry no such key.
- **Holding priority.** A holding priority above 250 inside an NSStackView with edge insets shortens divider moves by the inset.

## Limitations

- **Compatibility.** No capability is negotiated per node type. A client built before this ticket refuses a `Split` (`unsupportedNodeType`) and an unknown property id, explicitly (§4 inv. 13); a server must not send a `Split` to such a client. That is the ticket's recorded compatibility limit.
- **The optional `VALUE_CHANGED` for `Split` (§7.6) is not implemented.** It is documented in suite 2, `spec/registries.md` and the SDK docs.
- **No real mouse drag in automated tests** (design decision 5). Drags are represented by `setPosition(_:ofDividerAt:)` and accessibility adjustments, which take the same Auto Layout constraints.
- **`NSSplitViewUserResizeKey` is an AppKit userInfo key, not a documented constant.** If a future macOS dropped it, user moves would stop being remembered. `SplitRenderingTests` (memory after a move) would fail rather than pass silently.
- **Remounts recreate the Surface window at its default size.** This is existing renderer behaviour. Remembered Split proportions survive it; preferred lengths are re-applied at the new size.
- **`maximum_size` on a pane child bounds the child, not the pane:** the pane may be wider than its content (the remainder is empty). This is a hint, never a pixel mandate.
- **Review follow-ups (PR #127).**
  - Preferred lengths that would consume the axis are scaled down so panes without one keep at least half an equal share between them (`preferredSizesThatFillTheAxisStillLeaveRoomForTheOtherPanes`).
  - A later `preferred_size` or `grow` change is re-applied until the user moves a divider (`aChangedSizingHintIsAppliedUntilTheUserMovesADivider`).
  - A Split's 750-priority cross-axis fill is rebuilt with the stack's other fill constraints on a `padding_role` change (`aPaddingChangeRefitsTheSplitToItsStack`).
  - Each of these tests fails on the code before its fix.
