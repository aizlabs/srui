## What already held, and what was missing

Audited first, then proven by tests rather than rebuilt:

- **Already structural.** `ConnectionManager` already kept one `ConnectionSessionContext` per saved entry (`contexts[SavedConnection.ID]`), each with its own `TransactionApplier` (the replica, so its rows and `ItemId`s), `EventOutbox` (so its `client_instance_id`, `event_seq`, pending and settled events and resume generations), `ResourceCache`, `TransactionIngressGate`, `SessionContinuityContext` and `AppKitRenderer` (so its `RenderRegistry`, `ControlFactory` selection memory, collection adapters and their range trackers), and one attempt generation per entry (`activeTokens`). No client static holds per-session state (audited: `grep` for `static var`, `.shared`, `UserDefaults`, autosave names; the only shared object, `EventOutboxConnectionBindingEpochAllocator.shared`, mints process-unique epochs, which is isolation-safe). A renderer's `onInteraction` is wired to its own controller, which validates the node against its own replica before allocating a sequence. On the server, every srtop run draws its own confirmation panel range (PX-031 F1), so a Confirm names a node only its instance holds.
- **Missing.** (1) Nothing on a window said which host, account or incarnation it showed: two hosts serving srtop have the same title ("Process Explorer"), node IDs, PIDs, names and, as the native test shows, the same `ItemId`s; the subtitle is the PX-022-G01 status and is empty while connected. macOS window tabbing could also merge both hosts' windows into one tab group. (2) An attempt for one connection cleared any other connection's alert (`if alert?.kind != .sessionReplaced { alert = nil }` in `beginAttempt`), and another connection's alert folded into a Session Replaced disclosure did not say whose it was; the replacement message did not name the endpoint.

## Design decisions

- **A third piece of client-owned chrome, apart from the other two.** The server's `label` keeps `NSWindow.title`; PX-022-G01's status keeps `NSWindow.subtitle` and the accessibility help (and its absence is what enables selection while live). The identity is a new titlebar accessory (`NSTitlebarAccessoryViewController`, layout `.bottom`) holding one static text field, identifier `org.srui.session-identity`, middle-truncated with the full text as tooltip, reachable by VoiceOver as one static-text element labelled "Session" whose value is the line. So none of the three overwrites another, and every existing title/subtitle assertion is unchanged. `LayoutRenderer.setSessionWindowIdentity` applies it to every Surface window, and `mount(nodeID:from:)` to every window mounted later (a remount, a new Surface, the confirmation's commit), exactly as the status is.
- **What the line says.** `<user>@<host>[:port] · session <session_id> · saved as “<label>”`: the endpoint the client itself connected to comes first, because the local label is the user's free text and can look like another endpoint; the label is added only when it differs from the endpoint (the default label is the endpoint). The incarnation is the `session_id` the handshake attached to (§17), recorded at `ready` and at a REPLACED decision (`showIncarnation`), validated by `SavedConnection.validSessionID` (a failing ID shows `session with an invalid ID`, never its scalars); before the first ready the line says `no session attached yet`. A warm reconnect keeps the incarnation the replica came from until the transport says otherwise. Nothing in it is a server property. The full 32-hex-digit ID is shown, not a prefix: "unmistakable" is the requirement, and the field truncates in the middle only when the window is narrow.
- **Account.** The account is the SSH user the client connected as, which is the account the `srui` subsystem (bridge and srtop) runs under; the line does not show srtop's own UID claim.
- **Tab groups.** Each entry's windows get `tabbingIdentifier = "org.srui.session.<entry UUID>"`, so automatic window tabbing never puts two sessions' windows in one tab group.
- **Alerts.** `beginAttempt` now clears only an alert of its own connection or one that names no connection (a persistence failure), never another host's, and still never a replacement disclosure. An alert of another connection folded into a Session Replaced alert is titled with its endpoint (`Connection Failed (alice@host-b:2229): …`). The Session Replaced message names the endpoint (`Remote session X on alice@host-a:2228 was replaced by Y.`). Other alert texts are unchanged (several tests pin them exactly, and the ssh-failure text already names the endpoint).
- **No side-by-side view.** The ticket allows one ("may"); none was built. No cross-host action, bulk action, shared selection or fleet store exists: the manager has no API that addresses more than one entry.
- **No new state to close.** The identity lives in the renderer and context it describes, so it is dropped with them; `discardContext`/`closeWindows` already close a dropped context's windows.

## Limitations

- **The Window menu and the Dock list windows by title.** Both hosts' windows are "Process Explorer" there; the identity line is in each window's titlebar, not in those lists. Rewriting the menu item title was not attempted: AppKit derives it from the title, which the server owns (reasoned, not tested).
- **One alert at a time.** The manager still holds a single alert: a new alert of one connection replaces a non-replacement alert of another (as before); only clearing on a new attempt, and folding into a replacement disclosure, are now connection-aware. A failure alert's own text names the endpoint only for `ssh` failures before the stream (unchanged texts are pinned by existing tests).
- **The account is the SSH user.** The line names the account the client connected as; it does not read or display the server account's UID.
- **Identical endpoints.** Two saved entries for the same account, host and port are the same host and account; their windows differ by incarnation (and label, when set), and each is still its own isolated context.
- **M1 is pinned by a unit test only**, as recorded above.
- **No side-by-side comparison view** (optional in the ticket) and no fleet view.
- **Native evidence is on localhost fixtures**, not two Linux devboxes: the acceptance property needs identical PIDs and names, which the fixtures give by construction; nothing in the client distinguishes a local from a remote sshd. The PX-030/PX-031 devbox suites stay opt-in and were skipped.

## Verification round 1 hardening (`impl2-*`)

The independent verification of `0f21868a` passed with warnings. W1 and W3 are addressed in one new commit on top of it. `0f21868a` is unchanged. No srtop product, protocol, SDK, runtime or `server-rust` file changed.

- **W1: a server-chosen session ID could decoy the identity line.** `SavedConnection.validSessionID`, the storage rule, admits spaces, `·`, quotes and `@`. The verifier's ID `x · saved as “prod” · root@host-b.example:22` therefore produced `alice@host-a.example:2228 · session x · saved as “prod” · root@host-b.example:22 · saved as “srtop”`.
  - **Fix.** Display now has its own rule, `ConnectionManager.shownSessionID`: 1 to `maximumShownSessionIDLength` (64) ASCII letters, digits, `.`, `_` or `-`. Any other ID shows as `session with an invalid ID`.
  - **Why 64.** `srui-sessiond`'s `mint_session_id`, which srtop serves through, makes 32 lowercase hex characters. 64 leaves room for a UUID string or a prefixed token.
  - **Where it applies.** The `sessionWindowIdentity` formatter applies it, so every path to the line goes through it. The context keeps the reported ID cut to 65 scalars, which keeps it bounded and keeps an over-long ID over-long. The Session Replaced alert, which now names the endpoint, applies the same rule to both IDs. Storage keeps the looser rule, unchanged.
  - **The saved label.** It is user-controlled and, from the saved file, was not checked on load. It is now shown only if it passes the Connect form's rule (`ConnectionEndpoint.validate(label:)`: at most 128 scalars, no control, format or separator scalar). Otherwise it is left out of the line.
  - **The server's title and subtitle.** The subtitle is the client's own status and never a server property. The title is server text and may say anything, including a copy of another host's identity line. It cannot replace or join the identity: the identity is the one field in the titlebar accessory, outside the window's content view, and no server node is ever mounted there. This is now tested.
  - **Residue.** A server's content can still *look like* an identity line inside its own content. The line's position in the titlebar strip is what tells the two apart.
- **W3: the native test never remounted one session while the other held a selection.** It does now, in both directions.
  - With A holding 4101, B is remounted (`renderer.attach(store:)`, as a snapshot does) and then warm-reconnected (`connect(id:)`, `RESUME_OK`, the same session). Each time B's table selects nothing and its inspector says `none`.
  - With B holding 4102, A is remounted and keeps 4101.
  - The shared-selection-memory mutant is now killed natively (M1n below). Under it, B's table took A's 4101 at the remount (`ProcessExplorerMultiHostTests.swift:166`) and at the reconnect (`:173`), and A took B's selection at its remount (`:188`).
