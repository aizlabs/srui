## What R0 is

One window of the unchanged generic macOS client shows, read-only: a status line that says what the source read and what fell short; a system summary of overall CPU, memory, swap, load averages, uptime, the process count and the last successful sample's time and source ([PX-007](../completions/PX-007.md)); and a PID / Name / Resident / CPU table that one refresh loop keeps current by model operations on the existing transaction path ([PX-004](../completions/PX-004.md)), with resident memory from `statm` ([PX-005](../completions/PX-005.md), [PX-005-G01](../completions/PX-005-G01.md)) and sampled CPU ([PX-006](../completions/PX-006.md)), process-instance identity and honest unavailable states ([PX-003](../completions/PX-003.md)), on the snapshot delivery the runtime gained in [PX-004-G01](../completions/PX-004-G01.md). Live data needs a Linux `/proc`; the fake and scripted sources need nothing. Nothing in it can act on a process.

Not claimed: process actions, sorting, filtering, search, trees, an inspector, reconnect UX, packaging, htop parity, a macOS process source, or any scale beyond the collection ceilings the README states.

### The end-to-end scenario

From an empty client (no surface, revision 0), the client connects over the box's real sshd subsystem and shows the box's processes. A worker is then created inside the box as its unprivileged user — `bash` run under the name `r0-worker`, a loop of shell builtins with no child process that ends by itself after eight seconds. Recorded on the evidence run (`window 12442`, nine published states):

gone 7.83 s after the spawn: 5 rows, 5 listed

         Swap: 199.9 MiB used of 1023.9 MiB (19.5% of total) · Load average (1, 5, 15 min): 5.11, 4.24, 3.74

Asserted on every run: the new row is first published as `Warming up` with a resident size in bytes, is then measured as a percentage under the same item ID and PID, stays present until the worker ends and is then deleted, its identity never coming back; every scan is complete and its process count equals the rows the client shows; the freshness line advances and overall CPU is measured; srtop's own row keeps one item ID; the native controls show what the client holds after every rendered transaction and the window, table, status and summary controls are built once. The two repeat runs saw the worker appear 0.59 s and 0.36 s after its spawn, measured at 99.9%, and gone 8.59 s and 7.38 s after it. Before the picture the test enlarges the window — local presentation, §4 invariant 3 — so every row is visible.

## No code path can signal or reconfigure a process

`no_process_control_test.rs` makes three checks, on every `cargo test` (macOS and Linux both green on `05df9a28`):

- **The audit is live** (`the_source_audit_catches_what_it_is_for`): each construct it exists for is reported in a snippet, innocent look-alikes are not (a `nice` field, `write!`, `std::process::id()`, `symlink_metadata`, a `child_token`), test code is not production code, and code placed after a test module is refused rather than skipped.
- **Sources and manifest** (`no_production_source_can_signal_or_reconfigure_a_process`): the production part of every `src/**/*.rs` file — everything before its first column-zero `#[cfg(test)]`, with any later column-zero code refused — has no process spawn (`Command`, `Child`, `tokio::process`, `std::os::unix::process`), no FFI or raw system call (`unsafe`, `extern`, `libc`, `nix`, `syscall`, `#[link`), no call of `kill`, `killpg`, `tgkill`, `pidfd_send_signal`, `ptrace`, `setpriority`, `nice`, `sched_setaffinity`, `setrlimit`, `prlimit`, `ioprio_set`, `setpgid`, `setsid`, `fork` or `exec*`, no file write of any kind (the only way to reach `/proc/<pid>/*`, `/proc/sys` or `/sys/fs/cgroup`), no use of the runtime's PTY facility (`create_terminal_node`, `TerminalSpec`, `PTYManager`), and no handler for client input (`Session::on`, `on_result`, `on_result_with_transaction`, `on_text_edit`, a model range provider) — so nothing a client sends reaches application code at all. The only signal API is receiving SIGINT and SIGTERM (owned-socket cleanup) and, under `--smoke-fixture` only, SIGUSR1 (the title fixture): exactly three `SignalKind` receivers. The direct dependencies are exactly tokio, tokio-util and the five SRUI runtime crates; there is no build script, native link or target-specific dependency. srtop creates and removes only its own socket, through `srui-unix-security`.
- **Binary imports** (`the_binary_imports_no_process_creation_signalling_or_reconfiguration_function`): `nm` lists the debug `srtop`'s imported symbols (115 on macOS, 111 on Linux). None of `fork`, `vfork`, `clone`, `clone3`, `exec*`, `posix_spawn*`, `system`, `popen`, `killpg`, `tgkill`, `tkill`, `pidfd_send_signal`, `pidfd_open`, `sigqueue`, `pthread_kill`, `raise`, `ptrace`, `process_vm_*`, `task_for_pid`, `setpriority`, `nice`, `sched_set*`, `setrlimit*`, `prlimit*`, `ioprio_set`, `setpgid`, `setsid`, `setpgrp`, `thread_policy_set`, `task_policy_set`, `setiopolicy_np` or `proc_rlimit_control` is imported. Imported and attributed: `kill` and `waitpid` (and `waitid` on Linux) are the runtime PTY manager's teardown of a PTY child (`srui-pty` `signal_child_tree`, `Child::kill`, `wait`), which acts only on a child `PTYManager::spawn` created — a path absent from this binary, which imports no process-creation function at all, and never reached from `src/`; on Linux `syscall` is imported by std and tokio (futex, `statx`, `getrandom`, pidfd), and `src/` cannot make a raw system call without the `unsafe` the source check forbids. `sched_getaffinity` (Linux) only reads.

Mutations, each applied to a scratch copy of `apps/srtop` outside the repository and restored byte for byte (SHA-256 checked): M2 — `main` runs `std::process::Command::new("/bin/true")` — is killed by the source audit and by the import audit, which then sees `fork`, `execvp`, `posix_spawnp`, `setpgid` and `setsid`; M3 — `main` receives SIGHUP — and M4 — an `ACTIVATE` handler is installed — are killed by the source audit.

What these checks cannot prove: what a dependency's own code does beyond the functions it imports; the arguments of a raw `syscall` a dependency makes; code a dependency's macro might generate; anything another program does to the same processes. They prove that this application's own code has no such path, that the runtime path which can signal (PTY teardown) is unreachable from it, and that the shipped binary contains no way to create a process or change one's priority, affinity, limits, group or session.

## Corrections during the gate

- **Row 7, pass 1.** The new same-client test sent the counter's activation as soon as the counter's text was rendered. Under the parallel suites the catch-up snapshot's dispatch latch had not reopened yet, and `sendActivate` refused with `resumeNotConfirmed`. The test now also waits for `SessionController.isEventDispatchEnabled`, the client's documented readiness signal (§15, §18), as `SemanticInspectionAutomationTests` does; it then passed in rows 6, 7 and 16 and 5 of 5 repeats. The older `SSHTransportLiveIntegrationTests` makes the same call without that wait; it passed in every run here and is outside this gate, so it is reported, not changed.
- **Row 11, pass 1.** The profile ran conformance before building the client suite's fixture servers; suite 7's Swift runner needs `examples/coding-agent-demo`. Rerun after row 15: every suite passed or is a documented gap.
- **Screenshots in a test host.** A `swift test` host never runs an `NSApplication` event loop, so its windows are never flushed to the window server: a `screencapture -l` of one returned a blank white image even with Screen Recording permission. The scenario's picture is therefore AppKit's own rendering of the window's frame view — title bar, background and content, which also keeps the labels readable where PX-001's content-view capture lost them — and the launcher's picture is the window server's image of the production client's window.

## Known limitations

- The live evidence is a container on Docker Desktop's Linux VM (6.10, aarch64, `USER_HZ` 100), which lists only the container's own processes; no separate physical Linux host was used for this gate. `run.sh ssh` against one is documented, not exercised here.
- On Linux 6.2–6.15 resident memory is approximate (PX-005-G01); per-process CPU is quantized by the tick rate and warms up on its first sample (PX-006); the process count is this reader's view (PX-007).
- The frozen-source window is three seconds; a defect that published something only after a longer quiet period would not be seen.
- The import audit reads the debug binary the tests build; a release build was not audited.
- `apps/srtop/devbox/r0-scenario.sh` and `ProcessExplorerDevboxScenarioTests` need Docker; without the box's coordinates the suite reports itself skipped, which is not a pass, and nothing in CI runs the box.
