## What R0 is

One window of the unchanged generic macOS client shows, read-only: a status line that says what the source read and what fell short; a system summary of overall CPU, memory, swap, load averages, uptime, the process count and the last successful sample's time and source ([PX-007](../completions/PX-007.md)); and a PID / Name / Resident / CPU table that one refresh loop keeps current by model operations on the existing transaction path ([PX-004](../completions/PX-004.md)), with resident memory from `statm` ([PX-005](../completions/PX-005.md), [PX-005-G01](../completions/PX-005-G01.md)) and sampled CPU ([PX-006](../completions/PX-006.md)), process-instance identity and honest unavailable states ([PX-003](../completions/PX-003.md)), on the snapshot delivery the runtime gained in [PX-004-G01](../completions/PX-004-G01.md). Live data needs a Linux `/proc`; the fake and scripted sources need nothing. Nothing in it can act on a process.

Not claimed: process actions, sorting, filtering, search, trees, an inspector, reconnect UX, packaging, htop parity, a macOS process source, or any scale beyond the collection ceilings the README states.

### The end-to-end scenario

From an empty client (no surface, revision 0), the client connects over the box's real sshd subsystem and shows the box's processes. A worker is then created inside the box as its unprivileged user — `bash` run under the name `r0-worker`, a loop of shell builtins with no child process that ends by itself after eight seconds. Asserted on every run: the new row is first published as `Warming up` with a resident size in bytes, is then measured as a percentage under the same item ID and PID, stays present until the worker ends and is then deleted, its identity never coming back; every scan is complete and its process count equals the rows the client shows; the freshness line advances and overall CPU is measured; srtop's own row keeps one item ID; the native controls show what the client holds after every rendered transaction and the window, table, status and summary controls are built once. ## No code path can signal or reconfigure a process

### What is established for this revision, and on what evidence

This revision is read-only. Its production code — `apps/srtop/src`, which PX-008 does not change — has no way to create, signal, trace or reconfigure a process, to write a file, to connect to another program, or to act on anything a client sends. Two kinds of evidence say so: the repeatable audit below passes on macOS and Linux at `29a42f72`, and the independent verification and the adversarial review of `a98b568e` found the product read-only from their own reading, grep and probes.

The binary's process-related imports were attributed by the linker, for this revision only (logs `correction/logs/why-live-macos.log`, `correction/logs/linux-trace-symbols.log`); this is a review of one binary, not a check later changes must pass:

- macOS (`ld64 -why_live`, debug build of `29a42f72`): `kill` is live only through `srui_pty::stream::signal_child_tree` ← `TerminalStream::kill_and_reap` ← `PTYManager::shutdown` ← `PTYManager`'s `Drop` ← the drop of the `Session` at the end of `srtop::main`; with no PTY child ever spawned, it signals nothing. `waitpid` is live only through `std::process::Child::try_wait` ← tokio's process-driver orphan reaper (`OrphanQueueImpl::reap_orphans` ← `GlobalOrphanQueue::reap_orphans` ← `process::Driver::park_timeout`, on every runtime park), which reaps only children of this process — not, as the first version of this record said, through the PTY teardown (verification F3).
- Linux (GNU ld `--trace-symbol`, the same tree in the disposable container): the linked inputs that reference `kill` are std, `portable_pty` and `srui_pty`; `waitpid` and `waitid`: std and `nix` (a `portable_pty` dependency); `syscall`: std, tokio, `parking_lot`, `parking_lot_core`, `getrandom` and `nix`. No input from srtop's library or binary references any of them. (`--trace-symbol` lists references in the objects pulled into the link, before section garbage collection: an over-approximation of what is live.)

### What the repeatable audit catches

`apps/srtop/tests/no_process_control_test.rs`, six tests, on every `cargo test`:

- **Package shape, from Cargo** (`the_package_declares_only_the_runtime_and_builds_only_from_src`). `cargo metadata --no-deps` (Cargo at `$CARGO`) lists every declared dependency with its real package name, rename, kind and target: the normal dependencies must be exactly `tokio`, `tokio-util` and the five SRUI runtime crates, the only development dependency `proc-macro2` (the audit's tokenizer), with no rename, no build or target-specific dependency, no `links`, no build script; the library and the binary must be compiled from `src/`; the manifest may not carry `[patch]` or `[replace]`. A renamed table dependency such as `[dependencies.posix] package = "nix"` is therefore refused whatever it is called.
- **Sources, as Rust tokens** (`no_production_source_can_signal_or_reconfigure_a_process`). Every `.rs` file under `src/` is tokenized with proc-macro2 — so comments, and string, raw-string, byte-string and character literals, can neither hide code nor be mistaken for it — and items or statements gated by exactly `#[cfg(test)]` are set aside token by token; no symbolic link may stand under `src/`. The production tokens may not contain: process creation or control (`Command`, `CommandExt`, `Child`, `fork`, `exec*`, `posix_spawn`, `kill`, `killpg`, `tgkill`, `pidfd_*`, `sigqueue`, `raise`, `ptrace`, `process_vm_*`); reconfiguration (`setpriority`, `sched_set*`, `setrlimit`, `prlimit`, `ioprio_set`, `setpgid`, `setsid`); FFI, assembly, raw system calls and dynamic loading (`unsafe`, `extern`, `asm`/`global_asm`/`naked_asm`, `libc`, `nix`, `rustix`, `syscall`, `dlopen`, `dlsym`, `libloading`); outbound connections (`UnixStream`, `UnixDatagram`, `TcpStream`, `UdpSocket`, `connect`); the runtime's PTY facility (`pty`, `PTYManager`, `TerminalSpec`, `create_terminal_node`, `attach_terminals`, `srui_pty`); and every way client input reaches application code (`on` as a method or a path segment, so `Session::on(&session, ..)` too, `on_result`, `on_result_with_transaction`, `on_text_edit`, `register_handler`, `ModelRangeProvider`, `run_model_range_worker`). Files are reached only through an allowlist: `File::open`, and of `std::fs` and `std::os::unix::fs` only `File`, `read_dir`, `read_link`, `metadata`, `symlink_metadata` and `MetadataExt`. Any other `File::` or `<File>::` item (`options`, `create`, `create_new`, …), any other `fs::` item (`write`, `OpenOptions`, `set_permissions`, `chown`, tokio's `fs::write`, …), a grouped import naming one (`use std::fs::{metadata, write}`), a glob or renamed import of `fs` or `File`, a type alias of a file type, the methods `options`, `write`, `write_all`, `write_at`, `write_vectored`, `set_len`, `set_permissions`, `set_times` and `set_modified`, the identifiers `OpenOptions`, `OpenOptionsExt` and `FileExt`, the attributes `#[path]`, `#[link]`, `#[link_name]`, `#[link_section]`, `#[no_mangle]` and `#[export_name]`, and `include!` are refused. The only signal API is receiving SIGINT, SIGTERM and, under `--smoke-fixture`, SIGUSR1: any other `SignalKind` is refused, and exactly three receivers exist.
- **Binary imports** (`the_binary_imports_no_process_creation_targeted_signal_or_reconfiguration_function`). `nm` lists the debug binary's imported symbols (115 on macOS, 111 on Linux). None of `fork`, `vfork`, `clone`, `clone3`, `exec*`, `posix_spawn*`, `system`, `popen`, `killpg`, `tgkill`, `tkill`, `pidfd_send_signal`, `pidfd_open`, `sigqueue`, `pthread_kill`, `raise`, `ptrace`, `process_vm_*`, `task_for_pid`, `setpriority`, `nice`, `sched_set*`, `setrlimit*`, `prlimit*`, `ioprio_set`, `setpgid`, `setsid`, `setpgrp`, `thread_policy_set`, `task_policy_set`, `setiopolicy_np` or `proc_rlimit_control` may be imported. `kill`, `waitpid`, `waitid` (Linux) and `syscall` (Linux) are imported and reported as not attributed by this test.
- **Self-tests** (`the_source_audit_reports_every_known_bypass`, `the_package_checks_report_every_known_bypass`, `line_numbers_point_at_the_violation`): every rule has a snippet the audit must report — each bypass the review and the verification found among them — and the look-alikes srtop really writes (`rows.truncate`, `merged.append`, an SDK builder's `.create(ui)`, `File::open`, a `nice` field, `write!`, comments and literals of every kind) must not be reported; a gated test module, statement and field are set aside, code after a test module and under another `cfg` is read.

The first version of this audit, at `05df9a28`, could be bypassed; the review and the verification confirmed it with real mutations: a dependency declared as a TOML table under another name (`[dependencies.posix] package = "nix"`), whose `kill` then signalled an arbitrary PID through the import the binary audit had attributed to the PTY teardown — a disposable `sleep` was terminated on Linux; a write through `File::options()`, which set another process's `oom_score_adj` from 0 to 1000 on Linux; a grouped `use std::fs::{.., write}`; a `#[path]` module outside `src/`; `Session::on` called as a path; `//` inside a string literal hiding the rest of its line; a `#[cfg(test)]` inside a string literal ending the audited region; a binary entry point moved out of `src/`. All were re-run as real mutations of a scratch copy at `29a42f72`, with 13 further classes: 34 of 34 compile and are caught (table below).

### Its remaining blind spots

- **Dependencies.** What std, tokio and the SRUI runtime crates — and their own dependencies — do internally, beyond the symbols the binary imports. The allowlist decides which crates srtop may call, not what they do; a future runtime or tokio API that signals or reconfigures an arbitrary process under a name the lists do not contain would not be refused.
- **Raw system calls inside dependencies.** `syscall` is imported on Linux; its numbers and arguments are invisible to `nm`.
- **Which code reaches `kill`, `waitpid`, `waitid` and `syscall`.** Reported, not attributed, by the test; the attribution above is a one-time linker review of this revision.
- **Debug versus release.** The audited binary is the debug build the tests produce; a release build is not audited.
- **Configuration outside the package.** A `.cargo/config.toml` in a parent directory or in `$CARGO_HOME`, `RUSTFLAGS`, or a `[patch]` there can change what is compiled; the audit reads only the package.
- **Token rules, not types.** The source audit matches names and paths, not resolved items: a capability reached through a trait, a generic or a re-export under a name it does not list, or a new aliasing form beyond the `fs`, `File` and type-alias forms it covers, would not be seen. `append`, `truncate` and `create` are not refused as methods, because srtop calls them on vectors and SDK builders; on a file they need an `OpenOptions`, and every known way to obtain one is refused.
- **Other programs.** Nothing here constrains what another program does to the same processes.

## Known limitations

- The live evidence is a container on Docker Desktop's Linux VM (6.10, aarch64, `USER_HZ` 100), which lists only the container's own processes; no separate physical Linux host was used for this gate. `run.sh ssh` against one is documented, not exercised here.
- On Linux 6.2–6.15 resident memory is approximate (PX-005-G01); per-process CPU is quantized by the tick rate and warms up on its first sample (PX-006); the process count is this reader's view (PX-007).
- The frozen-source window is three seconds; a defect that published something only after a longer quiet period would not be seen.
- The process-control audit has the blind spots listed under "Its remaining blind spots": dependency internals, raw system calls inside dependencies, unattributed `kill`/`waitpid`/`waitid`/`syscall` imports, the debug-only binary, Cargo configuration outside the package, and token rather than type matching.
- `apps/srtop/devbox/r0-scenario.sh` and `ProcessExplorerDevboxScenarioTests` need Docker; without the box's coordinates the suite reports itself skipped, which is not a pass, and nothing in CI runs the box.
