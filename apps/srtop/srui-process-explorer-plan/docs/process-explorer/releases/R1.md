# R1 notes: the installable read-only Process Explorer

PX-026-G01 is the R1 package gate. It covers installation, compatibility, privacy and native
verification. These notes are its release notes. PX-027 closes R1 itself: it adds the showcase
bundle and the measured traffic and latency comparison, and depends on this gate. The gate's
commands and results are in the [completion record](../completions/PX-026-G01.md).

**Status: open.** Two pieces of required evidence can only come from the user, and neither has
come back yet (see "Awaiting user evidence"). Until both arrive and pass, this gate and R1 are
blocked.

**R1 is a read-only showcase, not htop parity.** PX-027 adds the showcase bundle and the measured
traffic, latency and support envelope: see "The showcase (PX-027)" below. PX-027 is blocked on the
same two user items, and is not passed either.

PX-026-G02, the server's reasoned handshake refusal, is merged into this branch. Everything else
listed here has passed, and the completion record lists the commands that reproduce it. That
includes three consecutive runs in which all seven live checks passed, the server-refusal check
among them.

## Scope

R1 is the read-only monitor that R0 established, grown through PX-009 to PX-026 and PX-068:

- a live Linux process list, with sorting, filtering, search and go-to-PID;
- user and PID-set filters, a column chooser, and pause, interval and refresh controls;
- follow, the process tree, threads, tags and last-observed records;
- an inspector, which shows the selected process's command line on demand;
- disconnect, resume and replacement handling;
- the Connect form and saved endpoints;
- bounded demonstration workers;
- in-process semantic inspection.

The server is `srtop` behind the existing `srui-ssh-bridge` SSH subsystem and its same-user Unix
socket. The client is the generic macOS client. Install, update, rollback and uninstall are
user-owned. See [apps/srtop/r1/README.md](../../../../r1/README.md).

## Out of scope

- Full htop parity. R1 is a read-only showcase, not an htop replacement.
- Any process-changing action: termination arrives with PX-028 to PX-031.
- A privileged installer or helper.
- External automation: inspection is in-process only (PX-026).
- Advanced diagnostics: R1 has no diagnostic bundle (PX-076 to PX-083).
- Signed or notarized distribution. R1 is built from source and carries only the ad-hoc signature
  the linker applies (`Signature=adhoc`, flags `adhoc,linker-signed`). No Apple credentials are
  involved.
- Linux hosts other than the devbox. The steps are documented, but no other host is tested.

## Compatibility, security and privacy, as verified

- **Compatible profiles.** A client offering `standard-widgets/1` reaches the live data plane.
  Core version 0.5.0 is on both sides.
- **Compatibility.** Four incompatible pairings are tried against the live server. Each fails at
  the handshake with nothing applied and no event dispatch.
  - **Refused by the client, clearly.** A client that requires a profile the server lacks gets
    "Server does not satisfy client required profiles: […]". A server of core 1.5.0 gets
    "SERVER WELCOME core_version 1.5.0 is not compatible with 0.5.0". Both are shown in the
    "Connection Failed" alert. This check passes.
  - **Refused by the server, clearly (PX-026-G02).** Core-version compatibility is a symmetric
    major.minor match, and the server checks the CLIENT HELLO first, so in a real version skew this
    is the refusal a user meets. The server now sends the existing `SERVER HANDSHAKE_REFUSED`
    (reason `UNSPECIFIED`, with a bounded detail) before it closes. Before PX-026-G02 the client saw
    only "transport ended: receive stream closed by peer".
    - A client offering only `standard-widgets/2` sees "server refused the handshake: client offer
      does not satisfy required profiles: [org.srui.standard-widgets/1]".
    - A client of core 1.5.0 sees "server refused the handshake: unsupported core protocol version
      1.5.0 (this server serves 0.5)".
    - The connection manager's alert is "Connection Failed" with that same text.
  - **The check.** `theServerRefusesAnIncompatibleClientWithItsReason` requires that text, and
    never "transport ended". It passed in three of three runs.
- **Host keys.** An unknown key and a changed key are both refused by OpenSSH's strict checking
  before any SRUI byte. Both end in a blocking "Connection Failed" alert that quotes `ssh`, notes
  what the local known_hosts holds, and says "SRUI never adds or changes host keys". The
  known_hosts file is byte-for-byte unchanged. The argv carries `StrictHostKeyChecking=yes`,
  `BatchMode=yes` and `UpdateHostKeys=no`.
- **Authentication failure.** A key the box does not authorize gets the same alert, quoting
  `Permission denied (publickey)`.
- **Reconnect and replacement.** A dropped transport leaves the window marked "disconnected —
  showing data from revision N (stale)", and the next attempt resumes the same session with
  `RESUME_OK`. A restarted srtop is reported as REPLACED. A blocking "Session Replaced" alert names
  both sessions, the window reads "session replaced — rebuilding", and the window is rebuilt from
  the new incarnation's snapshot.
- **No process-changing action.** 41 controls accept events in the live package, and none of them
  can change a process. The source, manifest and binary audit (`no_process_control_test.rs`) runs
  on every `cargo test`, on macOS and on Linux.
- **Privacy.**
  - srtop reads a process's arguments, executable and working directory only for the one
    selected instance, and only on demand. It never logs them (PX-014). A selected process's
    command line is shown to the same reader `ps` would show it to.
  - A planted token and password in a worker's arguments were shown on selection. Neither
    appeared in srtop's log, in the box's sshd and start-up output, or in the client's unified
    log.
  - The saved-connections file holds only the endpoint, its label, the last session ID and the
    revision (PX-024). It holds no credential: authentication stays OpenSSH's. The live checks
    keep the file the real client store wrote during the reconnect test, and audit it.
  - R1 has no diagnostic bundle.
  - `privacy-audit.sh` is the repeatable check. Its self-test plants one secret of each class.
    It is run over the live checks' logs and saved-connections file, over the walkthrough's
    result file and logs, over the install prefix and over the settings directory. It knows
    macOS (`/Users/<name>/`) and Linux (`/home/<name>/`) home paths, and the auditing user's own
    `$HOME` wherever it is.
  - Nothing it cannot read counts as clean. Each of these fails the audit with exit 2 and an
    `ERROR` line naming the path:
    - a file that cannot be read, which grep's exit status 2 or more decides;
    - a directory entry it cannot list;
    - a FIFO, device or socket, refused without being opened;
    - a dangling symbolic link;
    - a directory passed as `--file`.

### How it was measured

- **Hardware.** Mac14,6, Apple M2 Max, 12 cores, 32 GiB, macOS 26.4.1 (25E253) arm64. Docker
  Desktop engine 28.3.2, Linux 6.10.14-linuxkit aarch64, 12 CPUs and 16 GiB for the box.
- **Box.** Debian 12.15 (bookworm), openssh-server 1:9.2p1-2+deb12u10, procps 2:4.0.2-3, htop
  3.2.2-2 (pinned in the Dockerfile). The full record is
  [evidence/PX-027/environment.txt](../evidence/PX-027/environment.txt).
- **Build.** Release builds throughout. `srtop`, `srui-ssh-bridge` and the workers are built in the
  image with `cargo build --release --locked`. The measuring tool, `srtop-demo`, is a release build
  on the Mac.
  - The measurements ran against the image of `c7712e58`. The final image, of `c142104f`, has a
    byte-identical srtop (sha256 `78e0b003…`) and bridge (sha256 `712deb73…`). Only a test file
    changed in between.
- **SSH.** OpenSSH_10.2p1 on the Mac, with `-F /dev/null`, cipher `chacha20-poly1305@openssh.com`
  and compression off.
- **The two counts.**
  - *Semantic payload* is the SRUI frames: the bytes of the `srui` subsystem channel, which is what
    `ssh -s srui` reads and writes. The probe counts them twice, as raw bytes and as decoded
    frames, and refuses a run where the two differ. Against PX-025's delay relay on the bridge's
    side of the same stream, the counts agree to the byte (13,176 B both ways in the differential
    test).
  - *Encrypted transport* is the bytes of the SSH connection's TCP stream. A userspace TCP relay in
    front of the box's SSH port counts every byte in each direction; no root and no pcap are
    involved.
    - Since round 2, a byte is counted when the relay delivers it to the far side. At an injected
      RTT, the encrypted window therefore moves with what `ssh` or sshd has received, instead of
      leading the payload window by RTT/2.
    - The comparison and the scale runs added no RTT, so their figures are unaffected.
    - The RTT table was measured with the earlier read-time count. Its steady window then
      started and ended RTT/2 early on the encrypted side. In a continuous stream that shifts the
      window but leaves its length unchanged; the round-2 quick run reproduced the same rates.
  - The SSH overhead is the difference. A run in which the payload exceeds the encrypted bytes is
    refused, because that would mean the split is swapped or double counted.
- **Windows.** A 3 s warm-up after the snapshot (SRUI) or the first screen (htop), then a 15 s
  steady window, 7 runs per side per workload. The two sides alternate, and which goes first
  changes from run to run.
- **Matched.** srtop ran with `--refresh-interval-ms 1000` and htop with `-d 10`. The comparison
  reads each side's interval back from what that side reports: srtop's from its own published
  sampling status ("Live · sampling every 1000 ms"), and htop's from its argument vector in the
  box. It refuses any mismatch, along with a window that differs by more than 5%, process counts
  that differ by more than 10%, or any terminal size other than 120×40. htop runs over `ssh -tt`,
  with `stty cols 120 rows 40`, `TERM=xterm-256color` and its default configuration. Since
  round 2, the session itself reports its terminal size with `stty size` before htop starts. The
  record carries that reported size, not the requested one; every round-2 run reported 120×40.
- **Workloads**, the same processes for both sides:
  - *idle*: the box at rest, 3 processes;
  - *busy*: 200 fixed-lifetime `sleep`s plus PX-025's 1-thread CPU, 64 MiB memory and 16-thread
    workers, 208 processes;
  - *churn*: busy plus PX-025's short-lived-process worker, with 64 children and a birth every
    429 ms, each living 500 ms, 210 processes.
  - Every worker is bounded and ends by itself. Every run waited until none was left: at most
    7.6 s after its window, which was the sleeps reaching their lifetime. None was left after the
    last run.
- **The SRUI client** is the measuring probe: a minimal replica that applies every commit, the same
  as PX-025's. The server-to-client stream does not depend on the client. In the steady state
  neither the probe nor the AppKit client sends anything; PX-025 measured 0 bytes sent after ready.

- **In the steady state of these three workloads, htop's stream was the larger one.** The medians,

    expected to be the larger one.
- **None of this makes SRUI automatically smaller than an ncurses program.** Both depend on the
  workload, the refresh interval, the terminal size and the client. These are the measured
  conditions.

**High-churn delayed range requests make bounded progress.** A replica behind PX-025's delay relay
asks for a 16-row window with the standard range request every 250 ms, overlapping, cycling head,
middle and tail. Meanwhile the table churns: 2% of 2,000 synthetic rows are replaced every 100 ms,
or, on Linux, PX-025's short-lived workers start a child every 20 ms on the live `/proc` source.

- **srtop installs no range provider** and publishes every row it holds. Every range request is
  therefore answered `AlreadyCached` from rows already pushed, and nothing is sent. What the request
  needs is for those rows to keep arriving.
- This test therefore cannot tell an answered request from an ignored one: a session that drops
  every range request passes it.
- Bounded progress on the generic provider path rests on PX-010-G01's
  `test_model_range_fulfillment_under_concurrent_telemetry` (`apps/srtop/tests/scale_test.rs`).
  A future srtop range provider needs its own progress test.
- A request converges when the replica has applied a revision committed after the request reached
  srtop, holds every row of the window, and those rows equal an undelayed replica's at the same
  revision.
- The stated bound is RTT + 2 × interval + 750 ms. All 12 of 12 requests converged at every RTT,
  in every run.

### Zero app mutations for an unchanged fake source

The box ran `srtop --fake-source --smoke-fixture --refresh-interval-ms 100`.

- Over real SSH, the session saw 0 app transactions in the 10.0 s after the snapshot at revision
  1. That is about 100 ticks. No message of any kind arrived, and 0 bytes crossed the encrypted
  stream.
- Then srtop's own SIGUSR1 title change, sent only to the PID `ps` confirmed as srtop, arrived
  132.6 ms later as the very next transaction: revision 1 to 2, two operations.
- "App mutation" is PX-008's definition: a `Transaction`, the `Ui` class by the runtime's own
  `logical_class_for_server_envelope`. srtop has no heartbeat, so nothing else is exempt.
- The same check, run locally at the 50 ms minimum interval, passes the unchanged source and
  refuses a changing one.

### The tested envelope

R1 is supported inside what was measured, and claims nothing outside it.

| Dimension | Tested | Notes |
| --- | --- | --- |
| Processes (real `/proc`) | 3 to 210 in the devbox, idle, busy and churning | matched with htop; the devbox is its own PID namespace |
| Rows (synthetic) | 1,000 and 10,000 over real SSH (above); 1,000 rendered natively (PX-010-G01); 100,000 is the cap, not supported | 10,000 rows: a 689 KB attach and 59 KB/s at 1 s with 2% churn |
| Refresh interval | 1,000 ms (traffic, RTT); 100 ms (range progress, the idle check); 50 ms (the local idle check) | 50 ms to 300 s accepted |
| RTT | 0, 100, 300 and 600 ms over real SSH (TCP relay) and behind the bridge (delay relay) | attach grows about ten RTTs; results arrive one RTT later; nothing stalls |
| Bandwidth | measured: 0.34 to 0.69 KB/s in the steady state for 5 to 212 real rows, and 6.6 and 59 KB/s for 1,000 and 10,000 synthetic rows; 19 to 31 KB per attach with real rows, and 87 and 689 KB with synthetic ones | no link was throttled, so R1 is untested below these rates. What a slower link does is not measured. By design (`server-rust/sessiond/src/outbound/coalesce.rs`), a client that falls behind may be sent scalar-only commits merged into one non-authoritative delta. Model updates, inserts and deletes are never merged, and a client whose queue overflows is made to resynchronize (§20.2) |

## Known gaps

- **PX-027 measurement gaps.**
  - **htop's version.** The comparison used Debian 12's htop 3.2.2-2, not the 3.5.3 that H1 names
    as the latest. bookworm packages only 3.2.2, and building htop from source is out of scope.
  - **No matched comparison above 210 processes.** No matched comparison was run above 210
    processes, or at an interval other than 1 s.
  - **No constrained link.** No bandwidth cap or packet loss was imposed. The RTT was added in
    userspace on loopback, through Docker Desktop's port forward.
  - **No release native client in the latency figures.** The native client's local latency is
    PX-025's debug-build figure.
  - **The SRUI side of the traffic figures** is the measuring replica, not the AppKit client.
    srtop's stream to a client does not depend on which client it is.

- **The refused version is logged unbounded.**
  - When a connection fails, srtop logs `srtop: connection ended: {error}` to stderr
    (`apps/srtop/src/main.rs`), and `srui-sessiond` logs `Connection ended: {e}` at WARN through
    `tracing_subscriber::fmt()` to stdout (`server-rust/sessiond/src/main.rs`). R1 runs srtop, not
    the standalone daemon. Both lines carry the session error, unchanged since `e549ee8a`.
  - For an unsupported core version, that error is `unsupported core protocol version {requested:?};
    this server speaks {supported:?}` (`session.rs`), with the client's own requested version.
    The live box logged `srtop: connection ended: session error: unsupported core protocol version
    "1.5.0"; this server speaks "0.5.0"`.
  - `{:?}` escapes newlines, ESC and bidirectional controls, so a client cannot forge log lines.
    But the version is not length-bounded. One 2.5 MiB version gives a WARN line of about 2.5 MB,
    and this repeats once per connection, up to the 16 MiB frame limit.
  - The client's offered profiles are likewise echoed only when they are missing ones the server
    requires, so those are the server's own names.
  - Only the client's version reaches these logs from client input. No credential or command line
    does, and the live privacy check passes over both streams. The follow-up below bounds the
    line; R1 does not change it.
- **The resumed window is a new NSWindow.** After a resume the session window is a different
  `NSWindow` object, while the session, the rows and the selection continue. PX-022 makes no
  window-identity claim across a resume. The checklist's item 9 asks a person to watch what
  VoiceOver does there.
- **Build paths in the binary.** A from-source build embeds the builder's checkout path. The
  privacy audit reports this as `BINARY-PATH` information, not as a finding.
- **Unpinned apt packages.** The devbox's apt packages are installed at image build and are not
  pinned to a snapshot.
- **Opt-in live checks.** The live checks and the walkthrough need Docker and are not run by CI.
  `apps/srtop/r1/selftest.sh` runs in `apps/srtop/test.sh`, the macOS pre-push path, but not in a
  CI job.

## Follow-ups already known

- The shared `SSHTestSupport.terminate` still calls `Process.waitUntilExit()` from cooperative
  threads in other suites. It can wedge a test process (PX-023 round 7).
- macOS AF_UNIX lost-FIN wakeups: PX-025 fixed its relay with short re-read timeouts. The
  client's and the tests' other socket readers still need the same audit.
- The pre-push hook does not keep the display awake. Native tests run under `caffeinate -u -d`
  only when they are started that way.
- Load-sensitive timing tests: PX-025's worker-deadline tests and PX-010-G01's
  wall-clock budgets can flake on a loaded machine.
- PX-023's `posix_spawn` lc-debt: a PID-reuse window between Foundation's reap and the recorded
  exit in `BoundedProcess.stop`.
- G02 O2: a `selection_mode` change from multiple to single lets AppKit trim the selection
  without passing through the stale-selection gate (PX-022-G02).
- The T35 capability-only automation check: an automated action that skips only the
  `standardWidgetsV1` capability check is not caught by PX-026's tests.
- PX-026: an automated `SemanticNodeHandle.select` sends the selection, but does not move the
  native table's highlight.
- PX-024 V3-4: the "Session Replaced" alert can be dropped if Connect is pressed while the save
  of the replacement is still pending.
- PX-025 demonstration workers: no `setrlimit` bound, and a worker stopped with SIGSTOP misses its
  own deadline.
- PX-068: the column layout is not persisted, and no expensive-tier column is offered.
- Bound sessiond's "Connection ended" log line, and srtop's "connection ended" line, which prints
  the same error: cap the client-supplied version they echo (pre-existing since `e549ee8a`; see
  Known gaps).
- The live compatibility check waited for the handshake and the first revision but sampled event
  dispatch, which is enabled later, after the snapshot is rendered. That made it flaky; the
  verifier's first round saw 2 failures in 3 runs. It now waits for dispatch too, and five
  consecutive runs passed. Watch for any recurrence.
